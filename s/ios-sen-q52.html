Sau khi tách codebase thành nhiều Swift Package local, bạn thấy nhiều hàm generic và protocol ở module Core khi gọi từ module Feature chạy chậm hơn trước, còn dùng any Protocol để giấu kiểu cụ thể lại làm tăng allocation. Cơ chế biên dịch nào gây ra điều này, và bạn dùng some, any, @inlinable hay @usableFromInline thế nào cho hợp lý?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
Khi tách module, mỗi target thường được biên dịch độc lập: nếu một hàm generic public trong Core không lộ phần thân ra ngoài, compiler khi biên dịch Feature chỉ thấy chữ ký hàm chứ không thấy implementation để thực hiện generic specialization cho kiểu cụ thể. Kết quả là lời gọi phải chạy qua bản unspecialized dùng Value Witness Table và Protocol Witness Table để truyền kích thước, copy và gọi hàm gián tiếp thay vì tĩnh hoá và inline như lúc nằm chung một target. Trong khi đó, any Protocol đóng gói giá trị vào existential container có buffer nội tuyến 3 word: mọi struct lớn hơn kích thước này (chẳng hạn chứa nhiều property hoặc string) đều bị cấp phát động trên heap kèm chi phí retain/release khi truyền qua lại. Để khắc phục đúng chỗ, trước hết ưu tiên tham số generic hoặc some Protocol ở các API không cần lưu trữ nhiều kiểu khác nhau trong cùng một collection, tránh lạm dụng any trong vòng lặp hay đường nóng. Với các hàm generic thực sự nằm trên hot path ở Core (như parse dữ liệu, tính toán collection, helper toán học) đã được đo bằng Time Profiler và Allocations, gắn @inlinable để compiler xuất phần thân vào .swiftmodule cho phép module gọi inline và specialize, đồng thời chỉ đánh dấu @usableFromInline cho những helper internal tối thiểu mà phần thân đó cần chạm tới. Không rải @inlinable bừa bãi lên toàn bộ Core, vì nó làm phình kích thước .swiftmodule và binary do nhân bản code ở nơi gọi, kéo dài thời gian build tăng dần khi sửa phần thân, và trói chặt tương thích nhị phân nếu sau này phát hành framework dạng binary.
