ViewModel cần lấy chuỗi thông báo lỗi từ strings.xml hoặc kiểm tra kết nối mạng, nên một dev truyền thẳng Activity hoặc Application Context vào constructor của ViewModel. Cách nào gây lỗi nghiêm trọng, cách nào có nhược điểm gì, và bạn thiết kế thế nào để ViewModel sạch và dễ unit test?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
Truyền Activity vào ViewModel là lỗi nghiêm trọng vì ViewModel sống sót qua configuration change như xoay màn hình, giữ tham chiếu tới Activity đã bị destroy và toàn bộ cây view của nó, gây memory leak. Dùng AndroidViewModel với Application context thì tránh được leak do Application sống theo vòng đời process, nhưng vẫn có nhược điểm: ViewModel bị gắn chặt với lớp của Android nên khó viết unit test thuần trên JVM (phải mock Application hoặc dùng Robolectric), và Application context có thể không cập nhật cấu hình giao diện hoặc ngôn ngữ theo từng Activity. Cách sạch hơn là không để ViewModel chạm tới Context: với chuỗi hiển thị, ViewModel chỉ phát ra @StringRes hoặc một sealed interface UiText (phân biệt chuỗi động từ server và resource ID kèm tham số), rồi để tầng UI gọi context.getString() hoặc stringResource() để tự ăn đúng ngôn ngữ hiện tại. Còn với các dịch vụ hệ thống như kiểm tra mạng hay đọc cài đặt, hãy bọc sau một interface như NetworkMonitor hoặc SettingsRepository và inject vào ViewModel qua constructor; khi viết unit test chỉ cần truyền một bản fake là kiểm thử được ngay.
sealed interface UiText {
  data class DynamicString(val value: String) : UiText
  class StringResource(@StringRes val resId: Int, vararg val args: Any) : UiText
}
