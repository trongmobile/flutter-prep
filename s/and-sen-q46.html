Màn Home của app thương mại điện tử phải gọi 6 endpoint REST (banner, giỏ hàng, gợi ý...), payload nặng, sang mạng yếu thì rất chậm và tốn pin. Backend đề xuất chuyển sang GraphQL, một team khác muốn gRPC. Dưới góc nhìn client, bạn so sánh REST, GraphQL và gRPC thế nào, và phân trang cùng versioning nên thiết kế ra sao?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
Với mobile, thứ cần tối ưu là số vòng mạng (mỗi request có thể đánh thức radio), kích thước payload và khả năng dùng offline. REST + JSON đơn giản, tận dụng được HTTP cache/ETag/CDN và Retrofit, nhưng dễ over/under-fetching và phải gọi nhiều endpoint cho một màn hình; cách trung gian là một BFF gom dữ liệu theo màn hình. GraphQL cho client xin đúng trường cần và gom một màn hình vào một request, có schema để sinh code chặt kiểu (Apollo Kotlin); đổi lại thường là POST tới một endpoint nên mất HTTP cache/CDN thông thường (cần persisted queries), server phải chặn query quá nặng, và lỗi có thể đi kèm dữ liệu một phần. Điểm mạnh cho offline là normalized cache của Apollo: lưu theo id thực thể nên cập nhật ở một màn hình lan sang mọi màn hình dùng thực thể đó, nhưng phải cấu hình khoá nhận diện và tự lo chính sách hết hạn. gRPC dùng protobuf nhị phân (nhỏ, parse nhanh), hợp với streaming và hợp đồng chặt giữa các dịch vụ, nhưng khó debug bằng proxy, không có HTTP cache, cần HTTP/2 xuyên suốt; trên mobile hay dành cho realtime hơn là API chính. Phân trang: offset dễ làm và nhảy được tới trang bất kỳ, nhưng khi dữ liệu thêm/xoá giữa hai lần gọi thì lặp hoặc sót phần tử và chậm dần khi offset lớn; cursor (con trỏ đục sau phần tử cuối) ổn định và hiệu quả cho feed/infinite scroll, ghép tự nhiên với RemoteMediator của Paging 3. Versioning: app cũ sống rất lâu nên chỉ thay đổi kiểu cộng thêm (client bỏ qua trường lạ), khi buộc phá vỡ thì dùng /v2 hoặc header kèm cơ chế ép cập nhật; GraphQL dùng @deprecated, protobuf không bao giờ tái sử dụng số field. Dù chọn gì, Room vẫn nên là nguồn dữ liệu duy nhất cho UI.
interface FeedApi {
  // Offset: có bài mới chèn lên đầu giữa hai lần gọi -> trang sau lặp lại phần tử cuối của trang trước
  @GET("feed") suspend fun byOffset(@Query("offset") offset: Int, @Query("limit") limit: Int): List<Post>

  // Cursor: server trả con trỏ đục (opaque) trỏ ngay sau phần tử cuối, ổn định khi dữ liệu đổi
  @GET("feed") suspend fun byCursor(@Query("after") cursor: String?, @Query("limit") limit: Int): Page<Post>
}

@Serializable
data class Page<T>(val items: List<T>, val nextCursor: String?) // null = hết dữ liệu
