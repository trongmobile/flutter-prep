App thương mại điện tử lưu catalog hàng chục nghìn sản phẩm và giỏ hàng trong Room. Khi background worker đang sync catalog, thao tác thêm vào giỏ trên UI hay bị chậm rõ rệt; ngoài ra thỉnh thoảng app crash SQLiteBlobTooBigException khi query một bảng có cột lưu chuỗi JSON cấu hình lớn. Giải thích cơ chế locking của SQLite/Room và CursorWindow, và bạn thiết kế lại thế nào?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
SQLite dùng hai cơ chế journal chính: chế độ rollback journal cũ (DELETE/TRUNCATE) khoá toàn bộ thao tác đọc khi có transaction ghi, còn chế độ Write-Ahead Logging (WAL, được Room bật mặc định qua JournalMode.AUTOMATIC trên các thiết bị hiện đại) ghi thay đổi vào file -wal riêng nên thao tác đọc và ghi có thể chạy song song mà không chặn nhau. Tuy vậy, kể cả trong WAL mode, SQLite tại một thời điểm vẫn chỉ cho phép một writer duy nhất và Room tuần tự hoá các transaction ghi trên transaction executor. Nếu sync catalog gộp hàng chục nghìn dòng vào một transaction quá lớn, hoặc tệ hơn là gọi mạng hay parse nặng bên trong database.withTransaction, lock ghi bị giữ quá lâu khiến thao tác ghi giỏ hàng của người dùng phải xếp hàng chờ và ngăn WAL checkpoint làm file -wal phình to. Cách xử lý là không bao giờ thực hiện network I/O hay xử lý nặng trong withTransaction, chia sync lớn thành các batch vừa phải (khoảng vài trăm đến một nghìn dòng mỗi transaction) để thao tác ghi từ UI xen vào được, và dùng @Upsert hoặc bulk insert thay vì query từng dòng; nếu dữ liệu cache biến động liên tục, có thể tách DB cache riêng khỏi DB dữ liệu người dùng. Với SQLiteBlobTooBigException, nguyên nhân đến từ CursorWindow của Android dùng để truyền dữ liệu từ SQLite lên tầng ứng dụng có kích thước đệm giới hạn khoảng 2 MB: chỉ cần một dòng có cột TEXT hoặc BLOB quá lớn làm dòng vượt ngưỡng CursorWindow là query sẽ crash, còn các cột kích thước lớn cũng làm mỗi cửa sổ chứa được ít dòng hơn và gây cấp phát bộ nhớ liên tục. Không nên lưu JSON khổng lồ hay dữ liệu nhị phân trong cột SQLite; hãy ghi payload lớn ra file trong internal storage rồi chỉ lưu đường dẫn hoặc hash vào Room, hoặc chuẩn hoá thành bảng con và dùng projection để chỉ SELECT những cột thực sự cần.
// SAI: giữ transaction ghi suốt thời gian gọi mạng hoặc ghi một lần quá lớn
// database.withTransaction { val items = api.fetchCatalog(); dao.upsertAll(items) }

// ĐÚNG: tải và parse ngoài transaction, sau đó ghi theo batch để không nghẽn write từ UI
val items = api.fetchCatalog()
items.chunked(500).forEach { batch ->
  database.withTransaction {
    dao.upsertAll(batch)
  }
}
