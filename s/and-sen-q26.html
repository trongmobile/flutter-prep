Repository có đoạn try { api.fetchProfile() } catch (e: Exception) { ... } (hoặc runCatching) chạy trong coroutine của ViewModel. Sau khi user rời màn hình, log vẫn báo lỗi huỷ coroutine và đôi khi coroutine còn chạy tiếp sang bước sau. Vì sao, và bạn xử lý việc huỷ coroutine đúng cách thế nào?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
Huỷ coroutine là hợp tác: cancel() chỉ chuyển Job sang trạng thái cancelling, còn các suspend function chuẩn (delay, withContext, hàm suspend của Retrofit hay Room…) kiểm tra trạng thái này và ném CancellationException để coroutine được unwind. catch (e: Exception) hay runCatching bắt luôn ngoại lệ đó và coi như lỗi thường, nên coroutine chạy tiếp các dòng sau catch cho tới lần suspend kế tiếp (lúc đó mới bị ném lại), đủ thời gian để emit state lỗi hoặc ghi DB sai trong khi scope đã bị huỷ. Cách đúng: bắt ngoại lệ cụ thể (IOException, HttpException), hoặc nếu bắt rộng thì phải ném lại CancellationException trước. Vòng lặp tính toán không có điểm suspend thì không bao giờ tự bị huỷ giữa chừng, cần kiểm tra bằng ensureActive() hoặc yield(). Việc dọn dẹp cần chạy cả khi đã bị huỷ (đóng file, báo server) thì đặt trong finally và bọc phần suspend bằng withContext(NonCancellable), nếu không lời gọi suspend đầu tiên trong finally lại ném tiếp. runCatching cũng nuốt cancellation nên nhiều team viết helper riêng để ném lại nó.
suspend fun loadProfile(): Result<Profile> =
  try {
    Result.success(api.fetchProfile())
  } catch (e: CancellationException) {
    throw e // bắt buộc ném lại, nếu không coroutine đã bị huỷ vẫn chạy tiếp
  } catch (e: IOException) {
    Result.failure(e)
  }

suspend fun compressAll(files: List<File>) {
  try {
    for (f in files) {
      currentCoroutineContext().ensureActive() // vòng lặp CPU không có điểm suspend sẵn
      compress(f)
    }
  } finally {
    withContext(NonCancellable) { api.reportStopped() } // dọn dẹp vẫn chạy khi đã bị huỷ
  }
}
