Backend đề xuất chuyển từ REST sang GraphQL (hoặc gRPC) "để mobile gọi ít request hơn". Từ góc nhìn app iOS, bạn đánh giá thế nào về payload, cache, offline, phân trang và việc giữ tương thích với các bản app cũ?

Tự trả lời thành tiếng trước, rồi mới xem đáp án mẫu nhé.

Xem đáp án mẫu
REST tận dụng được HTTP cache (ETag, URLCache, CDN) và tooling đơn giản với URLSession cùng Codable; điểm yếu là over-fetching và nhiều round trip cho màn hình ghép nhiều resource, thứ thường giải được bằng một endpoint tổng hợp theo màn hình (BFF). GraphQL cho client chọn field nên payload nhỏ và thường chỉ một request mỗi màn hình, schema có kiểu và codegen (Apollo iOS) cho model an toàn kiểu; đổi lại thường là POST vào một endpoint nên cache HTTP và CDN khó dùng (cần persisted query hoặc GET), phải cache ở phía client (normalized cache theo __typename và id), lỗi có thể nằm trong errors của một response 200, server phải chặn query quá sâu hoặc quá nặng, và codegen làm tăng thời gian build lẫn kích thước app. gRPC dùng protobuf nhị phân gọn và nhanh, hợp streaming hai chiều và contract chặt; nhưng thêm dependency lớn, khó debug bằng proxy thông thường, không cache được ở tầng HTTP, nên ở mobile thường dành cho realtime hay streaming hơn là CRUD. Phân trang cursor (token mờ do server trả) ổn định khi dữ liệu được chèn hay xoá giữa các lần tải, còn offset đơn giản nhưng gây trùng hoặc sót item và chậm khi offset lớn; client giữ cursor kế tiếp và loại trùng theo id khi merge. Versioning: không ép được user cập nhật nên server phải tương thích ngược với nhiều bản app cũ: chỉ thêm field chứ không đổi nghĩa hay xoá, enum mới phải decode được giá trị lạ, và dùng header phiên bản app để gate tính năng; GraphQL tiến hoá bằng @deprecated, REST thường dùng /v2 hay header. Offline cần kho dữ liệu bền ở client (Core Data, SwiftData hay SQLite) bất kể giao thức nào. Kết luận: đo số request và payload thật của từng màn hình trước, thử endpoint tổng hợp, rồi mới cân nhắc đổi giao thức; đổi giao thức không sửa được một thiết kế API sai.
