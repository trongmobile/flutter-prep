  1. var, let và const khác nhau thế nào? Khai báo object bằng const thì có sửa được thuộc tính không?

    Xem đáp án mẫu
    var có phạm vi theo function, được hoist và khởi tạo sẵn undefined, lại cho khai báo lại cùng tên nên dễ gây bug. let và const có phạm vi theo block {}; chúng cũng được hoist nhưng nằm trong temporal dead zone (TDZ) cho tới dòng khai báo, truy cập sớm sẽ ném ReferenceError. Riêng function declaration được hoist cả thân hàm nên gọi trước dòng khai báo vẫn chạy. const chỉ cấm gán lại biến chứ không làm object bất biến: sửa user.name vẫn được, gán user = {} mới lỗi. Quy ước hiện nay là mặc định dùng const, cần gán lại thì dùng let, không dùng var.
    const user = { name: 'An' };
user.name = 'Bình'; // OK: chỉ sửa thuộc tính
// user = {};       // lỗi: không gán lại được biến const

if (true) {
  var a = 1;
  let b = 2;
}
console.log(a); // 1: var không bị giới hạn trong block
// console.log(b); // ReferenceError: b is not defined

console.log(c); // ReferenceError: Cannot access 'c' before initialization
let c = 3;

  2. Closure là gì? Cho một ví dụ closure bạn gặp khi viết code thực tế.

    Xem đáp án mẫu
    Closure là khi một hàm ghi nhớ và truy cập được các biến của scope nơi nó được tạo, kể cả khi hàm bên ngoài đã chạy xong. Ví dụ createCounter trả về một hàm vẫn giữ được biến count; mỗi lần gọi createCounter lại tạo ra một closure với count riêng. Ứng dụng thực tế: giấu dữ liệu private, tạo hàm cấu hình sẵn (factory), viết debounce. Trong React, mỗi event handler khai báo trong component cũng là closure: nó nhìn thấy props và state của đúng lần render đã tạo ra nó. Bẫy kinh điển là dùng var trong vòng for với callback chạy sau: mọi callback dùng chung một biến, nên hãy dùng let.
    function createCounter() {
  let count = 0; // bên ngoài không truy cập trực tiếp được
  return () => {
    count += 1;
    return count;
  };
}

const next = createCounter();
next(); // 1
next(); // 2: count vẫn còn sống nhờ closure
const other = createCounter();
other(); // 1: closure mới, count riêng

  3. this trong JavaScript được xác định thế nào? Arrow function khác function thường ở điểm nào về this?

    Xem đáp án mẫu
    Với function thường, this được quyết định lúc gọi chứ không phải lúc khai báo: gọi user.greet() thì this là user, nhưng gán const f = user.greet rồi gọi f() thì this không còn là user: trong strict mode (mặc định của ES module và class) nó là undefined và truy cập this.name sẽ ném lỗi. Arrow function không có this riêng mà dùng this của scope bao quanh nơi nó được viết, và call/apply/bind cũng không đổi được. Vì vậy arrow function hợp làm callback bên trong method (setTimeout, map), còn method của object cần dùng this thì không nên viết bằng arrow. Với function component và hooks gần như không cần this; nó chủ yếu còn gặp ở class component cũ, nơi phải bind handler hoặc khai báo handler bằng arrow class field.

  4. == và === khác nhau thế nào? Những giá trị nào là falsy trong JavaScript?

    Xem đáp án mẫu
    === so sánh nghiêm ngặt: khác kiểu là false ngay; == ép kiểu trước khi so nên cho ra những kết quả khó đoán như '1' == 1 hay 0 == '' đều là true. Quy ước là luôn dùng ===; ngoại lệ hay gặp là x == null để bắt cùng lúc null và undefined, và TypeScript cũng báo lỗi nhiều phép so sánh giữa hai kiểu không liên quan. Falsy chỉ gồm false, 0, -0, 0n, '', null, undefined và NaN; mọi giá trị khác đều truthy, kể cả '0', [] và {}. Bẫy thường gặp: price || 'Liên hệ' hiển thị "Liên hệ" khi giá bằng 0, trong khi price ?? 'Liên hệ' chỉ thay thế khi giá là null hoặc undefined.

  5. Destructuring và spread ... dùng thế nào? Vì sao nói spread chỉ là shallow copy?

    Xem đáp án mẫu
    Destructuring tách giá trị từ object hoặc array ra biến: const { name, age = 18 } = user, const [first, ...rest] = list; giá trị mặc định chỉ áp dụng khi thuộc tính là undefined. Trong component, destructuring thường dùng ngay ở tham số để nhận props: function Card({ title, onPress }). Spread sao chép phần tử hoặc thuộc tính sang mảng/object mới, key viết sau ghi đè key trước, nên rất hợp để tạo state mới thay vì mutate. Nhưng spread chỉ copy một tầng: object lồng bên trong vẫn dùng chung tham chiếu, sửa bản copy cũng làm đổi bản gốc; khi cập nhật state lồng nhau phải spread lại từng tầng cần sửa.
    const user = { name: 'An', address: { city: 'Hà Nội' } };

const renamed = { ...user, name: 'Bình' }; // key sau ghi đè key trước

const shallow = { ...user };
shallow.address.city = 'Đà Nẵng';
console.log(user.address.city); // 'Đà Nẵng': address vẫn dùng chung

// Cập nhật đúng: copy lại từng tầng cần sửa
const moved = { ...user, address: { ...user.address, city: 'Huế' } };

  6. Promise và async/await liên quan thế nào? await có làm đứng UI không, và xử lý lỗi ra sao?

    Xem đáp án mẫu
    Promise đại diện cho một kết quả sẽ có trong tương lai, ở một trong ba trạng thái pending, fulfilled hoặc rejected, và được xử lý bằng .then/.catch/.finally. async/await là cú pháp viết Promise cho dễ đọc: hàm async luôn trả về Promise, còn await chỉ tạm dừng riêng hàm đó cho tới khi Promise xong. await không chặn JS thread, trong lúc chờ app vẫn render và nhận thao tác của người dùng. Lỗi được bắt bằng try/catch quanh await, còn finally dùng để tắt loading dù thành công hay thất bại. Bẫy hay gặp là quên await: bạn nhận về Promise thay vì dữ liệu và lỗi không rơi vào catch.
    const [loading, setLoading] = useState(false);

async function onSubmit() {
  setLoading(true);
  try {
    await api.saveProfile(form); // chờ nhưng không chặn UI
    Alert.alert('Đã lưu');
  } catch (e) {
    Alert.alert('Lỗi', 'Không lưu được, thử lại sau');
  } finally {
    setLoading(false); // luôn chạy
  }
}

  7. Trong TypeScript, type và interface khác nhau thế nào khi khai báo props cho component? Prop optional viết ra sao?

    Xem đáp án mẫu
    Cả hai đều mô tả được shape của object, nên với props gần như dùng thay nhau được; nhiều team chọn một cách và dùng thống nhất. interface mở rộng bằng extends và hỗ trợ declaration merging (hai khai báo trùng tên được gộp lại). type là alias cho mọi kiểu, nên chỉ type viết được union như 'primary' | 'secondary', tuple, hay kết hợp kiểu bằng &. Prop optional thêm dấu ?: bên trong component nó có kiểu string | undefined, nên phải gán giá trị mặc định khi destructuring hoặc kiểm tra trước khi dùng.
    type ButtonVariant = 'primary' | 'secondary'; // union: chỉ type làm được

interface AppButtonProps {
  title: string;
  variant?: ButtonVariant; // optional: có thể không truyền
  onPress: () => void;
}

function AppButton({ title, variant = 'primary', onPress }: AppButtonProps) {
  return (
    <Pressable onPress={onPress} style={variant === 'primary' ? styles.primary : styles.secondary}>
      <Text>{title}</Text>
    </Pressable>
  );
}

  8. export default và named export khác nhau thế nào? Vì sao import { Button } from './Button' đôi khi nhận về undefined?

    Xem đáp án mẫu
    Một file module có thể có nhiều named export nhưng chỉ có một export default. Named export được import bằng đúng tên trong ngoặc nhọn (import { formatPrice } from './utils', đổi tên bằng as), còn default export import không có ngoặc và đặt tên tuỳ ý (import Button from './Button'). Nhầm hai kiểu là lỗi kinh điển: import { Card } từ một file chỉ có default thì nhận về undefined, và khi render sẽ báo "Element type is invalid: expected a string... but got: undefined". Ngoài ra undefined còn xuất hiện khi hai file import vòng tròn lẫn nhau (circular import), hay gặp khi gom export qua file index.ts (barrel file). Quy ước thường thấy là cả team chọn một kiểu; nhiều nhóm ưu tiên named export vì tên cố định ở mọi nơi nên auto-import và đổi tên (refactor) của editor hoạt động tốt hơn.
    // Button.tsx
export const Button = () => null;                // named export
export default function Card() { return null; }  // default export (chỉ một)

// App.tsx
import Card, { Button } from './Button';         // default không ngoặc, named có ngoặc
import { Button as AppButton } from './Button';  // đổi tên khi bị trùng

// SAI: Card là default export, import kiểu named sẽ ra undefined
// import { Card } from './Button';

  9. map, filter, find và reduce dùng để làm gì? Vì sao render danh sách phải dùng map chứ forEach thì không được?

    Xem đáp án mẫu
    map biến mỗi phần tử thành một giá trị mới và trả về mảng mới cùng độ dài, hợp để chuyển dữ liệu thành các element JSX. filter giữ lại phần tử thoả điều kiện và trả về mảng mới. find trả về phần tử đầu tiên thoả điều kiện hoặc undefined. some và every trả về boolean. reduce gộp cả mảng thành một giá trị (tổng, object) bắt đầu từ giá trị khởi tạo. Những hàm này không sửa mảng gốc, rất hợp với state của React vốn phải cập nhật theo kiểu bất biến. forEach luôn trả về undefined và chỉ để chạy side effect, nên viết {items.forEach(...)} trong JSX sẽ không render gì; nó cũng không break được và không đợi await bên trong callback async. Cẩn thận sort() và reverse() thì lại sửa mảng gốc, cần copy trước bằng [...items].sort(...) khi đang làm việc với state.
    const cart = [
  { id: 1, name: 'Áo', price: 200, qty: 1 },
  { id: 2, name: 'Mũ', price: 50, qty: 3 },
];

const names = cart.map((i) => i.name);                            // ['Áo', 'Mũ']
const expensive = cart.filter((i) => i.price > 100);              // chỉ còn Áo
const hat = cart.find((i) => i.id === 2);                         // object hoặc undefined
const total = cart.reduce((sum, i) => sum + i.price * i.qty, 0);  // 350

// Cập nhật state mà không sửa mảng gốc
setCart((prev) => prev.map((i) => (i.id === 2 ? { ...i, qty: i.qty + 1 } : i)));

  10. Vì sao nên dùng TypeScript trong React Native? Khai báo kiểu cho useState và dữ liệu API thế nào, và any khác unknown ra sao?

    Xem đáp án mẫu
    TypeScript bắt lỗi sai kiểu, sai tên prop hay thiếu tham số ngay trong editor trước khi chạy app và cho gợi ý code tốt hơn; template của React Native hiện cũng mặc định dùng TS. Nó chỉ kiểm tra lúc phát triển, lúc chạy vẫn là JavaScript thuần. useState suy luận kiểu từ giá trị khởi tạo, nên khi khởi tạo bằng null hoặc mảng rỗng bạn phải chỉ rõ bằng generic, như useState<User | null>(null). Dữ liệu API chỉ là kiểu bạn "hứa" với compiler (as User), TS không kiểm tra response thật, nên nếu server không đáng tin hãy kiểm tra thêm bằng thư viện như Zod. any tắt hoàn toàn việc kiểm tra kiểu cho giá trị đó, dùng nhiều thì mất ý nghĩa của TS; unknown an toàn hơn: nhận mọi giá trị nhưng phải thu hẹp kiểu (typeof, instanceof) rồi mới dùng được, hợp cho lỗi trong catch hay JSON chưa rõ cấu trúc. Union literal như 'idle' | 'loading' | 'error' mô tả trạng thái chặt hơn nhiều so với string.
    type User = { id: number; name: string };
type Status = 'idle' | 'loading' | 'error';       // union: chỉ nhận 3 giá trị này

const [user, setUser] = useState<User | null>(null); // cần generic vì khởi tạo là null
const [status, setStatus] = useState<Status>('idle');

async function load() {
  setStatus('loading');
  try {
    const res = await fetch('https://api.example.com/me');
    setUser((await res.json()) as User);          // chỉ "hứa" với TS, không kiểm tra lúc chạy
    setStatus('idle');
  } catch (e: unknown) {
    const message = e instanceof Error ? e.message : 'Lỗi không xác định';
    console.warn(message);
    setStatus('error');
  }
}

// user?.name có kiểu string | undefined, phải xử lý null trước khi dùng

  1. Props và state khác nhau thế nào? Component con có được sửa props mà nó nhận không?

    Xem đáp án mẫu
    Props là dữ liệu component cha truyền xuống, với component con chúng là read-only; state là dữ liệu component tự sở hữu, tạo bằng useState và chỉ thay đổi qua hàm setter. Khi props hoặc state thay đổi, component render lại để UI khớp với dữ liệu mới. Con không được sửa props vì React coi props là bất biến; muốn đổi dữ liệu do cha quản lý thì cha truyền xuống một callback như onChange và con gọi callback đó. Đây là luồng dữ liệu một chiều: dữ liệu chảy xuống qua props, sự kiện đi ngược lên qua callback, nhờ vậy dễ biết state nằm ở đâu và ai được phép đổi nó.

  2. Vì sao gọi setCount(count + 1) ba lần liên tiếp trong một handler mà count chỉ tăng 1? Sửa thế nào?

    Xem đáp án mẫu
    Setter của useState không đổi biến count ngay mà xếp yêu cầu cập nhật vào hàng đợi và lên lịch render lại. Trong cùng một lần render, count là hằng số của lần render đó, nên cả ba lời gọi đều tương đương setCount(0 + 1). Khi giá trị mới phụ thuộc giá trị cũ, hãy dùng updater function setCount((c) => c + 1): React chạy lần lượt từng updater với giá trị mới nhất trong hàng đợi, nên tăng đủ 3. Cũng vì cơ chế này, console.log(count) ngay sau khi gọi setter vẫn in ra giá trị cũ.
    const [count, setCount] = useState(0);

const addThreeWrong = () => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1); // count chỉ thành 1
};

const addThree = () => {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  setCount((c) => c + 1); // count thành 3
};

  3. JSX là gì? Kể vài quy tắc JSX hay bị viết sai, đặc biệt khi dùng trong React Native.

    Xem đáp án mẫu
    JSX là cú pháp mở rộng của JavaScript, được Babel biên dịch thành lời gọi hàm (jsx() hoặc React.createElement) tạo ra object mô tả UI, nên bản chất nó là JavaScript chứ không phải HTML. Quy tắc cần nhớ: mỗi biểu thức JSX chỉ có một phần tử gốc (bọc bằng View hoặc Fragment <>...</>), mọi thẻ phải đóng (<Image />), trong {} chỉ đặt được biểu thức nên dùng toán tử ba ngôi hoặc map thay cho if/for, và tên component phải viết hoa chữ cái đầu. Riêng React Native, chữ phải nằm trong <Text>: đặt chuỗi trực tiếp trong <View> sẽ lỗi "Text strings must be rendered within a <Text> component". Style truyền qua prop style dưới dạng object, không có className như web.

  4. Khi render danh sách, key dùng để làm gì? Nên chọn giá trị nào làm key?

    Xem đáp án mẫu
    React dùng key để nhận ra phần tử nào giữ nguyên, được thêm, bị xoá hay đổi chỗ giữa hai lần render, từ đó tái sử dụng đúng component cùng state của nó. Key cần ổn định và duy nhất trong cùng một list, tốt nhất là id từ dữ liệu. Dùng index làm key chỉ an toàn khi list không bao giờ thêm, xoá hay sắp xếp; nếu chèn item lên đầu, index bị dịch chuyển khiến state như nội dung TextInput hay checkbox bị gắn nhầm sang item khác. Cũng đừng dùng Math.random() làm key, vì mỗi lần render ra key mới nên React huỷ và tạo lại toàn bộ item.
    {todos.map((todo) => (
  <TodoRow key={todo.id} todo={todo} /> // id ổn định từ dữ liệu
))}

  5. Có những cách nào để render có điều kiện trong React? Vì sao {count && <Text>…</Text>} có thể làm app React Native bị lỗi?

    Xem đáp án mẫu
    Với nhánh lớn như loading hoặc lỗi, dùng if rồi return sớm; với hai nhánh trong JSX dùng toán tử ba ngôi cond ? <A /> : <B />; khi chỉ hiện hoặc ẩn thì dùng cond && <A />; muốn không render gì thì trả về null. Bẫy nằm ở chỗ && trả về chính vế trái khi vế trái falsy: nếu count là 0 thì biểu thức cho ra số 0, và React render nó như một đoạn text. Trên web bạn chỉ thấy một số 0 thừa, còn trong React Native đoạn text nằm ngoài <Text> gây lỗi "Text strings must be rendered within a <Text> component". Cách tránh là ép điều kiện về boolean (count > 0 &&) hoặc dùng toán tử ba ngôi.
    function CartBadge({ count }: { count: number }) {
  return (
    <View>
      {/* Sai: count = 0 thì render số 0 ngoài <Text> → lỗi */}
      {/* {count && <Text>{count} sản phẩm</Text>} */}
      {count > 0 && <Text>{count} sản phẩm</Text>}
      {count === 0 ? <Text>Giỏ hàng trống</Text> : null}
    </View>
  );
}

  6. Controlled TextInput là gì? Vì sao form đăng nhập thường được làm theo kiểu controlled?

    Xem đáp án mẫu
    Controlled nghĩa là nội dung ô nhập lấy từ state qua prop value, và mỗi lần người dùng gõ thì onChangeText cập nhật lại state; state trở thành nguồn dữ liệu duy nhất. Nhờ vậy dễ validate ngay khi gõ, format dữ liệu, reset form hoặc disable nút submit khi dữ liệu chưa hợp lệ. onChangeText nhận thẳng chuỗi mới, còn onChange nhận event và text nằm ở e.nativeEvent.text. Bẫy: truyền value mà không cập nhật state trong onChangeText thì ô nhập luôn bị ép về giá trị cũ, gõ không đổi được; nếu chỉ cần giá trị ban đầu thì dùng defaultValue (uncontrolled).

  const [email, setEmail] = useState('');
  const isValid = email.includes('@');
  return (
    <View>
      <TextInput
        value={email}
        onChangeText={setEmail} // nhận thẳng chuỗi mới

  7. useEffect dùng để làm gì? Mảng dependency [], [id] và không truyền mảng khác nhau thế nào?

    Xem đáp án mẫu
    useEffect chạy side effect sau khi component render xong: những việc nằm ngoài phần render thuần như gọi API, đăng ký listener, đặt timer. Thời điểm chạy phụ thuộc vào mảng dependency. Không truyền mảng thì chạy sau mọi lần render, nếu bên trong lại setState thì dễ thành vòng lặp vô hạn. Truyền [] thì chỉ chạy một lần sau lần render đầu (mount). Truyền [id] thì chạy lần đầu và chạy lại mỗi khi id đổi giá trị. Mọi biến từ component (props, state, hàm) mà effect dùng nên có mặt trong mảng; quy tắc ESLint react-hooks/exhaustive-deps sẽ nhắc bạn. Hàm trả về từ effect là cleanup, chạy trước lần effect kế tiếp và khi component unmount. Callback truyền cho useEffect không được là async trực tiếp vì nó trả về Promise thay vì hàm cleanup, nên hãy khai báo hàm async bên trong rồi gọi nó. Lưu ý khi bật StrictMode ở môi trường dev, effect lúc mount chạy hai lần để lộ ra lỗi quên cleanup.
    type User = { name: string };

function UserScreen({ userId }: { userId: number }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    let cancelled = false;                 // tránh setState khi đã đổi user hoặc rời màn
    async function load() {                // không viết async trực tiếp cho effect
      const res = await fetch(`https://api.example.com/users/${userId}`);
      const data: User = await res.json();
      if (!cancelled) setUser(data);
    }
    load();
    return () => { cancelled = true; };    // cleanup
  }, [userId]);                            // chạy lại mỗi khi userId đổi

  return <Text>{user ? user.name : 'Đang tải...'}</Text>;
}

  8. Khi nào một component render lại? Vì sao component cha render lại thì component con cũng render lại dù props không đổi?

    Xem đáp án mẫu
    Component render lại khi state của nó đổi (setter của useState nhận giá trị khác theo Object.is), khi props đổi, khi context nó đang dùng đổi, và mặc định cả khi component cha render lại, dù props truyền xuống y nguyên. "Render" ở đây chỉ là gọi hàm component để tính ra cây element mới; React so sánh với lần trước (reconciliation) và chỉ cập nhật các view native thật sự khác, nên render lại không đồng nghĩa với vẽ lại cả màn hình. Render thừa chỉ thành vấn đề khi component nặng hoặc nằm trong danh sách dài; lúc đó mới dùng React.memo (bỏ qua render khi props bằng nhau theo so sánh nông), kèm useCallback/useMemo để giữ nguyên tham chiếu của hàm và object truyền xuống, vì hàm hay object tạo mới ở mỗi lần render làm memo vô tác dụng. Đừng tối ưu sớm: hãy đo bằng React DevTools Profiler trước. Cũng đừng gọi setState trực tiếp trong thân component vì sẽ gây vòng lặp render vô hạn.
    const Child = React.memo(function Child({ title }: { title: string }) {
  console.log('Child render');
  return <Text>{title}</Text>;
});

function Parent() {
  const [count, setCount] = useState(0);

  return (
    <View>
      <Button title={`Bấm ${count}`} onPress={() => setCount(count + 1)} />
      {/* Bọc React.memo: title không đổi nên Child không render lại khi count đổi */}
      <Child title="Xin chào" />
    </View>
  );
}

Đừng lồng FlatList trong ScrollView cùng chiều cuộn vì mất tối ưu và sẽ có cảnh báo VirtualizedLists should never be nested.

    Xem đáp án mẫu

Muốn style từ ngoài ghi đè được thì đặt style gốc trước và style truyền vào sau trong mảng, vì phần tử đứng sau thắng: style={[styles.base, style]}. Thay vì copy component ra nhiều bản, dùng prop biến thể như variant: 'primary' | 'outline'. Bọc bằng Pressable để có phản hồi khi nhấn và có disabled.   title: string;
  onPress: () => void;
  variant?: 'primary' | 'outline';     // tuỳ chọn, mặc định primary
  disabled?: boolean;

      disabled={disabled}

    </Pressable>
  );
}

  1. Khi nào chỉ cần useState, khi nào nên dùng Context hoặc thư viện như Redux Toolkit, Zustand?

    Xem đáp án mẫu
    Hãy bắt đầu bằng state cục bộ: state chỉ phục vụ một component (nội dung ô nhập, bật tắt modal) thì giữ bằng useState ngay tại đó. Nguyên tắc: chọn công cụ nhỏ nhất đủ dùng, đừng đưa mọi thứ vào store toàn cục.

  1. Trong stack navigator của React Navigation, navigate, push, goBack và popToTop khác nhau thế nào?

    Xem đáp án mẫu
    Stack navigator giữ một chồng màn hình: navigation.navigate('Detail') chuyển tới màn hình theo tên, còn goBack() bỏ màn hiện tại để về màn trước, giống nút back của Android hay cử chỉ vuốt back trên iOS. push('Detail', params) luôn đẩy thêm một màn mới, kể cả khi đang đứng ở chính Detail, hợp với luồng như sản phẩm liên quan (chi tiết → chi tiết); còn navigate tới đúng màn đang hiển thị thì không tạo màn mới mà chỉ cập nhật params. popToTop() quay thẳng về màn đầu tiên của stack, ví dụ sau khi đặt hàng xong.   2. Truyền dữ liệu sang màn hình khác bằng params thế nào? Nên truyền cả object sản phẩm hay chỉ truyền id?

    Xem đáp án mẫu
    Params đặt ở tham số thứ hai: navigation.navigate('ProductDetail', { productId: 42 }), màn hình đích đọc qua route.params (prop route hoặc hook useRoute()), và có thể đổi params của màn hiện tại bằng navigation.setParams. Tài liệu React Navigation khuyên params chỉ chứa dữ liệu tối thiểu để dựng màn hình như id hay bộ lọc, chứ không phải cả object lấy từ API: object truyền qua có thể đã cũ so với dữ liệu thật, và khi màn hình được mở từ deep link thì cũng chỉ có id. Params cũng nên serializable; truyền function hay class instance sẽ bị cảnh báo vì làm hỏng việc lưu, khôi phục state điều hướng và deep link. Màn hình đích dùng id để tự lấy dữ liệu từ API hoặc store.

  3. Cài React Navigation cần những gì? NavigationContainer, navigator và screen liên hệ thế nào, khi nào dùng Stack, Tab, Drawer?

    Xem đáp án mẫu
    Cài @react-navigation/native cùng hai package có native code là react-native-screens và react-native-safe-area-context (với Expo dùng npx expo install), rồi cài navigator cần dùng như @react-navigation/native-stack hoặc @react-navigation/bottom-tabs; trên iOS cần pod install và phải build lại app vì có native code. Cấu trúc: chỉ có một NavigationContainer ở gốc app để giữ state điều hướng; bên trong là navigator tạo bằng createNativeStackNavigator() hay createBottomTabNavigator(), mỗi navigator chứa nhiều Screen với name duy nhất và component. Gọi useNavigation() ở component nằm ngoài NavigationContainer sẽ báo Couldn't find a navigation object, còn render navigator mà thiếu container thì báo Couldn't register the navigator. Chọn loại: Stack cho luồng đi sâu có nút Back (danh sách rồi tới chi tiết); Tab cho 3–5 mục cấp một luôn cần truy cập (Trang chủ, Đơn hàng, Tài khoản); Drawer cho nhiều mục ít dùng (Drawer cần thêm react-native-gesture-handler và react-native-reanimated). Thường lồng nhau: Tab ở ngoài, mỗi tab chứa một Stack riêng. Khai báo kiểu ParamList cho navigator giúp TypeScript kiểm tra tên màn hình và params khi gọi navigate.
    type RootStackParamList = {
  Home: undefined;            // không có params
  Detail: { id: number };
};

const Stack = createNativeStackNavigator<RootStackParamList>();

export default function App() {
  return (
    <NavigationContainer>     {/* chỉ một container ở gốc app */}
      <Stack.Navigator initialRouteName="Home">
        <Stack.Screen name="Home" component={HomeScreen} options={{ title: 'Trang chủ' }} />
        <Stack.Screen name="Detail" component={DetailScreen} />
      </Stack.Navigator>
    </NavigationContainer>
  );
}

Native & New Architecture

Mọi rank →

  1. React Native là gì? Khác gì với app hybrid dùng WebView (Ionic, Cordova) và với Flutter?

    Xem đáp án mẫu
    React Native cho phép viết app bằng JavaScript/TypeScript với React, nhưng giao diện được dựng bằng view native thật của hệ điều hành: <View> thành UIView trên iOS và ViewGroup trên Android, <Text> thành UILabel/TextView. Code JS chạy trong một JS engine (Hermes) trên JS thread, tính ra cây UI rồi ra lệnh cho phía native tạo và cập nhật view, còn việc vẽ và cuộn do native đảm nhiệm nên cảm giác gần với app native. Khác app hybrid như Ionic hay Cordova: những app đó chạy giao diện HTML/CSS bên trong WebView và không có component native. Khác Flutter: Flutter tự vẽ mọi pixel bằng engine riêng (Skia/Impeller) và dùng ngôn ngữ Dart, còn React Native dùng component của nền tảng nên giao diện mang sẵn phong cách hệ thống và tận dụng được hệ sinh thái JavaScript/React. Đổi lại phải xử lý khác biệt giữa iOS và Android, và lớp giao tiếp JS với native (New Architecture dùng JSI thay cho bridge bất đồng bộ cũ). Khi cần tính năng native chưa có sẵn thì viết module bằng Swift/Kotlin.

Networking & Storage

Mọi rank →

  1. Gọi API bằng fetch thế nào? Vì sao server trả 404 hoặc 500 mà code không nhảy vào catch?

    Xem đáp án mẫu
    fetch(url, options) trả về Promise của Response; với POST cần method, header Content-Type: application/json và body: JSON.stringify(data), còn body trả về đọc bằng await res.json() (cũng là Promise). Promise của fetch chỉ reject khi có lỗi mạng như mất kết nối hay không phân giải được tên miền; HTTP 404 hay 500 vẫn là một response hợp lệ nên Promise vẫn resolve. Vì vậy phải tự kiểm tra res.ok (status 200–299) hoặc res.status rồi ném lỗi để tầng trên xử lý. Lưu ý thêm: bản release trên Android và iOS mặc định chặn request http:// không mã hoá, nên API thật cần dùng HTTPS.
    async function createTodo(title: string) {
  const res = await fetch('https://api.example.com/todos', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ title }),
  });
  if (!res.ok) {
    throw new Error(`HTTP ${res.status}`); // 4xx/5xx không tự reject
  }
  return res.json();
}

  2. AsyncStorage là gì, lưu một object vào đó thế nào? Có nên lưu mọi thứ vào AsyncStorage không?

    Xem đáp án mẫu
    AsyncStorage là kho key–value bất đồng bộ, lưu bền trên máy, hợp với dữ liệu nhỏ như cài đặt, theme hay cờ đã xem onboarding. Bản nằm trong core React Native đã bị tách ra, nay dùng package cộng đồng @react-native-async-storage/async-storage. Cả key và value đều là string và mọi hàm đều trả về Promise, nên object phải JSON.stringify khi ghi, JSON.parse khi đọc, và getItem trả về null khi key chưa tồn tại. Dữ liệu không được mã hoá nên không dùng cho token hay mật khẩu, và nó cũng không thay được database khi dữ liệu lớn hoặc cần truy vấn.
    import AsyncStorage from '@react-native-async-storage/async-storage';

type Settings = { darkMode: boolean };

async function saveSettings(settings: Settings) {
  await AsyncStorage.setItem('settings', JSON.stringify(settings));
}

async function loadSettings(): Promise<Settings> {
  const raw = await AsyncStorage.getItem('settings'); // string | null
  return raw ? JSON.parse(raw) : { darkMode: false };
}

  3. Server chạy ở localhost:3000 trên máy dev nhưng app báo Network request failed. Nguyên nhân thường gặp và cách xử lý trên iOS Simulator, Android Emulator và máy thật?

    Xem đáp án mẫu
    localhost luôn là chính thiết bị đang chạy app. iOS Simulator dùng chung mạng với máy Mac nên http://localhost:3000 thường chạy được. Android Emulator là máy ảo riêng, localhost trỏ vào chính emulator; địa chỉ của máy dev là 10.0.2.2 (hoặc chạy adb reverse tcp:3000 tcp:3000 để dùng localhost). Máy thật phải cùng mạng Wi-Fi và dùng IP LAN của máy dev (như 192.168.1.10), đồng thời server phải lắng nghe trên 0.0.0.0 chứ không chỉ 127.0.0.1, và firewall phải cho phép cổng đó. Còn có hai rào cản về HTTP không mã hoá: iOS có App Transport Security, template React Native đã mở cho mạng cục bộ nhưng nếu gọi IP LAN thì vẫn phải khai báo ngoại lệ trong Info.plist; Android 9 trở lên chặn cleartext, template chỉ bật usesCleartextTraffic ở bản debug. Nên đặt base URL theo môi trường thay vì ghi cứng khắp nơi, và dùng HTTPS cho production.
    import { Platform } from 'react-native';

// Chọn địa chỉ máy dev theo nền tảng khi chạy trên simulator/emulator
const DEV_HOST = Platform.OS === 'android' ? '10.0.2.2' : 'localhost';

export const API_URL = __DEV__
  ? `http://${DEV_HOST}:3000`
  : 'https://api.myshop.com';

// Máy thật: dùng IP LAN của máy dev, ví dụ http://192.168.1.10:3000
// Android + adb reverse tcp:3000 tcp:3000: dùng được http://localhost:3000

Expo, Build & Release

Mọi rank →

  1. Expo và React Native CLI khác nhau thế nào? Dự án mới bạn sẽ chọn cái nào?

    Xem đáp án mẫu
    React Native CLI tạo project "bare" với sẵn thư mục android/ và ios/: bạn tự cài Android Studio, Xcode, tự quản lý code native và cấu hình build, đổi lại kiểm soát được mọi thứ. Expo là framework xây trên React Native: có Expo SDK với nhiều module dựng sẵn (camera, notification, file…), chạy thử nhanh bằng app Expo Go, build và phát hành trên cloud bằng EAS. Quan niệm cũ "dùng Expo thì không thêm được native code" không còn đúng: với development build, bạn vẫn dùng được thư viện native bất kỳ hoặc tự viết module; chỉ riêng Expo Go là giới hạn ở các module có sẵn trong nó. Tài liệu chính thức của React Native hiện khuyên bắt đầu dự án mới với một framework như Expo; RN CLI hợp khi cần tích hợp sâu vào hệ thống build native sẵn có.

  2. Metro là gì? Fast Refresh hoạt động thế nào và khi nào bạn buộc phải build lại app?

    Xem đáp án mẫu
    Metro là bundler của React Native: dùng Babel biên dịch JSX/TypeScript, gộp các module và asset thành bundle, khi phát triển thì chạy dev server (mặc định cổng 8081) để app tải bundle về. Babel chỉ bỏ phần type chứ không kiểm tra type, nên muốn bắt lỗi TypeScript phải chạy tsc hoặc dựa vào editor. Với Fast Refresh, khi bạn lưu file chỉ export component thì chỉ component đó được cập nhật và state của useState được giữ; nếu file export cả thứ khác, module đó cùng các module import nó được chạy lại nên state có thể mất. Mọi thay đổi native như cài thư viện có native code, sửa AndroidManifest.xml, Info.plist hay Podfile đều phải build lại app; reload JS hay xoá cache Metro không giải quyết được.

  3. Giải thích cấu trúc một project React Native: android/, ios/, node_modules/, package.json, index.js, App.tsx. dependencies và devDependencies khác nhau thế nào?

    Xem đáp án mẫu
    index.js là điểm vào của app, gọi AppRegistry.registerComponent để đăng ký component gốc App (viết trong App.tsx) với đúng tên project mà phía native sẽ tìm khi khởi động. android/ và ios/ là hai project native thật (Gradle và Xcode) mà bạn mở bằng Android Studio hoặc Xcode, nơi sửa quyền, icon, AndroidManifest.xml, Info.plist hay thêm code native; project Expo "managed" có thể không có hai thư mục này vì chúng được sinh ra khi chạy prebuild. node_modules/ chứa thư viện cài từ npm hoặc yarn, rất nặng, không commit lên git và luôn cài lại được từ lockfile. package.json liệt kê tên project, các script (start, android, ios, test) và phiên bản thư viện. dependencies là thư viện app cần khi chạy (react, react-native, react-navigation...), devDependencies chỉ phục vụ lúc phát triển (TypeScript, ESLint, Jest, các gói type). Với app React Native thì Metro chỉ đóng gói những gì bạn import, nên sự phân biệt này chủ yếu để mô tả ý nghĩa, và quan trọng hơn khi bạn xuất bản thư viện lên npm. Lockfile (package-lock.json hoặc yarn.lock) cần commit để cả team cài cùng một phiên bản.
    // index.js: điểm vào của app
import { AppRegistry } from 'react-native';
import App from './App';
import { name as appName } from './app.json';

// Tên đăng ký phải khớp với tên mà phía native tìm khi khởi động
AppRegistry.registerComponent(appName, () => App);
