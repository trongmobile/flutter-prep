  1. Bạn mô hình hoá trạng thái tải dữ liệu của màn hình bằng TypeScript thế nào để tránh kiểu { loading: boolean; error?: string; data?: T } dễ sinh trạng thái vô lý?

    Xem đáp án mẫu
    Kiểu nhiều field optional cho phép những tổ hợp vô nghĩa như vừa loading: true vừa có error, và mỗi lần dùng data lại phải thêm ! hoặc ?.. Dùng discriminated union: mỗi trạng thái là một nhánh có chung field status mang literal type, và chỉ nhánh success mới có data. Khi switch (state.status), TypeScript tự thu hẹp (narrow) kiểu trong từng case; thêm nhánh default gán vào never thì sau này thêm trạng thái mới mà quên xử lý, compiler sẽ báo lỗi. Kết hợp generic <T> để dùng chung kiểu này cho mọi màn hình.
    type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };

function describe(state: AsyncState<User[]>): string {
  switch (state.status) {
    case 'idle': return 'Chưa tải';
    case 'loading': return 'Đang tải...';
    case 'success': return state.data.length + ' người dùng'; // data: User[]
    case 'error': return state.error;
    default: { const unhandled: never = state; return unhandled; }
  }
}

  2. App hiển thị ngày giờ lệch 7 tiếng ở một số máy, new Date('2025-03-01 10:00') cho Invalid Date trên iOS, và giá tiền hiện 1000000 thay vì 1.000.000 ₫. Bạn xử lý Date, múi giờ và Intl trong React Native thế nào?

    Xem đáp án mẫu
    Date trong JS là một thời điểm (mili giây từ epoch UTC); múi giờ chỉ tham gia khi parse chuỗi và khi hiển thị. Parse là nguồn lỗi chính: chỉ định dạng ISO 8601 là được đặc tả chắc chắn, còn chuỗi như '2025-03-01 10:00' (dấu cách thay cho T) hay '03/01/2025' do engine tự diễn giải nên mỗi engine một khác, có nơi cho Invalid Date. Quy tắc: server trả ISO 8601 kèm offset (2025-03-01T03:00:00Z) hoặc epoch, client parse bằng new Date(iso) hoặc thư viện (date-fns, dayjs) chứ không tự cắt chuỗi. Cẩn thận: chuỗi chỉ có ngày ('2025-03-01') được hiểu là nửa đêm UTC, còn '2025-03-01T00:00:00' (không có offset) được hiểu là giờ local, nên cùng một ngày có thể lệch ngày ở múi giờ âm. Hiển thị cho user theo múi giờ và locale của thiết bị bằng Intl.DateTimeFormat hay toLocaleString; muốn cố định múi giờ nghiệp vụ thì truyền timeZone: 'Asia/Ho_Chi_Minh'. Intl.NumberFormat('vi-VN', { style: 'currency', currency: 'VND' }) cho ra 1.000.000 ₫; khởi tạo formatter tốn kém nên tạo một lần rồi dùng lại. Hermes hỗ trợ Intl (dựa vào dữ liệu locale của hệ điều hành) nhưng dữ liệu đó phụ thuộc phiên bản OS, nên kiểm tra trên máy thật và máy cũ, và dùng polyfill (@formatjs) nếu cần kết quả nhất quán. Tính toán ngày dùng thư viện (addDays, startOfDay) thay vì cộng 24 giờ vì có đổi giờ mùa hè ở một số múi giờ; còn tiền nên lưu bằng số nguyên theo đơn vị nhỏ nhất hoặc chuỗi decimal, không cộng bằng số thực (0.1 + 0.2).
    // Parse: chỉ tin ISO 8601 có offset; không tự cắt chuỗi hay dùng chuỗi có dấu cách
const created = new Date('2025-03-01T03:00:00Z'); // thời điểm tuyệt đối

// Chuỗi chỉ có ngày là UTC, chuỗi ngày giờ không offset là local: dễ lệch ngày
new Date('2025-03-01'); // 2025-03-01T00:00:00Z
new Date('2025-03-01T00:00:00'); // nửa đêm theo giờ máy

// Tạo formatter một lần và tái sử dụng (khởi tạo tốn kém)
const vnd = new Intl.NumberFormat('vi-VN', { style: 'currency', currency: 'VND' });
const orderTime = new Intl.DateTimeFormat('vi-VN', {
  timeZone: 'Asia/Ho_Chi_Minh', // giờ nghiệp vụ cố định, không phụ thuộc múi giờ của máy
  dateStyle: 'short',
  timeStyle: 'short',
});

vnd.format(1_000_000); // "1.000.000 ₫"
orderTime.format(created);

  2. Cần đo vị trí một View rồi đặt tooltip ngay bên dưới mà không bị nháy ở vị trí sai trong một frame. Dùng useEffect hay useLayoutEffect, vì sao?

    Xem đáp án mẫu
    useEffect chạy sau khi kết quả đã được commit và vẽ ra màn hình, nên đo rồi setState vị trí trong đó có thể khiến người dùng thấy một frame tooltip ở chỗ cũ rồi mới nhảy. useLayoutEffect chạy đồng bộ sau commit nhưng trước khi frame được hiển thị, và cập nhật state bên trong nó được xử lý luôn trước khi vẽ. Với New Architecture (Fabric), layout đọc được đồng bộ trong useLayoutEffect (ví dụ qua measureInWindow của ref) nên tooltip đúng vị trí ngay frame đầu; kiến trúc cũ đo bất đồng bộ qua bridge nên khó tránh nháy. Vì useLayoutEffect chặn việc vẽ, chỉ dùng nó cho đo đạc và định vị; gọi API hay subscribe vẫn để ở useEffect.
    const anchorRef = useRef<View>(null);
const [pos, setPos] = useState<{ x: number; y: number } | null>(null);

useLayoutEffect(() => {
  // New Architecture: đo và setState trước khi frame được vẽ
  anchorRef.current?.measureInWindow((x, y, width, height) => {
    setPos({ x, y: y + height });
  });
}, []);

  3. Một màn hình lỗi lúc render làm cả app trắng màn hình ở bản release. Error boundary giúp gì, và nó không bắt được loại lỗi nào?

    Xem đáp án mẫu
    Error boundary là class component có static getDerivedStateFromError (để render UI dự phòng) và componentDidCatch (để log lên Sentry/Crashlytics). Nó bắt lỗi ném ra trong lúc render, trong lifecycle và constructor của các component con, nhờ đó chỉ một phần cây bị thay bằng màn hình lỗi thay vì cả app sập. Nó không bắt lỗi trong event handler (onPress), code bất đồng bộ (setTimeout, promise bị reject), lỗi của chính nó và crash phía native; các trường hợp này phải try/catch, hoặc lưu lỗi vào state rồi ném lại khi render. Hiện chưa có hook tương đương nên thường viết một class dùng chung hoặc dùng thư viện react-error-boundary, và đặt boundary theo từng màn hình hay khối tính năng thay vì chỉ một cái ở root.

  5. App có AppContext chứa { user, theme, cart, setCart } trong một object. Mỗi lần thêm hàng vào giỏ, mọi màn hình dùng context (kể cả màn chỉ cần theme) đều render lại. Vì sao, và bạn tổ chức Context thế nào để giảm re-render?

    Xem đáp án mẫu
    Mọi component gọi useContext(AppContext) sẽ render lại khi value của Provider đổi theo Object.is. Nếu value={{ user, theme, cart, setCart }} là object tạo mới ở mỗi lần Provider render, mọi consumer render lại mỗi khi Provider render; còn khi cart đổi thì cả object đổi nên consumer chỉ cần theme cũng bị render. React.memo không chặn được vì thay đổi context bỏ qua memo. Cách làm: một là bọc value bằng useMemo để nó ổn định khi không có gì đổi; hai là tách context theo chủ đề và tốc độ thay đổi (ThemeContext, AuthContext, CartContext) để component chỉ subscribe thứ nó dùng; ba là tách state khỏi dispatch (CartStateContext và CartDispatchContext) vì dispatch có tham chiếu ổn định, nên component chỉ cần gọi hành động sẽ không render lại khi state đổi; bốn là đặt state gần nơi dùng thay vì đưa mọi thứ lên root. Context không có selector như useSelector của Redux hay Zustand, nên với state đổi thường xuyên và có nhiều consumer (giỏ hàng, bộ lọc) hãy dùng store có selector; Context hợp với giá trị ít đổi như theme, locale, user. Kiểm chứng bằng React DevTools Profiler (mục 'Why did this render?' hiện 'Context changed').
    const CartStateContext = createContext<CartItem[]>([]);
const CartDispatchContext = createContext<React.Dispatch<CartAction>>(() => {});

export function CartProvider({ children }: { children: React.ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, []);
  // dispatch có tham chiếu ổn định: component chỉ gọi hành động sẽ không render lại khi items đổi
  return (
    <CartDispatchContext.Provider value={dispatch}>
      <CartStateContext.Provider value={items}>{children}</CartStateContext.Provider>
    </CartDispatchContext.Provider>
  );
}

// Provider có nhiều giá trị: useMemo để value không đổi tham chiếu ở mỗi lần render
export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const value = useMemo(() => ({ user, signOut: () => setUser(null) }), [user]);
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

  1. Danh sách sản phẩm dùng <Image source={{ uri }} /> của core: ảnh nhấp nháy khi cuộn lại, không có placeholder, và đôi khi không hiện vì thiếu kích thước. Bạn xử lý ảnh remote thế nào, và expo-image khác Image của core ra sao?

    Xem đáp án mẫu
    Ảnh remote không có kích thước biết trước khi tải, nên bắt buộc phải đặt width và height (hoặc aspectRatio) trong style, nếu không ảnh có kích thước 0 và không hiện. Image của core có cache nhưng hạn chế: hành vi cache phụ thuộc nền tảng (iOS có prop cache như force-cache, Android dùng Fresco), không có placeholder hay chuyển cảnh mượt, và trong list ảnh bị tải lại khi view được tái sử dụng nên nhấp nháy. expo-image (dùng được cả trong project bare) bổ sung: cache bộ nhớ và đĩa với chính sách rõ ràng (cachePolicy="memory-disk"), placeholder (blurhash hoặc thumbhash sinh từ server) kèm transition để mờ dần khi ảnh thật về, contentFit thay cho resizeMode, hỗ trợ WebP, AVIF, SVG và ảnh động, priority để ưu tiên ảnh trong màn hình, và recyclingKey để list tái chế view (FlashList) không hiện nhầm ảnh của item trước trong lúc ảnh mới đang tải. Tối ưu thêm: để server hoặc CDN trả đúng kích thước theo nhu cầu (kích thước hiển thị nhân PixelRatio) thay vì ảnh gốc, ưu tiên WebP, và prefetch ảnh sắp hiện bằng Image.prefetch. Ảnh có ý nghĩa cần accessibilityLabel; xử lý onError bằng ảnh dự phòng. Ảnh cục bộ require('./a.png') đã biết sẵn kích thước và nằm trong bundle nên không gặp các vấn đề này.
    import { Image } from 'expo-image';

function ProductImage({ product }: { product: Product }) {
  return (
    <Image
      source={{ uri: `${product.imageUrl}?w=${PixelRatio.getPixelSizeForLayoutSize(120)}` }} // CDN trả đúng kích thước
      placeholder={{ blurhash: product.blurhash }} // hiện ngay khi ảnh thật chưa về
      transition={200}
      contentFit="cover"
      cachePolicy="memory-disk"
      recyclingKey={product.id} // list tái chế view: không hiện nhầm ảnh của item trước
      style={{ width: 120, height: 120, borderRadius: 8 }} // ảnh remote bắt buộc có kích thước
      accessibilityLabel={product.name}
    />
  );
}

  2. App cần hỗ trợ tiếng Việt và tiếng Anh, tự chọn theo ngôn ngữ máy nhưng user đổi được trong app; có câu 'Bạn có 1 tin nhắn' và 'Bạn có 5 tin nhắn' (số nhiều), và vài thị trường cần RTL. Bạn dựng i18n trong React Native thế nào?

    Xem đáp án mẫu
    Cách phổ biến là i18next kèm react-i18next, dùng expo-localization để biết ngôn ngữ thiết bị. Tách chuỗi ra file theo ngôn ngữ (vi.json, en.json), dùng key có ý nghĩa (inbox.unreadCount) và gọi t('inbox.unreadCount', { count }) qua hook useTranslation() để component render lại khi đổi ngôn ngữ. Ngôn ngữ ban đầu lấy từ getLocales()[0].languageCode; user chọn thủ công thì lưu vào storage và ưu tiên hơn ngôn ngữ máy; đặt fallbackLng: 'en' để thiếu bản dịch vẫn hiện được chữ. Số nhiều: i18next dựa vào Intl.PluralRules nên khai báo các dạng theo từng ngôn ngữ (unreadCount_one, unreadCount_other; tiếng Việt chỉ có other, tiếng Ả Rập có nhiều dạng) và truyền count. Không ghép chuỗi bằng tay ('Bạn có ' + n + ' tin nhắn') vì thứ tự từ khác nhau giữa các ngôn ngữ, hãy dùng placeholder {{count}}, {{name}}. Số, ngày, tiền định dạng bằng Intl theo locale thay vì hard-code. Với TypeScript, sinh kiểu cho key (type augmentation của i18next) để gõ sai key bị báo ngay. RTL: I18nManager.forceRTL(true) đổi chiều layout nhưng cần khởi động lại app mới có hiệu lực, và nên dùng start/end (marginStart, paddingEnd) thay cho left/right, lật icon có hướng bằng transform: [{ scaleX: -1 }] khi RTL. Sót chuỗi là lỗi hay gặp nên cần script kiểm tra key thiếu ở CI, và bản dịch dài hơn (tiếng Đức, tiếng Pháp) làm vỡ layout cố định chiều rộng nên cần thử với chuỗi dài và cỡ chữ lớn. Chuỗi từ server cần theo Accept-Language. Để user chọn ngôn ngữ riêng cho từng app trong Settings của iOS và Android 13 trở lên, cần khai báo các ngôn ngữ hỗ trợ ở cấu hình native (Expo: locales trong app.json).
    import i18n from 'i18next';
import { initReactI18next, useTranslation } from 'react-i18next';
import { getLocales } from 'expo-localization';

const deviceLang = getLocales()[0]?.languageCode ?? 'en';

i18n.use(initReactI18next).init({
  lng: savedLang ?? deviceLang, // lựa chọn của user (lưu trong storage) ưu tiên hơn ngôn ngữ máy
  fallbackLng: 'en', // thiếu bản dịch thì dùng tiếng Anh thay vì hiện key
  resources: {
    vi: { translation: { inbox: { unreadCount_other: 'Bạn có {{count}} tin nhắn' } } },
    en: {
      translation: {
        inbox: {
          unreadCount_one: 'You have {{count}} message',
          unreadCount_other: 'You have {{count}} messages',
        },
      },
    },
  },
});

function Inbox({ count }: { count: number }) {
  const { t } = useTranslation(); // component render lại khi đổi ngôn ngữ
  return <Text>{t('inbox.unreadCount', { count })}</Text>; // i18next chọn dạng số nhiều theo ngôn ngữ
}

  1. Trong createSlice bạn viết state.items.push(...) ngay trong reducer. Vì sao như vậy không phá nguyên tắc immutable của Redux, và cách viết này có bẫy gì?

    Xem đáp án mẫu
    Redux Toolkit dùng Immer: state trong case reducer là một draft (Proxy), bạn 'mutate' draft, Immer ghi lại thay đổi rồi tạo ra state mới bất biến. Immer chỉ copy những nhánh bị đổi, phần còn lại giữ nguyên reference nên selector và React.memo vẫn so sánh === được. Bẫy hay gặp nhất là vừa sửa draft vừa return giá trị mới, ví dụ arrow function một dòng (state, a) => state.push(a.payload) trả về độ dài mảng khiến Immer ném lỗi; muốn thay toàn bộ state thì return object mới và không đụng vào draft.     Xem đáp án mẫu

  4. Hermes khác JavaScriptCore ở điểm nào, và vì sao nó giúp app React Native khởi động nhanh hơn?

    Xem đáp án mẫu
    Hermes là JS engine Meta viết riêng cho React Native và là engine mặc định hiện nay. Khác biệt chính: JS được biên dịch thành bytecode ngay lúc build, nên khi mở app engine không phải parse và compile source mà chỉ việc nạp bytecode, giúp thời gian tới khi tương tác được (TTI) ngắn hơn và tốn ít RAM hơn. Hermes không dùng JIT mà tối ưu cho interpreter, kèm GC có thời gian dừng ngắn; đánh đổi là code chạy nóng trong thời gian dài có thể chậm hơn engine có JIT, và một số tính năng JS mới có thể chưa được hỗ trợ đầy đủ. Kiểm tra app có đang chạy Hermes bằng typeof HermesInternal === 'object', và debug qua React Native DevTools.

  5. Mở app thấy màn hình trắng chớp giữa splash và màn đầu tiên, font đổi sau một nhịp, và trạng thái đăng nhập mất vài trăm ms mới có. Bạn kiểm soát splash screen và việc 'app đã sẵn sàng' trong Expo hoặc RN thế nào?

    Xem đáp án mẫu
    Splash native mặc định tự ẩn ngay khi app render xong lần đầu, thường sớm hơn lúc font, token đăng nhập hay dữ liệu cache sẵn sàng, nên user thấy khoảng trắng hoặc UI nhảy. Cách xử lý là giữ splash tới khi đủ điều kiện: gọi SplashScreen.preventAutoHideAsync() ở cấp module (trước khi component render), chạy các việc khởi tạo cần thiết (tải font bằng useFonts, đọc token từ SecureStore, hydrate store đã persist, tải vài asset), rồi gọi SplashScreen.hideAsync() khi xong, tốt nhất trong onLayout của view gốc để chắc UI đã được vẽ trước khi ẩn. Chỉ chờ những thứ thật sự cần cho frame đầu; không chờ API chậm mà hiện skeleton hoặc dữ liệu cache rồi tải tiếp, nếu không splash kéo dài làm app có cảm giác chậm. Đặt thời gian tối đa (timeout) để một tác vụ bị treo không giữ app mãi. Quyết định điều hướng ban đầu (đã đăng nhập hay chưa) xong trước khi ẩn splash để không nháy màn Login. Cho màu nền splash trùng với nền màn đầu tiên để chuyển cảnh liền mạch; trên Android 12 trở lên, splash do hệ thống vẽ (icon trên nền một màu) nên không dùng được ảnh toàn màn hình tuỳ ý như trước. Đo thời gian từ lúc mở tới khi màn đầu tương tác được làm chỉ số của startup, vì giữ splash lâu hơn chỉ che giấu chứ không làm app nhanh hơn.
    import * as SplashScreen from 'expo-splash-screen';
import { useFonts } from 'expo-font';

SplashScreen.preventAutoHideAsync(); // cấp module: chạy trước khi component render

export default function App() {
  const [fontsLoaded] = useFonts({ Inter: require('./assets/Inter.ttf') });
  const [authReady, setAuthReady] = useState(false);

  useEffect(() => {
    // Chỉ chờ thứ cần cho frame đầu; có timeout để tác vụ treo không giữ app mãi
    Promise.race([restoreSession(), timeout(3000)]).finally(() => setAuthReady(true));
  }, []);

  const ready = fontsLoaded && authReady;
  const onLayoutRoot = useCallback(() => {
    if (ready) SplashScreen.hideAsync(); // ẩn sau khi UI đã được vẽ, không phải trước
  }, [ready]);

  if (!ready) return null;
  return (
    <View style={{ flex: 1 }} onLayout={onLayoutRoot}>
      <RootNavigator />
    </View>
  );
}

  1. Chạy Jest cho component dùng thư viện có native module (AsyncStorage, camera…) bị lỗi native module là null. Vì sao, và nên mock thế nào cho hợp lý?

    Xem đáp án mẫu
    Jest chạy component trong Node với preset react-native, không có runtime native nào phía sau, nên mọi NativeModules.X hay Turbo Module đều không tồn tại. Nhiều thư viện cung cấp sẵn mock (ví dụ @react-native-async-storage/async-storage/jest/async-storage-mock), chỉ cần jest.mock trong file setupFiles. Với module tự viết thì mock chính file spec/wrapper JS để trả giá trị cố định, dùng jest.fn() để kiểm tra lời gọi. Nên bọc native module sau một hook hoặc service của mình để test logic với mock, còn hành vi native thật thì để E2E (Detox, Maestro) kiểm tra.

jest.mock('@react-native-async-storage/async-storage', () =>
  require('@react-native-async-storage/async-storage/jest/async-storage-mock'),

// Mock Turbo Module tự viết
jest.mock('./specs/NativeBattery', () => ({

  2. Team chuẩn bị viết E2E test cho luồng đăng nhập và thanh toán. Bạn chọn Detox hay Maestro, dựa trên tiêu chí nào?

    Xem đáp án mẫu
    Detox là gray-box: nó build app kèm thư viện đồng bộ, theo dõi request mạng, timer, animation và hàng đợi của JS thread để tự đợi app rảnh trước mỗi bước, nên test ổn định; test viết bằng JS/TS chạy với Jest. Đổi lại cấu hình build phức tạp hơn, và đôi khi phải tắt đồng bộ cho animation lặp vô hạn hoặc polling. Maestro là black-box: flow viết bằng YAML, điều khiển app qua UI như người dùng, tự chờ và retry, cài đặt nhanh, chạy được với bất kỳ bản build nào, nhưng không biết trạng thái bên trong app. Cả hai nên tìm phần tử qua testID thay vì text. Thường chọn Maestro khi cần có test nhanh, ít bảo trì; chọn Detox khi cần kiểm soát sâu và gắn chặt với codebase JS.

  3. Bạn viết custom hook useOrders dùng TanStack Query và test nó: hook ném lỗi 'No QueryClient set', test thứ hai bị lẫn cache của test đầu, và việc mock API bằng jest.mock cho fetch rất rối. Bạn test hook và API trong RN thế nào với renderHook, wrapper và MSW?

    Xem đáp án mẫu
    Hook chỉ chạy được bên trong component, nên dùng renderHook của React Native Testing Library và truyền wrapper để bọc các provider mà hook cần (QueryClientProvider, theme, navigation). Với React Query, mỗi test phải tạo một QueryClient mới (không dùng chung instance, nếu không cache tràn giữa các test và kết quả phụ thuộc thứ tự chạy) và tắt retry (defaultOptions: { queries: { retry: false } }), nếu không test lỗi sẽ chờ hết các lần retry tới khi timeout. Chờ kết quả bất đồng bộ bằng await waitFor(() => expect(result.current.isSuccess).toBe(true)); RNTL đã bọc sẵn act trong renderHook, waitFor và fireEvent, nên cảnh báo 'not wrapped in act' thường là dấu hiệu quên await hoặc state cập nhật sau khi test đã kết thúc. Về mock mạng, thay vì jest.mock từng hàm (gắn chặt vào cách gọi), dùng MSW (Mock Service Worker) với setupServer chạy ở tầng mạng trong Node: định nghĩa handler http.get(url, ...), code ứng dụng vẫn gọi fetch thật nên test kiểm tra được URL, query, header, decode và xử lý lỗi; mỗi test có thể ghi đè bằng server.use(...) để giả lập 500 hay 401, và dùng chung handler cho cả test component lẫn hook. Nhớ server.resetHandlers() ở afterEach, server.close() ở afterAll, và onUnhandledRequest: 'error' để bắt request quên mock; môi trường Jest của RN có thể cần cấu hình thêm cho MSW. Hook thuần logic không cần mạng thì mock dependency trực tiếp; hook phụ thuộc thời gian thì dùng jest.useFakeTimers() và act(() => jest.advanceTimersByTime(...)). Hành vi mà user thấy ở component quan trọng hơn chi tiết nội bộ của hook.
    import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('https://api.shop.vn/orders', () => HttpResponse.json([{ id: '1', total: 50000 }])),
);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' })); // request quên mock sẽ làm test fail
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

function createWrapper() {
  // QueryClient mới cho mỗi test: cache không lẫn giữa các test, tắt retry để test lỗi chạy nhanh
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  return ({ children }: { children: React.ReactNode }) => (
    <QueryClientProvider client={client}>{children}</QueryClientProvider>
  );
}

test('trả về danh sách đơn hàng', async () => {
  const { result } = renderHook(() => useOrders(), { wrapper: createWrapper() });
  await waitFor(() => expect(result.current.isSuccess).toBe(true));
  expect(result.current.data).toHaveLength(1);
});

test('báo lỗi khi server trả 500', async () => {
  // ghi đè handler chỉ cho test này
  server.use(http.get('https://api.shop.vn/orders', () => new HttpResponse(null, { status: 500 })));
  const { result } = renderHook(() => useOrders(), { wrapper: createWrapper() });
  await waitFor(() => expect(result.current.isError).toBe(true));
});
