JavaScript & TypeScript

Mọi rank →

  1. Bạn mô hình hoá trạng thái tải dữ liệu của màn hình bằng TypeScript thế nào để tránh kiểu { loading: boolean; error?: string; data?: T } dễ sinh trạng thái vô lý?

    Xem đáp án mẫu
    Kiểu nhiều field optional cho phép những tổ hợp vô nghĩa như vừa loading: true vừa có error, và mỗi lần dùng data lại phải thêm ! hoặc ?.. Dùng discriminated union: mỗi trạng thái là một nhánh có chung field status mang literal type, và chỉ nhánh success mới có data. Khi switch (state.status), TypeScript tự thu hẹp (narrow) kiểu trong từng case; thêm nhánh default gán vào never thì sau này thêm trạng thái mới mà quên xử lý, compiler sẽ báo lỗi. Kết hợp generic <T> để dùng chung kiểu này cho mọi màn hình.
    type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };

function describe(state: AsyncState<User[]>): string {
  switch (state.status) {
    case 'idle': return 'Chưa tải';
    case 'loading': return 'Đang tải...';
    case 'success': return state.data.length + ' người dùng'; // data: User[]
    case 'error': return state.error;
    default: { const unhandled: never = state; return unhandled; }
  }
}

Mọi rank →

  1. Màn EditProfile nhận prop userId và khởi tạo form bằng useState(user.name). Khi chuyển sang xem user khác ngay trên màn đó, form vẫn hiện dữ liệu của user cũ. Vì sao, và sửa thế nào cho gọn?

    Xem đáp án mẫu
    React giữ state theo vị trí và type của component trong cây: EditProfile vẫn nằm đúng chỗ cũ với cùng type nên được giữ nguyên instance, chỉ nhận props mới, còn giá trị truyền vào useState chỉ dùng ở lần mount đầu. Cách hay gặp nhưng không tốt là dùng useEffect theo dõi userId rồi setName: component render một lần với dữ liệu cũ, rồi mới render lại, và dễ quên reset field nào đó. Cách gọn là cho component một key gắn với danh tính dữ liệu, như <EditProfile key={userId} userId={userId} />: key đổi thì React coi đây là component khác, unmount cái cũ và mount cái mới với state ban đầu. Đánh đổi là toàn bộ cây con mount lại (effect chạy lại, mất vị trí cuộn), nên chỉ đặt key ở mức component thực sự cần reset.
    function ProfileScreen({ route }: Props) {
  const { userId } = route.params;
  // key đổi -> EditProfile mount lại, state form về giá trị ban đầu
  return <EditProfile key={userId} userId={userId} />;
}

  2. Cần đo vị trí một View rồi đặt tooltip ngay bên dưới mà không bị nháy ở vị trí sai trong một frame. Dùng useEffect hay useLayoutEffect, vì sao?

    Xem đáp án mẫu
    useEffect chạy sau khi kết quả đã được commit và vẽ ra màn hình, nên đo rồi setState vị trí trong đó có thể khiến người dùng thấy một frame tooltip ở chỗ cũ rồi mới nhảy. useLayoutEffect chạy đồng bộ sau commit nhưng trước khi frame được hiển thị, và cập nhật state bên trong nó được xử lý luôn trước khi vẽ. Với New Architecture (Fabric), layout đọc được đồng bộ trong useLayoutEffect (ví dụ qua measureInWindow của ref) nên tooltip đúng vị trí ngay frame đầu; kiến trúc cũ đo bất đồng bộ qua bridge nên khó tránh nháy. Vì useLayoutEffect chặn việc vẽ, chỉ dùng nó cho đo đạc và định vị; gọi API hay subscribe vẫn để ở useEffect.
    const anchorRef = useRef<View>(null);
const [pos, setPos] = useState<{ x: number; y: number } | null>(null);

useLayoutEffect(() => {
  // New Architecture: đo và setState trước khi frame được vẽ
  anchorRef.current?.measureInWindow((x, y, width, height) => {
    setPos({ x, y: y + height });
  });
}, []);

  3. Một màn hình lỗi lúc render làm cả app trắng màn hình ở bản release. Error boundary giúp gì, và nó không bắt được loại lỗi nào?

    Xem đáp án mẫu
    Error boundary là class component có static getDerivedStateFromError (để render UI dự phòng) và componentDidCatch (để log lên Sentry/Crashlytics). Nó bắt lỗi ném ra trong lúc render, trong lifecycle và constructor của các component con, nhờ đó chỉ một phần cây bị thay bằng màn hình lỗi thay vì cả app sập. Nó không bắt lỗi trong event handler (onPress), code bất đồng bộ (setTimeout, promise bị reject), lỗi của chính nó và crash phía native; các trường hợp này phải try/catch, hoặc lưu lỗi vào state rồi ném lại khi render. Hiện chưa có hook tương đương nên thường viết một class dùng chung hoặc dùng thư viện react-error-boundary, và đặt boundary theo từng màn hình hay khối tính năng thay vì chỉ một cái ở root.

  4. Ô tìm kiếm lọc vài nghìn item ngay ở client, gõ phím bị giật. useTransition giúp gì trong trường hợp này và giới hạn của nó là gì?

    Xem đáp án mẫu
    Ý tưởng là tách cập nhật khẩn cấp (text trong ô input) khỏi cập nhật không khẩn cấp (kết quả lọc): text cập nhật bình thường, còn setQuery cho danh sách được bọc trong startTransition (hoặc dùng useDeferredValue). React render phần transition với mức ưu tiên thấp và có thể bỏ dở lần render đó khi có input mới, nên ô nhập vẫn mượt, isPending cho biết danh sách đang được cập nhật. Giới hạn: đây là concurrent rendering nên trong RN chỉ có khi bật New Architecture; nó không làm phép lọc nhanh hơn và vẫn chạy trên JS thread, nên một hàm đồng bộ quá nặng vẫn block. Không đưa state của chính TextInput controlled vào transition, vì input phải cập nhật đồng bộ.
    const [text, setText] = useState('');
const [query, setQuery] = useState('');
const [isPending, startTransition] = useTransition();
const results = useMemo(() => filterProducts(all, query), [all, query]);

<TextInput
  value={text}
  onChangeText={(t) => {
    setText(t); // khẩn cấp: cập nhật ngay
    startTransition(() => setQuery(t)); // không khẩn cấp: có thể bị ngắt
  }}
/>

State Management

Mọi rank →

  1. Trong createSlice bạn viết state.items.push(...) ngay trong reducer. Vì sao như vậy không phá nguyên tắc immutable của Redux, và cách viết này có bẫy gì?

    Xem đáp án mẫu
    Redux Toolkit dùng Immer: state trong case reducer là một draft (Proxy), bạn 'mutate' draft, Immer ghi lại thay đổi rồi tạo ra state mới bất biến. Immer chỉ copy những nhánh bị đổi, phần còn lại giữ nguyên reference nên selector và React.memo vẫn so sánh === được. Bẫy hay gặp nhất là vừa sửa draft vừa return giá trị mới, ví dụ arrow function một dòng (state, a) => state.push(a.payload) trả về độ dài mảng khiến Immer ném lỗi; muốn thay toàn bộ state thì return object mới và không đụng vào draft. Ngoài ra console.log(state) trong reducer chỉ in ra Proxy, hãy dùng current(state); và đừng đưa giá trị non-serializable (class instance, Promise) vào store vì middleware kiểm tra của RTK sẽ cảnh báo.
    const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] as CartItem[] },
  reducers: {
    added(state, action: PayloadAction<CartItem>) {
      state.items.push(action.payload); // sửa draft, Immer tạo state mới
    },
    cleared() {
      return { items: [] }; // thay toàn bộ state: return, không sửa draft
    },
  },
});

  2. Dự án đang gọi API bằng createAsyncThunk và tự lưu loading/error/data vào slice. Chuyển sang RTK Query được lợi gì, và làm sao để danh sách tự làm mới sau khi tạo bài viết mới?

    Xem đáp án mẫu
    Với thunk, mỗi endpoint phải tự viết reducer cho pending/fulfilled/rejected, tự lưu cache và tự chống gọi trùng. RTK Query sinh sẵn hook như useGetPostsQuery, useAddPostMutation, cache theo endpoint + tham số, gộp các request trùng nhau, tự xoá cache không còn component nào dùng sau keepUnusedDataFor (mặc định 60 giây) và hỗ trợ polling. Để danh sách tự làm mới, query khai báo providesTags, mutation khai báo invalidatesTags cùng tag; mutation xong thì mọi query mang tag đó được refetch, không cần dispatch tay. Thunk vẫn hợp với logic nhiều bước không thuần là đọc/ghi dữ liệu server, như luồng checkout phối hợp nhiều service.

  3. Màn hình dùng Zustand bị re-render mỗi khi bất kỳ field nào trong store đổi, dù nó chỉ cần user.name. Vì sao và sửa thế nào?

    Xem đáp án mẫu
    Gọi useStore() không có selector nghĩa là subscribe toàn bộ state, nên mọi lần set đều làm component render lại. Hãy chọn đúng phần cần dùng: useStore((s) => s.user.name); Zustand so sánh kết quả selector bằng Object.is và chỉ re-render khi nó đổi. Bẫy tiếp theo là selector trả về object/array mới mỗi lần như (s) => ({ a: s.a, b: s.b }): kết quả luôn 'khác' nên vẫn re-render, ở Zustand v5 còn có thể gây lỗi vòng lặp render. Khi cần nhiều field, bọc selector bằng useShallow hoặc gọi nhiều hook riêng; action trong store có reference ổn định nên lấy riêng chúng không gây re-render.
    import { useShallow } from 'zustand/react/shallow';

// Chỉ re-render khi name đổi
const name = useStore((s) => s.user.name);

// Nhiều field: so sánh shallow thay vì so reference của object mới
const { count, inc } = useStore(
  useShallow((s) => ({ count: s.count, inc: s.inc })),
);

  4. Team đang lưu mọi response API vào Redux. Bạn đề xuất tách server state và client state: hai loại khác nhau thế nào, và staleTime/gcTime của TanStack Query nghĩa là gì?

    Xem đáp án mẫu
    Client state do app sở hữu hoàn toàn (tab đang chọn, form nhập dở, theme), còn server state là bản sao của dữ liệu nằm trên server: có thể đã cũ, cần cache, dedupe, refetch, retry, phân trang. Nhét server state vào Redux buộc ta tự viết lại tất cả những thứ đó; để TanStack Query lo phần này thì Redux/Zustand chỉ còn giữ client state, gọn hơn nhiều. staleTime (mặc định 0) là khoảng thời gian dữ liệu còn được coi là 'tươi': trong khoảng này mount lại hay focus lại sẽ không refetch. gcTime (mặc định 5 phút, tên cũ là cacheTime) là thời gian cache của một query không còn observer được giữ lại trước khi bị xoá. Trên RN cần nối focusManager với AppState và onlineManager với NetInfo, vì không có sự kiện focus/online như trình duyệt.

  1. Sau khi đăng nhập, app gọi navigation.navigate('Home'), nhưng bấm back trên Android lại quay về màn Login; đăng xuất xong cũng có thể back vào màn cần đăng nhập. Bạn tổ chức auth flow với React Navigation thế nào?

    Xem đáp án mẫu
    Vấn đề là màn Login và màn chính nằm chung một stack, nên navigate chỉ đẩy thêm màn mới và Login vẫn còn trong lịch sử. Cách React Navigation khuyến nghị là khai báo màn hình có điều kiện theo trạng thái đăng nhập: chưa đăng nhập thì navigator chỉ có nhóm màn auth, đã đăng nhập thì chỉ có nhóm màn chính. Khi state auth đổi (lưu trong Context hoặc store), navigator tự chuyển sang nhóm màn mới và các màn của nhóm cũ bị gỡ khỏi lịch sử, nên không back lại được, cũng không cần tự gọi navigate hay reset sau khi đăng nhập. Lúc mở app, trong khi đọc token từ secure storage thì hiển thị splash, tránh nháy màn Login. Deep link tới màn cần đăng nhập phải được xử lý sau khi auth sẵn sàng, vì lúc chưa đăng nhập màn đó chưa tồn tại trong navigator.
    function RootNavigator() {
  const { isLoading, token } = useAuth();
  if (isLoading) return <SplashScreen />;

  return (
    <Stack.Navigator>
      {token == null ? (
        <Stack.Screen name="Login" component={LoginScreen} />
      ) : (
        <Stack.Screen name="Home" component={HomeScreen} />
      )}
    </Stack.Navigator>
  );
}

Native & New Architecture

Mọi rank →

  1. Bạn cần viết một Turbo Native Module đọc mức pin cho cả Android và iOS. Các bước với Codegen là gì, và được lợi gì so với native module kiểu cũ?

    Xem đáp án mẫu
    Bước một: viết spec bằng TypeScript trong file có tên bắt đầu bằng Native (như NativeBattery.ts), gồm interface Spec extends TurboModule và export TurboModuleRegistry.getEnforcing<Spec>('NativeBattery'). Bước hai: khai báo codegenConfig trong package.json (name, type: "modules", jsSrcsDir). Codegen chạy khi build Android hoặc khi pod install trên iOS, sinh ra abstract class Java và protocol Objective-C++ để bạn implement phía native. So với module cũ đi qua bridge: lời gọi đi qua JSI nên không phải serialize JSON bất đồng bộ, có thể khai báo hàm đồng bộ khi thật cần, module chỉ được khởi tạo khi dùng lần đầu, và kiểu dữ liệu giữa JS với native được kiểm tra lúc build thay vì vỡ lúc runtime.
    // specs/NativeBattery.ts
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  getBatteryLevel(): Promise<number>;
  isCharging(): boolean; // hàm đồng bộ
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeBattery');

  2. Native module cần đẩy sự kiện liên tục lên JS (vị trí GPS, tiến độ tải file). Bạn làm thế nào ở cả hai phía, và cần chú ý gì để không rò rỉ?

    Xem đáp án mẫu
    Cách truyền thống: Android lấy RCTDeviceEventEmitter qua reactApplicationContext.getJSModule(...) rồi gọi emit("onProgress", params); iOS kế thừa RCTEventEmitter, khai báo supportedEvents và gọi sendEventWithName. Phía JS tạo NativeEventEmitter (iOS bắt buộc truyền module vào), addListener trong useEffect và gọi subscription.remove() ở cleanup; quên remove thì callback vẫn chạy sau khi màn hình unmount và closure bị giữ lại trong bộ nhớ. Phía native chỉ nên bật nguồn sự kiện (GPS, cảm biến) khi có listener, iOS có sẵn startObserving/stopObserving cho việc này, tránh tốn pin vô ích. Với New Architecture, spec Codegen có thể khai báo event emitter có kiểu, JS subscribe thẳng qua module mà không cần NativeEventEmitter.

  3. Khi nào cần viết Fabric Native Component thay vì Turbo Native Module? Props và event của component được khai báo thế nào?

    Xem đáp án mẫu
    Turbo Native Module dành cho chức năng không có giao diện: gọi API hệ thống, trả dữ liệu về JS. Khi cần đặt một view native vào cây layout của RN, như map, camera preview, video player hay một chart viết sẵn bằng native, thì viết native component. Spec là file <Tên>NativeComponent.ts export codegenNativeComponent<NativeProps>(...); props dùng kiểu của Codegen (Int32, Double, WithDefault…) còn event là prop kiểu DirectEventHandler hoặc BubblingEventHandler. Phía native viết ViewManager (Android) hoặc component view (iOS) để nhận props và bắn event, còn view vẫn được Yoga layout như View thường. Muốn gọi lệnh mệnh lệnh như zoomTo() từ JS thì khai báo thêm codegenNativeCommands.
    // MapViewNativeComponent.ts
import type { ViewProps } from 'react-native';
import type { Double, DirectEventHandler } from 'react-native/Libraries/Types/CodegenTypes';
import codegenNativeComponent from 'react-native/Libraries/Utilities/codegenNativeComponent';

type RegionEvent = Readonly<{ latitude: Double; longitude: Double }>;

export interface NativeProps extends ViewProps {
  zoomLevel?: Double;
  onRegionChange?: DirectEventHandler<RegionEvent>;
}

export default codegenNativeComponent<NativeProps>('CustomMapView');

Networking & Storage

Mọi rank →

  1. Người dùng bấm 'thích' một bài viết và muốn UI đổi ngay, không chờ API trả về. Bạn làm optimistic update với TanStack Query thế nào cho an toàn?

    Xem đáp án mẫu
    Trong onMutate: gọi cancelQueries để refetch đang chạy không ghi đè, lưu snapshot cũ bằng getQueryData, rồi setQueryData để cập nhật cache ngay; trả snapshot ra làm context. onError dùng context đó để rollback về dữ liệu cũ và báo lỗi cho người dùng. onSettled gọi invalidateQueries để đồng bộ lại với server dù thành công hay thất bại. Bẫy hay gặp là sửa trực tiếp object đang nằm trong cache thay vì tạo object mới, và quên cancelQueries khiến một response cũ về muộn ghi đè trạng thái optimistic.
    useMutation({
  mutationFn: likePost,
  onMutate: async (id: string) => {
    await queryClient.cancelQueries({ queryKey: ['post', id] });
    const prev = queryClient.getQueryData<Post>(['post', id]);
    queryClient.setQueryData<Post>(['post', id], (p) =>
      p ? { ...p, liked: true, likes: p.likes + 1 } : p,
    );
    return { prev };
  },
  onError: (_err, id, ctx) => queryClient.setQueryData(['post', id], ctx?.prev),
  onSettled: (_data, _err, id) => queryClient.invalidateQueries({ queryKey: ['post', id] }),
});

Animation & Gesture

Mọi rank →

  1. Animated với useNativeDriver: true khác false thế nào? Vì sao animate height lại báo lỗi khi bật native driver?

    Xem đáp án mẫu
    Với useNativeDriver: false, mỗi frame JS thread phải tính giá trị rồi gửi sang native để cập nhật view, nên khi JS đang bận (render list, parse JSON) animation sẽ giật. Bật native driver thì toàn bộ animation được mô tả và gửi sang native một lần khi start(), sau đó native tự chạy từng frame trên UI thread, không phụ thuộc JS thread. Đổi lại, native driver chỉ hỗ trợ thuộc tính không ảnh hưởng layout như transform và opacity; width, height, top, flex cần tính lại layout nên báo lỗi 'not supported by native animated module'. Muốn hiệu ứng mở rộng thì dùng transform: [{ scaleY }], hoặc chuyển sang Reanimated nếu thật sự cần animate layout; Animated.event cho scroll cũng nên bật native driver.

  2. Reanimated chạy animation 'trên UI thread' nghĩa là gì? Shared value và worklet khác useState và hàm JS thường ra sao?

    Xem đáp án mẫu
    Reanimated tạo một JS runtime thứ hai chạy trên UI thread; worklet là hàm được đánh dấu để chạy trên runtime đó (callback của useAnimatedStyle, useAnimatedScrollHandler được Babel plugin tự biến thành worklet). Shared value (useSharedValue) đọc/ghi được từ cả hai runtime qua .value; gán nó không gây React re-render, và useAnimatedStyle phụ thuộc vào nó được tính lại ngay trên UI thread mỗi frame, nên animation vẫn mượt khi JS thread đang bận. Bẫy thường gặp: worklet không gọi trực tiếp được hàm JS thường như setState hay navigation mà phải lên lịch chạy về JS thread bằng runOnJS (ở Reanimated 4, các API luồng này được tách sang thư viện react-native-worklets); và không nên đọc hay ghi .value trong lúc component đang render.
    const offset = useSharedValue(0);

const animatedStyle = useAnimatedStyle(() => ({
  transform: [{ translateX: offset.value }], // worklet, chạy trên UI thread
}));

const onPress = () => {
  offset.value = withSpring(offset.value === 0 ? 120 : 0); // không re-render
};

return <Animated.View style={[styles.box, animatedStyle]} />;

  3. Làm swipe-to-delete hay bottom sheet kéo theo tay, vì sao nên dùng react-native-gesture-handler kết hợp Reanimated thay vì PanResponder?

    Xem đáp án mẫu
    PanResponder xử lý touch ở JS thread: mỗi lần ngón tay di chuyển, event phải đi sang JS rồi kết quả mới quay lại native, nên khi JS bận thì cử chỉ trễ và giật. Gesture Handler nhận diện cử chỉ bằng hệ thống gesture native; khi dùng cùng Reanimated, callback của Gesture.Pan() là worklet chạy thẳng trên UI thread và cập nhật shared value, nên view bám theo ngón tay mượt mà. Nó còn có API phối hợp cử chỉ như Gesture.Simultaneous, Gesture.Exclusive, requireExternalGestureToFail để xử lý xung đột với ScrollView, điều rất khó làm với PanResponder. Nhớ bọc gốc app trong GestureHandlerRootView, nếu không gesture sẽ không hoạt động.

  1. Dự án Expo cần tích hợp một SDK yêu cầu thêm meta-data vào AndroidManifest.xml. Với Continuous Native Generation (expo prebuild), bạn làm thế nào thay vì sửa tay thư mục native?

    Xem đáp án mẫu
    Với CNG, thư mục android/ios được coi là sản phẩm sinh ra từ app.json/app.config.ts cùng các config plugin và thường không commit; npx expo prebuild --clean có thể xoá đi sinh lại, nên mọi sửa tay đều mất. Nếu thư viện có sẵn config plugin thì chỉ cần thêm vào mảng plugins kèm option. Nếu không, tự viết config plugin bằng các mod như withAndroidManifest, withInfoPlist, withAppDelegate để chỉnh file native một cách lặp lại được và review được. Lưu ý app có native code tuỳ biến thì không chạy trong Expo Go nữa, cần development build (qua EAS Build hoặc npx expo run:android).
    // plugins/withMapsApiKey.ts
import { ConfigPlugin, withAndroidManifest, AndroidConfig } from 'expo/config-plugins';

const withMapsApiKey: ConfigPlugin<{ apiKey: string }> = (config, { apiKey }) =>
  withAndroidManifest(config, (cfg) => {
    const app = AndroidConfig.Manifest.getMainApplicationOrThrow(cfg.modResults);
    AndroidConfig.Manifest.addMetaDataItemToMainApplication(
      app, 'com.google.android.geo.API_KEY', apiKey,
    );
    return cfg;
  });

export default withMapsApiKey;

  2. Sếp hỏi: 'Đã có EAS Update rồi thì sao không sửa mọi lỗi qua OTA cho nhanh?'. Bạn giải thích giới hạn của OTA update thế nào?

    Xem đáp án mẫu
    OTA chỉ thay được JS bundle và asset đi kèm (ảnh, font). Mọi thứ thuộc binary native như thêm hay nâng thư viện có native code, nâng React Native/Expo SDK, đổi quyền trong Info.plist/AndroidManifest, icon, splash đều cần build mới và nộp store. runtimeVersion đánh dấu bản JS tương thích với binary nào: nếu đẩy JS gọi một native module mà binary cũ không có, app sẽ crash, nên phải đổi runtimeVersion (ví dụ dùng policy fingerprint) mỗi khi phần native thay đổi. Mặc định update được tải khi mở app và chỉ áp dụng ở lần khởi động sau, trừ khi tự gọi fetchUpdateAsync rồi reloadAsync, nên không phải người dùng nào cũng nhận ngay. Chính sách store cũng chỉ chấp nhận OTA cho sửa lỗi và thay đổi nhỏ, không được đổi bản chất của app.

Performance

Mọi rank →

  1. Một component con vẫn re-render dù props 'không đổi'. Những nguyên nhân nào khiến component render lại, và React.memo chặn được trường hợp nào?

    Xem đáp án mẫu
    Component render lại khi state của chính nó đổi, khi component cha render lại (mặc định React render lại toàn bộ cây con, bất kể props), hoặc khi context mà nó đọc đổi giá trị. React.memo chỉ chặn trường hợp thứ hai: nó so sánh shallow từng prop bằng Object.is, nên object, array, function hay style inline tạo mới mỗi lần render đều khiến memo vô tác dụng; memo cũng không chặn được state nội bộ hay context thay đổi. Cách xử lý: đưa style vào StyleSheet.create, đưa hằng số ra ngoài component, ổn định callback bằng useCallback, tách context lớn thành nhiều context nhỏ. Quan trọng nhất là đo bằng React DevTools Profiler (bật highlight updates) trước khi tối ưu.

  2. Màn Home có ô tìm kiếm ở đầu và một feed nặng bên dưới; mỗi lần gõ phím cả feed render lại. Trước khi rải React.memo khắp nơi, bạn có thể tái cấu trúc component thế nào?

    Xem đáp án mẫu
    Nguyên nhân là state text của ô tìm kiếm nằm ở component Home, nên mỗi lần gõ Home render lại và kéo theo toàn bộ cây con, trong đó có feed. Cách đầu tiên là đưa state xuống gần nơi dùng (state colocation): tách SearchBar tự giữ text, chỉ báo lên cha khi thật sự cần (ví dụ lúc submit hoặc sau debounce), khi đó gõ phím chỉ render lại SearchBar. Cách thứ hai khi component giữ state phải bao quanh nội dung nặng: truyền phần nặng qua children hoặc prop; element đó do cha tạo ra nên giữ nguyên reference khi component bọc ngoài render lại, và React bỏ qua nó. Hai cách này giảm re-render mà không phải thêm memo/useCallback và lo deps; chỉ khi state buộc phải dùng chung mới cân nhắc memo hoá hoặc store có selector, và luôn kiểm chứng bằng Profiler.
    // State `text` nằm trong SearchBar: gõ phím không làm Home và HeavyFeed render lại
function SearchBar({ onSubmit }: { onSubmit: (q: string) => void }) {
  const [text, setText] = useState('');
  return <TextInput value={text} onChangeText={setText} onSubmitEditing={() => onSubmit(text)} />;
}

function Home() {
  const [query, setQuery] = useState('');
  return (
    <>
      <SearchBar onSubmit={setQuery} />
      <HeavyFeed query={query} />
    </>
  );
}

  3. Feed sản phẩm dùng FlatList vài nghìn item, cuộn nhanh thì thấy vùng trắng và giật. Bạn sẽ tinh chỉnh những gì?

    Xem đáp án mẫu
    Trước hết làm item rẻ: renderItem trả về component bọc React.memo, không tạo object/hàm inline, ảnh có kích thước cố định và được cache (ví dụ expo-image), keyExtractor dùng id ổn định; nếu item cao cố định thì cung cấp getItemLayout để FlatList khỏi phải đo. Sau đó chỉnh virtualization: windowSize (mặc định 21 màn hình) nhỏ lại giúp giảm bộ nhớ nhưng dễ thấy vùng trắng hơn; initialNumToRender, maxToRenderPerBatch, updateCellsBatchingPeriod cân bằng giữa độ mượt và tốc độ lấp đầy; removeClippedSubviews tách view ngoài màn hình khỏi hierarchy nhưng đôi khi gây mất nội dung. Nếu vẫn chưa đạt thì chuyển sang FlashList: nó recycle view thay vì mount/unmount, nhưng vì thế state cục bộ trong item phải được reset theo dữ liệu mới.

  data={products}
  keyExtractor={(p) => p.id}
  renderItem={renderProduct} // khai báo ngoài component, item bọc React.memo
  getItemLayout={(_, index) => ({ length: ROW_H, offset: ROW_H * index, index })}
  windowSize={7}
  initialNumToRender={8}
  maxToRenderPerBatch={8}
/>

  4. Hermes khác JavaScriptCore ở điểm nào, và vì sao nó giúp app React Native khởi động nhanh hơn?

    Xem đáp án mẫu
    Hermes là JS engine Meta viết riêng cho React Native và là engine mặc định hiện nay. Khác biệt chính: JS được biên dịch thành bytecode ngay lúc build, nên khi mở app engine không phải parse và compile source mà chỉ việc nạp bytecode, giúp thời gian tới khi tương tác được (TTI) ngắn hơn và tốn ít RAM hơn. Hermes không dùng JIT mà tối ưu cho interpreter, kèm GC có thời gian dừng ngắn; đánh đổi là code chạy nóng trong thời gian dài có thể chậm hơn engine có JIT, và một số tính năng JS mới có thể chưa được hỗ trợ đầy đủ. Kiểm tra app có đang chạy Hermes bằng typeof HermesInternal === 'object', và debug qua React Native DevTools.

  1. Chạy Jest cho component dùng thư viện có native module (AsyncStorage, camera…) bị lỗi native module là null. Vì sao, và nên mock thế nào cho hợp lý?

    Xem đáp án mẫu
    Jest chạy component trong Node với preset react-native, không có runtime native nào phía sau, nên mọi NativeModules.X hay Turbo Module đều không tồn tại. Nhiều thư viện cung cấp sẵn mock (ví dụ @react-native-async-storage/async-storage/jest/async-storage-mock), chỉ cần jest.mock trong file setupFiles. Với module tự viết thì mock chính file spec/wrapper JS để trả giá trị cố định, dùng jest.fn() để kiểm tra lời gọi. Nên bọc native module sau một hook hoặc service của mình để test logic với mock, còn hành vi native thật thì để E2E (Detox, Maestro) kiểm tra.
    // jest.setup.ts
jest.mock('@react-native-async-storage/async-storage', () =>
  require('@react-native-async-storage/async-storage/jest/async-storage-mock'),
);

// Mock Turbo Module tự viết
jest.mock('./specs/NativeBattery', () => ({
  __esModule: true,
  default: {
    getBatteryLevel: jest.fn().mockResolvedValue(0.8),
    isCharging: jest.fn(() => false),
  },
}));

  2. Team chuẩn bị viết E2E test cho luồng đăng nhập và thanh toán. Bạn chọn Detox hay Maestro, dựa trên tiêu chí nào?

    Xem đáp án mẫu
    Detox là gray-box: nó build app kèm thư viện đồng bộ, theo dõi request mạng, timer, animation và hàng đợi của JS thread để tự đợi app rảnh trước mỗi bước, nên test ổn định; test viết bằng JS/TS chạy với Jest. Đổi lại cấu hình build phức tạp hơn, và đôi khi phải tắt đồng bộ cho animation lặp vô hạn hoặc polling. Maestro là black-box: flow viết bằng YAML, điều khiển app qua UI như người dùng, tự chờ và retry, cài đặt nhanh, chạy được với bất kỳ bản build nào, nhưng không biết trạng thái bên trong app. Cả hai nên tìm phần tử qua testID thay vì text. Thường chọn Maestro khi cần có test nhanh, ít bảo trì; chọn Detox khi cần kiểm soát sâu và gắn chặt với codebase JS.
