JavaScript & TypeScript

Mọi rank →

  1. Backend đổi trường price từ number sang string ("199000.00") mà không báo, app RN crash ở price.toFixed(0) dù TypeScript build xanh với strict bật hết. Vì sao, và bạn thiết kế lớp dữ liệu từ API thế nào để không lặp lại?

    Xem đáp án mẫu
    TypeScript chỉ kiểm tra lúc biên dịch và kiểu bị xoá hoàn toàn khi chạy; (await res.json()) as Product chỉ là lời hứa của dev với compiler, còn dữ liệu thật đến từ mạng thì không ai kiểm tra. Nguyên tắc: các biên của hệ thống (API, deep link, storage, native module, push payload) là nơi dữ liệu không đáng tin. Coi res.json() là unknown rồi parse bằng schema chạy lúc runtime (Zod, Valibot, ArkType), và suy ra kiểu TypeScript từ chính schema (z.infer) để chỉ có một nguồn sự thật. Parse ở một chỗ duy nhất (API client), phần còn lại của app chỉ nhận kiểu đã được xác thực; khi sai schema thì lỗi hiện ngay ở biên với thông báo rõ ràng và được log lên Sentry kèm endpoint, thay vì crash ngẫu nhiên ở màn hình xa. Cân nhắc độ nghiêm ngặt: trường quan trọng thì fail cứng hoặc có fallback hợp lý, trường phụ thì dùng .catch(giá trị mặc định) để một trường lạ không làm hỏng cả màn hình; và đo chi phí parse trên máy yếu, vì validate hàng nghìn phần tử tốn JS thread (có thể chỉ validate các trường cần dùng). Về lâu dài nên giảm lệch từ gốc: sinh type và client từ OpenAPI hay GraphQL schema (openapi-typescript, GraphQL Codegen), thêm contract test ở CI của backend, dùng unknown thay vì any, và bật lint hạn chế ép kiểu bừa bằng as.
    import { z } from 'zod';

const ProductSchema = z.object({
  id: z.string(),
  name: z.string(),
  price: z.coerce.number(), // backend lúc trả number lúc trả string: chuẩn hoá về number ở biên
  imageUrl: z.string().url().nullable().catch(null), // trường phụ: sai thì dùng null, không làm hỏng cả màn hình
});
export type Product = z.infer<typeof ProductSchema>; // kiểu sinh từ schema, một nguồn sự thật

export async function fetchProduct(id: string): Promise<Product> {
  const res = await fetch(`${API_URL}/products/${id}`);
  const json: unknown = await res.json(); // không tin dữ liệu từ mạng
  const parsed = ProductSchema.safeParse(json);
  if (!parsed.success) {
    reportToSentry(parsed.error, { endpoint: 'products/:id' }); // lỗi hợp đồng API lộ ra ngay ở biên
    throw new ApiContractError('products/:id', parsed.error);
  }
  return parsed.data;
}

  1. Ô tìm kiếm lọc một danh sách vài nghìn sản phẩm bị khựng khi gõ: mỗi ký tự làm cả list render lại và TextInput giật. Ngoài debounce, bạn dùng useDeferredValue hay useTransition (concurrent rendering) thế nào trong React Native, và điều kiện để chúng thật sự có tác dụng là gì?

    Xem đáp án mẫu
    Gốc vấn đề là cập nhật gấp (giá trị trong ô nhập) và cập nhật nặng (lọc, render list) có cùng mức ưu tiên, nên render list chặn JS thread và TextInput bị trễ. useDeferredValue(query) trả về một bản 'trễ' của giá trị: React render ngay với query cũ để ô nhập phản hồi tức thì, rồi render lại ở ưu tiên thấp với query mới ở nền; nếu có ký tự mới được gõ trong lúc render dở thì lần render đó bị bỏ và làm lại với giá trị mới nhất. useTransition (hoặc startTransition) đánh dấu một lần setState là không khẩn cấp và cho isPending để làm mờ UI trong lúc chờ. Khác debounce: debounce trì hoãn cố định kể cả khi máy nhanh và không làm render bớt chặn, còn deferred value tự thích nghi theo tốc độ máy và có thể ngắt giữa chừng. Điều kiện: concurrent rendering chỉ có đầy đủ trên New Architecture (Fabric, mặc định từ RN 0.76) với React 18 trở lên; phần render nặng phải nằm trong cây con nhận giá trị trễ, và component đó cần memo để khi giá trị trễ chưa đổi thì nó không render lại. Transition không làm việc nặng nhẹ đi, chỉ đổi thứ tự ưu tiên, nên vẫn cần tối ưu thật: ảo hoá list, useMemo cho bước lọc, hoặc lọc ở server khi dữ liệu lớn.

  2. Team muốn bật React Compiler cho app RN và đề xuất xoá hết useMemo, useCallback, memo trong codebase. Compiler làm gì, nó đòi hỏi gì ở code, và bạn đưa nó vào dự án đang chạy thế nào cho an toàn?

    Xem đáp án mẫu
    React Compiler là một plugin Babel phân tích component và hook lúc build rồi tự thêm memoization ở mức chi tiết (từng giá trị, từng JSX element), kể cả sau các nhánh điều kiện mà useMemo viết tay không làm được. Nó chỉ an toàn khi code tuân thủ Rules of React: render phải thuần (không sửa props, state hay biến ngoài trong lúc render, không đọc ref khi render) và hook gọi đúng quy tắc. Khi phát hiện chỗ vi phạm rõ ràng, compiler bỏ qua (không compile) component đó chứ không cố sửa, nhưng nó không phát hiện hết mọi vi phạm, nên code sai quy tắc vẫn có thể được compile và chạy sai; vì vậy cần test, không nên tin tuyệt đối. Kế hoạch đưa vào: chạy npx react-compiler-healthcheck để biết tỉ lệ component tương thích, bật lint của compiler (đã tích hợp trong bản mới của eslint-plugin-react-hooks) để sửa các vi phạm, rồi bật dần: dùng compilationMode: 'annotation' và gắn directive 'use memo' cho vài màn quan trọng, hoặc bật toàn bộ và dùng 'use no memo' để loại trừ component có vấn đề. Với Expo thì bật bằng experiments.reactCompiler trong cấu hình app. Đo trước và sau bằng React DevTools Profiler (component được compile hiện nhãn 'Memo ✨') cùng số lần render, thay vì tin rằng nó nhanh hơn. Đừng vội xoá useMemo/useCallback đang có: để lại không hại và đôi khi còn dùng làm dependency của effect, chỉ là không cần viết mới. Compiler không thay cho thiết kế đúng: state đặt quá cao, list không ảo hoá hay tính toán nặng trong render vẫn là vấn đề.

  1. Team chuyển danh sách từ FlatList sang FlashList để cuộn mượt hơn, nhưng sau đó có lỗi lạ: trạng thái như ô 'đã mở rộng' hay nội dung ô nhập trong item hiện sai ở item khác sau khi cuộn nhanh. Giải thích cơ chế và cách xử lý?

    Xem đáp án mẫu
    FlatList huỷ (unmount) item ra khỏi vùng cửa sổ và dựng item mới khi cuộn tới, nên state cục bộ của item luôn bắt đầu từ đầu. FlashList thì tái chế (recycle) view giống RecyclerView hay UITableView: khi một item trượt khỏi màn hình, component của nó không bị unmount mà được dùng lại cho item mới và chỉ đổi props. Vì vậy useState bên trong item được giữ nguyên qua các dữ liệu khác nhau, nên trạng thái 'đã mở rộng' của item A xuất hiện ở item B. Cách sửa: không giữ trạng thái theo từng item trong chính item mà nâng lên theo id (một map trong state của cha hoặc store, như expandedIds), hoặc dùng useRecyclingState(initial, deps) của FlashList để state tự reset khi deps (thường là id) đổi; effect phụ thuộc vào dữ liệu item cũng phải chạy lại theo id chứ không chỉ chạy lúc mount. Ngoài ra khi list có nhiều loại item (header, ảnh, quảng cáo) cần cung cấp getItemType để chỉ tái chế giữa các item cùng loại, kèm keyExtractor ổn định. FlashList v1 yêu cầu estimatedItemSize gần đúng, còn v2 (chỉ chạy trên New Architecture) tự đo nên không cần. Cuối cùng hãy đo bằng profiler thật: FlashList có lợi khi item nặng và list dài, còn item rẻ hoặc list ngắn thì FlatList được cấu hình tốt (getItemLayout, windowSize, removeClippedSubviews) có thể đã đủ.

  1. App RN 5 năm tuổi dùng Redux cổ điển (connect, saga, hơn 200 reducer, dữ liệu API nằm chung với state UI). Team muốn chuyển sang RTK Query hoặc React Query kết hợp Zustand mà không viết lại cả app. Bạn lập lộ trình và chọn công cụ thế nào?

    Xem đáp án mẫu
    Việc đầu tiên là phân loại state, vì nhiều thứ trong Redux thật ra là server state (dữ liệu API cần cache, refetch, invalidate), mảng này RTK Query hay TanStack Query làm tốt hơn nhiều so với reducer và saga viết tay; phần còn lại là client state (đăng nhập, theme, giỏ hàng nháp, state UI phức tạp) cần một store nhỏ gọn. Nếu app đã dùng Redux thì tiến hoá trong cùng hệ sinh thái rẻ hơn: Redux Toolkit (createSlice, configureStore) tương thích với reducer cũ (gộp được vào cùng store), và RTK Query dùng chung store và devtools; chuyển sang TanStack Query cộng Zustand thì nhẹ hơn nhưng phải chạy hai hệ thống song song trong thời gian dài. Tôi chọn theo nỗi đau thực tế: đau nhất là boilerplate và cache API thì RTK Query, còn team muốn bỏ hẳn Redux thì TanStack Query cho server state và Zustand cho phần còn lại. Lộ trình kiểu strangler, không dừng việc làm tính năng: feature mới viết bằng kiến trúc mới, feature cũ chỉ chuyển khi đằng nào cũng phải sửa lớn; ưu tiên những nơi gây đau nhất (list hay bị stale, loading và error lặp lại khắp nơi). Bước kỹ thuật: bọc truy cập state bằng custom hook và selector, thay connect bằng hook trước (giữ nguyên store), chuyển saga gọi API thành query hoặc mutation, xoá reducer khi không còn ai đọc. Kiểm soát bằng lint cấm code mới import từ module cũ, đếm số file còn dùng kiến trúc cũ như một chỉ số tiến độ, và viết test theo hành vi (không test chi tiết reducer) để refactor an toàn. Tránh tranh luận công cụ kéo dài: viết một ADR ngắn, thử trên một feature thật rồi quyết định.

  1. App RN dùng React Navigation, link shop://order/123 (hoặc universal link) cần mở màn chi tiết đơn khi app đang tắt, và nếu user chưa đăng nhập thì phải đăng nhập xong mới vào đúng màn đó. Bạn cấu hình deep link, luồng đăng nhập và back stack thế nào, và các bẫy chính là gì?

    Xem đáp án mẫu
    Khai báo linking cho NavigationContainer với prefixes và config ánh xạ đường dẫn sang route (OrderDetail: 'order/:id', kèm parse để ép kiểu tham số); React Navigation xử lý cả cold start (getInitialURL) lẫn khi app đang chạy (subscribe). Với luồng đăng nhập, cách tự nhiên là điều kiện hoá màn hình theo trạng thái: chưa đăng nhập chỉ render nhóm màn Auth, đăng nhập xong thì render nhóm màn chính (từ React Navigation 7.1 có Stack.Protected với prop guard, Expo Router cũng có Stack.Protected). Nhưng link tới màn chưa tồn tại trong navigator thì bị bỏ qua, nên tôi chủ động giữ link đích: nếu chưa đăng nhập, getInitialURL (và subscribe cho lúc app đang chạy) lưu URL vào store rồi trả về null, sau khi đăng nhập thì điều hướng bằng chính linking.config qua useLinkTo(). Back stack: deep link chỉ dựng đúng màn đích; muốn nút back về danh sách đơn thay vì thoát app thì cấu hình initialRouteName cho navigator lồng nhau hoặc tuỳ biến getStateFromPath để dựng stack đầy đủ. Các bẫy: universal link và app link chỉ mở app khi xác minh domain đúng (apple-app-site-association, assetlinks.json), còn custom scheme thì app khác có thể đăng ký trùng; mọi tham số trong link là input không đáng tin nên phải validate và server phải kiểm tra quyền; link tới ID không tồn tại phải ra một màn lỗi hợp lý thay vì crash. Với Expo Router, mỗi file là một route nên deep link tự khớp với cấu trúc thư mục.

Native & New Architecture

Mọi rank →

  1. Ở kiến trúc cũ, mọi lời gọi giữa JS và native đi qua bridge. Bridge có những giới hạn gì, JSI khắc phục chúng ra sao, và dùng JSI có bẫy gì?

    Xem đáp án mẫu
    Bridge cũ serialize mọi lời gọi thành JSON, gom batch rồi gửi bất đồng bộ giữa JS thread và native, nên tốn chi phí serialize hai chiều, không chia sẻ được bộ nhớ, và những việc cần kết quả ngay (đọc storage, đo layout) rất khó làm; method đồng bộ có tồn tại nhưng bị hạn chế và không chạy được khi debug từ xa qua Chrome. JSI là API C++ cho phép JS runtime (Hermes) giữ tham chiếu tới host object C++ và gọi method của nó trực tiếp, đồng bộ hoặc bất đồng bộ, không qua JSON. TurboModules, Fabric và các thư viện như Reanimated, MMKV, VisionCamera đều dựa trên JSI. Bẫy thứ nhất: lời gọi đồng bộ chạy ngay trên JS thread, native chậm bao lâu thì JS đứng bấy lâu, nên việc tốn thời gian vẫn phải trả Promise và chạy ở thread khác. Bẫy thứ hai: jsi::Runtime không thread-safe; muốn gọi lại JS từ thread native phải lên lịch qua CallInvoker, đụng vào runtime từ thread khác sẽ gây crash ngẫu nhiên rất khó tái hiện.

  2. Fabric thay renderer cũ như thế nào? Những lợi ích nào của Fabric mà user và dev thực sự cảm nhận được?

    Xem đáp án mẫu
    Fabric đưa lõi renderer về C++ dùng chung cho iOS và Android. Mỗi lần React render, Fabric tạo shadow tree bất biến (immutable) trong C++, tính layout bằng Yoga, rồi commit cây mới và mount các thay đổi lên view native trên UI thread. Vì shadow tree bất biến và đọc được an toàn từ nhiều thread, renderer hỗ trợ concurrent features của React 18 như startTransition, Suspense, automatic batching — điều kiến trúc cũ không làm được.   const startY = useSharedValue(0);

  useEffect(() => {
    translateY.value = withSpring(SNAP_OPEN); // mở sheet
  }, [translateY]);

  const pan = Gesture.Pan()
    .onStart(() => {
      startY.value = translateY.value; // chạy trên UI thread
    })
    .onChange((e) => {
      translateY.value = Math.max(SNAP_OPEN, startY.value + e.translationY);
    })
    .onEnd((e) => {
      const shouldClose = translateY.value > SNAP_CLOSED / 2 || e.velocityY > 800;
      translateY.value = withSpring(
        shouldClose ? SNAP_CLOSED : SNAP_OPEN,
        { velocity: e.velocityY },
        (finished) => {
          if (finished && shouldClose) runOnJS(onClose)(); // chỉ gọi sang JS một lần khi xong
        },
      );
    });

  const style = useAnimatedStyle(() => ({ transform: [{ translateY: translateY.value }] }));

  return (
    <GestureDetector gesture={pan}>
      <Animated.View style={[styles.sheet, style]}>{children}</Animated.View>
    </GestureDetector>
  );
}

Hai: lỗi JS không được bắt (uncaught exception) đi tới ErrorUtils.setGlobalHandler (Sentry hay Crashlytics gắn handler ở đây); lỗi fatal ở bản release làm app thoát, còn ở dev thì hiện LogBox; unhandled promise rejection mặc định chỉ cảnh báo ở dev nên SDK như Sentry cài thêm hook để ghi nhận. Ba: crash native (lỗi trong thư viện native, OOM, bị kill vì memory, ANR trên Android, watchdog trên iOS) không có JS stack và JS không bắt được vì process đã chết; cần SDK native (Sentry, Crashlytics) cùng các nguồn như Android vitals, Xcode Organizer, MetricKit. Vì vậy 'app tự tắt' mà không có lỗi tương ứng thường là OOM hay jetsam hoặc ANR, còn màn hình trắng thường do lỗi render ở nơi không có ErrorBoundary hoặc lỗi nằm ngay trong fallback. Thiết kế: nhiều ErrorBoundary theo vùng (root, từng màn, từng widget quan trọng) với fallback có nút thử lại; thêm breadcrumb (điều hướng, request, hành động của user), gắn đúng release, dist và source map, theo dõi crash-free users chứ không chỉ session, và đặt cảnh báo theo ngưỡng; lỗi nhẹ như API fail thì ghi ở mức handled kèm context. Kiểm chứng bằng cách giả lập từng loại lỗi (ném lỗi trong handler, Promise reject, crash native) trên bản staging để biết SDK bắt được chưa.
    // Lỗi JS không bắt được (event handler, setTimeout...): Sentry/Crashlytics gắn handler này
const defaultHandler = ErrorUtils.getGlobalHandler();
ErrorUtils.setGlobalHandler((error, isFatal) => {
  logger.captureException(error, { fatal: isFatal });
  defaultHandler(error, isFatal); // vẫn giữ hành vi mặc định (fatal thì app thoát)
});

// Lỗi render: ErrorBoundary theo từng vùng, không chỉ ở root
class SectionBoundary extends React.Component<
  { name: string; children: React.ReactNode },
  { failed: boolean }
> {
  state = { failed: false };

  static getDerivedStateFromError() {
    return { failed: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logger.captureException(error, { section: this.props.name, componentStack: info.componentStack });
  }

  render() {
    return this.state.failed ? (
      <Button title="Thử lại" onPress={() => this.setState({ failed: false })} />
    ) : (
      this.props.children
    );
  }
}

    Xem đáp án mẫu
    Ý chính là tách app thành host (shell) và nhiều mini-app là các bundle JS tải lúc chạy. Với RN có hai hướng: dùng Re.Pack (bundler dựa trên webpack/Rspack của Callstack) cùng Module Federation để mỗi mini-app build ra bundle riêng và dùng chung react, react-native dưới dạng singleton, host nạp bundle từ xa qua ScriptManager; hoặc mỗi mini-app là một bundle Metro độc lập chạy trong runtime riêng (cô lập tốt hơn nhưng tốn memory và khó dùng chung dependency). Hợp đồng giữa host và mini-app phải rõ ràng: một API 'bridge' có version (xác thực, điều hướng, thanh toán, analytics, storage riêng cho từng mini-app) thay vì cho mini-app chạm thẳng vào native module của host; mỗi mini-app khai báo phiên bản host tối thiểu, host từ chối nạp nếu không tương thích. Rủi ro lớn nhất: binary của host là cố định nên phải đóng gói sẵn mọi native dependency mà mini-app dùng (camera, maps) vì mini-app chỉ đổi được JS; lệch version react hay react-native giữa host và mini-app gây lỗi hook hay crash khó hiểu; bundle remote là code thực thi nên phải ký và kiểm tra tính toàn vẹn, đồng thời phải quản lý quyền (permission, dữ liệu user) của mini-app bên thứ ba; và Apple, Google có điều khoản về việc tải code lúc chạy nên cần xem lại chính sách của từng store. Vận hành: registry mini-app có kênh staging và production, rollout theo phần trăm, kill switch từ xa, theo dõi crash gắn nhãn theo mini-app và version, cache bundle để chạy được offline; và đo thời gian khởi động mini-app (tải bundle, khởi tạo) vì đó là trải nghiệm user cảm nhận.

ScriptManager.shared.addResolver(async (scriptId) => {
  const entry = await miniAppRegistry.resolve(scriptId, { hostVersion: HOST_VERSION, channel });
  if (!entry) return undefined; // host quá cũ cho mini-app này: không nạp
  return { url: entry.url, verifyScriptSignature: 'strict' }; // bundle remote là code thực thi: phải ký
});

  1. Một bản OTA vừa đẩy lên production làm app crash ngay khi mở ở khoảng 20% user. Bạn xử lý sự cố này thế nào, cả lúc đang cháy lẫn sau đó?

    Xem đáp án mẫu
    Ưu tiên cầm máu: dừng mọi rollout đang chạy và rollback ngay — publish lại bản update ổn định trước đó hoặc quay về bundle nhúng trong binary — trên đúng channel và runtime version. Cần nhớ máy đã tải update lỗi chỉ nhận bản sửa ở lần khởi động sau, và nếu app crash ngay lúc khởi động thì phải trông vào cơ chế error recovery của thư viện update — cần hiểu rõ cơ chế này trước khi dùng OTA. Song song, chỉ định một người điều phối, một kênh liên lạc, cập nhật cho support và PM theo mốc thời gian, dùng Sentry (đã có source map) để khoanh vùng — nguyên nhân hay gặp là update gọi native module mà binary cũ chưa có do sai runtime version.
