  1. Backend đổi trường price từ number sang string ("199000.00") mà không báo, app RN crash ở price.toFixed(0) dù TypeScript build xanh với strict bật hết. Vì sao, và bạn thiết kế lớp dữ liệu từ API thế nào để không lặp lại?

    Xem đáp án mẫu
    TypeScript chỉ kiểm tra lúc biên dịch và kiểu bị xoá hoàn toàn khi chạy; (await res.json()) as Product chỉ là lời hứa của dev với compiler, còn dữ liệu thật đến từ mạng thì không ai kiểm tra. Nguyên tắc: các biên của hệ thống (API, deep link, storage, native module, push payload) là nơi dữ liệu không đáng tin. Coi res.json() là unknown rồi parse bằng schema chạy lúc runtime (Zod, Valibot, ArkType), và suy ra kiểu TypeScript từ chính schema (z.infer) để chỉ có một nguồn sự thật. Parse ở một chỗ duy nhất (API client), phần còn lại của app chỉ nhận kiểu đã được xác thực; khi sai schema thì lỗi hiện ngay ở biên với thông báo rõ ràng và được log lên Sentry kèm endpoint, thay vì crash ngẫu nhiên ở màn hình xa. Cân nhắc độ nghiêm ngặt: trường quan trọng thì fail cứng hoặc có fallback hợp lý, trường phụ thì dùng .catch(giá trị mặc định) để một trường lạ không làm hỏng cả màn hình; và đo chi phí parse trên máy yếu, vì validate hàng nghìn phần tử tốn JS thread (có thể chỉ validate các trường cần dùng). Về lâu dài nên giảm lệch từ gốc: sinh type và client từ OpenAPI hay GraphQL schema (openapi-typescript, GraphQL Codegen), thêm contract test ở CI của backend, dùng unknown thay vì any, và bật lint hạn chế ép kiểu bừa bằng as.
    import { z } from 'zod';

const ProductSchema = z.object({
  id: z.string(),
  name: z.string(),
  price: z.coerce.number(), // backend lúc trả number lúc trả string: chuẩn hoá về number ở biên
  imageUrl: z.string().url().nullable().catch(null), // trường phụ: sai thì dùng null, không làm hỏng cả màn hình
});
export type Product = z.infer<typeof ProductSchema>; // kiểu sinh từ schema, một nguồn sự thật

export async function fetchProduct(id: string): Promise<Product> {
  const res = await fetch(`${API_URL}/products/${id}`);
  const json: unknown = await res.json(); // không tin dữ liệu từ mạng
  const parsed = ProductSchema.safeParse(json);
  if (!parsed.success) {
    reportToSentry(parsed.error, { endpoint: 'products/:id' }); // lỗi hợp đồng API lộ ra ngay ở biên
    throw new ApiContractError('products/:id', parsed.error);
  }
  return parsed.data;
}

  1. Bạn tự viết một store nhỏ (object ở module-level kèm subscribe) và cho component đọc nó bằng useEffect + useState. Với concurrent rendering của React 18, thỉnh thoảng hai component cùng màn hình hiện hai giá trị khác nhau của cùng store (tearing). useSyncExternalStore giải quyết gì, quy tắc bắt buộc của nó là gì, và vì sao Redux, Zustand dùng nó?

    Xem đáp án mẫu
    Khi render có thể bị ngắt rồi tiếp tục (concurrent), một store nằm ngoài React có thể đổi giữa chừng một lần render: component trước đọc giá trị cũ, component sau đọc giá trị mới, và màn hình hiện trạng thái không nhất quán (tearing). Mẫu useEffect + useState còn có khoảng hở giữa lúc render và lúc effect subscribe nên có thể lỡ một thay đổi. useSyncExternalStore(subscribe, getSnapshot) là API dành cho store bên ngoài: React gọi getSnapshot lúc render và kiểm tra lại trước khi commit; nếu giá trị đã đổi thì render lại đồng bộ, để mọi component trong một lần commit thấy cùng một snapshot. Quy tắc bắt buộc: getSnapshot phải trả về giá trị ổn định, cùng một tham chiếu khi store chưa đổi; nếu mỗi lần gọi lại trả object mới (như () => ({ ...state }) hay .filter trong selector) thì React cảnh báo và có thể render lặp vô hạn. subscribe cũng phải ổn định (khai báo ngoài component hoặc bọc useCallback), nếu không sẽ unsubscribe rồi subscribe lại ở mỗi render. Selector nên trả primitive hoặc một phần state đã có sẵn, để chỉ re-render khi đúng phần đó đổi. Đó là lý do react-redux (v8 trở lên) và Zustand dùng nó bên dưới. Đánh đổi: cập nhật qua useSyncExternalStore luôn đồng bộ nên không hưởng lợi từ transition. Hiếm khi cần tự viết store, nhưng hiểu cơ chế này giúp chọn đúng thư viện và dùng cho các nguồn ngoài React như Appearance, Dimensions, NetInfo.
    type Listener = () => void;

function createCounterStore() {
  let state = { count: 0 };
  const listeners = new Set<Listener>();
  return {
    getState: () => state, // cùng một tham chiếu khi chưa đổi
    increment() {
      state = { count: state.count + 1 }; // đổi thì tạo object mới
      listeners.forEach((l) => l());
    },
    subscribe(listener: Listener) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

const store = createCounterStore();

function useCount() {
  // subscribe ổn định, getSnapshot trả về primitive nên không render thừa
  return useSyncExternalStore(store.subscribe, () => store.getState().count);
}

// Nguồn ngoài React: chế độ sáng/tối của hệ thống
function useColorScheme() {
  return useSyncExternalStore(
    (onChange) => {
      const sub = Appearance.addChangeListener(onChange);
      return () => sub.remove();
    },
    () => Appearance.getColorScheme(),
  );
}

  2. Team muốn bật React Compiler cho app RN và đề xuất xoá hết useMemo, useCallback, memo trong codebase. Compiler làm gì, nó đòi hỏi gì ở code, và bạn đưa nó vào dự án đang chạy thế nào cho an toàn?

    Xem đáp án mẫu
    React Compiler là một plugin Babel phân tích component và hook lúc build rồi tự thêm memoization ở mức chi tiết (từng giá trị, từng JSX element), kể cả sau các nhánh điều kiện mà useMemo viết tay không làm được. Nó chỉ an toàn khi code tuân thủ Rules of React: render phải thuần (không sửa props, state hay biến ngoài trong lúc render, không đọc ref khi render) và hook gọi đúng quy tắc. Khi phát hiện chỗ vi phạm rõ ràng, compiler bỏ qua (không compile) component đó chứ không cố sửa, nhưng nó không phát hiện hết mọi vi phạm, nên code sai quy tắc vẫn có thể được compile và chạy sai; vì vậy cần test, không nên tin tuyệt đối. Kế hoạch đưa vào: chạy npx react-compiler-healthcheck để biết tỉ lệ component tương thích, bật lint của compiler (đã tích hợp trong bản mới của eslint-plugin-react-hooks) để sửa các vi phạm, rồi bật dần: dùng compilationMode: 'annotation' và gắn directive 'use memo' cho vài màn quan trọng, hoặc bật toàn bộ và dùng 'use no memo' để loại trừ component có vấn đề. Với Expo thì bật bằng experiments.reactCompiler trong cấu hình app. Đo trước và sau bằng React DevTools Profiler (component được compile hiện nhãn 'Memo ✨') cùng số lần render, thay vì tin rằng nó nhanh hơn. Đừng vội xoá useMemo/useCallback đang có: để lại không hại và đôi khi còn dùng làm dependency của effect, chỉ là không cần viết mới. Compiler không thay cho thiết kế đúng: state đặt quá cao, list không ảo hoá hay tính toán nặng trong render vẫn là vấn đề.

  1. App RN 5 năm tuổi dùng Redux cổ điển (connect, saga, hơn 200 reducer, dữ liệu API nằm chung với state UI). Team muốn chuyển sang RTK Query hoặc React Query kết hợp Zustand mà không viết lại cả app. Bạn lập lộ trình và chọn công cụ thế nào?

    Xem đáp án mẫu

JSI là API C++ cho phép JS runtime (Hermes) giữ tham chiếu tới host object C++ và gọi method của nó trực tiếp, đồng bộ hoặc bất đồng bộ, không qua JSON. TurboModules, Fabric và các thư viện như Reanimated, MMKV, VisionCamera đều dựa trên JSI. Bẫy thứ nhất: lời gọi đồng bộ chạy ngay trên JS thread, native chậm bao lâu thì JS đứng bấy lâu, nên việc tốn thời gian vẫn phải trả Promise và chạy ở thread khác. Bẫy thứ hai: jsi::Runtime không thread-safe; muốn gọi lại JS từ thread native phải lên lịch qua CallInvoker, đụng vào runtime từ thread khác sẽ gây crash ngẫu nhiên rất khó tái hiện.

  `CREATE TABLE product (id INTEGER PRIMARY KEY, sku TEXT NOT NULL, name TEXT NOT NULL, price INTEGER NOT NULL);
   CREATE INDEX idx_product_name ON product(name COLLATE NOCASE);`,
  'ALTER TABLE product ADD COLUMN barcode TEXT;',

export async function openDb() {
  const db = await SQLite.openDatabaseAsync('shop.db');
  await db.execAsync('PRAGMA journal_mode = WAL;');
  const row = await db.getFirstAsync<{ user_version: number }>('PRAGMA user_version');
  for (let v = row?.user_version ?? 0; v < MIGRATIONS.length; v++) {
    await db.withTransactionAsync(async () => {
      await db.execAsync(MIGRATIONS[v]);
      await db.execAsync(`PRAGMA user_version = ${v + 1}`); // tăng phiên bản cùng transaction với bước migrate
    });
  }
  return db;
}

// Nhập hàng loạt trong một transaction
export async function importProducts(db: SQLite.SQLiteDatabase, items: Product[]) {
  await db.withTransactionAsync(async () => {
    for (const p of items) {
      await db.runAsync('INSERT OR REPLACE INTO product (id, sku, name, price) VALUES (?, ?, ?, ?)', [p.id, p.sku, p.name, p.price]);
    }
  });
}

const SNAP_CLOSED = 400;

function BottomSheet({ onClose, children }: { onClose: () => void; children: React.ReactNode }) {
  const translateY = useSharedValue(SNAP_CLOSED);
  const startY = useSharedValue(0);

  useEffect(() => {
    translateY.value = withSpring(SNAP_OPEN); // mở sheet
  }, [translateY]);

  const pan = Gesture.Pan()
    .onStart(() => {
      startY.value = translateY.value; // chạy trên UI thread
    })
    .onChange((e) => {
      translateY.value = Math.max(SNAP_OPEN, startY.value + e.translationY);
    })
    .onEnd((e) => {
      const shouldClose = translateY.value > SNAP_CLOSED / 2 || e.velocityY > 800;
      translateY.value = withSpring(
        shouldClose ? SNAP_CLOSED : SNAP_OPEN,
        { velocity: e.velocityY },
        (finished) => {
          if (finished && shouldClose) runOnJS(onClose)(); // chỉ gọi sang JS một lần khi xong
        },
      );
    });

  const style = useAnimatedStyle(() => ({ transform: [{ translateY: translateY.value }] }));

  return (
    <GestureDetector gesture={pan}>
      <Animated.View style={[styles.sheet, style]}>{children}</Animated.View>
    </GestureDetector>
  );
}

    async function processInChunks<T, R>(
  items: T[],
  mapFn: (item: T) => R,
  signal: AbortSignal,
  chunkSize = 500,
): Promise<R[]> {
  const out: R[] = [];
  for (let i = 0; i < items.length; i += chunkSize) {
    if (signal.aborted) throw new Error('aborted');
    for (const item of items.slice(i, i + chunkSize)) out.push(mapFn(item));
    await new Promise<void>((resolve) => setTimeout(resolve, 0)); // nhường thread cho chạm và render
  }
  return out;
}

Chỉ test hai nhánh của flag quan trọng, đừng nhân tổ hợp.

export async function refreshFlags(): Promise<void> {
  try {
    const remote: Partial<Record<FlagName, boolean>> = await fetchJson(FLAGS_URL, { timeoutMs: 3000 });
    storage.set('flags', JSON.stringify(remote)); // flag thường: áp dụng từ lần mở app sau

      const value = remote[key];
      if (value !== undefined && value !== active[key]) {
        active = { ...active, [key]: value }; // kill-switch có hiệu lực ngay trong phiên
        changed = true;
      }
    }
    if (changed) listeners.forEach((notify) => notify());
  } catch {
    // mất mạng hoặc server lỗi: giữ nguyên giá trị cache/mặc định
  }
}

  );
}

  1. Một bản OTA vừa đẩy lên production làm app crash ngay khi mở ở khoảng 20% user. Bạn xử lý sự cố này thế nào, cả lúc đang cháy lẫn sau đó?

Cần nhớ máy đã tải update lỗi chỉ nhận bản sửa ở lần khởi động sau, và nếu app crash ngay lúc khởi động thì phải trông vào cơ chế error recovery của thư viện update — cần hiểu rõ cơ chế này trước khi dùng OTA. Sau sự cố là postmortem không đổ lỗi: timeline, root cause, vì sao quy trình không chặn được, rồi action item có người chịu trách nhiệm như bắt buộc thử update trên build production qua channel preview, rollout theo phần trăm kèm theo dõi crash-free, chuyển runtime version sang fingerprint.
