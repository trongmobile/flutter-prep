Native & New Architecture

Mọi rank →

  1. Ở kiến trúc cũ, mọi lời gọi giữa JS và native đi qua bridge. Bridge có những giới hạn gì, JSI khắc phục chúng ra sao, và dùng JSI có bẫy gì?

    Xem đáp án mẫu
    Bridge cũ serialize mọi lời gọi thành JSON, gom batch rồi gửi bất đồng bộ giữa JS thread và native, nên tốn chi phí serialize hai chiều, không chia sẻ được bộ nhớ, và những việc cần kết quả ngay (đọc storage, đo layout) rất khó làm; method đồng bộ có tồn tại nhưng bị hạn chế và không chạy được khi debug từ xa qua Chrome. JSI là API C++ cho phép JS runtime (Hermes) giữ tham chiếu tới host object C++ và gọi method của nó trực tiếp, đồng bộ hoặc bất đồng bộ, không qua JSON. TurboModules, Fabric và các thư viện như Reanimated, MMKV, VisionCamera đều dựa trên JSI. Bẫy thứ nhất: lời gọi đồng bộ chạy ngay trên JS thread, native chậm bao lâu thì JS đứng bấy lâu, nên việc tốn thời gian vẫn phải trả Promise và chạy ở thread khác. Bẫy thứ hai: jsi::Runtime không thread-safe; muốn gọi lại JS từ thread native phải lên lịch qua CallInvoker, đụng vào runtime từ thread khác sẽ gây crash ngẫu nhiên rất khó tái hiện.

  2. Fabric thay renderer cũ như thế nào? Những lợi ích nào của Fabric mà user và dev thực sự cảm nhận được?

    Xem đáp án mẫu
    Fabric đưa lõi renderer về C++ dùng chung cho iOS và Android. Mỗi lần React render, Fabric tạo shadow tree bất biến (immutable) trong C++, tính layout bằng Yoga, rồi commit cây mới và mount các thay đổi lên view native trên UI thread. Vì shadow tree bất biến và đọc được an toàn từ nhiều thread, renderer hỗ trợ concurrent features của React 18 như startTransition, Suspense, automatic batching — điều kiến trúc cũ không làm được. Fabric cũng cho phép đọc layout đồng bộ: đo vị trí trong useLayoutEffect rồi cập nhật ngay trong cùng frame, nên hết cảnh tooltip hay popover nháy sai vị trí một frame. Với dev, một implementation chung giúp giảm khác biệt hành vi giữa hai nền tảng. Khi migrate cần chú ý: native component cũ dùng requireNativeComponent chỉ chạy được nhờ interop layer, và code dựa vào API nội bộ của UIManager cũ có thể đổi hành vi.

  3. Team bạn duy trì một TurboModule nội bộ (thanh toán, sinh trắc học) dùng chung cho 3 app, các app đều phát hành JS qua OTA. Khi cần thêm method hoặc đổi kiểu trong spec, bạn đặt quy trình gì để không làm vỡ app đang chạy?

    Xem đáp án mẫu
    Điểm mấu chốt: Codegen chỉ bảo đảm JS và native khớp nhau trong cùng một lần build; còn khi bundle JS đi qua OTA, JS mới có thể chạy trên binary cũ mà native chưa có method mới. Vì vậy mọi thay đổi spec được coi là thay đổi native: phải ra binary mới và đổi runtimeVersion (policy fingerprint làm việc này tự động) để update dùng spec mới không tới được binary cũ. Thứ hai, ưu tiên thay đổi tương thích ngược: thêm method mới thay vì đổi chữ ký method cũ, đánh dấu deprecated rồi mới xoá sau vài bản phát hành. Thứ ba, thư viện có version theo semver và changelog ghi rõ thay đổi nào cần build native; phía JS có thể kiểm tra khả năng của binary (ví dụ một hằng số version do module trả về) trước khi gọi tính năng mới. Cuối cùng, CI của từng app chạy E2E với bản thư viện mới trước khi nâng, và review spec như review API public vì nó là hợp đồng giữa các team.
    // NativePayment.ts
export interface Spec extends TurboModule {
  getApiVersion(): number; // JS kiểm tra trước khi dùng tính năng mới
  pay(orderId: string): Promise<string>;
  // Thêm mới thay vì đổi chữ ký của pay()
  payWithBiometric(orderId: string, reason: string): Promise<string>;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativePayment');

  4. App của bạn vẫn chạy kiến trúc cũ với khoảng 60 thư viện native bên thứ ba. Bạn lên kế hoạch chuyển sang New Architecture thế nào để không làm vỡ production?

    Xem đáp án mẫu
    Bước đầu là kiểm kê: đối chiếu từng thư viện với React Native Directory (có cờ hỗ trợ New Architecture) và xếp loại: đã hỗ trợ, chạy được qua interop layer, hay phải thay thế/fork, nhân tiện bỏ các thư viện không còn được bảo trì. Interop layer giúp phần lớn module và component kiểu cũ chạy trên New Architecture mà không cần viết lại, nhưng không phải tất cả: thư viện truy cập thẳng bridge hay API nội bộ của renderer cũ thường hỏng, nhất là ở chế độ bridgeless. Về kỹ thuật, tôi nâng RN lên bản mới trước (từ 0.76 New Architecture bật mặc định, các bản gần đây đã bỏ hẳn tuỳ chọn tắt), làm trên một nhánh riêng, chạy toàn bộ E2E và QA thủ công các màn nhạy cảm như map, video, camera, WebView trên cả hai nền tảng. Native code tự viết thì chuyển sang TurboModule/Fabric component với Codegen. Khi phát hành, dùng staged rollout, so sánh crash-free rate và thời gian startup với bản cũ, và giữ sẵn đường lùi là binary trước đó.

  5. Công ty muốn nhúng vài màn React Native vào app native Android/iOS đang chạy (brownfield). Những vấn đề kỹ thuật chính bạn phải thiết kế là gì?

    Xem đáp án mẫu
    Thứ nhất là vòng đời runtime: khởi tạo React Native (JS runtime, load bundle, native module) tốn đáng kể, nên tạo một instance dùng chung ở mức Application/AppDelegate, có thể pre-warm trước khi user vào màn RN, thay vì tạo mới mỗi lần mở màn. Thứ hai là ranh giới điều hướng: mỗi điểm vào RN là một root component đăng ký bằng AppRegistry.registerComponent và nhận initial props; phải quy ước rõ bên nào quản lý back stack, nút back Android và deep link. Thứ ba là giao tiếp hai chiều: native module cho JS gọi vào native (lấy token, analytics, mở màn native), event cho native báo sang JS, với contract có type qua Codegen. Thứ tư là build và phân phối: team native thường không muốn cài Node, nên đóng gói phần RN (kèm bundle đã build) thành artifact AAR/XCFramework để tích hợp như dependency thường, đồng thời xử lý các thư viện native trùng giữa hai phía (OkHttp, Firebase). Cuối cùng, nếu dùng OTA cho phần RN thì update phải gắn với version native của host app.

Expo, Build & Release

Mọi rank →

  1. Sau khi App Center/CodePush ngừng hoạt động, team chuyển sang EAS Update. runtimeVersion dùng để làm gì, và cấu hình sai thì hậu quả là gì?

    Xem đáp án mẫu
    OTA chỉ thay được JS bundle và asset; phần native (thư viện native, quyền, cấu hình Info.plist/Manifest, bản thân React Native) chỉ đổi được qua binary mới trên store. runtimeVersion là hợp đồng giữa một bản build native và các update: app chỉ nhận update có cùng runtimeVersion. Nếu thêm thư viện native mà quên đổi runtime version, update dùng thư viện đó sẽ tới tay binary cũ chưa có code native tương ứng và crash ngay khi gọi tới. Vì vậy tôi chọn policy tự động: fingerprint tính hash từ cấu hình và code native, đổi native là đổi runtime; hoặc appVersion nếu team kỷ luật tăng version mỗi lần đổi native. Kết hợp channel theo môi trường (preview, production), rollout update theo phần trăm, theo dõi crash trước khi mở rộng, và luôn thử update trên build production thật chứ không chỉ trên dev client.
    // app.config.ts
import type { ExpoConfig } from 'expo/config';

const config: ExpoConfig = {
  name: 'Shop',
  slug: 'shop',
  version: '2.4.0',
  runtimeVersion: { policy: 'fingerprint' }, // đổi native -> runtime mới
  updates: { url: 'https://u.expo.dev/<project-id>' },
};

export default config;

  2. Crash report từ production trên Sentry chỉ hiện stack trace kiểu index.android.bundle:1:284731. Vì sao, và quy trình release cần làm gì để đọc được?

    Xem đáp án mẫu
    Bundle production đã được minify và, với Hermes, biên dịch sang bytecode, nên vị trí lỗi chỉ là offset trong file đã biến đổi; cần source map để map ngược về file và dòng gốc. Với Hermes phải dùng source map đã ghép (map của Metro cộng map do hermesc sinh ra), map của Metro đứng một mình sẽ cho kết quả sai. Quy trình: mỗi build trên CI tạo source map và upload lên Sentry, gắn đúng release/dist (hoặc debug ID ở các bản SDK mới) khớp với giá trị SDK gửi lên khi crash. Mỗi bản OTA là một bundle mới nên cũng phải upload map tương ứng, nếu không crash từ bản update sẽ không đọc được. Phần native cũng cần dSYM trên iOS và mapping file của R8 trên Android. @sentry/react-native có tích hợp vào bước build Gradle/Xcode và EAS; điều quan trọng là tự động hoá trong pipeline chứ không làm tay, và kiểm chứng bằng một crash thử trên bản staging.

  3. Team đang commit thư mục ios/ và android/, sửa tay rất nhiều, và mỗi lần nâng React Native mất cả tuần. Bạn có đề xuất chuyển sang Continuous Native Generation (Expo prebuild) không? Đánh đổi là gì?

    Xem đáp án mẫu
    Với Continuous Native Generation, ios/ và android/ không được commit mà được sinh lại từ app.json/app.config.ts cùng config plugin mỗi khi build (npx expo prebuild). Lợi ích lớn nhất là nâng cấp: không còn phải merge diff template vào project native đã bị sửa tay nhiều năm. Mọi thay đổi native (quyền, entitlement, Gradle, Podfile, đoạn code trong AppDelegate) phải viết thành config plugin, nên chúng được ghi lại, có version và review được thay vì nằm rải rác. Đánh đổi: tốn công chuyển các chỉnh sửa tay hiện có thành plugin; tuỳ biến native phức tạp viết plugin khá vất vả, nhất là plugin sửa file bằng chuỗi/regex dễ vỡ khi template đổi; và team phải bỏ thói quen sửa trực tiếp thư mục sinh ra. Tôi sẽ đánh giá lượng code native tự viết và tần suất nâng cấp, rồi thử trên một nhánh; code native tự viết nhiều có thể chuyển thành local Expo module thay vì để trong thư mục sinh ra.

Performance

Mọi rank →

  1. Màn danh sách đơn hàng giật khi cuộn trên Android tầm thấp. Perf Monitor cho thấy JS FPS tụt mạnh còn UI FPS vẫn gần 60. Điều đó nói lên gì, và bạn profile tiếp thế nào?

    Xem đáp án mẫu
    JS thread chạy React (render, reconcile), business logic và handler sự kiện; UI thread vẽ và xử lý scroll native. UI FPS ổn nghĩa là scroll native vẫn mượt, nhưng JS không kịp render item mới nên FlatList lộ vùng trắng, onPress phản hồi trễ, animation không dùng native driver bị khựng. Trước hết tôi tái hiện trên build release trên đúng máy yếu, vì dev mode chậm hơn nhiều và cho số liệu sai lệch. Sau đó dùng React DevTools Profiler xem commit nào lâu và vì sao component render lại, kết hợp Hermes sampling profiler để tìm hàm JS nặng. Thủ phạm hay gặp: renderItem tạo object/closure mới khiến memo vô dụng, item quá nặng, format ngày/tiền tốn kém trong mỗi lần render, state đặt quá cao khiến cả list render lại. Nếu ngược lại UI FPS tụt mà JS ổn thì xem Perfetto (Android) hoặc Instruments (iOS) để tìm layout phức tạp, overdraw, decode ảnh lớn, shadow.
    // Mỗi lần cha render, style và onPress đều là giá trị mới
// nên OrderRow dù bọc memo vẫn render lại toàn bộ
<FlatList
  data={orders}
  renderItem={({ item }) => (
    <OrderRow order={item} style={{ padding: 12 }} onPress={() => open(item.id)} />
  )}
/>;

// Sửa: style để trong StyleSheet của OrderRow, `open` ổn định (useCallback)
const renderItem = useCallback(
  ({ item }: { item: Order }) => <OrderRow order={item} onOpen={open} />,
  [open],
);

  2. Cold start của app RN mất gần 4 giây trên máy Android tầm trung. Bạn đo và tối ưu theo những hướng nào?

    Xem đáp án mẫu
    Tôi đo trên build release, trên đúng máy tầm trung, và tách cold start thành các đoạn: khởi tạo native (Application.onCreate, SDK native), khởi tạo React Native và load bundle, thực thi module JS lúc import, render màn đầu và chờ dữ liệu; công cụ là Perfetto/Android Studio, Instruments trên iOS, cộng marker thời gian trong JS. Hướng tối ưu: đảm bảo dùng Hermes để bundle được biên dịch sẵn thành bytecode, không phải parse lúc chạy; giữ inline requires bật (template RN đã bật) để module chỉ thực thi khi được dùng lần đầu, và tránh side effect nặng ở top-level module; lazy-load màn hình và thư viện lớn ít dùng; chỉ khởi tạo SDK cần cho màn đầu, phần còn lại dời ra sau first render; hiển thị dữ liệu cache hoặc skeleton thay vì chờ API. Phía native cũng phải xem, vì SDK khởi tạo đồng bộ trong Application.onCreate/AppDelegate có thể tốn đáng kể. Cuối cùng đặt ngân sách startup và theo dõi qua Android vitals, Xcode Organizer để không bị thoái lui âm thầm.

  3. Một thuật toán xử lý dữ liệu viết bằng JS thuần chạy rất nhanh khi thử trên Node, nhưng trong app dùng Hermes lại chậm hơn hẳn. Vì sao, bạn xử lý thế nào, và Hermes còn khác V8/JavaScriptCore ở điểm nào cần biết?

    Xem đáp án mẫu
    Hermes được thiết kế cho React Native với ưu tiên là startup và memory: ở bản release, bundle được hermesc biên dịch sẵn thành bytecode lúc build, nên app không phải parse và compile JS khi khởi động. GC của Hermes (Hades) làm phần lớn công việc song song trên thread nền nên các lần dừng ngắn, hợp với ứng dụng có UI. Đổi lại, Hermes không dùng JIT, nên code CPU-bound chạy lâu (xử lý chuỗi lớn, crypto viết bằng JS thuần, parse dữ liệu khổng lồ) có thể chậm hơn trên engine có JIT; cách xử lý đúng là đưa việc nặng xuống native/JSI hoặc backend chứ không phải đổi engine. Vài khác biệt hành vi cần biết: Function.prototype.toString không trả lại source gốc, và một số tính năng JS mới có thể chưa được hỗ trợ đầy đủ. Hermes là engine mặc định từ RN 0.70, và React Native DevTools kết nối thẳng vào Hermes để debug, thay cho cách remote debugging qua Chrome trước đây vốn chạy JS trên một engine khác.

  4. Memory của app tăng dần sau mỗi lần vào ra màn chi tiết sản phẩm, cuối cùng app bị OS kill. Bạn tìm và xử lý leak trong RN thế nào?

    Xem đáp án mẫu
    Tôi lặp lại flow vào/ra vài chục lần trên build release, theo dõi memory bằng Android Studio Profiler hoặc Xcode, rồi tách xem phần tăng nằm ở JS heap hay bộ nhớ native. Với JS heap, chụp heap snapshot bằng tab Memory của React Native DevTools trước và sau, so sánh object không được giải phóng và lần theo retaining path; với native thì dùng heap dump (Android) hoặc Allocations/Memory Graph (iOS). Nguyên nhân hay gặp trong RN: subscription không được gỡ (AppState, Keyboard, Dimensions, event emitter của native module, WebSocket), setInterval/setTimeout không clear, closure giữ state của màn bị lưu vào store toàn cục hoặc cache cấp module không giới hạn, callback JS bị SDK native giữ lại, và cache ảnh không giới hạn. Cách phòng: effect nào đăng ký thì cleanup phải huỷ, dùng API trả subscription và gọi .remove(), giới hạn kích thước cache, và có kịch bản E2E lặp flow để bắt hồi quy.
    useEffect(() => {
  const sub = AppState.addEventListener('change', onAppStateChange);
  const timer = setInterval(refreshPrice, 30_000);
  return () => {
    sub.remove(); // thiếu dòng này: listener và closure sống mãi
    clearInterval(timer);
  };
}, [onAppStateChange, refreshPrice]);

  5. Feed hiển thị ảnh user upload (ảnh gốc 12MP). Trên Android tầm thấp app hay bị OOM khi cuộn nhanh. Vì sao, và bạn sửa thế nào?

    Xem đáp án mẫu
    Dung lượng file JPEG không phản ánh memory: khi hiển thị, ảnh được decode thành bitmap khoảng width × height × 4 byte, nên ảnh 4000×3000 chiếm khoảng 48MB dù chỉ hiện trong thumbnail nhỏ — vài ảnh như vậy cùng lúc là đủ OOM. Sửa tận gốc ở server/CDN: sinh nhiều kích thước hoặc resize theo tham số, và client xin đúng kích thước hiển thị nhân với mật độ điểm ảnh. Phía client, dùng thư viện ảnh có downsampling và cache tốt như expo-image; với Image của core trên Android, resizeMethod="resize" giúp giảm kích thước ảnh trước khi decode. List dùng FlashList hoặc FlatList được cấu hình hợp lý để không giữ quá nhiều item ngoài viewport, và chỉ tải ảnh full-size khi user thực sự mở màn xem ảnh.
    const px = PixelRatio.getPixelSizeForLayoutSize(120);

<Image
  source={{ uri: `${photo.url}?w=${px}&h=${px}` }} // CDN resize sẵn
  style={{ width: 120, height: 120 }}
  resizeMethod="resize" // Android: downsample trước khi decode
/>

  6. Sau một năm, JS bundle của app tăng từ 6MB lên 14MB và startup chậm dần. Bạn phân tích và kiểm soát kích thước bundle thế nào?

    Xem đáp án mẫu
    Tôi tạo bundle production kèm source map rồi phân tích bằng source-map-explorer hoặc react-native-bundle-visualizer để thấy module nào chiếm chỗ. Để kiểm soát lâu dài: đặt ngân sách kích thước bundle và báo chênh lệch trên CI ở mỗi PR, review dependency mới theo kích thước, tình trạng bảo trì và có kèm native code hay không.   1. Một dev đặt secret key của cổng thanh toán vào .env và đọc qua react-native-config, lập luận rằng Hermes đã biên dịch ra bytecode nên không ai đọc được. Bạn phản hồi thế nào?

    Xem đáp án mẫu
    Lập luận này sai. Biến từ .env qua react-native-config hay EXPO_PUBLIC_* đều được nhúng nguyên văn vào app (trong bundle JS hoặc resource native), và bytecode Hermes không phải là mã hoá: string literal vẫn nằm nguyên trong file, có sẵn công cụ disassemble/decompile bytecode Hermes, thậm chí lệnh strings cũng đủ thấy key. Kẻ tấn công còn có thể dùng proxy hoặc Frida để xem request lúc chạy. Nguyên tắc là mọi thứ nằm trong app đều coi như public: secret thật (key thanh toán, key AI, key quản trị) phải ở backend; app gọi backend bằng token ngắn hạn của user, backend mới gọi dịch vụ bên thứ ba. Key bắt buộc nằm ở client (Maps SDK, analytics) thì giới hạn bằng restriction theo package name/bundle id/chữ ký và quota. App Check, Play Integrity hay App Attest giúp backend biết request đến từ app thật, nhưng chỉ là lớp bổ sung chứ không thay cho việc không giao secret cho client.

await fetch('https://api.payment.example/charge', {
  method: 'POST',
  headers: { Authorization: `Bearer ${Config.PAYMENT_SECRET_KEY}` },
});

// Đúng: app chỉ gửi token của user, backend giữ secret
await fetch(`${API_URL}/orders/${orderId}/pay`, {
  method: 'POST',
  headers: { Authorization: `Bearer ${accessToken}` },
});

  2. Bạn triển khai SSL pinning cho app RN thế nào, và cần chuẩn bị gì để pinning không 'khoá' toàn bộ user khi server đổi chứng chỉ?

    Xem đáp án mẫu
    fetch của RN đi qua stack mạng native (OkHttp trên Android, NSURLSession trên iOS), nên pinning phải làm ở tầng native: trên Android cấu hình CertificatePinner cho OkHttp client mà RN dùng thông qua OkHttpClientProvider.setOkHttpClientFactory, trên iOS dùng TrustKit hoặc một thư viện pinning dựng sẵn cho RN. Nhớ rằng SDK có HTTP client riêng hay WebView sẽ không được bao phủ. Pin public key (hash SPKI) thay vì cả certificate để gia hạn chứng chỉ với cùng key không làm vỡ pin, và luôn có ít nhất một pin dự phòng (key backup tạo sẵn hoặc key của CA trung gian). Cần quy trình xoay key phối hợp với backend/infra: phát hành app chứa pin mới trước, đợi đa số user cập nhật rồi mới đổi chứng chỉ; không trông vào OTA vì cấu hình pin nằm trong code native. Pinning chặn được MITM qua proxy trên máy bình thường, nhưng trên máy root/jailbreak có Frida thì vẫn bị bypass, nên chỉ là một lớp bảo vệ.
    class PinnedClientFactory : OkHttpClientFactory {
  override fun createNewNetworkModuleClient(): OkHttpClient {
    val pinner = CertificatePinner.Builder()
      .add("api.shop.vn", "sha256/AAAA...=") // key đang dùng
      .add("api.shop.vn", "sha256/BBBB...=") // key dự phòng
      .build()
    return OkHttpClientProvider.createClientBuilder()
      .certificatePinner(pinner)
      .build()
  }
}

  3. Khách hàng (một ví điện tử) yêu cầu app RN phải 'chặn máy root/jailbreak và chống sửa app'. Bạn thiết kế lớp bảo vệ này thế nào cho thực tế?

    Xem đáp án mẫu
    Trước hết nói rõ với stakeholder: mọi kiểm tra phía client đều có thể bị bypass (Frida, patch bundle), nên client chỉ cung cấp tín hiệu, quyết định cuối cùng nằm ở server. Tôi kết hợp nhiều lớp: thư viện phát hiện root/jailbreak, debugger, hook chạy ở tầng native để gắn cờ rủi ro; attestation của nền tảng — Play Integrity API trên Android, App Attest trên iOS — để server xác minh request đến từ bản app chính hãng trên thiết bị đáng tin, vì kết quả do Google/Apple ký nên client không tự giả được. Server áp dụng chính sách theo mức rủi ro: thiết bị đáng ngờ vẫn xem được số dư nhưng giao dịch lớn cần thêm OTP hoặc sinh trắc học, hoặc chặn hẳn nếu quy định yêu cầu. Token và dữ liệu nhạy cảm lưu trong Keychain/Keystore qua react-native-keychain hoặc expo-secure-store; không log token, tắt dev menu và log debug ở bản release; bật FLAG_SECURE cho màn nhạy cảm trên Android. Obfuscation JS và native chỉ làm tăng chi phí reverse, không phải hàng rào chính.

  1. Công ty có 3 app RN (khách hàng, tài xế, merchant) dùng chung nhiều UI và logic. Bạn tổ chức monorepo thế nào, và những bẫy riêng của RN trong monorepo là gì?

    Xem đáp án mẫu
    Tôi dùng workspace của package manager (pnpm hoặc Yarn workspaces), thêm Turborepo/Nx để cache và chỉ chạy task bị ảnh hưởng. Cấu trúc: apps/* cho từng app; packages/* cho design system (token, component), API client có type, utils và các feature package có ranh giới rõ, chỉ export qua entry public. Bẫy riêng của RN: thứ nhất, cả repo chỉ được có một bản react và react-native — hai bản react gây lỗi 'Invalid hook call', hai bản thư viện native gây đăng ký trùng hoặc autolinking sai — nên package dùng chung khai báo chúng là peerDependencies và ép version thống nhất ở root. Hiển thị: list đảo chiều (inverted), phân trang theo cursor khi cuộn lên, key dùng clientId để tin không bị remount khi nhận serverId. Thêm trạng thái failed cho user gửi lại, sắp xếp theo thời gian server, và giới hạn dữ liệu lưu local.

  clientId: string; // UUID tạo ở client, dùng làm idempotency key
  serverId?: string; // có sau khi server ack
  conversationId: string;
  body: string;
  status: 'pending' | 'sent' | 'failed';
  createdAt: number; // giờ server khi đã ack, giờ máy khi pending

  1. Một bản OTA vừa đẩy lên production làm app crash ngay khi mở ở khoảng 20% user. Bạn xử lý sự cố này thế nào, cả lúc đang cháy lẫn sau đó?

    Xem đáp án mẫu
    Ưu tiên cầm máu: dừng mọi rollout đang chạy và rollback ngay — publish lại bản update ổn định trước đó hoặc quay về bundle nhúng trong binary — trên đúng channel và runtime version.
