  1. Vì sao callback của Promise.then luôn chạy trước setTimeout(fn, 0) dù timer được đặt trước? Hiểu biết này liên quan gì tới việc app React Native bị đơ khi xử lý dữ liệu lớn?

    Xem đáp án mẫu
    JS chạy đơn luồng: sau khi đoạn code đồng bộ hiện tại chạy xong, engine xả hết hàng đợi microtask (callback của Promise, queueMicrotask) rồi mới lấy một macrotask tiếp theo (timer, sự kiện I/O). Vì vậy .then luôn chạy trước setTimeout(fn, 0). Trong React Native, logic JS, các callback như onPress và việc tính toán cho render đều chạy trên JS thread, nên một vòng lặp nặng (parse JSON lớn, lọc list hàng chục nghìn phần tử) sẽ chặn nó: nút bấm không phản hồi, animation chạy bằng JS bị giật. Microtask liên tục sinh microtask mới cũng chặn event loop y như vậy; việc nặng nên chia nhỏ, đẩy về server hoặc xuống native.
    console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// In ra: 1, 4, 3, 2

  2. Màn hình Home gọi 3 API song song (banner, danh mục, sản phẩm gợi ý). Chỉ cần API banner lỗi là cả màn hình trắng. Bạn dùng Promise.all hay Promise.allSettled, và vì sao?

    Xem đáp án mẫu
    Promise.all reject ngay khi một promise reject (fail-fast), nên chỉ cần banner lỗi là mất luôn dữ liệu hai API kia dù chúng thành công; nó hợp khi các kết quả phụ thuộc nhau, thiếu một cái là vô nghĩa. Promise.allSettled chờ tất cả xong và trả về mảng { status: 'fulfilled', value } hoặc { status: 'rejected', reason }, nên từng khu vực tự hiển thị dữ liệu hoặc trạng thái lỗi riêng. Cả hai đều chạy các request song song, khác với await lần lượt từng cái làm tổng thời gian cộng dồn. Lưu ý Promise.all reject sớm không huỷ các request còn lại, chúng vẫn chạy tới khi xong.
    const [banner, categories, products] = await Promise.allSettled([
  api.getBanner(),
  api.getCategories(),
  api.getRecommended(),
]);

setBanner(banner.status === 'fulfilled' ? banner.value : null);
setCategories(categories.status === 'fulfilled' ? categories.value : []);
setProductsError(products.status === 'rejected' ? products.reason : null);

  3. Đoạn code upload ảnh dưới đây báo "Xong" ngay lập tức dù ảnh chưa upload, và lỗi upload không bị catch bắt. Vì sao?

    Xem đáp án mẫu
    forEach không biết gì về Promise: nó gọi callback async cho từng phần tử, bỏ qua Promise trả về và kết thúc ngay, nên showToast('Xong') chạy khi các upload mới bắt đầu. Lỗi trong callback trở thành Promise bị reject mà không ai await, nên try/catch bên ngoài không bắt được, chỉ thấy cảnh báo unhandled promise rejection. Muốn chạy lần lượt thì dùng for (const p of photos) { await uploadPhoto(p); }; muốn song song thì await Promise.all(photos.map(uploadPhoto)). Quy tắc chung: try/catch chỉ bắt được lỗi async của Promise được await bên trong khối try.
    async function uploadAll(photos: Photo[]) {
  try {
    photos.forEach(async (p) => {
      await uploadPhoto(p);
    });
    showToast('Xong');
  } catch (e) {
    showToast('Upload lỗi');
  }
}

  4. Bạn có CountryPicker và CategoryPicker gần như giống hệt nhau, chỉ khác kiểu dữ liệu. Làm sao gộp thành một component SelectList dùng chung mà onSelect vẫn nhận đúng kiểu, không phải dùng any?

    Xem đáp án mẫu
    Dùng generic: khai báo tham số kiểu T cho component để items: T[] và onSelect: (item: T) => void cùng một kiểu. TypeScript tự suy ra T từ items ở nơi dùng, nên onSelect nhận đúng Country hay Category và gõ sai thuộc tính bị báo ngay. Phần component cần đọc nhưng không biết kiểu thì nhận qua prop như getLabel, hoặc ràng buộc T extends { id: string } để dùng item.id làm key. Bẫy hay gặp: trong file .tsx, arrow function generic phải viết <T,>(props) => ... hoặc <T extends object> vì <T> bị hiểu là thẻ JSX; khai báo bằng function thì không bị. Bọc React.memo làm mất tham số kiểu, cần ép lại bằng memo(SelectList) as typeof SelectList. Custom hook cũng dùng generic được, như useFetch<T>, nhưng kiểu chỉ có lúc biên dịch, dữ liệu server thật vẫn có thể sai.
    type SelectListProps<T extends { id: string }> = {
  items: T[];
  getLabel: (item: T) => string;
  onSelect: (item: T) => void;
};

function SelectList<T extends { id: string }>({ items, getLabel, onSelect }: SelectListProps<T>) {
  return (
    <FlatList
      data={items}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <Pressable onPress={() => onSelect(item)}>
          <Text>{getLabel(item)}</Text>
        </Pressable>
      )}
    />
  );
}

// T được suy ra là Country, nên country.dialCode có gợi ý và được kiểm tra kiểu
<SelectList items={countries} getLabel={(c) => c.name} onSelect={(country) => setDial(country.dialCode)} />

  1. Màn hình đăng ký listener (AppState, Keyboard, socket…) trong useEffect. Sau vài lần vào ra màn hình, mỗi sự kiện bị xử lý nhiều lần. Nguyên nhân và cách sửa?

    Xem đáp án mẫu
    Mỗi lần component mount, effect đăng ký thêm một listener nhưng listener cũ không được gỡ khi unmount, nên chúng chồng lên nhau và còn giữ tham chiếu tới state cũ (memory leak). Effect cần return một hàm cleanup để huỷ đăng ký: React gọi cleanup khi component unmount và cả trước mỗi lần chạy lại effect do dependency đổi. Các API của React Native như AppState.addEventListener hay Keyboard.addListener trả về một subscription, chỉ cần gọi remove() trong cleanup. Nếu app được bọc trong <StrictMode>, ở development React cố tình chạy mount → cleanup → mount để bạn phát hiện sớm effect thiếu cleanup.
    const [appState, setAppState] = useState(AppState.currentState);

useEffect(() => {
  const sub = AppState.addEventListener('change', setAppState);
  return () => sub.remove(); // gỡ listener khi unmount
}, []);

  2. Đồng hồ đếm ngược dưới đây chỉ giảm từ 60 xuống 59 rồi đứng yên. Vì sao, và sửa thế nào?

    Xem đáp án mẫu
    Đây là stale closure: effect chỉ chạy một lần (deps []) nên callback của setInterval giữ mãi giá trị seconds của lần render đầu tiên là 60, giây nào cũng set lại 59. Cách sửa gọn nhất là functional update setSeconds((s) => s - 1): React luôn truyền vào giá trị mới nhất nên không cần đưa seconds vào deps. Thêm seconds vào deps cũng chạy đúng, nhưng interval bị huỷ rồi tạo lại mỗi giây. Rule react-hooks/exhaustive-deps của ESLint cảnh báo loại lỗi này ngay khi viết, đừng tắt nó cho nhanh.
    const [seconds, setSeconds] = useState(60);

useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds - 1); // seconds luôn là 60
  }, 1000);
  return () => clearInterval(id);
}, []);

  3. Màn hình đăng ký cần: nhấn Next trên bàn phím thì focus sang ô mật khẩu, và giữ id của timer gửi lại OTP để huỷ khi rời màn hình. Vì sao cả hai việc này dùng useRef chứ không dùng useState?

    Xem đáp án mẫu
    useRef trả về một object { current } sống suốt vòng đời component; đổi ref.current không gây re-render và đọc lúc nào cũng ra giá trị mới nhất, không bị stale closure. Vì vậy nó hợp với dữ liệu không hiển thị lên UI như id của timer, cờ đang xử lý, giá trị của lần render trước. Ref cũng dùng để giữ tham chiếu tới native component, ví dụ gọi passwordRef.current?.focus(). Ngược lại, giá trị nào cần hiện trên màn hình phải để trong state, vì đổi ref không cập nhật UI; cũng không nên đọc hay ghi ref.current ngay trong lúc render.

const otpTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

useEffect(() => () => {
  if (otpTimerRef.current) clearTimeout(otpTimerRef.current); // rời màn hình thì huỷ
}, []);

<TextInput
  returnKeyType="next"
  onSubmitEditing={() => passwordRef.current?.focus()}
/>

  4. Màn hình có 2.000 sản phẩm, ô lọc theo giá và một nút mở modal sắp xếp. Mỗi lần mở hay đóng modal, app khựng lại vì lọc lại cả danh sách. Bạn dùng useMemo thế nào, và useMemo khác useCallback ra sao?

    Xem đáp án mẫu
    Mở modal làm đổi state nên component render lại, và phép filter viết thẳng trong thân component chạy lại dù dữ liệu lọc không đổi. Bọc phép lọc trong useMemo với deps là products và minPrice: React giữ kết quả cũ và chỉ tính lại khi một dep đổi (so bằng Object.is), nên mở modal không còn phải lọc lại. useMemo nhớ giá trị trả về của hàm, còn useCallback(fn, deps) nhớ chính hàm fn, có ích khi hàm được truyền cho component con bọc React.memo hoặc nằm trong deps của effect. Deps phải khai báo đủ, thiếu minPrice thì danh sách không cập nhật khi đổi bộ lọc; và chỉ nên memo phép tính thật sự tốn kém, vì useMemo cũng có chi phí riêng.
    function ProductScreen({ products }: { products: Product[] }) {
  const [minPrice, setMinPrice] = useState(0);
  const [sortOpen, setSortOpen] = useState(false);

  // Chỉ lọc lại khi products hoặc minPrice đổi, mở/đóng modal không tính lại
  const visible = useMemo(
    () => products.filter((p) => p.price >= minPrice),
    [products, minPrice],
  );

  const openSort = useCallback(() => setSortOpen(true), []);
  return <ProductList items={visible} onOpenSort={openSort} />;
}

  5. Ô tìm kiếm gọi API mỗi lần gõ một ký tự. Hãy viết custom hook useDebounce để chỉ gọi API khi người dùng ngừng gõ 400ms. Hai component cùng dùng hook này có chung state không?

    Xem đáp án mẫu
    Custom hook là hàm có tên bắt đầu bằng use và gọi các hook khác bên trong, dùng để tái sử dụng logic có state. useDebounce giữ một bản sao của giá trị và chỉ cập nhật khi giá trị đứng yên đủ delay; mỗi lần value đổi, cleanup huỷ timer cũ nên chỉ lần gõ cuối được tính. Component dùng debouncedKeyword làm dependency của effect gọi API thay vì keyword. Mỗi lần gọi hook là một bộ state riêng, nên hai component dùng useDebounce không chia sẻ gì với nhau; muốn dùng chung state thì cần Context hoặc store.
    function useDebounce<T>(value: T, delay = 400): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // gõ tiếp thì huỷ timer cũ
  }, [value, delay]);

  return debounced;
}

  6. Màn hình Profile crash với lỗi Rendered more hooks than during the previous render ngay khi người dùng đăng nhập xong. Nhìn đoạn code, nguyên nhân là gì và vì sao React có quy tắc này?

    Xem đáp án mẫu
    React không định danh hook theo tên mà theo thứ tự gọi trong mỗi lần render: hook thứ nhất, thứ hai… được lưu thành danh sách gắn với component. Quy tắc là chỉ gọi hook ở cấp cao nhất của function component hoặc custom hook, trước mọi return sớm, không đặt trong if, vòng lặp hay callback. Cách sửa: chuyển useState lên trên if, hoặc tách phần sau đăng nhập thành component con; plugin eslint-plugin-react-hooks bắt lỗi này ngay khi viết.

  const scrollRef = useRef<ScrollView>(null); // hook trước return sớm: OK
  if (!user) {
    return <LoginPrompt />;

  const [tab, setTab] = useState<'info' | 'orders'>('info');

const loadMore = async () => {

  5. Trang chủ gồm banner, danh mục và một danh sách sản phẩm dọc dài, được viết là ScrollView bọc FlatList. Console báo VirtualizedLists should never be nested inside plain ScrollViews và danh sách vài trăm item render chậm. Nguyên nhân và cách tổ chức lại?

    Xem đáp án mẫu
    Cảnh báo này nói đúng vấn đề: ScrollView cho con chiều cao theo nội dung, nên FlatList bên trong không biết chỉ một phần của nó đang nằm trong màn hình và thường render gần như toàn bộ item; ảo hoá (windowing) mất tác dụng, màn hình chậm và tốn RAM khi dữ liệu lớn. Hai thứ cuộn cùng chiều còn dễ tranh cử chỉ vuốt của nhau. Cách đúng là chỉ để một list cuộn: đưa banner và danh mục vào ListHeaderComponent (phần cuối vào ListFooterComponent) của chính FlatList. Màn có nhiều khu vực khác loại thì dùng SectionList, hoặc một FlatList với dữ liệu gồm nhiều kiểu item. Nên truyền element (ListHeaderComponent={<Header />}) thay vì một hàm tạo component mới sau mỗi render, nếu không phần header bị mount lại. List ngang nằm trong ScrollView dọc, như carousel, thì không sao vì khác chiều cuộn.

Validate ở client chỉ để cải thiện trải nghiệm: server vẫn phải kiểm tra lại, và lỗi server trả về hiển thị được qua setError.
    type FormValues = { email: string; password: string };

function RegisterForm({ onRegister }: { onRegister: (v: FormValues) => Promise<void> }) {
  const {
    control,
    handleSubmit,
    formState: { errors, isSubmitting },

  return (
    <View>
      <Controller
        control={control}
        name="email"

          required: 'Nhập email',

      {/* ô password viết tương tự, thêm rule minLength */}

  1. Thông tin user đăng nhập đang được truyền qua props qua 4–5 tầng component chỉ để tới một nút ở sâu bên dưới. Khi nào lifting state và truyền props là đủ, khi nào nên chuyển sang Context, và Context có bẫy gì cần biết?

Bẫy cần biết: khi value của Provider đổi tham chiếu, mọi component dùng Context đó đều re-render, và viết value={{ user, logout }} inline tạo object mới mỗi lần Provider render; nên bọc value bằng useMemo và tách Context theo mức độ thay đổi.   2. Màn hình giỏ hàng đang có bốn useState riêng (items, coupon, loading, error), mỗi thao tác phải gọi 2–3 hàm set liền nhau và thỉnh thoảng quên reset error. Khi nào nên chuyển sang useReducer, và nó khác useState thế nào?

    Xem đáp án mẫu
    useReducer gom state vào một object và mọi thay đổi đều đi qua hàm reducer(state, action), nên luật cập nhật nằm ở một chỗ thay vì rải trong nhiều handler. Mỗi action trả về state mới trọn vẹn, ví dụ loadStarted vừa bật loading vừa xoá error, nên không còn trạng thái nửa vời. Nên dùng khi nhiều giá trị đổi cùng nhau hoặc có nhiều loại thao tác; state đơn giản, độc lập như bật/tắt modal thì useState gọn hơn. Reducer phải là hàm thuần: không gọi API, không sửa state tại chỗ mà trả về object mới (Strict Mode chạy reducer hai lần ở development để lộ lỗi này). Việc gọi API vẫn nằm ở handler hoặc effect, xong thì dispatch kết quả. dispatch có tham chiếu ổn định nên truyền cho component con không gây render thừa. Đây vẫn là state cục bộ; muốn chia sẻ thì kết hợp Context.
    type CartState = { items: CartItem[]; coupon: string | null; loading: boolean; error: string | null };
type CartAction =
  | { type: 'loadStarted' }
  | { type: 'loaded'; items: CartItem[] }
  | { type: 'loadFailed'; message: string }
  | { type: 'couponApplied'; code: string }
  | { type: 'removed'; id: string };

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case 'loadStarted':
      return { ...state, loading: true, error: null }; // bật loading và xoá lỗi cũ cùng lúc
    case 'loaded':
      return { ...state, loading: false, items: action.items };
    case 'loadFailed':
      return { ...state, loading: false, error: action.message };
    case 'couponApplied':
      return { ...state, coupon: action.code };
    case 'removed':
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };
  }
}

const [state, dispatch] = useReducer(cartReducer, { items: [], coupon: null, loading: false, error: null });
dispatch({ type: 'removed', id: '42' });

    function HomeScreen() {
  const [sheetOpen, setSheetOpen] = useState(false);
  const lastBackRef = useRef(0);

  useFocusEffect(
    useCallback(() => {
      const sub = BackHandler.addEventListener('hardwareBackPress', () => {
        if (sheetOpen) {
          setSheetOpen(false); // đóng sheet trước
          return true; // true: đã xử lý, không chạy handler nào khác
        }
        const now = Date.now();
        if (now - lastBackRef.current < 2000) return false; // false: để hệ thống thoát app
        lastBackRef.current = now;
        ToastAndroid.show('Nhấn back lần nữa để thoát', ToastAndroid.SHORT);
        return true;
      });
      return () => sub.remove(); // mất focus thì gỡ, không chặn back của màn khác
    }, [sheetOpen]),
  );

  return <HomeContent sheetOpen={sheetOpen} onCloseSheet={() => setSheetOpen(false)} />;
}

Trên nền JSI có TurboModules (native module khởi tạo khi cần, gọi trực tiếp) và Fabric (renderer mới).   1. Màn hình chi tiết sản phẩm gọi API theo id trong useEffect. Bạn tổ chức trạng thái loading/error thế nào, và cần xử lý gì khi người dùng thoát màn hình hoặc đổi id trước khi request xong?

    Xem đáp án mẫu
    fetch chỉ reject khi không có response (mất mạng, lỗi DNS, request bị huỷ); 4xx/5xx vẫn resolve bình thường, nên phải tự kiểm tra res.ok hoặc res.status rồi ném lỗi. Màn hình nên có đủ ba trạng thái loading, error, data để UI không quay loading mãi khi API lỗi. Khi unmount hoặc id đổi, cleanup gọi abort() của AbortController để huỷ request cũ, tránh race condition: kết quả của id cũ về sau đè lên id mới. Request bị abort cũng reject, nên kiểm tra signal.aborted để không set state hay hiện lỗi cho trường hợp này.
    useEffect(() => {
  const controller = new AbortController();
  setLoading(true);
  setError(null);
  fetch(`${API_URL}/products/${id}`, { signal: controller.signal })
    .then((res) => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`); // 4xx/5xx không tự reject
      return res.json();
    })
    .then(setProduct)
    .catch((e) => !controller.signal.aborted && setError(e))
    .finally(() => !controller.signal.aborted && setLoading(false));
  return () => controller.abort(); // rời màn hình hoặc đổi id
}, [id]);

Hook useNetInfo() trả về isConnected (thiết bị đã nối mạng) và isInternetReachable (thật sự ra được Internet): đang ở Wi-Fi nhưng chưa qua trang đăng nhập của captive portal thì isConnected là true còn isInternetReachable là false. Cả hai có thể là null lúc chưa xác định, nên so sánh === false thay vì !isConnected, nếu không banner offline sẽ chớp mỗi lần mở app. NetInfo chỉ phản ánh kết nối chung, không đảm bảo server của bạn gọi được, nên request thật vẫn phải xử lý lỗi và hiện thông báo dễ hiểu kèm nút thử lại. Khi có mạng trở lại hoặc app quay về từ nền (AppState sang 'active'), nên tải lại dữ liệu đang hiển thị, không retry vô hạn.

  4. API trả 401 khi access token hết hạn. Bạn viết interceptor Axios để tự gắn token và tự làm mới token, nhưng khi màn Home bắn 4 request cùng lúc thì app gọi /refresh tới 4 lần, và có lần người dùng bị đăng xuất oan. Nguyên nhân và cách xử lý?

    Xem đáp án mẫu
    Request interceptor gắn token vào header Authorization; response interceptor bắt 401, gọi refresh rồi gửi lại request gốc. Khi bốn request cùng nhận 401, mỗi cái tự gọi refresh nên có bốn lần refresh chạy song song; nếu server xoay vòng refresh token (mỗi token chỉ dùng một lần) thì các lần sau dùng token đã bị vô hiệu, bị từ chối và người dùng bị đăng xuất. Cách xử lý: giữ một Promise refresh dùng chung ở cấp module; request 401 đầu tiên tạo ra nó, các request còn lại await cùng Promise đó, rồi tất cả gửi lại với token mới và biến được xoá khi xong. Đánh dấu _retry để không lặp vô hạn nếu request gửi lại vẫn 401, và gọi /refresh bằng một instance Axios không gắn interceptor này. Refresh thất bại thì xoá token và đưa người dùng về màn đăng nhập.
    let refreshing: Promise<string> | null = null;

api.interceptors.request.use((config) => {
  const token = tokenStore.access;
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

api.interceptors.response.use(
  (res) => res,
  async (error: AxiosError) => {
    const original = error.config as (InternalAxiosRequestConfig & { _retry?: boolean }) | undefined;
    if (error.response?.status !== 401 || !original || original._retry) throw error;
    original._retry = true;

    if (!refreshing) {
      // authClient: instance riêng, không gắn interceptor này
      refreshing = refreshAccessToken(authClient).finally(() => {
        refreshing = null;
      });
    }
    const newToken = await refreshing; // mọi request 401 cùng chờ một lần refresh
    original.headers.Authorization = `Bearer ${newToken}`;
    return api(original);
  },
);

Animation & Gesture

Mọi rank →

  1. Làm hiệu ứng mờ dần (fade-in) cho thẻ khi màn hình mở. Bạn viết const opacity = new Animated.Value(0) thẳng trong thân component, nhưng mỗi lần state đổi thì thẻ lại nhấp nháy và chạy lại từ đầu. Vì sao, và viết thế nào cho đúng?

    Xem đáp án mẫu
    Thân component chạy lại sau mỗi lần render, nên new Animated.Value(0) viết thẳng ở đó tạo ra value mới ở 0 mỗi lần, tiến độ animation cũ mất và thẻ nhấp nháy. Value phải được giữ ổn định qua các lần render bằng useRef(new Animated.Value(0)).current, còn animation nên khởi chạy trong useEffect thay vì trong lúc render. Value chỉ có tác dụng khi gắn vào Animated.View, Animated.Text, Animated.Image…; View thường không biết cập nhật khi value đổi. Từ một value có thể suy ra nhiều thuộc tính bằng interpolate. Luôn khai báo useNativeDriver: với opacity và transform đặt true để animation chạy phía native, không giật khi JS thread bận. Animation lặp bằng Animated.loop thì gọi .stop() trong cleanup. Hiệu ứng theo cử chỉ hoặc phức tạp hơn thì chuyển sang Reanimated.
    function FadeInCard({ children }: { children: React.ReactNode }) {
  const opacity = useRef(new Animated.Value(0)).current; // giữ nguyên qua các lần render

  useEffect(() => {
    Animated.timing(opacity, {
      toValue: 1,
      duration: 300,
      useNativeDriver: true,
    }).start();
  }, [opacity]);

  const translateY = opacity.interpolate({ inputRange: [0, 1], outputRange: [12, 0] });

  return <Animated.View style={{ opacity, transform: [{ translateY }] }}>{children}</Animated.View>;
}

Expo, Build & Release

Mọi rank →

  1. Bạn debug một lỗi logic JS và một màn hình re-render quá nhiều thế nào? Vì sao các hướng dẫn cũ dùng Flipper hay "Debug JS Remotely" trên Chrome không còn phù hợp?

    Xem đáp án mẫu
    Với React Native hiện tại chạy Hermes, công cụ chính là React Native DevTools: mở từ Dev Menu hoặc nhấn j trong terminal đang chạy Metro, có Console, Sources để đặt breakpoint, cùng tab Components và Profiler của React DevTools để xem props/state và đo component nào render lại, mất bao lâu. Flipper đã bị bỏ khỏi template mặc định, còn Remote JS Debugging chạy JS trên V8 của Chrome thay vì trên thiết bị nên hành vi có thể khác thật (khác engine, gọi native đồng bộ không chạy) và đã bị deprecated. Lỗi phía native thì đọc Logcat trong Android Studio hoặc console của Xcode; lỗi network có thể log ở tầng API client hoặc dùng proxy như Proxyman, Charles.

  2. App cần trỏ tới API khác nhau cho dev, staging và production. Bạn cấu hình biến môi trường thế nào, và vì sao không được để secret trong .env của app?

    Xem đáp án mẫu
    Với Expo, đặt biến có tiền tố EXPO_PUBLIC_ trong các file như .env.development, .env.production (hoặc trong cấu hình môi trường của EAS) rồi đọc bằng process.env.EXPO_PUBLIC_API_URL; phải viết đầy đủ như vậy, destructure từ process.env sẽ không được thay thế. Với bare React Native thường dùng react-native-config để biến dùng được cả trong JS lẫn native (Gradle, Info.plist), kết hợp build flavor trên Android và scheme trên iOS. Các giá trị này được nhúng vào bundle hoặc binary lúc build, nên bản app đã phát hành chỉ nhận giá trị mới khi build lại (hoặc publish update), khi dev đôi khi phải khởi động lại Metro với --reset-cache, và ai giải nén app cũng đọc được. Vì vậy .env của app chỉ chứa cấu hình công khai như URL, feature flag; secret phải nằm ở backend.

  3. Kéo code mới về và chạy yarn install xong thì iOS không build được (The sandbox is not in sync with the Podfile.lock), còn Android báo lỗi liên quan tới phiên bản Java/Gradle. Bạn xử lý theo thứ tự nào?

    Xem đáp án mẫu
    Lỗi sandbox nghĩa là thư mục Pods không khớp Podfile.lock: package.json vừa đổi (thêm hoặc nâng thư viện có code native) mà chưa cài lại pod. Vào thư mục ios chạy bundle exec pod install (Bundler dùng đúng CocoaPods của Gemfile), thêm --repo-update nếu báo không tìm thấy phiên bản pod, rồi mở .xcworkspace chứ không mở .xcodeproj. Android: kiểm tra JDK đúng phiên bản React Native của bạn yêu cầu (hiện là JDK 17), sdk.dir trong android/local.properties hoặc ANDROID_HOME, rồi chạy ./gradlew clean trong android. Lỗi JS lạ sau khi đổi dependency thì khởi động Metro với --reset-cache. Trước khi xoá cache hàng loạt, đọc dòng lỗi gốc (mục What went wrong của Gradle hoặc lỗi đầu tiên trong Xcode), và dùng npx react-native doctor để kiểm tra môi trường; với Expo, npx expo install --check báo thư viện lệch phiên bản SDK.

  1. Danh sách chạy giật khi test bằng bản debug trên máy thật, đồng nghiệp bảo "đo bản release mới chuẩn". Vì sao hai bản khác nhau, bạn đo hiệu năng thế nào, và console.log còn sót trong code ảnh hưởng gì?

    Xem đáp án mẫu

Security

Mọi rank →

  1. Sau khi đăng nhập, bạn lưu access token và refresh token ở đâu? Đồng nghiệp bảo "AsyncStorage nằm trong sandbox của app nên an toàn", bạn trả lời thế nào?

    Xem đáp án mẫu
    Sandbox chỉ ngăn app khác đọc dữ liệu trên máy bình thường; AsyncStorage vẫn lưu plain text, nên trên máy đã root/jailbreak hoặc qua bản backup, token bị đọc trực tiếp. Chỉ lưu những gì thật cần (thường là refresh token, access token có thể chỉ giữ trong bộ nhớ) và xoá sạch khi logout. Lưu ý trên iOS mục Keychain có thể còn lại sau khi gỡ app, nên lần mở đầu tiên sau khi cài lại nên xoá token cũ.

Mọi rank →

  1. Bạn merge main vào nhánh feature thì dính conflict ở yarn.lock (hoặc package-lock.json), Podfile.lock và cả project.pbxproj. Bạn xử lý thế nào, và team làm gì để ít gặp conflict kiểu này?

    Xem đáp án mẫu
    File lock không sửa tay từng dòng: giải quyết package.json trước (giữ dependency của cả hai bên), lấy bản lock của main làm gốc rồi chạy lại yarn install (hoặc npm install) để công cụ tự sinh phần của nhánh bạn, sau đó commit. Với conflict ở code, đọc cả hai phía để hiểu ý định của từng người thay vì bấm "Accept mine" cho nhanh; chưa chắc thì hỏi người sửa đoạn đó. Gộp xong phải chạy lại app, lint và test trước khi push. Giảm conflict bằng nhánh sống ngắn, PR nhỏ, thường xuyên cập nhật main về nhánh của mình, tách commit nâng thư viện khỏi commit tính năng; nhánh dùng chung thì không git push --force.
