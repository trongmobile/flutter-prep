  1. Vì sao callback của Promise.then luôn chạy trước setTimeout(fn, 0) dù timer được đặt trước? Hiểu biết này liên quan gì tới việc app React Native bị đơ khi xử lý dữ liệu lớn?

    Xem đáp án mẫu
    JS chạy đơn luồng: sau khi đoạn code đồng bộ hiện tại chạy xong, engine xả hết hàng đợi microtask (callback của Promise, queueMicrotask) rồi mới lấy một macrotask tiếp theo (timer, sự kiện I/O). Vì vậy .then luôn chạy trước setTimeout(fn, 0). Trong React Native, logic JS, các callback như onPress và việc tính toán cho render đều chạy trên JS thread, nên một vòng lặp nặng (parse JSON lớn, lọc list hàng chục nghìn phần tử) sẽ chặn nó: nút bấm không phản hồi, animation chạy bằng JS bị giật. Microtask liên tục sinh microtask mới cũng chặn event loop y như vậy; việc nặng nên chia nhỏ, đẩy về server hoặc xuống native.
    console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// In ra: 1, 4, 3, 2

  2. Màn hình Home gọi 3 API song song (banner, danh mục, sản phẩm gợi ý). Chỉ cần API banner lỗi là cả màn hình trắng. Bạn dùng Promise.all hay Promise.allSettled, và vì sao?

    Xem đáp án mẫu
    Promise.all reject ngay khi một promise reject (fail-fast), nên chỉ cần banner lỗi là mất luôn dữ liệu hai API kia dù chúng thành công; nó hợp khi các kết quả phụ thuộc nhau, thiếu một cái là vô nghĩa. Promise.allSettled chờ tất cả xong và trả về mảng { status: 'fulfilled', value } hoặc { status: 'rejected', reason }, nên từng khu vực tự hiển thị dữ liệu hoặc trạng thái lỗi riêng. Cả hai đều chạy các request song song, khác với await lần lượt từng cái làm tổng thời gian cộng dồn. Lưu ý Promise.all reject sớm không huỷ các request còn lại, chúng vẫn chạy tới khi xong.
    const [banner, categories, products] = await Promise.allSettled([
  api.getBanner(),
  api.getCategories(),
  api.getRecommended(),
]);

setBanner(banner.status === 'fulfilled' ? banner.value : null);
setCategories(categories.status === 'fulfilled' ? categories.value : []);
setProductsError(products.status === 'rejected' ? products.reason : null);

  3. Đoạn code upload ảnh dưới đây báo "Xong" ngay lập tức dù ảnh chưa upload, và lỗi upload không bị catch bắt. Vì sao?

    Xem đáp án mẫu
    forEach không biết gì về Promise: nó gọi callback async cho từng phần tử, bỏ qua Promise trả về và kết thúc ngay, nên showToast('Xong') chạy khi các upload mới bắt đầu. Lỗi trong callback trở thành Promise bị reject mà không ai await, nên try/catch bên ngoài không bắt được, chỉ thấy cảnh báo unhandled promise rejection. Muốn chạy lần lượt thì dùng for (const p of photos) { await uploadPhoto(p); }; muốn song song thì await Promise.all(photos.map(uploadPhoto)). Quy tắc chung: try/catch chỉ bắt được lỗi async của Promise được await bên trong khối try.
    async function uploadAll(photos: Photo[]) {
  try {
    photos.forEach(async (p) => {
      await uploadPhoto(p);
    });
    showToast('Xong');
  } catch (e) {
    showToast('Upload lỗi');
  }
}

  1. Màn hình đăng ký listener (AppState, Keyboard, socket…) trong useEffect. Sau vài lần vào ra màn hình, mỗi sự kiện bị xử lý nhiều lần. Nguyên nhân và cách sửa?

    Xem đáp án mẫu
    Mỗi lần component mount, effect đăng ký thêm một listener nhưng listener cũ không được gỡ khi unmount, nên chúng chồng lên nhau và còn giữ tham chiếu tới state cũ (memory leak). Effect cần return một hàm cleanup để huỷ đăng ký: React gọi cleanup khi component unmount và cả trước mỗi lần chạy lại effect do dependency đổi. Các API của React Native như AppState.addEventListener hay Keyboard.addListener trả về một subscription, chỉ cần gọi remove() trong cleanup. Nếu app được bọc trong <StrictMode>, ở development React cố tình chạy mount → cleanup → mount để bạn phát hiện sớm effect thiếu cleanup.
    const [appState, setAppState] = useState(AppState.currentState);

useEffect(() => {
  const sub = AppState.addEventListener('change', setAppState);
  return () => sub.remove(); // gỡ listener khi unmount
}, []);

  2. Đồng hồ đếm ngược dưới đây chỉ giảm từ 60 xuống 59 rồi đứng yên. Vì sao, và sửa thế nào?

    Xem đáp án mẫu
    Đây là stale closure: effect chỉ chạy một lần (deps []) nên callback của setInterval giữ mãi giá trị seconds của lần render đầu tiên là 60, giây nào cũng set lại 59. Cách sửa gọn nhất là functional update setSeconds((s) => s - 1): React luôn truyền vào giá trị mới nhất nên không cần đưa seconds vào deps. Thêm seconds vào deps cũng chạy đúng, nhưng interval bị huỷ rồi tạo lại mỗi giây. Rule react-hooks/exhaustive-deps của ESLint cảnh báo loại lỗi này ngay khi viết, đừng tắt nó cho nhanh.
    const [seconds, setSeconds] = useState(60);

useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds - 1); // seconds luôn là 60
  }, 1000);
  return () => clearInterval(id);
}, []);

  3. Màn hình đăng ký cần: nhấn Next trên bàn phím thì focus sang ô mật khẩu, và giữ id của timer gửi lại OTP để huỷ khi rời màn hình. Vì sao cả hai việc này dùng useRef chứ không dùng useState?

    Xem đáp án mẫu
    useRef trả về một object { current } sống suốt vòng đời component; đổi ref.current không gây re-render và đọc lúc nào cũng ra giá trị mới nhất, không bị stale closure. Vì vậy nó hợp với dữ liệu không hiển thị lên UI như id của timer, cờ đang xử lý, giá trị của lần render trước. Ref cũng dùng để giữ tham chiếu tới native component, ví dụ gọi passwordRef.current?.focus(). Ngược lại, giá trị nào cần hiện trên màn hình phải để trong state, vì đổi ref không cập nhật UI; cũng không nên đọc hay ghi ref.current ngay trong lúc render.
    const passwordRef = useRef<TextInput>(null);
const otpTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

useEffect(() => () => {
  if (otpTimerRef.current) clearTimeout(otpTimerRef.current); // rời màn hình thì huỷ
}, []);

<TextInput
  returnKeyType="next"
  onSubmitEditing={() => passwordRef.current?.focus()}
/>
<TextInput ref={passwordRef} secureTextEntry />

  4. Màn hình có 2.000 sản phẩm, ô lọc theo giá và một nút mở modal sắp xếp. Mỗi lần mở hay đóng modal, app khựng lại vì lọc lại cả danh sách. Bạn dùng useMemo thế nào, và useMemo khác useCallback ra sao?

    Xem đáp án mẫu
    Mở modal làm đổi state nên component render lại, và phép filter viết thẳng trong thân component chạy lại dù dữ liệu lọc không đổi. Bọc phép lọc trong useMemo với deps là products và minPrice: React giữ kết quả cũ và chỉ tính lại khi một dep đổi (so bằng Object.is), nên mở modal không còn phải lọc lại. useMemo nhớ giá trị trả về của hàm, còn useCallback(fn, deps) nhớ chính hàm fn, có ích khi hàm được truyền cho component con bọc React.memo hoặc nằm trong deps của effect. Deps phải khai báo đủ, thiếu minPrice thì danh sách không cập nhật khi đổi bộ lọc; và chỉ nên memo phép tính thật sự tốn kém, vì useMemo cũng có chi phí riêng.
    function ProductScreen({ products }: { products: Product[] }) {
  const [minPrice, setMinPrice] = useState(0);
  const [sortOpen, setSortOpen] = useState(false);

  // Chỉ lọc lại khi products hoặc minPrice đổi, mở/đóng modal không tính lại
  const visible = useMemo(
    () => products.filter((p) => p.price >= minPrice),
    [products, minPrice],
  );

  const openSort = useCallback(() => setSortOpen(true), []);
  return <ProductList items={visible} onOpenSort={openSort} />;
}

  5. Ô tìm kiếm gọi API mỗi lần gõ một ký tự. Hãy viết custom hook useDebounce để chỉ gọi API khi người dùng ngừng gõ 400ms. Hai component cùng dùng hook này có chung state không?

    Xem đáp án mẫu
    Custom hook là hàm có tên bắt đầu bằng use và gọi các hook khác bên trong, dùng để tái sử dụng logic có state. useDebounce giữ một bản sao của giá trị và chỉ cập nhật khi giá trị đứng yên đủ delay; mỗi lần value đổi, cleanup huỷ timer cũ nên chỉ lần gõ cuối được tính. Component dùng debouncedKeyword làm dependency của effect gọi API thay vì keyword. Mỗi lần gọi hook là một bộ state riêng, nên hai component dùng useDebounce không chia sẻ gì với nhau; muốn dùng chung state thì cần Context hoặc store.
    function useDebounce<T>(value: T, delay = 400): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // gõ tiếp thì huỷ timer cũ
  }, [value, delay]);

  return debounced;
}

  6. Màn hình Profile crash với lỗi Rendered more hooks than during the previous render ngay khi người dùng đăng nhập xong. Nhìn đoạn code, nguyên nhân là gì và vì sao React có quy tắc này?

    Xem đáp án mẫu
    React không định danh hook theo tên mà theo thứ tự gọi trong mỗi lần render: hook thứ nhất, thứ hai… được lưu thành danh sách gắn với component. Khi chưa đăng nhập, component return sớm nên chỉ gọi useRef mà không gọi useState; đăng nhập xong thì gọi thêm một hook, số hook giữa hai lần render lệch nhau nên React báo lỗi (trường hợp khác có thể gán nhầm state). Quy tắc là chỉ gọi hook ở cấp cao nhất của function component hoặc custom hook, trước mọi return sớm, không đặt trong if, vòng lặp hay callback. Cách sửa: chuyển useState lên trên if, hoặc tách phần sau đăng nhập thành component con; plugin eslint-plugin-react-hooks bắt lỗi này ngay khi viết.
    function Profile({ user }: { user?: User }) {
  const scrollRef = useRef<ScrollView>(null); // hook trước return sớm: OK
  if (!user) {
    return <LoginPrompt />;
  }
  // SAI: hook nằm sau return sớm
  const [tab, setTab] = useState<'info' | 'orders'>('info');
  return <ProfileTabs user={user} tab={tab} onChange={setTab} />;

const loadMore = async () => {
  if (loadingRef.current || !hasMore) return; // đang tải hoặc đã hết
  loadingRef.current = true;

  2. Màn hình đăng nhập: trên iOS bàn phím che mất nút Đăng nhập, còn sau khi bọc KeyboardAvoidingView thì trên Android nội dung lại bị đẩy lên quá nhiều. Bạn xử lý thế nào?

    Xem đáp án mẫu
    iOS không tự đẩy nội dung khi bàn phím hiện nên cần KeyboardAvoidingView với behavior="padding". Trên Android, template mặc định khai báo android:windowSoftInputMode="adjustResize" nên hệ thống thường đã tự thu nhỏ cửa sổ, thêm behavior nữa dễ bị đẩy hai lần; vì vậy hay viết behavior={Platform.OS === 'ios' ?   3. Component DatePicker cần UI khác hẳn nhau giữa iOS và Android. Khi nào dùng Platform.OS/Platform.select, khi nào tách file .ios.tsx và .android.tsx?

    Xem đáp án mẫu

Khi UI hoặc logic khác nhiều, tách thành DatePicker.ios.tsx và DatePicker.android.tsx, nơi dùng vẫn import DatePicker from './DatePicker'; Metro chọn file theo nền tảng lúc bundle nên code của nền tảng kia không nằm trong bundle.   4. Màn hình lưới sản phẩm tính bề rộng ô từ Dimensions.get('window') đặt ở đầu file. Khi xoay ngang hoặc chạy trên tablet chia đôi màn hình, layout bị sai. Vì sao và sửa thế nào?

    Xem đáp án mẫu
    Dimensions.get chỉ trả về kích thước tại thời điểm gọi; đặt ở cấp module thì giá trị bị chốt từ lúc file được load, xoay máy hay đổi kích thước cửa sổ đều không cập nhật. Trong component nên dùng hook useWindowDimensions(), nó re-render khi kích thước đổi, từ đó tính số cột hoặc bề rộng ô. Nên ưu tiên layout co giãn bằng Flexbox (flex: 1, flexWrap, phần trăm) thay vì tính pixel cứng cho mọi thứ. Bẫy hay gặp: FlatList không cho đổi numColumns khi đang chạy, phải đổi kèm key để list được tạo lại.
    function ProductGrid({ items }: { items: Product[] }) {

  return (
    <FlatList
      key={numColumns} // đổi số cột thì phải tạo lại list
      numColumns={numColumns}
      data={items}
      keyExtractor={(p) => p.id}
      renderItem={({ item }) => <ProductCard product={item} width={width / numColumns} />}
    />
  );
}

  1. Thông tin user đăng nhập đang được truyền qua props qua 4–5 tầng component chỉ để tới một nút ở sâu bên dưới. Khi nào lifting state và truyền props là đủ, khi nào nên chuyển sang Context, và Context có bẫy gì cần biết?

    Xem đáp án mẫu
    Với state chỉ vài component gần nhau cần, cứ lifting state lên cha chung gần nhất và truyền props: đơn giản, luồng dữ liệu rõ ràng. Khi dữ liệu phải đi xuyên nhiều tầng mà các tầng giữa không dùng tới (prop drilling), Context cho phép component ở sâu đọc thẳng bằng useContext; nó hợp cho dữ liệu ít đổi mà nhiều nơi cần như user, theme, ngôn ngữ. Bẫy cần biết: khi value của Provider đổi tham chiếu, mọi component dùng Context đó đều re-render, và viết value={{ user, logout }} inline tạo object mới mỗi lần Provider render; nên bọc value bằng useMemo và tách Context theo mức độ thay đổi. Component dùng Context mà không có Provider phía trên sẽ nhận giá trị mặc định truyền cho createContext, nên thường viết hook useAuth kiểm tra và báo lỗi rõ ràng.

  2. Marketing muốn gửi link myshop://product/42 để mở thẳng màn hình chi tiết sản phẩm. Bạn cấu hình deep link với React Navigation thế nào, và có bẫy gì khi người dùng bấm back từ màn hình đó?

    Xem đáp án mẫu
    Có hai phần. Phía native phải đăng ký scheme: Android thêm intent-filter có <data android:scheme="myshop" /> cho MainActivity, iOS thêm URL type trong Info.plist và chuyển URL cho RCTLinkingManager trong AppDelegate; với Expo chỉ cần khai báo scheme trong app.json. Phía JS, truyền prop linking cho NavigationContainer gồm prefixes và config.screens ánh xạ path tới màn hình; :id trở thành route.params.id và luôn là string. Bẫy hay gặp: mở từ link thì stack chỉ có mỗi màn chi tiết, bấm back là thoát app; khai báo initialRouteName trong config để màn Home nằm bên dưới. Test nhanh bằng npx uri-scheme open myshop://product/42 --android (hoặc --ios) trước khi giao link cho marketing.
    const linking = {
  prefixes: ['myshop://'],
  config: {
    initialRouteName: 'Home' as const, // back từ link vẫn về Home
    screens: {
      Home: '',
      ProductDetail: 'product/:id', // route.params.id === '42'
    },
  },
};

<NavigationContainer linking={linking}>
  <RootStack />
</NavigationContainer>

  3. Người dùng rời tab Giỏ hàng sang tab khác thêm sản phẩm rồi quay lại, nhưng Giỏ hàng vẫn hiện dữ liệu cũ dù đã gọi API trong useEffect. Vì sao, và dùng useFocusEffect thế nào cho đúng?

    Xem đáp án mẫu
    Trong React Navigation, chuyển tab hay push màn hình mới đè lên không unmount màn hình cũ, nên useEffect(..., []) chỉ chạy một lần lúc mount và không chạy lại khi quay về. useFocusEffect chạy callback mỗi khi màn hình được focus và chạy cleanup khi mất focus, hợp để làm mới dữ liệu hoặc bật/tắt listener chỉ khi màn hình đang hiển thị. Callback phải bọc trong useCallback, nếu không nó là hàm mới sau mỗi render và effect sẽ chạy lại sau mỗi lần render. Nếu chỉ cần biết màn hình có đang focus để render khác đi thì dùng useIsFocused.
    useFocusEffect(
  useCallback(() => {
    let active = true;
    fetchCart().then((data) => {
      if (active) setCart(data);
    });
    return () => {
      active = false; // mất focus thì bỏ qua kết quả về muộn
    };
  }, []),
);

Native & New Architecture

Mọi rank →

  1. Dự án vừa nâng lên bản React Native chạy New Architecture mặc định. Giải thích ngắn gọn New Architecture khác kiến trúc cũ (bridge) ở đâu, và khi thêm một thư viện native mới bạn cần kiểm tra gì?

    Xem đáp án mẫu
    Với bridge, JS và native là hai thế giới tách biệt: mỗi lời gọi được serialize thành JSON, gom theo batch và gửi bất đồng bộ qua lại, nên tốn chi phí chuyển đổi, không gọi đồng bộ được và dễ nghẽn khi dữ liệu dồn dập như sự kiện cuộn hay animation. JSI (JavaScript Interface) là lớp C++ cho phép JS giữ tham chiếu tới object C++/native và gọi method trực tiếp, kể cả đồng bộ, không cần serialize JSON. Trên nền JSI có TurboModules (native module khởi tạo khi cần, gọi trực tiếp) và Fabric (renderer mới). New Architecture được bật mặc định từ React Native 0.76, nên khi chọn thư viện native cần xem README hoặc React Native Directory để biết nó đã hỗ trợ New Architecture chưa, thư viện còn được bảo trì không, rồi test kỹ trên cả hai nền tảng; nhiều thư viện cũ vẫn chạy nhờ lớp tương thích (interop layer) nhưng không phải trường hợp nào cũng ổn.

  2. README cũ của một thư viện native (ví dụ react-native-keychain) vẫn hướng dẫn chạy react-native link và sửa tay MainApplication, Podfile. Với React Native hiện tại, autolinking làm thay bạn những gì, và bạn vẫn phải tự làm bước nào?

    Xem đáp án mẫu
    Autolinking (có từ 0.60) tự tìm các dependency có code native khai báo trong package.json: trên Android, Gradle sinh danh sách package và tự đăng ký, trên iOS Podfile của template gọi use_native_modules! để thêm pod; vì vậy không cần react-native link (lệnh này đã bị bỏ) hay sửa tay MainApplication. Bạn vẫn phải build lại binary vì reload hay Fast Refresh chỉ nạp lại JS bundle: iOS chạy pod install trong thư mục ios rồi build, Android build lại. Các bước cấu hình riêng của thư viện như khai báo quyền, key trong Info.plist vẫn phải làm theo README; muốn loại một thư viện khỏi autolinking trên một nền tảng thì cấu hình trong react-native.config.js. Với Expo, thư viện native không có sẵn trong Expo Go thì cần development build.

Networking & Storage

Mọi rank →

  1. Màn hình chi tiết sản phẩm gọi API theo id trong useEffect. Bạn tổ chức trạng thái loading/error thế nào, và cần xử lý gì khi người dùng thoát màn hình hoặc đổi id trước khi request xong?

    Xem đáp án mẫu
    fetch chỉ reject khi không có response (mất mạng, lỗi DNS, request bị huỷ); 4xx/5xx vẫn resolve bình thường, nên phải tự kiểm tra res.ok hoặc res.status rồi ném lỗi. Màn hình nên có đủ ba trạng thái loading, error, data để UI không quay loading mãi khi API lỗi. Khi unmount hoặc id đổi, cleanup gọi abort() của AbortController để huỷ request cũ, tránh race condition: kết quả của id cũ về sau đè lên id mới. Request bị abort cũng reject, nên kiểm tra signal.aborted để không set state hay hiện lỗi cho trường hợp này.
    useEffect(() => {
  const controller = new AbortController();
  setLoading(true);
  setError(null);
  fetch(`${API_URL}/products/${id}`, { signal: controller.signal })
    .then((res) => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`); // 4xx/5xx không tự reject
      return res.json();
    })
    .then(setProduct)
    .catch((e) => !controller.signal.aborted && setError(e))
    .finally(() => !controller.signal.aborted && setLoading(false));
  return () => controller.abort(); // rời màn hình hoặc đổi id
}, [id]);

  2. Team định dùng AsyncStorage để lưu danh sách vài nghìn sản phẩm cho chế độ offline cùng với cài đặt người dùng. Bạn góp ý gì?

    Xem đáp án mẫu
    AsyncStorage là key-value bất đồng bộ, chỉ lưu chuỗi (object phải JSON.stringify/JSON.parse), không mã hoá, không có truy vấn hay index. Nó hợp với dữ liệu nhỏ như cài đặt, cờ đã xem onboarding. Lưu cả nghìn sản phẩm trong một key nghĩa là mỗi lần đọc/ghi phải parse lại cả khối trên JS thread, và implementation mặc định trên Android còn giới hạn tổng dung lượng database. Dữ liệu lớn hoặc cần truy vấn nên dùng SQLite (expo-sqlite, op-sqlite) hoặc WatermelonDB; key-value cần đọc nhanh có thể dùng MMKV. Vì không mã hoá, AsyncStorage cũng không dành cho dữ liệu nhạy cảm.

Expo, Build & Release

Mọi rank →

  1. Bạn debug một lỗi logic JS và một màn hình re-render quá nhiều thế nào? Vì sao các hướng dẫn cũ dùng Flipper hay "Debug JS Remotely" trên Chrome không còn phù hợp?

    Xem đáp án mẫu
    Với React Native hiện tại chạy Hermes, công cụ chính là React Native DevTools: mở từ Dev Menu hoặc nhấn j trong terminal đang chạy Metro, có Console, Sources để đặt breakpoint, cùng tab Components và Profiler của React DevTools để xem props/state và đo component nào render lại, mất bao lâu. Flipper đã bị bỏ khỏi template mặc định, còn Remote JS Debugging chạy JS trên V8 của Chrome thay vì trên thiết bị nên hành vi có thể khác thật (khác engine, gọi native đồng bộ không chạy) và đã bị deprecated. Lỗi phía native thì đọc Logcat trong Android Studio hoặc console của Xcode; lỗi network có thể log ở tầng API client hoặc dùng proxy như Proxyman, Charles.

  2. App cần trỏ tới API khác nhau cho dev, staging và production. Bạn cấu hình biến môi trường thế nào, và vì sao không được để secret trong .env của app?

    Xem đáp án mẫu
    Với Expo, đặt biến có tiền tố EXPO_PUBLIC_ trong các file như .env.development, .env.production (hoặc trong cấu hình môi trường của EAS) rồi đọc bằng process.env.EXPO_PUBLIC_API_URL; phải viết đầy đủ như vậy, destructure từ process.env sẽ không được thay thế. Với bare React Native thường dùng react-native-config để biến dùng được cả trong JS lẫn native (Gradle, Info.plist), kết hợp build flavor trên Android và scheme trên iOS. Các giá trị này được nhúng vào bundle hoặc binary lúc build, nên bản app đã phát hành chỉ nhận giá trị mới khi build lại (hoặc publish update), khi dev đôi khi phải khởi động lại Metro với --reset-cache, và ai giải nén app cũng đọc được. Vì vậy .env của app chỉ chứa cấu hình công khai như URL, feature flag; secret phải nằm ở backend.

    jest.mock('../api'); // automock: mọi hàm của module api thành jest.fn()

  expect(await screen.findByText('Sai mật khẩu')).toBeTruthy();

});

Security

Mọi rank →

  1. Sau khi đăng nhập, bạn lưu access token và refresh token ở đâu? Đồng nghiệp bảo "AsyncStorage nằm trong sandbox của app nên an toàn", bạn trả lời thế nào?

    Xem đáp án mẫu
    Sandbox chỉ ngăn app khác đọc dữ liệu trên máy bình thường; AsyncStorage vẫn lưu plain text, nên trên máy đã root/jailbreak hoặc qua bản backup, token bị đọc trực tiếp. Token nên lưu bằng thư viện dùng storage bảo mật của hệ điều hành như react-native-keychain hoặc expo-secure-store: Keychain trên iOS, còn trên Android dữ liệu được mã hoá bằng khoá nằm trong Android Keystore. Chỉ lưu những gì thật cần (thường là refresh token, access token có thể chỉ giữ trong bộ nhớ) và xoá sạch khi logout. Lưu ý trên iOS mục Keychain có thể còn lại sau khi gỡ app, nên lần mở đầu tiên sau khi cài lại nên xoá token cũ.
