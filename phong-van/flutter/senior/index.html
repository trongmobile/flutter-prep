  1. Vì sao Flutter có hot reload ở debug mà bản release thì không, và vì sao app Flutter không dùng được reflection (dart:mirrors) mà phải dùng sinh code? Dart chạy ở chế độ JIT và AOT khác nhau thế nào, và hệ quả với kích thước, startup và bảo mật ra sao?

    Xem đáp án mẫu
    Debug chạy Dart VM ở chế độ JIT: code được nạp dưới dạng kernel (biểu diễn trung gian), biên dịch khi chạy và có thể thay thế ngay khi app đang chạy, đó chính là cơ chế của hot reload (đẩy kernel mới vào isolate và giữ nguyên state). Release biên dịch AOT ra mã máy ngay lúc build; trên iOS bắt buộc phải AOT vì hệ điều hành không cho cấp phát bộ nhớ vừa ghi vừa thực thi, còn Android dùng AOT cho bản release để khởi động nhanh và hiệu năng ổn định, không có giai đoạn 'khởi động nguội' của JIT. Vì AOT biên dịch trước và phải biết toàn bộ chương trình để tối ưu, trình biên dịch dùng tree shaking toàn cục (phân tích luồng kiểu) để loại bỏ code và class không thể được gọi tới: nhờ đó binary nhỏ hơn, nhưng cũng nghĩa là truy cập động theo tên (reflection) không thể hoạt động vì code đó có thể đã bị loại, nên dart:mirrors không được hỗ trợ trong Flutter và các thư viện phải dùng sinh code (json_serializable, freezed, build_runner). Hệ quả khác: hàm được gọi từ native hay tra cứu theo tên cần @pragma('vm:entry-point') để không bị loại (như callback chạy nền của plugin); không thể tải và chạy code Dart mới sau khi build nên code push phải dùng cơ chế riêng; --obfuscate chỉ đổi tên symbol trong snapshot chứ không mã hoá chuỗi hay asset; và chỉ profile mode (AOT kèm công cụ đo) phản ánh hiệu năng thật, còn debug cố tình chậm hơn hẳn nên không dùng để kết luận về jank. Flutter web biên dịch sang JavaScript hoặc Wasm và có chi phí, khác biệt riêng.

  2. Đoạn code List<num> nums = <int>[1, 2]; nums.add(1.5); compile được nhưng crash lúc chạy với TypeError. Vì sao generic của Dart là covariant, từ khoá covariant giải quyết gì, và gặp lỗi tương tự trong code Flutter thế nào?

    Xem đáp án mẫu
    Generic trong Dart là covariant theo thiết kế: List<int> được coi là kiểu con của List<num>, nên gán được mà analyzer không báo. Cách này tiện (truyền List<Text> vào chỗ cần List<Widget>) nhưng không an toàn kiểu ở thời điểm compile: khi add(1.5) vào một list thực chất là List<int>, Dart phải kiểm tra lúc chạy và ném TypeError ('type double is not a subtype of type int'). Vì vậy Dart chèn kiểm tra runtime ở mọi chỗ ghi qua một giao diện covariant; chỉ đọc (Iterable<T>) thì luôn an toàn. Gặp trong Flutter: final items = [Text('a'), Text('b')]; được suy ra là List<Text>, đưa vào Column(children: items) vẫn compile, nhưng nếu về sau items.add(const Icon(Icons.add)) thì lỗi lúc chạy; cách tránh là khai báo kiểu tường minh <Widget>[...]. Tương tự, Map<String, dynamic> khác Map<String, Object?> khi parse JSON, và nên dùng List<T>.from/List<T>.of để tạo bản sao có kiểu đúng thay vì ép kiểu. Từ khoá covariant ở tham số cho phép lớp con thu hẹp kiểu tham số của method khi override (void accept(covariant Dog d)), điều vốn bị cấm, đổi lại việc kiểm tra dời sang runtime nên chỉ dùng khi thật cần (framework dùng nó ở những chỗ như RenderObject.setupParentData(covariant RenderObject child)). Khi thiết kế API, ưu tiên trả Iterable<T> hoặc list bất biến (List.unmodifiable) để chủ động tránh việc ghi vào list sai kiểu.

}

  1. Thiết kế một worker isolate sống lâu để xử lý tác vụ nặng liên tục (mã hoá file, xử lý ảnh). Bạn lưu ý gì về giao tiếp và truyền dữ liệu lớn?

    Xem đáp án mẫu
    Với tác vụ lẻ tẻ thì Isolate.run là đủ, nhưng khi xử lý liên tục thì spawn mỗi lần vừa tốn chi phí vừa mất state đã khởi tạo, nên tôi spawn một worker bằng Isolate.spawn, bắt tay để trao đổi SendPort hai chiều, gắn mỗi request một id ánh xạ tới Completer, có timeout, theo dõi lỗi/thoát qua onError/onExit và kill khi không còn dùng. Message giữa các isolate mặc định bị copy, nên với buffer vài chục MB tôi dùng TransferableTypedData: chỉ tốn một lần copy lúc tạo, gửi qua port trong thời gian hằng số, và bên nhận chỉ được materialize() đúng một lần; kết quả cuối của một isolate sắp kết thúc có thể trả bằng Isolate.exit để VM chuyển giao object mà không phải copy. Isolate tạo bằng Isolate.spawn cùng isolate group với isolate gốc nên spawn nhanh và gửi được cả closure, khác với Isolate.spawnUri. Nếu worker cần gọi plugin thì phải truyền RootIsolateToken và gọi BackgroundIsolateBinaryMessenger.ensureInitialized, đồng thời nhớ rằng isolate nền không nhận được message do phía native chủ động gửi.
    void _worker(SendPort toMain) {
  final inbox = ReceivePort();
  toMain.send(inbox.sendPort); // bắt tay: trả SendPort cho main
  inbox.listen((msg) {
    final (int id, TransferableTypedData data, SendPort reply) =
        msg as (int, TransferableTypedData, SendPort);
    final bytes = data.materialize().asUint8List(); // không copy lại
    reply.send((id, bytes.length)); // thay bằng xử lý thật
  });
}

Mọi rank →

  1. Khi nào bạn viết một RenderBox tùy biến thay vì dùng CustomPaint hay CustomMultiChildLayout? Mô tả các bước chính khi implement.

    Xem đáp án mẫu
    Tôi chỉ xuống tầng RenderBox khi widget có sẵn không diễn đạt được layout cần thiết: size của cha phụ thuộc vào con theo cách đặc biệt (ví dụ bong bóng chat co theo dòng cuối của text để nhét giờ gửi), hit-test tùy biến, hoặc muốn xử lý thay đổi ngay ở tầng render để tránh rebuild. CustomPaint chỉ vẽ, còn CustomMultiChildLayout không cho size của chính nó phụ thuộc vào size của con, nên khi cần cả hai thì mới đáng viết RenderBox. Các bước: tạo LeafRenderObjectWidget/SingleChildRenderObjectWidget với createRenderObject và updateRenderObject; trong RenderBox override performLayout (layout con với constraints phù hợp, truyền parentUsesSize: true nếu đọc size con, set size qua constraints.constrain), paint, hitTestChildren/hitTestSelf, cùng computeDryLayout và các hàm intrinsic nếu widget có thể nằm trong IntrinsicHeight hoặc bị cha gọi getDryLayout. Chỗ hay bug nhất là setter: phải so sánh giá trị cũ rồi gọi đúng markNeedsLayout hoặc markNeedsPaint, và updateRenderObject phải truyền đủ mọi property.
    class RenderDot extends RenderBox {
  RenderDot(this._radius);
  double _radius;
  set radius(double value) {
    if (value == _radius) return;
    _radius = value;
    markNeedsLayout(); // size đổi; layout xong sẽ tự markNeedsPaint
  }
  @override
  Size computeDryLayout(BoxConstraints constraints) =>
      constraints.constrain(Size.square(_radius * 2));
  @override
  void performLayout() => size = computeDryLayout(constraints);
}

  2. Relayout boundary là gì? Khi nào một RenderObject tự trở thành relayout boundary, và nó liên quan gì đến markNeedsLayout?

    Xem đáp án mẫu
    Khi một RenderObject gọi markNeedsLayout, nếu nó không phải boundary thì framework đánh dấu tiếp lên cha, cho tới relayout boundary gần nhất, rồi chỉ layout lại từ điểm đó — nên boundary quyết định phạm vi của một lần relayout. Một node là relayout boundary khi cha không dùng size của nó (parentUsesSize: false), khi nó sizedByParent, khi constraints nhận được là tight, hoặc khi nó là root, vì trong các trường hợp đó size của nó thay đổi cũng không bắt cha phải tính lại. Khác với RepaintBoundary là widget bạn chủ động đặt để tách layer, relayout boundary do framework tự suy ra trong layout(); muốn tận dụng thì cho subtree hay thay đổi nhận tight constraints, ví dụ bọc trong SizedBox kích thước cố định. Còn markNeedsPaint chỉ đi lên tới repaint boundary gần nhất và không kéo theo layout, nên property chỉ ảnh hưởng hình vẽ thì đừng gọi markNeedsLayout.

  3. Danh sách 5.000 item bằng ListView.builder cuộn nhanh thì giật, thanh cuộn nhảy khi kéo, jumpTo không tới đúng chỗ, và state trong item bị lẫn khi danh sách đổi thứ tự. Cơ chế dựng lazy của ListView.builder hoạt động thế nào, và itemExtent, prototypeItem, findChildIndexCallback, cacheExtent giải quyết gì?

    Xem đáp án mẫu
    ListView.builder tạo một SliverList với SliverChildBuilderDelegate: sliver chỉ gọi itemBuilder cho các item nằm trong vùng nhìn cộng cacheExtent (mặc định 250 logical pixel mỗi phía), và các Element ngoài vùng đó bị dispose (trừ khi được keep-alive). Vì không biết chiều cao của các item chưa dựng, sliver phải ước lượng tổng chiều dài từ những item đã đo, nên thanh cuộn nhảy và jumpTo/animateTo tới vị trí xa không chính xác khi item có chiều cao khác nhau. Nếu mọi item cao bằng nhau, itemExtent (hoặc prototypeItem khi bạn có một item mẫu) cho sliver biết chiều cao cố định nên nó bỏ qua việc đo từng con, tính vị trí O(1), cuộn nhanh và chính xác hơn; item cao khác nhau thì không dùng được. findChildIndexCallback cho delegate biết 'key này giờ ở index nào' để khi danh sách đổi thứ tự hay chèn item, Flutter tái sử dụng đúng Element và State thay vì dựng lại (mỗi item cần một key ổn định, và tra cứu nên là O(1) bằng một Map). addAutomaticKeepAlives và addRepaintBoundaries (mặc định đều là true) thêm lớp bọc cho từng item: tắt addRepaintBoundaries khi item rất rẻ có thể giảm chi phí, còn item nặng thì nên giữ. Tăng cacheExtent thì dựng trước nhiều hơn nên cuộn nhanh ít bị trắng, đổi lại tốn bộ nhớ và CPU. Item nặng cần được tối ưu từ gốc: dùng const, tách widget, tránh Opacity hay clip lớn, và giải mã ảnh đúng kích thước; hãy đo bằng DevTools (build hay raster chậm) chứ không đoán.

  1. Pub workspaces (Dart 3.6+) giải quyết vấn đề gì trong một monorepo Flutter, và nó kết hợp với Melos ra sao?

    Xem đáp án mẫu
    Trước đây mỗi package trong monorepo có pubspec.lock riêng, nên cùng một dependency có thể resolve ra version khác nhau giữa các package, pub get phải chạy cho từng package và analyzer phải giữ nhiều context. Với pub workspaces, pubspec.yaml gốc khai báo danh sách workspace: và mỗi package con khai báo resolution: workspace: cả repo dùng chung một lần resolve, một lockfile và một package_config.json, nên mọi package chắc chắn dùng cùng version và IDE nhẹ hơn. Trade-off là không còn cho phép hai package cần hai version không tương thích của cùng một dependency — phải nâng cấp đồng loạt, điều thực ra lành mạnh cho một app monorepo. Workspaces chỉ lo phần resolve dependency; Melos vẫn hữu ích cho script chạy theo từng package, lọc package bị ảnh hưởng bởi thay đổi, versioning và changelog khi publish, và các bản Melos mới đã được xây trên nền pub workspaces.

    Xem đáp án mẫu

Sau đó áp dụng kiểu strangler: hai hệ thống sống song song trong một thời gian dài, feature mới viết bằng stack mới, feature cũ chỉ chuyển khi đằng nào cũng phải sửa lớn. Điều kiện để chạy song song an toàn: tách logic nghiệp vụ và dữ liệu ra khỏi lớp state (repository hay service thuần Dart, không phụ thuộc Provider hay Riverpod) để hai stack dùng chung một nguồn dữ liệu; nếu mỗi bên tự giữ bản sao thì sinh ra hai nguồn sự thật, nguyên nhân bug khó nhất của các cuộc migration.     Platform view buộc engine ghép một native view với nội dung Flutter, và cái giá tùy chế độ: với hybrid composition (iOS, và Android khi dùng initExpensiveAndroidView), Flutter UI được compose trên platform thread thay vì raster thread riêng nên phải tranh tài nguyên với OS và plugin, dễ tụt FPS; trên Android 9 trở xuống chế độ này còn copy frame qua lại giữa bộ nhớ GPU và bộ nhớ chính. Chế độ mặc định của AndroidView (Texture Layer Hybrid Composition, fallback Virtual Display) nhẹ hơn cho Flutter nhưng có hạn chế riêng như scroll nhanh trong WebView có thể giật, SurfaceView bị chuyển sang virtual display, accessibility và text input kém hơn. Thực tế tôi giới hạn số platform view cùng lúc (không đặt map trong từng item của list), dùng ảnh tĩnh làm placeholder và chỉ tạo view thật khi user tương tác, tránh animate hay transform platform view, và luôn đo trên máy Android tầm thấp ở profile mode.

  2. Khi tích hợp thư viện native qua FFI, bạn xử lý threading và callback thế nào để không làm treo UI? ffigen/jnigen đóng vai trò gì?

    Xem đáp án mẫu
    Lời gọi FFI là đồng bộ và chạy ngay trên thread của isolate gọi nó, nên một hàm C chạy 200ms gọi từ root isolate sẽ chặn UI 200ms; việc nặng phải chạy ở isolate khác (Isolate.run) hoặc để native tự chạy trên thread riêng rồi báo kết quả về. Với callback từ native: Pointer.fromFunction và NativeCallable.isolateLocal chỉ được gọi trên đúng thread của isolate (gọi từ thread khác sẽ abort process), còn NativeCallable.listener gọi được từ mọi thread nhưng chạy bất đồng bộ trên event loop, chỉ hỗ trợ hàm trả void, và phải close() khi xong nếu không isolate bị giữ sống mãi. ffigen sinh binding Dart từ header C/Objective-C, jnigen sinh binding gọi Java/Kotlin qua JNI, giúp bỏ phần glue code viết tay dễ sai kiểu và dễ lệch khi thư viện nâng version. Tôi vẫn bọc binding sinh ra sau một API Dart nhỏ, quản lý memory native bằng Arena hoặc NativeFinalizer, để phần còn lại của app không phụ thuộc trực tiếp vào FFI.

  3. Bạn viết một plugin nội bộ (ví dụ đọc thẻ NFC) dùng cho nhiều app, hỗ trợ Android, iOS và sau này cả web. Kiến trúc federated plugin gồm những package nào, PlatformInterface làm gì, và nó giúp ích gì so với một plugin đơn lẻ?

    Xem đáp án mẫu
    Federated plugin tách một plugin thành nhiều package: package app-facing (API Dart mà app gọi), package *_platform_interface (lớp trừu tượng định nghĩa hợp đồng, kế thừa PlatformInterface, kèm implementation mặc định dùng MethodChannel), và mỗi nền tảng một package implementation (*_android, *_ios, *_web), mỗi cái đăng ký bản của mình lúc khởi động (registerWith hoặc dartPluginClass). Trong pubspec.yaml của package app-facing, mục flutter: plugin: platforms: ghi default_package cho từng nền tảng (endorsed), còn package implementation khai báo implements: cho nền tảng của nó. PlatformInterface có token verify để chặn việc cài đặt bằng implements (chỉ cho extends hoặc mixin), nhờ đó thêm method mới vào interface không phá các implementation bên thứ ba vì luôn có bản mặc định. Lợi ích: nhóm khác thêm được nền tảng (Windows, web) mà không cần quyền sửa package gốc; test code app bằng cách đặt Plugin.instance = FakePlatform() mà không cần native; mỗi nền tảng phát hành và đặt version độc lập; ranh giới hợp đồng rõ ràng, và có thể sinh code kênh bằng Pigeon. Chi phí: nhiều package hơn phải quản lý version và publish (nên dùng monorepo với Melos hoặc pub workspaces), cần bài test hợp đồng chung cho mọi implementation, và breaking change ở interface là breaking cho cả hệ sinh thái nên phải theo semver chặt. Nếu plugin chỉ dùng nội bộ cho hai nền tảng và một team duy nhất thì plugin đơn (một package có android/ và ios/) là đủ; federated chỉ đáng khi có nhu cầu mở rộng nền tảng hoặc nhiều bên cùng đóng góp. Với thư viện C hoặc C++ có sẵn, plugin FFI (ffiPlugin: true) là một lựa chọn khác.
    // nfc_reader_platform_interface
abstract class NfcReaderPlatform extends PlatformInterface {
  NfcReaderPlatform() : super(token: _token);
  static final Object _token = Object();

  static NfcReaderPlatform _instance = MethodChannelNfcReader();
  static NfcReaderPlatform get instance => _instance;
  static set instance(NfcReaderPlatform value) {
    PlatformInterface.verify(value, _token); // chặn cài đặt bằng `implements`, chỉ cho extends
    _instance = value;
  }

  Stream<String> tags() => throw UnimplementedError('tags() chưa được hỗ trợ trên nền tảng này');
}

// nfc_reader (app-facing): app chỉ gọi API này
class NfcReader {
  Stream<String> get tags => NfcReaderPlatform.instance.tags();
}

  4. Crashlytics báo crash của bản release đã obfuscate chỉ toàn địa chỉ và tên bị đổi (a.b.c), và có crash native trong libflutter.so không có tên hàm. Quy trình symbolicate stack trace của Dart và của engine native là gì, và vì sao hay bị thiếu symbol?

    Xem đáp án mẫu
    Khi build --obfuscate --split-debug-info=<dir>, tên class và hàm trong snapshot bị đổi và thông tin debug được tách ra các file symbol (app.android-arm64.symbols...) nằm trong thư mục bạn chỉ định; stack trace Dart ở production vì vậy chỉ còn địa chỉ và tên bị xáo trộn. Để đọc lại, cần đúng file symbol của chính bản build đó: dùng flutter symbolize -i stack.txt -d <thư mục symbols> để dịch thủ công, hoặc upload symbol lên Crashlytics (firebase crashlytics:symbols:upload --app=<appId> <thư mục>) để stack được dịch ngay trên dashboard. Việc khớp symbol với crash dựa vào build id, nên build lại cùng source ở máy khác, hoặc cùng version nhưng build lại thì symbol cũ không dùng được: vì vậy pipeline CI phải lưu thư mục symbols của từng bản phát hành (artifact, kèm version và build number) và upload ngay khi build. Crash native của engine (libflutter.so trên Android, Flutter.framework trên iOS) là một lớp riêng: stack ở đó là địa chỉ trong thư viện native, cần symbol của đúng phiên bản engine (nên khoá phiên bản Flutter bằng FVM để biết chính xác engine nào), với Android dùng ndk-stack hoặc addr2line cùng file .so có symbol, còn iOS cần dSYM của app và của framework, upload lên Crashlytics trong bước archive. Các nguyên nhân thường thiếu symbol: quên upload cho một bản, build lại cho cùng version, bật --split-debug-info mà không giữ thư mục, hoặc plugin native không kèm dSYM. Hãy kiểm chứng bằng một crash thử trên bản staging đã obfuscate trước khi phát hành, và đặt kiểm tra trong CI rằng symbol đã được upload cho mọi bản release.
    # Build: tách symbol ra thư mục riêng, bắt buộc lưu lại theo từng bản phát hành
flutter build appbundle --release --obfuscate --split-debug-info=build/symbols/1.4.0+27

# Dịch thủ công một stack trace đã obfuscate
flutter symbolize -i crash_stack.txt -d build/symbols/1.4.0+27

# Upload symbol lên Crashlytics (nên làm tự động trong CI ngay sau khi build)
firebase crashlytics:symbols:upload --app=1:1234567890:android:abc123 build/symbols/1.4.0+27

  5. Pigeon giải quyết vấn đề gì so với viết MethodChannel thủ công?

    Xem đáp án mẫu
    Sinh code type-safe tự động cho cả Dart và Native (Kotlin/Swift) từ một file định nghĩa chung, tránh lỗi type mismatch và tránh tự parse Map/String thủ công dễ typo.

  6. Workflow cơ bản khi dùng Pigeon là gì?

    Xem đáp án mẫu
    Định nghĩa API trong một file Dart đặc biệt → chạy generator → sinh code Dart và code native tương ứng → implement phần logic native trong code sinh ra đó.

  7. Pigeon có hỗ trợ Native gọi ngược lại Dart không?

    Xem đáp án mẫu
    Có, hỗ trợ cả HostApi (Dart gọi Native) và FlutterApi (Native gọi ngược lại Dart).

  8. Khi nào KHÔNG nên dùng Pigeon mà nên dùng MethodChannel thủ công?

    Xem đáp án mẫu
    Khi cần logic encode/decode phức tạp tuỳ biến, hoặc project chỉ có một, hai method đơn giản không đáng để thêm bước generate code.

  9. FFI trong Dart dùng để làm gì?

    Xem đáp án mẫu
    Cho phép Dart gọi trực tiếp function viết bằng C mà không cần đi qua Platform Channel hay native host code trung gian.

  10. Vì sao FFI thường nhanh hơn Platform Channel?

    Xem đáp án mẫu
    Vì gọi trực tiếp vào native function giống gọi hàm C bình thường, không tốn chi phí serialize/deserialize qua message codec và không cần chuyển qua platform thread.

  11. FFI có gọi được code Swift/Kotlin thuần trực tiếp không?

    Xem đáp án mẫu
    Không trực tiếp — FFI chỉ giao tiếp qua C ABI, nên Swift/Kotlin cần expose thêm một lớp tương thích C, ví dụ qua @_cdecl trong Swift, để Dart FFI gọi vào được.

  12. Trường hợp thực tế nào nên ưu tiên FFI thay vì Platform Channel?

    Xem đáp án mẫu
    Khi cần hiệu năng cực cao và gọi liên tục, ví dụ xử lý ảnh hoặc audio real-time, tái sử dụng thư viện C/C++ có sẵn mà overhead của Channel gây bottleneck rõ rệt.

  13. Quản lý memory khi dùng FFI cần lưu ý gì?

    Xem đáp án mẫu
    Phải tự cấp phát và giải phóng memory native thủ công vì garbage collector của Dart không quản lý memory phía native, dễ gây leak nếu quên free.

  14. FlutterActivity và FlutterFragment khi nào nên dùng loại nào?

    Xem đáp án mẫu
    FlutterActivity dùng khi toàn màn hình là Flutter; FlutterFragment dùng trong add-to-app khi cần nhúng Flutter vào một phần của Activity Android đã tồn tại, cùng màn hình có cả View Android lẫn Flutter.

  15. Vì sao nên cache hoặc pre-warm FlutterEngine trong app hybrid?

    Xem đáp án mẫu
    Khởi tạo FlutterEngine tốn thời gian do phải load Dart VM; pre-warm sẵn một engine từ lúc app khởi động giúp lần mở màn hình Flutter đầu tiên không bị delay hay giật.

  16. Trong mô hình add-to-app, nhiều FlutterEngine cùng lúc có vấn đề gì?

    Xem đáp án mẫu
    Các engine trong cùng process dùng chung một Dart VM, nhưng mỗi engine có root isolate và pipeline render riêng nên tốn thêm memory và thời gian khởi tạo; các isolate cũng không chia sẻ state với nhau. Thường dùng FlutterEngineGroup để tạo các engine chia sẻ tài nguyên nội bộ (như code snapshot), giảm đáng kể chi phí cho mỗi engine thêm vào.

  17. Plugin native Android thường implement interface nào để nhận lifecycle Activity?

    Xem đáp án mẫu

  21. Kết quả MethodChannel cần được trả về trên thread nào ở cả hai nền tảng?

  22. Review: cần gọi một SDK native phức tạp có nhiều callback bất đồng bộ, chọn Pigeon hay FFI?

    Xem đáp án mẫu

  23. So sánh chi phí hiệu năng: MethodChannel vs FFI vs gọi trực tiếp package Dart thuần?

    Xem đáp án mẫu
    Dart thuần nhanh nhất vì cùng một isolate không overhead; FFI gần bằng gọi native trực tiếp qua C ABI; MethodChannel chậm nhất vì phải serialize qua message codec và platform thread.

  24. Vì sao một số plugin cần implement cả ActivityAware lẫn xử lý riêng cho add-to-app?

    Xem đáp án mẫu

    Xem đáp án mẫu

  3. App cold start mất khoảng 3 giây trên máy Android tầm trung. Bạn đo và tối ưu startup time thế nào?

    Xem đáp án mẫu

Cuối cùng đặt ngân sách startup và theo dõi theo từng release để không bị thoái lui âm thầm.

  4. Bạn cần biết app của người dùng thật có bị giật không, theo từng màn hình và dòng máy, chứ không chỉ đo trên máy dev. Dùng FrameTiming và addTimingsCallback thế nào để thu thập số liệu frame ở production, và gửi lên mà không ảnh hưởng hiệu năng?

    Xem đáp án mẫu
    Flutter báo thời gian từng frame cho app qua SchedulerBinding.instance.addTimingsCallback, nhận danh sách FrameTiming theo lô (không phải từng frame một); mỗi phần tử có buildDuration (UI thread), rasterDuration (raster thread), totalSpan và vsyncOverhead, và callback có cả ở release nên dùng được cho telemetry. Quy trình: coi một frame là chậm khi totalSpan vượt chu kỳ vsync của máy (16,7 ms ở 60Hz, 8,3 ms ở 120Hz, nên đọc refresh rate thay vì hard-code), 'đóng băng' khi quá 700 ms (cách Android vitals phân loại), rồi gom theo màn hình (gắn tên route hiện tại qua NavigatorObserver) thành bộ đếm và phân vị (p50, p90, p99, tỉ lệ frame chậm) thay vì gửi từng frame. Tách build và raster để biết nguyên nhân: build chậm là do logic hay rebuild, raster chậm là do hiệu ứng đắt (saveLayer, blur, shader). Gửi theo lô định kỳ hoặc khi app ra background, lấy mẫu một phần người dùng, kèm phiên bản app, model máy, bản OS và việc có bật Impeller hay không.   3. App Flutter cần đăng nhập qua SSO của công ty (OIDC/OAuth2). Vì sao dùng Authorization Code kèm PKCE với trình duyệt hệ thống thay vì WebView hay lưu client secret trong app, và bạn xử lý redirect, lưu token, refresh, đăng xuất ra sao?

    Xem đáp án mẫu
    App di động là public client: mọi thứ trong binary đều có thể bị trích xuất nên không thể giữ client_secret. Authorization Code kèm PKCE thay secret bằng một cặp giá trị động: app sinh code_verifier ngẫu nhiên, gửi code_challenge (băm SHA-256 của verifier, phương thức S256) trong yêu cầu đăng nhập, rồi gửi verifier khi đổi code lấy token; kẻ chặn được authorization code (qua custom scheme bị app khác đăng ký trùng) cũng không đổi được token vì không có verifier. Phải mở trang đăng nhập bằng trình duyệt hệ thống (Custom Tabs trên Android, ASWebAuthenticationSession trên iOS) chứ không phải WebView nhúng: app không thấy mật khẩu của người dùng, dùng được phiên SSO sẵn có của trình duyệt, và đó cũng là khuyến nghị của chuẩn (RFC 8252). Package flutter_appauth bọc các SDK AppAuth native và lo PKCE, state, nonce; dùng discovery document (.well-known/openid-configuration) để cấu hình. Redirect URI: App Links hay Universal Links (https đã xác minh) tốt hơn custom scheme vì custom scheme có thể bị app khác chiếm; luôn kiểm tra state để chống CSRF. Token: access token ngắn hạn giữ trong bộ nhớ, refresh token lưu Keychain/Keystore (flutter_secure_storage), bật refresh token rotation phía server và xử lý nhiều request cùng gặp 401 bằng một lần refresh dùng chung. Đăng xuất: xoá token cục bộ, gọi endpoint thu hồi token (revocation) và, nếu cần, end session của IdP để phiên SSO cũng kết thúc. ID token do server xác minh chữ ký cùng aud, iss, exp, đừng tin dữ liệu người dùng chỉ vì app giải mã được. Không dùng implicit flow hay password grant vì chúng đã bị khuyến cáo bỏ.

Bộ gửi (flush) chạy theo ngưỡng: đủ N event, quá T giây, hoặc khi app chuyển sang paused (qua AppLifecycleListener); gửi theo lô nén, retry với exponential backoff kèm jitter, chỉ xoá khỏi hàng đợi sau khi server xác nhận, giới hạn dung lượng hàng đợi (bỏ event cũ nhất hoặc ít quan trọng nhất khi đầy) và tôn trọng trạng thái mạng cùng chế độ tiết kiệm pin. Server dùng thời điểm nhận cùng độ lệch giữa giờ client và server để hiệu chỉnh thời gian vì đồng hồ máy có thể sai. Quyền riêng tư: chỉ bật khi người dùng đồng ý (consent theo khu vực, iOS ATT nếu dùng định danh quảng cáo), không đưa dữ liệu cá nhân (email, số điện thoại, nội dung nhập) vào thuộc tính, hash hoặc bỏ đi, cho phép xoá dữ liệu khi người dùng yêu cầu và ngừng thu thập khi họ rút consent. Lấy mẫu với event tần suất cao (cuộn, frame) nhưng không bao giờ lấy mẫu event quan trọng như mua hàng, và đo chính chi phí của hệ thống analytics (kích thước hàng đợi, tỉ lệ gửi lỗi). }

class AnalyticsClient {
  AnalyticsClient(this._queue, this._sink, {this.batchSize = 20});
  final EventQueue _queue; // bền: SQLite hoặc file, không chỉ giữ trong RAM
  final AnalyticsSink _sink;
  final int batchSize;
  bool _flushing = false;

  void track(String name, [Map<String, Object?> props = const {}]) {
    final event = AnalyticsEvent(
      id: const Uuid().v4(), // server dùng id để loại event trùng khi retry
      name: name,
      props: scrubPii(props), // bỏ dữ liệu cá nhân trước khi ghi
      clientTime: DateTime.now().toUtc(),
      sessionId: _session.id,
    );
    unawaited(_queue.add(event).then((_) => _flushIfNeeded()));
  }

  Future<void> flush() async {
    if (_flushing) return;
    _flushing = true;
    try {
      while (true) {
        final batch = await _queue.peek(batchSize);
        if (batch.isEmpty) break;
        if (!await _sink.send(batch)) break; // lỗi: giữ nguyên trong hàng đợi, thử lại sau với backoff
        await _queue.remove(batch.map((e) => e.id)); // chỉ xoá sau khi server xác nhận
      }
    } finally {
      _flushing = false;
    }
  }
}

  5. App cho nhân viên upload video hiện trường 300MB, người dùng thường khoá máy hoặc chuyển app ngay sau khi bấm gửi, mạng chập chờn. Bạn thiết kế upload hoặc download lớn và bền trong Flutter thế nào, và vì sao dùng Dio thuần trong Dart là không đủ?

Trong Flutter, plugin như background_downloader bọc các cơ chế này thành API Dart (hàng đợi, tiến độ, huỷ, thông báo) nên nên ưu tiên dùng thay vì tự dựng; chỉ tự viết platform channel khi có yêu cầu đặc thù. Thiết kế bền: lưu trạng thái job trong DB cục bộ (id, đường dẫn file, trạng thái, số byte đã gửi) để khôi phục sau khi app bị kill và hiển thị tiến độ; upload theo chunk hoặc giao thức resumable (tus, S3 multipart) để lỗi mạng chỉ phải gửi lại phần dở, kèm checksum để kiểm tra toàn vẹn; server idempotent theo id upload. Retry với backoff, chỉ chạy khi có mạng hoặc Wi-Fi nếu người dùng chọn, và tôn trọng chế độ tiết kiệm dữ liệu. Giới hạn cần nói với PM: người dùng force-quit thì iOS huỷ transfer nền, hệ điều hành có thể trì hoãn việc không gấp, và thông báo tiến độ là bắt buộc trên Android khi dùng foreground service.
