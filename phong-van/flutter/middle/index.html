Mọi rank →

  1. Vì sao sealed class kết hợp switch expression là cách tốt để mô hình hóa UI state (loading/success/error)?

    Xem đáp án mẫu
    sealed class cho compiler biết toàn bộ subtype (chúng phải nằm cùng library), nên switch trên nó được kiểm tra exhaustiveness: thiếu một case là lỗi compile chứ không phải bug runtime. Khi thêm state mới (ví dụ AuthExpired), mọi chỗ switch chưa xử lý sẽ báo lỗi ngay, rất an toàn khi refactor. Kết hợp object pattern như Authenticated(:final user) để destructure field gọn gàng. Lưu ý: đừng thêm case _ vì nó tắt luôn lợi ích này, và sealed class ngầm là abstract nên không khởi tạo trực tiếp được.
    sealed class AuthState {}
class AuthLoading extends AuthState {}
class Authenticated extends AuthState {
  Authenticated(this.user);
  final String user;
}
class AuthFailure extends AuthState {}

String label(AuthState s) => switch (s) {
  AuthLoading() => 'Đang tải...',
  Authenticated(:final user) => 'Xin chào $user',
  AuthFailure() => 'Đăng nhập thất bại',
};

  2. Record và pattern trong Dart 3 giải quyết vấn đề gì? Khi nào nên dùng record thay vì tạo class?

    Xem đáp án mẫu
    Record là kiểu tổng hợp ẩn danh, bất biến, có ==/hashCode theo giá trị, rất hợp để trả về nhiều giá trị từ một hàm mà không cần tạo class tạm. Pattern cho phép destructure record, list, map, object ngay khi khai báo hoặc trong switch/if-case, kể cả kiểm tra kiểu khi đọc JSON. Dùng record cho dữ liệu cục bộ, ngắn hạn (giá trị trả về, key ghép cho Map); khi dữ liệu mang ý nghĩa nghiệp vụ, đi qua nhiều layer hoặc cần method thì nên dùng class (hoặc freezed) để có tên rõ ràng và dễ mở rộng.
    (double min, double max) range(List<double> xs) {
  final sorted = [...xs]..sort();
  return (sorted.first, sorted.last);
}

void handle(Map<String, dynamic> json) {
  final (min, max) = range([3, 1, 4]);
  if (json case {'name': String name, 'age': int age}) {
    print('$name $age, range: $min-$max');
  }
}

  3. Các class modifier interface, base, final, sealed trong Dart 3 khác nhau thế nào? Khi nào dùng?

    Xem đáp án mẫu
    Chúng giới hạn cách code bên ngoài library sử dụng class: interface class cho implements nhưng cấm extends; base class cho extends nhưng cấm implements (và subclass cũng phải là base/final/sealed); final class cấm cả hai; sealed class là abstract, cấm kế thừa ngoài library và bật kiểm tra exhaustiveness. Bên trong cùng library thì không bị giới hạn. Thực tế: tác giả package dùng final/base để sau này thêm method mà không làm vỡ code người dùng, còn trong app hay dùng sealed cho state/result và abstract interface class cho contract của repository.

Async & Isolate

Mọi rank →

  1. Màn hình bị giật khi parse một JSON vài MB. Bạn dùng Isolate.run thế nào và cần lưu ý gì?

    Xem đáp án mẫu
    Đưa phần CPU-bound (decode và map sang model) vào Isolate.run: nó spawn isolate mới, chạy closure, gửi kết quả về bằng Isolate.exit (không phải copy lại) rồi tự đóng isolate. Closure và kết quả phải gửi được giữa các isolate — nếu closure vô tình capture this hoặc object chứa file/socket đang mở thì sẽ lỗi hoặc copy thừa, nên đặt logic trong hàm top-level/static chỉ nhận đúng dữ liệu cần. Isolate không chia sẻ memory: biến global/static ở isolate mới là bản riêng, và chỉ đáng dùng khi việc tính toán lâu hơn chi phí spawn + copy input. Trên web không có isolate thật, compute của Flutter sẽ chạy callback ngay trên main thread.
    Future<List<Product>> parseProducts(String body) {
  return Isolate.run(() {
    final list = jsonDecode(body) as List<dynamic>;
    return list
        .map((e) => Product.fromJson(e as Map<String, dynamic>))
        .toList();
  });
}

  2. Vì sao phải cancel() StreamSubscription? Có những cách nào để không quên việc này?

    Xem đáp án mẫu
    Nếu nguồn stream sống lâu (service, socket, Firebase…), subscription giữ callback và cả State mà callback capture, nên không cancel sẽ leak memory, vẫn nhận event và dễ gọi setState sau khi widget đã dispose. Cancel còn báo cho nguồn phát dọn dẹp: generator async* dừng và chạy finally, StreamController gọi onCancel. Cách an toàn: lưu subscription và cancel trong dispose(), dùng StreamBuilder để framework tự quản lý, ref.onDispose(sub.cancel) trong Riverpod, hoặc await for (thoát vòng lặp bằng break/return sẽ tự cancel). Nếu stream đến từ widget, nhớ hủy và subscribe lại trong didUpdateWidget khi stream thay đổi.
    class _PriceTickerState extends State<PriceTicker> {
  StreamSubscription<double>? _sub;
  double? _price;
  @override
  void initState() {
    super.initState();
    _sub = widget.prices.listen((p) => setState(() => _price = p));
  }
  @override
  void dispose() {
    _sub?.cancel();
    super.dispose();
  }
}

  3. Microtask queue và Event queue khác nhau thế nào? Cái nào ưu tiên hơn?

    Xem đáp án mẫu
    Microtask queue (sinh ra từ Future.then, async/await) luôn được xử lý hết trước khi Dart quay lại xử lý Event queue (I/O, timer, sự kiện UI).

  4. async* và sync* dùng để làm gì?

    Xem đáp án mẫu
    Cả hai đều tạo generator function dùng yield. sync* trả về Iterable (đồng bộ); async* trả về Stream (bất đồng bộ).

  5. Isolate trong Dart là gì? Vì sao Dart cần Isolate thay vì multi-threading truyền thống?

    Xem đáp án mẫu
    Isolate là một luồng thực thi độc lập với bộ nhớ riêng, giao tiếp qua message-passing (không share memory). Nhờ vậy tránh được race condition tự nhiên mà không cần lock/mutex như thread truyền thống.

  6. StreamController broadcast khác gì single-subscription?

    Xem đáp án mẫu
    Single-subscription chỉ cho một listener và buffer sự kiện nếu chưa có ai lắng nghe. Broadcast cho phép nhiều listener nhưng không buffer, listener chỉ nhận sự kiện phát sinh sau khi subscribe.

  7. StreamBuilder rebuild khi nào? Pitfall thường gặp là gì?

    Xem đáp án mẫu
    Rebuild mỗi khi Stream emit giá trị mới. Pitfall phổ biến: tạo Stream mới ngay trong build() khiến Stream bị recreate liên tục, mất dữ liệu hoặc gây rebuild vô hạn.

  8. Review: kể 2 khác biệt giữa Isolate và Thread hệ điều hành truyền thống.

    Xem đáp án mẫu
    (1) Isolate không share memory, giao tiếp qua message-passing, trong khi Thread share memory và cần lock. (2) Nhờ đó Isolate tránh race condition tự nhiên mà không cần đồng bộ hoá thủ công.

Widget & Lifecycle

Mọi rank →

  1. Implicit animation và explicit animation khác nhau thế nào? Khi nào chọn loại nào?

    Xem đáp án mẫu
    Implicit animation (AnimatedContainer, AnimatedOpacity, TweenAnimationBuilder…) tự tạo và quản lý controller bên trong: bạn chỉ đổi giá trị đích rồi setState, widget tự tween từ giá trị cũ sang mới. Explicit animation dùng AnimationController do bạn tự tạo (cần TickerProvider, tự dispose) kết hợp các widget *Transition hoặc AnimatedBuilder, cho phép forward/reverse/repeat, dừng giữa chừng, phối hợp nhiều animation hoặc gắn với gesture. Quy tắc thực tế: chuyển 'A → B khi state đổi' thì dùng implicit cho gọn; cần lặp, staggered hay chạy theo tay kéo thì dùng explicit.

  2. vsync/TickerProvider trong AnimationController để làm gì? Khi nào dùng SingleTickerProviderStateMixin, khi nào dùng TickerProviderStateMixin?

    Xem đáp án mẫu
    Ticker gọi callback mỗi frame để controller cập nhật giá trị; vsync cung cấp Ticker chịu sự điều khiển của TickerMode, nên khi route bị route khác che hoàn toàn (offstage) animation tạm ngưng thay vì tiêu tốn CPU/pin. SingleTickerProviderStateMixin nhẹ hơn nhưng chỉ tạo được đúng một Ticker; State có từ hai controller trở lên (hoặc tạo lại controller nhiều lần) phải dùng TickerProviderStateMixin, nếu không sẽ gặp assertion 'multiple tickers were created'. Luôn dispose() controller trong dispose() của State, nếu không sẽ báo lỗi State bị dispose khi Ticker còn active.
    class _PulseState extends State<Pulse> with SingleTickerProviderStateMixin {
  late final _c = AnimationController(
    vsync: this,
    duration: const Duration(milliseconds: 800),
  )..repeat(reverse: true);
  @override
  void dispose() {
    _c.dispose(); // bắt buộc, nếu không Ticker vẫn active
    super.dispose();
  }
  @override
  Widget build(BuildContext context) =>
      FadeTransition(opacity: _c, child: widget.child);
}

  3. Bạn thiết lập đa ngôn ngữ cho app Flutter bằng intl + ARB như thế nào? Xử lý tham số và số nhiều ra sao?

    Xem đáp án mẫu
    Thêm flutter_localizations và intl, bật generate: true trong pubspec.yaml, khai báo l10n.yaml (thư mục ARB, file template) và viết mỗi ngôn ngữ một file app_xx.arb; flutter gen-l10n (hoặc tự chạy khi build) sinh class AppLocalizations type-safe — các bản Flutter gần đây sinh file thẳng vào source thay vì synthetic package flutter_gen cũ. Đăng ký localizationsDelegates và supportedLocales vào MaterialApp, rồi gọi AppLocalizations.of(context)!.key. Tham số và số nhiều viết theo cú pháp ICU ({count, plural, =0{…} other{…}}) để mỗi ngôn ngữ có quy tắc riêng; tránh tự ghép chuỗi vì thứ tự từ khác nhau giữa các ngôn ngữ.
    // lib/l10n/app_vi.arb
// {
//   "hello": "Xin chào {name}",
//   "cartItems": "{count, plural, =0{Giỏ hàng trống} other{{count} sản phẩm}}"
// }

MaterialApp(
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,
  home: Builder(
    builder: (context) => Text(AppLocalizations.of(context)!.cartItems(3)),
  ),
)

  4. Widget tree, Element tree, RenderObject tree khác nhau thế nào?

    Xem đáp án mẫu
    Widget tree là cấu hình bất biến (blueprint); Element tree là instance quản lý lifecycle, giữ liên kết giữa Widget và RenderObject; RenderObject tree chịu trách nhiệm layout và paint thực tế.

  5. Vì sao Widget là immutable? Điều này ảnh hưởng gì đến hiệu năng?

    Xem đáp án mẫu
    Immutable giúp Flutter diff nhanh giữa widget cũ/mới bằng cách tạo object mới mỗi lần build thay vì mutate, giúp xác định chính xác phần nào cần cập nhật mà không side-effect.

  6. Element khi nào bị dispose và tạo lại hoàn toàn thay vì chỉ update?

    Xem đáp án mẫu
    Khi runtimeType và key của widget mới khác với widget cũ ở cùng vị trí trong tree — Flutter dispose Element cũ và tạo Element mới, làm mất toàn bộ state cũ.

  7. BuildContext thực chất là gì?

    Xem đáp án mẫu
    Chính là Element. BuildContext là interface để Element expose thông tin (vị trí trong tree, tìm ancestor widget như Theme, MediaQuery) mà không lộ toàn bộ implementation nội bộ.

  8. didUpdateWidget được gọi khi nào, dùng để làm gì?

    Xem đáp án mẫu
    Gọi khi parent rebuild và tạo widget mới cùng type/key (Element được tái sử dụng nhưng config đổi). Dùng để so sánh oldWidget với widget mới và xử lý side-effect, ví dụ restart animation.

  9. didChangeDependencies được gọi khi nào, ngoài lần đầu?

    Xem đáp án mẫu
    Mỗi khi một InheritedWidget mà widget đang subscribe (qua dependOnInheritedWidgetOfExactType) thay đổi giá trị.

  10. Vì sao không nên gọi Theme.of(context) trong initState()?

    Xem đáp án mẫu
    Vì initState() chỉ chạy một lần: nếu đăng ký phụ thuộc InheritedWidget ở đây thì khi Theme đổi, widget không được cập nhật lại, nên Flutter assert lỗi dependOnInheritedWidgetOfExactType() was called before initState() completed. Hãy đọc trong didChangeDependencies() hoặc build().

  11. ValueKey, ObjectKey, UniqueKey khác nhau ở điểm nào?

    Xem đáp án mẫu
    ValueKey so sánh bằng giá trị (String, int...); ObjectKey so sánh bằng identity của object cụ thể; UniqueKey luôn khác nhau mỗi lần tạo, ép Flutter luôn coi là widget mới.

  12. GlobalKey khác LocalKey ở điểm nào? Chi phí của GlobalKey là gì?

    Xem đáp án mẫu
    GlobalKey là duy nhất toàn app, cho phép truy cập State/RenderObject từ bất kỳ đâu và giữ state khi widget đổi vị trí trong tree. Chi phí: tốn kém hơn do phải maintain registry toàn cục, lạm dụng gây khó bảo trì.

  13. Khi nào bạn THỰC SỰ cần Key trong một ListView?

    Xem đáp án mẫu
    Khi item trong list có thể bị thêm, xoá hoặc sắp xếp lại ở giữa danh sách, và mỗi item cần giữ đúng state riêng theo item đó chứ không theo vị trí index.

  14. Giải thích khác biệt giữa Element tree và Widget tree, vì sao Element cần tồn tại riêng?

    Xem đáp án mẫu
    Widget tree là blueprint bất biến; Element là instance sống giữ trạng thái và liên kết với RenderObject, tồn tại xuyên suốt để Flutter biết chỗ nào cần update thay vì tạo lại từ đầu mỗi frame.

Layout & Rendering

Mọi rank →

  1. Khi nào cần CustomScrollView với sliver thay vì ListView/Column lồng nhau?

    Xem đáp án mẫu
    Khi một màn hình cuộn gồm nhiều phần khác loại (header co giãn, banner, grid, list dài) cần cuộn chung một scroll mà vẫn lazy-build. Đặt ListView/GridView với shrinkWrap: true trong SingleChildScrollView buộc layout toàn bộ item ngay từ đầu, mất lợi ích lazy và rất tốn với list dài. Trong CustomScrollView, mỗi phần là một sliver (SliverAppBar, SliverList.builder, SliverGrid…) và chỉ phần gần viewport mới được build. Lưu ý slivers: chỉ nhận sliver, widget box thường phải bọc bằng SliverToBoxAdapter.
    CustomScrollView(
  slivers: [
    const SliverAppBar(
      pinned: true, expandedHeight: 200,
      flexibleSpace: FlexibleSpaceBar(title: Text('Shop')),
    ),
    const SliverToBoxAdapter(child: PromoBanner()),
    SliverGrid.count(crossAxisCount: 4, children: categoryIcons),
    SliverList.builder(
      itemCount: products.length,
      itemBuilder: (context, i) => ProductTile(products[i]),
    ),
  ],
)

  2. Khi viết CustomPainter, shouldRepaint và tham số repaint dùng để làm gì?

    Xem đáp án mẫu
    shouldRepaint(old) được gọi khi CustomPaint nhận một instance painter mới: trả true nếu dữ liệu vẽ khác (so field với old), trả false để bỏ qua bước paint; luôn true thì lãng phí, luôn false thì chart không cập nhật khi data đổi. Với animation, truyền Listenable (ví dụ AnimationController) vào super(repaint: ...): painter vẽ lại mỗi khi listenable thông báo mà không cần rebuild widget. Giữ paint() nhẹ (không I/O, không tính toán nặng), và với hình animate liên tục có thể bọc RepaintBoundary để không kéo phần còn lại của màn hình repaint theo.
    class ProgressPainter extends CustomPainter {
  ProgressPainter(this.progress, this.color) : super(repaint: progress);
  final Animation<double> progress;
  final Color color;
  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()..color = color..strokeWidth = 6;
    canvas.drawLine(Offset.zero, Offset(size.width * progress.value, 0), paint);
  }
  @override
  bool shouldRepaint(ProgressPainter old) =>
      old.progress != progress || old.color != color;
}

  3. 'Constraints go down, sizes go up' nghĩa là gì?

    Xem đáp án mẫu
    Parent truyền constraint (min/max width/height) xuống con; con tự quyết định size trong giới hạn đó rồi trả size ngược lên để parent định vị.

  4. Giải thích 'constraints go down, size goes up' qua ví dụ Row chứa Expanded.

    Xem đáp án mẫu
    Row truyền constraint chia đều không gian còn lại xuống từng Expanded; mỗi Expanded tự tính kích thước con bên trong rồi trả size ngược lên để Row sắp xếp vị trí cuối cùng.

State Management

Mọi rank →

  1. Trong Riverpod hiện đại, Notifier/AsyncNotifier khác gì StateNotifier/StateProvider cũ? Viết một AsyncNotifier có load và thêm item.

    Xem đáp án mẫu
    Notifier/AsyncNotifier là API được khuyến nghị từ Riverpod 2: state khởi tạo trong build() (có thể ref.watch provider khác và tự chạy lại khi dependency đổi), class có sẵn ref nên không phải truyền Ref qua constructor như StateNotifier. AsyncNotifier trả Future từ build() và Riverpod tự bọc thành AsyncValue (loading/data/error); method thay đổi dữ liệu dùng AsyncValue.guard để bắt lỗi thành AsyncError. StateProvider, StateNotifierProvider, ChangeNotifierProvider giờ là legacy (Riverpod 3 tách chúng sang import legacy.dart), chỉ nên giữ khi bảo trì code cũ.
    final todosProvider =
    AsyncNotifierProvider<TodosNotifier, List<Todo>>(TodosNotifier.new);
class TodosNotifier extends AsyncNotifier<List<Todo>> {
  @override
  Future<List<Todo>> build() => ref.watch(todoRepoProvider).fetchAll();
  Future<void> add(Todo todo) async {
    final repo = ref.read(todoRepoProvider);
    state = const AsyncLoading();
    state = await AsyncValue.guard(() async {
      await repo.add(todo);
      return repo.fetchAll();
    });
  }
}

  2. Màn hình dùng BlocBuilder rebuild quá nhiều dù chỉ hiển thị một field của state. Bạn tối ưu thế nào?

    Xem đáp án mẫu
    Trước hết đảm bảo state so sánh theo giá trị (Equatable hoặc freezed): Bloc bỏ qua emit khi state mới == state hiện tại, nên nếu state không override == thì mỗi lần emit đều rebuild. Sau đó thu hẹp phạm vi: buildWhen so sánh đúng field cần dùng, hoặc gọn hơn là BlocSelector/context.select để chỉ rebuild khi giá trị được chọn thay đổi. Đặt BlocBuilder sát widget cần dữ liệu thay vì bọc cả Scaffold, và tách side effect (SnackBar, điều hướng) sang BlocListener với listenWhen.
    // Chỉ rebuild khi total đổi
BlocBuilder<CartBloc, CartState>(
  buildWhen: (prev, curr) => prev.total != curr.total,
  builder: (context, state) => Text('${state.total} đ'),
)

// Gọn hơn với BlocSelector
BlocSelector<CartBloc, CartState, int>(
  selector: (state) => state.total,
  builder: (context, total) => Text('$total đ'),
)

  3. Phân biệt ephemeral state và app state. Khi nào setState là đủ, khi nào nên đưa state vào Riverpod/Bloc?

    Xem đáp án mẫu
    Ephemeral state là state cục bộ của một widget mà nơi khác không cần biết (tab đang chọn, trạng thái expand, animation, giá trị form tạm) — setState trong StatefulWidget là đủ và đơn giản nhất. App state được chia sẻ giữa nhiều màn hình, sống lâu hơn widget, cần test logic riêng hoặc đồng bộ với server (user đăng nhập, giỏ hàng, dữ liệu cache) — nên đưa vào Riverpod/Bloc. Dấu hiệu cần nâng cấp: phải truyền data/callback qua nhiều tầng, hai màn hình cần cùng dữ liệu, hoặc logic nghiệp vụ nằm lẫn trong State. Ngược lại, đẩy mọi thứ (kể cả checkbox tạm) lên global state làm code rườm rà và khó theo dõi.

  4. InheritedWidget thông báo thay đổi cho widget con dựa trên cơ chế nào?

    Xem đáp án mẫu
    Khi updateShouldNotify() trả true, mọi widget con đã đăng ký qua dependOnInheritedWidgetOfExactType sẽ được đánh dấu rebuild, không cần truyền callback thủ công qua nhiều tầng.

  5. Vì sao package Provider được xây trên nền InheritedWidget?

    Xem đáp án mẫu
    Để tận dụng cơ chế dependency tracking và rebuild tối ưu có sẵn của Flutter, đồng thời thêm API tiện lợi như dispose tự động mà không cần tự viết InheritedWidget thủ công.

  6. Selector giải quyết vấn đề gì mà Consumer không làm được?

    Xem đáp án mẫu
    Cho phép chọn một phần cụ thể (derived value) từ model và chỉ rebuild khi riêng phần đó đổi, kể cả khi các field khác trong ChangeNotifier cũng thay đổi.

  7. ProxyProvider dùng để làm gì?

    Xem đáp án mẫu
    Tạo một provider mà giá trị phụ thuộc vào (kết hợp từ) một hoặc nhiều provider khác nằm phía trên nó trong tree.

  8. ChangeNotifier có nhược điểm gì so với các giải pháp khác?

    Xem đáp án mẫu
    Mutable state dễ gây side-effect khó trace, không có type-safety cho state như Bloc, và dễ quên gọi notifyListeners() dẫn đến UI không cập nhật.

  9. Riverpod giải quyết vấn đề gì mà Provider gặp phải?

    Xem đáp án mẫu
    Không phụ thuộc BuildContext nên đọc được ngoài widget tree, và compile-time safe — bắt lỗi thiếu provider lúc compile thay vì runtime, tránh ProviderNotFoundException.

  10. ref.watch, ref.read, ref.listen khác nhau thế nào?

    Xem đáp án mẫu
    watch subscribe và rebuild khi đổi (dùng trong build); read đọc một lần không subscribe (dùng trong callback); listen subscribe để chạy side-effect như show SnackBar mà không rebuild UI.

  11. autoDispose modifier dùng khi nào?

    Xem đáp án mẫu
    Khi muốn provider tự huỷ state khi không còn widget nào lắng nghe, phù hợp cho state gắn với một màn hình cụ thể thay vì global.

  12. family modifier giải quyết vấn đề gì?

    Xem đáp án mẫu
    Cho phép provider nhận tham số đầu vào để tạo nhiều instance state khác nhau dựa trên tham số đó, ví dụ provider theo userId.

  13. AsyncValue giúp gì khi xử lý trạng thái gọi network?

    Xem đáp án mẫu
    Đóng gói sẵn ba trạng thái loading/data/error, giúp UI dùng .when() xử lý đầy đủ mọi case mà không cần tự quản lý boolean thủ công.

  14. Cubit khác Bloc ở điểm cơ bản nào?

    Xem đáp án mẫu
    Cubit gọi method trực tiếp để emit state mới, đơn giản hơn. Bloc nhận Event qua add() rồi xử lý bất đồng bộ qua Stream để emit state, tách biệt rõ input và output, dễ trace hơn.

  15. BlocListener và BlocBuilder khác nhau thế nào?

    Xem đáp án mẫu
    BlocBuilder rebuild UI theo state; BlocListener chạy side-effect như navigation hay dialog mà không rebuild UI. BlocConsumer dùng khi cần cả hai.

  16. HydratedBloc giải quyết vấn đề gì?

    Xem đáp án mẫu
    Tự động persist và restore state của Bloc/Cubit xuống local storage, giữ lại state sau khi app bị kill hoặc restart.

  17. Review: gọi notifyListeners() sau khi ChangeNotifier đã dispose, hoặc setState() sau khi widget đã dispose thì sao?

    Xem đáp án mẫu
    Debug mode sẽ throw lỗi: A ChangeNotifier was used after being disposed hoặc setState() called after dispose(). Thường gặp khi callback chạy sau một await; cần kiểm tra mounted (với State) hoặc huỷ subscription/timer trong dispose().

  18. Khi nào bạn chọn Riverpod thay vì Provider cho một dự án mới bắt đầu?

    Xem đáp án mẫu
    Khi muốn compile-time safety, không phụ thuộc BuildContext và cần testability cao ngay từ đầu, đánh đổi là learning curve cao hơn một chút.

  19. Tại sao BLoC tách Event và State thành hai khái niệm riêng thay vì gộp như Cubit?

    Xem đáp án mẫu
    Event làm rõ cái gì kích hoạt hành động, dễ log và replay, tách biệt với State là kết quả sau xử lý — hữu ích khi cần trace toàn bộ luồng input-output trong hệ thống lớn.

  2. Làm auth guard với go_router như thế nào? Deep link vào một trang cần đăng nhập sẽ được xử lý ra sao?

    Xem đáp án mẫu
    Khai báo redirect (top-level hoặc trên từng GoRoute): trả về path mới để chuyển hướng, trả null để đi tiếp; truyền refreshListenable (ví dụ ChangeNotifier giữ trạng thái auth) để router chạy lại redirect khi đăng nhập/đăng xuất. Deep link cũng đi qua cùng cấu hình route, nên link /orders/42 khi chưa login sẽ bị chuyển sang /login; hãy lưu đích ban đầu (query from) để quay lại sau khi đăng nhập, và cẩn thận tránh hai route redirect qua lại lẫn nhau. Phía native vẫn phải cấu hình App Links/intent-filter (Android) và Universal Links/Associated Domains (iOS) thì OS mới mở app bằng URL đó.
    final router = GoRouter(
  refreshListenable: auth, // ChangeNotifier giữ trạng thái login
  redirect: (context, state) {
    final atLogin = state.matchedLocation == '/login';
    if (!auth.isLoggedIn) {
      if (atLogin) return null;
      final from = Uri.encodeComponent(state.uri.toString());
      return '/login?from=$from';
    }
    if (atLogin) return state.uri.queryParameters['from'] ?? '/';
    return null;
  },
  routes: routes,
);

Kiến trúc & DI

Mọi rank →

  1. Lỗi từ Dio (timeout, 401, 500) nên được xử lý ở layer nào và trả lên trên dưới dạng gì?

    Xem đáp án mẫu
    Bắt và chuyển đổi ở data layer (repository implementation hoặc data source), vì DioException là chi tiết hạ tầng mà domain và UI không nên biết. Repository map lỗi sang Failure của domain (NetworkFailure, UnauthorizedFailure, ServerFailure…) rồi trả về kiểu Result dạng sealed (hoặc Either của fpdart), buộc caller xử lý cả hai nhánh bằng switch exhaustive. Presentation chỉ việc map Failure sang thông điệp thân thiện. Nhờ vậy có thể thay Dio bằng client khác hay thêm cache mà không chạm UI, và test dễ hơn vì mock trả Err(...) thay vì phải dựng DioException.
    sealed class Result<T> { const Result(); }
final class Ok<T> extends Result<T> { const Ok(this.value); final T value; }
final class Err<T> extends Result<T> { const Err(this.failure); final Failure failure; }

// data layer: bắt DioException, trả về Failure của domain
Future<Result<User>> getUser(String id) async {
  try {
    final dto = await _api.fetchUser(id);
    return Ok(dto.toEntity());
  } on DioException catch (e) {
    return Err(e.response == null ? NetworkFailure() : ServerFailure());
  }
}

Testing & CI/CD

Mọi rank →

  1. Viết widget test cho màn hình đăng nhập phụ thuộc AuthRepository như thế nào?

    Xem đáp án mẫu
    Inject repository qua constructor hoặc DI (override của Riverpod, BlocProvider) để thay bằng mock của mocktail, stub hàm trả Future bằng when(...).thenAnswer(...). Dùng pumpWidget với MaterialApp bọc ngoài (cung cấp Directionality, Navigator, theme), tương tác qua enterText/tap, rồi pump() để frame mới được build trước khi expect với find.text/find.byKey. Cuối cùng verify repository được gọi đúng tham số. Nếu UI có animation hoặc delay thì dùng pump(duration)/pumpAndSettle, nhưng nhớ pumpAndSettle sẽ timeout nếu có animation chạy vô hạn như CircularProgressIndicator.
    class MockAuthRepo extends Mock implements AuthRepository {}

testWidgets('hiện lỗi khi sai mật khẩu', (tester) async {
  final repo = MockAuthRepo();
  when(() => repo.login(any(), any()))
      .thenAnswer((_) async => throw const WrongPassword());
  await tester.pumpWidget(MaterialApp(home: LoginPage(repo: repo)));
  await tester.enterText(find.byKey(const Key('email')), 'a@b.com');
  await tester.enterText(find.byKey(const Key('password')), '123');
  await tester.tap(find.text('Đăng nhập'));
  await tester.pump();
  expect(find.text('Sai mật khẩu'), findsOneWidget);
  verify(() => repo.login('a@b.com', '123')).called(1);
});

  2. Làm sao unit test một provider/notifier của Riverpod mà không cần dựng widget?

    Xem đáp án mẫu
    Tạo ProviderContainer với overrides để thay dependency (repository, API client) bằng mock/fake, đọc provider qua container và addTearDown(container.dispose) để dọn dẹp sau test. Với AsyncNotifier, await container.read(provider.future) để chờ build() xong; với mutation, gọi container.read(provider.notifier).method() rồi kiểm tra container.read(provider). Muốn kiểm tra chuỗi state (loading → data), dùng container.listen để ghi lại từng giá trị. Trong widget test, override tương tự bằng ProviderScope(overrides: [...]).
    class MockTodoRepo extends Mock implements TodoRepo {}

test('load todos từ repository', () async {
  final repo = MockTodoRepo();
  when(() => repo.fetchAll()).thenAnswer((_) async => [const Todo('a')]);
  final container = ProviderContainer(
    overrides: [todoRepoProvider.overrideWithValue(repo)],
  );
  addTearDown(container.dispose);
  final todos = await container.read(todosProvider.future);
  expect(todos, hasLength(1));
  verify(() => repo.fetchAll()).called(1);
});

  3. Vì sao nên có nhiều Unit test hơn Integration test?

    Xem đáp án mẫu
    Unit test chạy nhanh, ổn định, rẻ để maintain; Integration test chậm, dễ flaky và tốn chi phí CI hơn nhiều lần nên chỉ dùng cho các flow quan trọng nhất.

  4. pump() và pumpAndSettle() khác nhau thế nào?

    Xem đáp án mẫu
    pump() chỉ render đúng một frame hoặc sau một khoảng duration chỉ định; pumpAndSettle() pump liên tục cho tới khi không còn frame nào được lên lịch nữa.

  5. Mockito và Mocktail khác nhau cơ bản ở điểm nào?

    Xem đáp án mẫu
    Mockito cần code generation qua build_runner để tạo Mock class; Mocktail dùng thuần Dart dựa vào null safety, không cần code gen, đơn giản hoá setup.

  6. verify() khác when() ở điểm nào?

    Xem đáp án mẫu
    when() định nghĩa hành vi giả lập khi một method được gọi; verify() kiểm tra sau khi code chạy xong, xác nhận method đó có thực sự được gọi hay không và gọi bao nhiêu lần.

  7. Làm sao test một Bloc hiệu quả? Package nào thường dùng?

    Xem đáp án mẫu
    Dùng package bloc_test, định nghĩa build để khởi tạo bloc, act để bắn event vào, và expect để liệt kê danh sách state mong đợi phát ra theo đúng thứ tự.

  8. Kiểm tra kết quả của một hàm trả về Stream trong package test bằng cách nào?

    Xem đáp án mẫu
    Dùng matcher emitsInOrder([...]) kết hợp expectLater(stream, ...) để assert thứ tự và giá trị các sự kiện phát ra.

  9. 'Flavor' trong Flutter dùng để làm gì?

    Xem đáp án mẫu
    Cho phép build nhiều biến thể app như dev, staging, production từ cùng một codebase với config khác nhau, mà không cần maintain nhiều project riêng.
