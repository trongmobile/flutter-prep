  1. Vì sao sealed class kết hợp switch expression là cách tốt để mô hình hóa UI state (loading/success/error)?

    Xem đáp án mẫu
    sealed class cho compiler biết toàn bộ subtype (chúng phải nằm cùng library), nên switch trên nó được kiểm tra exhaustiveness: thiếu một case là lỗi compile chứ không phải bug runtime. Khi thêm state mới (ví dụ AuthExpired), mọi chỗ switch chưa xử lý sẽ báo lỗi ngay, rất an toàn khi refactor. Kết hợp object pattern như Authenticated(:final user) để destructure field gọn gàng. Lưu ý: đừng thêm case _ vì nó tắt luôn lợi ích này, và sealed class ngầm là abstract nên không khởi tạo trực tiếp được.
    sealed class AuthState {}
class AuthLoading extends AuthState {}
class Authenticated extends AuthState {
  Authenticated(this.user);
  final String user;
}
class AuthFailure extends AuthState {}

String label(AuthState s) => switch (s) {
  AuthLoading() => 'Đang tải...',
  Authenticated(:final user) => 'Xin chào $user',
  AuthFailure() => 'Đăng nhập thất bại',
};

  2. Record và pattern trong Dart 3 giải quyết vấn đề gì? Khi nào nên dùng record thay vì tạo class?

    Xem đáp án mẫu
    Record là kiểu tổng hợp ẩn danh, bất biến, có ==/hashCode theo giá trị, rất hợp để trả về nhiều giá trị từ một hàm mà không cần tạo class tạm. Pattern cho phép destructure record, list, map, object ngay khi khai báo hoặc trong switch/if-case, kể cả kiểm tra kiểu khi đọc JSON. Dùng record cho dữ liệu cục bộ, ngắn hạn (giá trị trả về, key ghép cho Map); khi dữ liệu mang ý nghĩa nghiệp vụ, đi qua nhiều layer hoặc cần method thì nên dùng class (hoặc freezed) để có tên rõ ràng và dễ mở rộng.

  3. Các class modifier interface, base, final, sealed trong Dart 3 khác nhau thế nào? Khi nào dùng?

    Xem đáp án mẫu
    Chúng giới hạn cách code bên ngoài library sử dụng class: interface class cho implements nhưng cấm extends; base class cho extends nhưng cấm implements (và subclass cũng phải là base/final/sealed); final class cấm cả hai; sealed class là abstract, cấm kế thừa ngoài library và bật kiểm tra exhaustiveness. Bên trong cùng library thì không bị giới hạn. Thực tế: tác giả package dùng final/base để sau này thêm method mà không làm vỡ code người dùng, còn trong app hay dùng sealed cho state/result và abstract interface class cho contract của repository.

  4. Hai hàm cùng nhận int là getUser(int userId) và getOrder(int orderId) nên rất dễ truyền nhầm id. Extension type của Dart 3.3 giải quyết việc này thế nào, và nó khác một class bọc thông thường ở điểm nào?

    Xem đáp án mẫu
    Extension type tạo một kiểu mới ở thời điểm compile bọc quanh một 'representation type' mà không tốn thêm object lúc chạy: với extension type UserId(int value) {} và OrderId tương tự, hai kiểu này khác nhau nên truyền nhầm là lỗi compile, nhưng ở runtime chúng chỉ là int (zero-cost, không cấp phát thêm như một class bọc). Nó chỉ lộ ra các thành viên bạn khai báo (hoặc implements int để dùng lại API của int), cho phép thêm method, getter và constructor kiểm tra hợp lệ (OrderId.parse). Đánh đổi: vì không tồn tại lúc chạy nên x is UserId thực chất kiểm tra is int, ép kiểu từ dynamic hay JSON không được kiểm tra thêm, và runtimeType thấy int. Do đó không dùng extension type thay cho class khi cần đa hình (override theo kiểu thật) hoặc lưu thêm thông tin theo từng instance. Chúng hợp cho id, đơn vị (Meters, Seconds), và wrapper quanh JSON (extension type User(Map<String, Object?> json)) khi muốn API gọn mà không tốn chi phí cấp phát.
    extension type const UserId(int value) {}

extension type const OrderId(int value) {
  OrderId.parse(String raw) : value = int.parse(raw);
  bool get isValid => value > 0;
}

Future<User> getUser(UserId id) async => api.fetchUser(id.value);
Future<Order> getOrder(OrderId id) async => api.fetchOrder(id.value);

void main() {
  const userId = UserId(7);

  getUser(userId);

}

  1. Màn hình bị giật khi parse một JSON vài MB. Bạn dùng Isolate.run thế nào và cần lưu ý gì?

    Xem đáp án mẫu
    Đưa phần CPU-bound (decode và map sang model) vào Isolate.run: nó spawn isolate mới, chạy closure, gửi kết quả về bằng Isolate.exit (không phải copy lại) rồi tự đóng isolate. Closure và kết quả phải gửi được giữa các isolate — nếu closure vô tình capture this hoặc object chứa file/socket đang mở thì sẽ lỗi hoặc copy thừa, nên đặt logic trong hàm top-level/static chỉ nhận đúng dữ liệu cần. Isolate không chia sẻ memory: biến global/static ở isolate mới là bản riêng, và chỉ đáng dùng khi việc tính toán lâu hơn chi phí spawn + copy input. Trên web không có isolate thật, compute của Flutter sẽ chạy callback ngay trên main thread.
    Future<List<Product>> parseProducts(String body) {
  return Isolate.run(() {
    final list = jsonDecode(body) as List<dynamic>;
    return list
        .map((e) => Product.fromJson(e as Map<String, dynamic>))
        .toList();
  });
}

  2. Vì sao phải cancel() StreamSubscription? Có những cách nào để không quên việc này?

    Xem đáp án mẫu
    Nếu nguồn stream sống lâu (service, socket, Firebase…), subscription giữ callback và cả State mà callback capture, nên không cancel sẽ leak memory, vẫn nhận event và dễ gọi setState sau khi widget đã dispose. Cancel còn báo cho nguồn phát dọn dẹp: generator async* dừng và chạy finally, StreamController gọi onCancel. Cách an toàn: lưu subscription và cancel trong dispose(), dùng StreamBuilder để framework tự quản lý, ref.onDispose(sub.cancel) trong Riverpod, hoặc await for (thoát vòng lặp bằng break/return sẽ tự cancel). Nếu stream đến từ widget, nhớ hủy và subscribe lại trong didUpdateWidget khi stream thay đổi.
    class _PriceTickerState extends State<PriceTicker> {
  StreamSubscription<double>? _sub;
  double? _price;
  @override
  void initState() {
    super.initState();
    _sub = widget.prices.listen((p) => setState(() => _price = p));
  }
  @override
  void dispose() {
    _sub?.cancel();
    super.dispose();
  }
}

  3. Ô tìm kiếm gọi API mỗi khi gõ một ký tự, và kết quả của từ khoá cũ đôi khi về sau, đè lên kết quả mới. Bạn debounce và loại bỏ kết quả cũ thế nào trong Flutter (Timer thuần, rxdart hay Bloc/Riverpod)?

    Xem đáp án mẫu
    Có hai vấn đề cần giải riêng: gọi quá nhiều request (cần debounce) và kết quả về sai thứ tự (race condition). Debounce thuần Dart: giữ một Timer?, mỗi lần onChanged thì cancel() timer cũ rồi tạo timer mới 300ms trước khi gọi API, và nhớ cancel() trong dispose(). Race condition: gắn cho mỗi lần tìm một mã (bộ đếm hoặc chính chuỗi query) và bỏ kết quả nếu nó không còn là lần tìm mới nhất; hoặc dùng CancelToken của Dio để huỷ request cũ (server vẫn có thể xử lý nhưng app không nhận kết quả). Với Stream, rxdart có debounceTime và switchMap (tự huỷ subscription của request cũ khi có query mới), gọn nhất khi đã dùng Stream hay Bloc. Với Bloc có EventTransformer kèm restartable() của bloc_concurrency; với Riverpod, AsyncNotifier có thể kiểm tra mã tìm kiếm sau mỗi await, hoặc dùng ref.onDispose để huỷ request khi provider bị invalidate. Cũng nên bỏ qua query rỗng hoặc quá ngắn, và hiển thị trạng thái loading riêng cho lần tìm đang chạy.
    class _SearchBoxState extends State<SearchBox> {
  Timer? _debounce;
  int _searchId = 0; // đánh dấu lần tìm mới nhất

  void _onChanged(String text) {
    _debounce?.cancel();
    _debounce = Timer(const Duration(milliseconds: 300), () => _search(text.trim()));
  }

  Future<void> _search(String query) async {
    if (query.length < 2) return;
    final id = ++_searchId;
    final results = await api.search(query);
    if (!mounted || id != _searchId) return; // kết quả của lần tìm cũ: bỏ
    setState(() => _results = results);
  }

  @override
  void dispose() {
    _debounce?.cancel();
    super.dispose();
  }
}

  4. Microtask queue và Event queue khác nhau thế nào? Cái nào ưu tiên hơn?

    Xem đáp án mẫu
    Microtask queue (sinh ra từ Future.then, async/await) luôn được xử lý hết trước khi Dart quay lại xử lý Event queue (I/O, timer, sự kiện UI).

  5. async* và sync* dùng để làm gì?

    Xem đáp án mẫu
    Cả hai đều tạo generator function dùng yield. sync* trả về Iterable (đồng bộ); async* trả về Stream (bất đồng bộ).

  6. Isolate trong Dart là gì? Vì sao Dart cần Isolate thay vì multi-threading truyền thống?

    Xem đáp án mẫu
    Isolate là một luồng thực thi độc lập với bộ nhớ riêng, giao tiếp qua message-passing (không share memory). Nhờ vậy tránh được race condition tự nhiên mà không cần lock/mutex như thread truyền thống.

  7. StreamController broadcast khác gì single-subscription?

    Xem đáp án mẫu
    Single-subscription chỉ cho một listener và buffer sự kiện nếu chưa có ai lắng nghe. Broadcast cho phép nhiều listener nhưng không buffer, listener chỉ nhận sự kiện phát sinh sau khi subscribe.

  8. StreamBuilder rebuild khi nào? Pitfall thường gặp là gì?

    Xem đáp án mẫu
    Rebuild mỗi khi Stream emit giá trị mới. Pitfall phổ biến: tạo Stream mới ngay trong build() khiến Stream bị recreate liên tục, mất dữ liệu hoặc gây rebuild vô hạn.

  9. Review: kể 2 khác biệt giữa Isolate và Thread hệ điều hành truyền thống.

    Xem đáp án mẫu
    (1) Isolate không share memory, giao tiếp qua message-passing, trong khi Thread share memory và cần lock. (2) Nhờ đó Isolate tránh race condition tự nhiên mà không cần đồng bộ hoá thủ công.

  1. Implicit animation và explicit animation khác nhau thế nào? Khi nào chọn loại nào?

    Xem đáp án mẫu
    Implicit animation (AnimatedContainer, AnimatedOpacity, TweenAnimationBuilder…) tự tạo và quản lý controller bên trong: bạn chỉ đổi giá trị đích rồi setState, widget tự tween từ giá trị cũ sang mới. Explicit animation dùng AnimationController do bạn tự tạo (cần TickerProvider, tự dispose) kết hợp các widget *Transition hoặc AnimatedBuilder, cho phép forward/reverse/repeat, dừng giữa chừng, phối hợp nhiều animation hoặc gắn với gesture. Quy tắc thực tế: chuyển 'A → B khi state đổi' thì dùng implicit cho gọn; cần lặp, staggered hay chạy theo tay kéo thì dùng explicit.

  2. vsync/TickerProvider trong AnimationController để làm gì? Khi nào dùng SingleTickerProviderStateMixin, khi nào dùng TickerProviderStateMixin?

    Xem đáp án mẫu
    Ticker gọi callback mỗi frame để controller cập nhật giá trị; vsync cung cấp Ticker chịu sự điều khiển của TickerMode, nên khi route bị route khác che hoàn toàn (offstage) animation tạm ngưng thay vì tiêu tốn CPU/pin. SingleTickerProviderStateMixin nhẹ hơn nhưng chỉ tạo được đúng một Ticker; State có từ hai controller trở lên (hoặc tạo lại controller nhiều lần) phải dùng TickerProviderStateMixin, nếu không sẽ gặp assertion 'multiple tickers were created'. Luôn dispose() controller trong dispose() của State, nếu không sẽ báo lỗi State bị dispose khi Ticker còn active.
    class _PulseState extends State<Pulse> with SingleTickerProviderStateMixin {
  late final _c = AnimationController(
    vsync: this,
    duration: const Duration(milliseconds: 800),
  )..repeat(reverse: true);
  @override
  void dispose() {
    _c.dispose(); // bắt buộc, nếu không Ticker vẫn active
    super.dispose();
  }
  @override
  Widget build(BuildContext context) =>
      FadeTransition(opacity: _c, child: widget.child);
}

  4. App cần làm mới dữ liệu khi người dùng quay lại từ background và tạm dừng timer khi app ra nền. AppLifecycleState và WidgetsBindingObserver hoạt động thế nào, và AppLifecycleListener khác gì?

    Xem đáp án mẫu
    Flutter báo trạng thái của app qua AppLifecycleState: resumed (đang hiển thị và nhận input), inactive (đang chuyển tiếp hoặc bị gián đoạn, như có cuộc gọi hay mở trình chuyển app), hidden (từ Flutter 3.13, không còn hiển thị), paused (ở background) và detached (engine còn chạy nhưng không còn view). Để lắng nghe, cho State mixin WidgetsBindingObserver, gọi WidgetsBinding.instance.addObserver(this) trong initState, override didChangeAppLifecycleState và bắt buộc removeObserver trong dispose. Từ Flutter 3.13 có AppLifecycleListener gọn hơn: truyền các callback onResume, onPause, onInactive, onHide, onShow... và gọi dispose() khi xong. Việc nên làm: ở resumed thì làm mới dữ liệu cũ (kiểm tra thời điểm lần cuối để không gọi API mỗi lần), kiểm tra lại quyền; ở paused thì lưu nháp, huỷ stream hoặc timer, dừng animation và camera. Lưu ý trên iOS inactive xảy ra cả khi kéo thanh thông báo nên không coi là rời app; và app có thể bị hệ thống kill khi đang paused mà không báo trước, nên lưu state quan trọng ngay lúc đó chứ đừng đợi detached.
    class _FeedPageState extends State<FeedPage> {
  late final AppLifecycleListener _listener;
  DateTime _lastFetch = DateTime.now();

  @override
  void initState() {
    super.initState();
    _listener = AppLifecycleListener(
      onResume: _refreshIfStale,
      onPause: _saveDraftAndStopPolling,
    );
  }

  void _refreshIfStale() {
    if (DateTime.now().difference(_lastFetch) > const Duration(minutes: 5)) {
      _lastFetch = DateTime.now();
      context.read<FeedCubit>().refresh();
    }
  }

  @override
  void dispose() {
    _listener.dispose(); // quên dispose là rò rỉ listener
    super.dispose();
  }
}

  5. Các design token riêng của app (màu thành công, màu cảnh báo, khoảng cách) không nằm trong ColorScheme của Material. Làm sao thêm chúng vào theme bằng ThemeExtension, hỗ trợ dark mode, và lưu lựa chọn sáng/tối của người dùng?

    Xem đáp án mẫu
    ThemeExtension<T> cho phép gắn dữ liệu tuỳ biến vào ThemeData và lấy ra qua Theme.of(context).extension<AppColors>(), thay vì rải hằng số màu khắp app. Class extension phải cài copyWith và lerp (để chuyển theme có animation mượt). Khai báo hai bản (sáng và tối) rồi gắn vào ThemeData(extensions: [...]) của theme và darkTheme. Với Material 3, dùng ColorScheme.fromSeed(seedColor:, brightness:) để sinh bảng màu nhất quán và chỉ thêm extension cho phần nằm ngoài scheme. Chọn chế độ bằng MaterialApp(themeMode: ThemeMode.system | light | dark); muốn người dùng đổi và nhớ lựa chọn thì giữ ThemeMode trong một notifier (Riverpod, Provider, Cubit), lưu bằng shared_preferences và đọc lúc khởi động để không nháy sai theme khi mở app. Giữ API gọn bằng extension trên BuildContext (context.appColors.success). Đừng hard-code màu trong widget, và kiểm tra cả hai theme (golden test sáng và tối) cùng độ tương phản.
    @immutable
class AppColors extends ThemeExtension<AppColors> {
  const AppColors({required this.success, required this.warning});
  final Color success;
  final Color warning;

  @override
  AppColors copyWith({Color? success, Color? warning}) =>
      AppColors(success: success ?? this.success, warning: warning ?? this.warning);

  @override
  AppColors lerp(ThemeExtension<AppColors>? other, double t) {
    if (other is! AppColors) return this;
    return AppColors(
      success: Color.lerp(success, other.success, t)!,
      warning: Color.lerp(warning, other.warning, t)!,
    );
  }
}

extension AppThemeX on BuildContext {
  AppColors get appColors => Theme.of(this).extension<AppColors>()!;
}

  10. Form đăng ký có nhiều TextField: bấm Enter trên bàn phím phải nhảy sang ô tiếp theo, ô cuối thì gửi form, chạm ra ngoài thì ẩn bàn phím, và khi validate sai thì phải focus vào ô lỗi. Bạn quản lý focus bằng FocusNode, TextInputAction và onTapOutside thế nào?

    Xem đáp án mẫu
    Mỗi ô nhập có một FocusNode; TextInputAction.next đổi nút Enter thành 'Tiếp' và onSubmitted/onFieldSubmitted chuyển focus bằng FocusScope.of(context).nextFocus() (đi theo thứ tự traversal mặc định) hoặc requestFocus tới một node cụ thể; ô cuối đặt TextInputAction.done và gọi hàm gửi.   final _passwordFocus = FocusNode();

    if (!_formKey.currentState!.validate()) {
      // Minh hoạ: thực tế tìm ô lỗi đầu tiên rồi requestFocus, Flutter tự cuộn tới ô đang focus

  2. Khi viết CustomPainter, shouldRepaint và tham số repaint dùng để làm gì?

    Xem đáp án mẫu

    class ProgressPainter extends CustomPainter {
  ProgressPainter(this.progress, this.color) : super(repaint: progress);
  final Animation<double> progress;
  final Color color;
  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()..color = color..strokeWidth = 6;
    canvas.drawLine(Offset.zero, Offset(size.width * progress.value, 0), paint);
  }
  @override
  bool shouldRepaint(ProgressPainter old) =>
      old.progress != progress || old.color != color;
}

  final _items = <String, Post>{}; // theo id: tự loại bài trùng
  String? _cursor;
  bool hasMore = true;
  bool isLoadingMore = false;
  Object? error;
  int _generation = 0; // tăng khi refresh để bỏ kết quả của request cũ

  List<Post> get items => _items.values.toList();

  Future<void> loadMore() async {
    if (isLoadingMore || !hasMore) return;
    isLoadingMore = true;
    error = null;
    notifyListeners();
    final gen = _generation;
    try {
      final page = await api.fetchPosts(cursor: _cursor, limit: 20);
      if (gen != _generation) return; // đã refresh trong lúc chờ: bỏ kết quả cũ
      for (final p in page.items) {
        _items[p.id] = p;
      }
      _cursor = page.nextCursor;
      hasMore = page.nextCursor != null;
    } catch (e) {
      if (gen == _generation) error = e; // giữ danh sách cũ, chỉ hiện nút thử lại ở cuối
    } finally {
      if (gen == _generation) isLoadingMore = false;
      notifyListeners();
    }
  }

  Future<void> refresh() {
    _generation++;
    _items.clear();
    _cursor = null;
    hasMore = true;
    isLoadingMore = false;
    return loadMore();
  }
}

    Ảnh được decode theo kích thước gốc: một ảnh 4000×3000 hiển thị trong thumbnail 100px vẫn chiếm khoảng 48MB bitmap, nên hãy truyền cacheWidth/cacheHeight (hoặc ResizeImage) để decode đúng kích thước hiển thị (nhân với devicePixelRatio). Image.network chỉ cache trong bộ nhớ (ImageCache, mặc định 1000 ảnh/100MB), nên dùng cached_network_image để có thêm cache trên disk, placeholder và không tải lại khi cuộn qua lại. Kết hợp ListView.builder để chỉ build item gần viewport, ưu tiên server trả thumbnail đúng kích thước, và kiểm tra bằng DevTools (tab Memory, tùy chọn highlight oversized images).

  2. Bản release Android đang nặng 60MB và PM yêu cầu giảm xuống dưới 30MB. Bạn phân tích kích thước app Flutter bằng --analyze-size và giảm bằng những cách nào?

    Xem đáp án mẫu
    Đo trước khi tối ưu: flutter build apk --analyze-size (hoặc appbundle, ios) tạo file phân tích kích thước theo package và thư viện, mở bằng công cụ App Size của DevTools để thấy phần nào lớn (engine, code Dart, asset, font, native library). Phần đầu tiên là cách phân phối: build appbundle (AAB) để Play phân phối APK theo ABI, mật độ màn hình và ngôn ngữ của từng máy; còn với APK phát trực tiếp thì dùng --split-per-abi. Giảm code: bỏ package không dùng hoặc trùng chức năng (mỗi package kéo theo cả dependency và native library), tránh kéo nguyên thư viện lớn khi chỉ dùng một phần, bật --obfuscate --split-debug-info để giảm kích thước symbol, và để --tree-shake-icons (mặc định ở release, lỗi nếu tạo IconData động không const) loại icon không dùng. Giảm tài nguyên: nén ảnh (WebP, AVIF), bỏ ảnh độ phân giải thừa, dùng SVG hoặc vẽ bằng code cho icon đơn giản, chỉ đóng gói các font và weight thật sự dùng (hoặc subset font), và tải tài nguyên lớn lúc chạy thay vì đóng gói. Với module ít dùng có thể dùng deferred components (Android) để tải theo yêu cầu. Cũng kiểm tra các native library lớn do plugin kéo vào (ML, video) và các ABI bạn phải hỗ trợ. Đặt ngân sách kích thước trong CI để cảnh báo khi một PR làm tăng nhiều, và nhớ so sánh kích thước tải xuống (download size ở store) chứ không chỉ kích thước cài đặt.
    flutter build appbundle --release --obfuscate --split-debug-info=build/symbols --analyze-size

  1. Viết widget test cho màn hình đăng nhập phụ thuộc AuthRepository như thế nào?

    Xem đáp án mẫu
    Inject repository qua constructor hoặc DI (override của Riverpod, BlocProvider) để thay bằng mock của mocktail, stub hàm trả Future bằng when(...).thenAnswer(...). Dùng pumpWidget với MaterialApp bọc ngoài (cung cấp Directionality, Navigator, theme), tương tác qua enterText/tap, rồi pump() để frame mới được build trước khi expect với find.text/find.byKey. Cuối cùng verify repository được gọi đúng tham số. Nếu UI có animation hoặc delay thì dùng pump(duration)/pumpAndSettle, nhưng nhớ pumpAndSettle sẽ timeout nếu có animation chạy vô hạn như CircularProgressIndicator.
    class MockAuthRepo extends Mock implements AuthRepository {}

testWidgets('hiện lỗi khi sai mật khẩu', (tester) async {
  final repo = MockAuthRepo();
  when(() => repo.login(any(), any()))
      .thenAnswer((_) async => throw const WrongPassword());
  await tester.pumpWidget(MaterialApp(home: LoginPage(repo: repo)));
  await tester.enterText(find.byKey(const Key('email')), 'a@b.com');
  await tester.enterText(find.byKey(const Key('password')), '123');
  await tester.tap(find.text('Đăng nhập'));
  await tester.pump();
  expect(find.text('Sai mật khẩu'), findsOneWidget);
  verify(() => repo.login('a@b.com', '123')).called(1);
});

  2. Làm sao unit test một provider/notifier của Riverpod mà không cần dựng widget?

    Xem đáp án mẫu
    Tạo ProviderContainer với overrides để thay dependency (repository, API client) bằng mock/fake, đọc provider qua container và addTearDown(container.dispose) để dọn dẹp sau test. Với AsyncNotifier, await container.read(provider.future) để chờ build() xong; với mutation, gọi container.read(provider.notifier).method() rồi kiểm tra container.read(provider). Muốn kiểm tra chuỗi state (loading → data), dùng container.listen để ghi lại từng giá trị. Trong widget test, override tương tự bằng ProviderScope(overrides: [...]).
    class MockTodoRepo extends Mock implements TodoRepo {}

test('load todos từ repository', () async {
  final repo = MockTodoRepo();
  when(() => repo.fetchAll()).thenAnswer((_) async => [const Todo('a')]);
  final container = ProviderContainer(
    overrides: [todoRepoProvider.overrideWithValue(repo)],
  );
  addTearDown(container.dispose);
  final todos = await container.read(todosProvider.future);
  expect(todos, hasLength(1));
  verify(() => repo.fetchAll()).called(1);
});

  3. Team muốn kiểm thử luồng 'đăng nhập, thêm vào giỏ, thanh toán' chạy trên thiết bị hoặc emulator. Viết integration_test thế nào, nó khác widget test ở đâu, và xử lý hộp thoại quyền của hệ điều hành cùng tính flaky ra sao?

    Xem đáp án mẫu
    integration_test chạy toàn bộ app (không phải một widget riêng) trên thiết bị hoặc emulator: khai báo trong dev_dependencies, đặt file ở integration_test/, bắt đầu bằng IntegrationTestWidgetsFlutterBinding.ensureInitialized(), gọi app.main() hoặc tester.pumpWidget(MyApp()), rồi dùng cùng API với widget test (find, tap, enterText, pumpAndSettle) và chạy bằng flutter test integration_test -d <device>. Khác widget test ở chỗ nó chạy trên engine và nền tảng thật (plugin thật, platform channel thật, hiệu năng thật) nên chậm và tốn kém hơn, chỉ nên phủ vài luồng sống còn. Để ổn định: tìm bằng Key hoặc find.bySemanticsLabel thay vì text dễ đổi; thay backend thật bằng server giả hoặc môi trường staging có dữ liệu cố định (qua dart-define hoặc DI override); pumpAndSettle có thể treo nếu có animation lặp vô hạn (spinner) nên dùng pump(duration) hoặc chờ theo điều kiện bằng vòng pump kèm timeout; reset state (đăng xuất, xoá DB) giữa các test. Hộp thoại quyền và UI native của hệ điều hành nằm ngoài Flutter nên integration_test không điều khiển được: dùng patrol (có native automation) hoặc cấp quyền trước bằng adb shell pm grant hay cấu hình simulator. Cũng có thể đo hiệu năng bằng binding.traceAction và chạy trên Firebase Test Lab hoặc device farm trong CI. Test flaky cần bị cách ly và có người sửa, không retry vô hạn.
    // integration_test/checkout_flow_test.dart
void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('đăng nhập, thêm vào giỏ và thanh toán thành công', (tester) async {
    app.main(); // chạy toàn bộ app, backend giả chọn qua dart-define
    await tester.pumpAndSettle();

    await tester.enterText(find.byKey(const Key('email')), 'an@example.com');
    await tester.enterText(find.byKey(const Key('password')), '123456');
    await tester.tap(find.byKey(const Key('login-button')));
    await tester.pumpAndSettle();

    await tester.tap(find.byKey(const Key('add-to-cart-1')));
    await tester.pump(const Duration(milliseconds: 500)); // không pumpAndSettle nếu có spinner lặp vô hạn

    await tester.tap(find.byKey(const Key('checkout-button')));
    await tester.pumpAndSettle();
    expect(find.text('Đặt hàng thành công'), findsOneWidget);
  });
}

  4. Vì sao nên có nhiều Unit test hơn Integration test?

    Xem đáp án mẫu
    Unit test chạy nhanh, ổn định, rẻ để maintain; Integration test chậm, dễ flaky và tốn chi phí CI hơn nhiều lần nên chỉ dùng cho các flow quan trọng nhất.

  5. pump() và pumpAndSettle() khác nhau thế nào?

    Xem đáp án mẫu
    pump() chỉ render đúng một frame hoặc sau một khoảng duration chỉ định; pumpAndSettle() pump liên tục cho tới khi không còn frame nào được lên lịch nữa.

  6. Mockito và Mocktail khác nhau cơ bản ở điểm nào?

    Xem đáp án mẫu
    Mockito cần code generation qua build_runner để tạo Mock class; Mocktail dùng thuần Dart dựa vào null safety, không cần code gen, đơn giản hoá setup.

  7. verify() khác when() ở điểm nào?

    Xem đáp án mẫu
    when() định nghĩa hành vi giả lập khi một method được gọi; verify() kiểm tra sau khi code chạy xong, xác nhận method đó có thực sự được gọi hay không và gọi bao nhiêu lần.

  8. Làm sao test một Bloc hiệu quả? Package nào thường dùng?

    Xem đáp án mẫu
    Dùng package bloc_test, định nghĩa build để khởi tạo bloc, act để bắn event vào, và expect để liệt kê danh sách state mong đợi phát ra theo đúng thứ tự.

  9. Kiểm tra kết quả của một hàm trả về Stream trong package test bằng cách nào?

    Xem đáp án mẫu
    Dùng matcher emitsInOrder([...]) kết hợp expectLater(stream, ...) để assert thứ tự và giá trị các sự kiện phát ra.

  10. 'Flavor' trong Flutter dùng để làm gì?

    Xem đáp án mẫu
    Cho phép build nhiều biến thể app như dev, staging, production từ cùng một codebase với config khác nhau, mà không cần maintain nhiều project riêng.
