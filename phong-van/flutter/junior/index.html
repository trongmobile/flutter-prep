  1. Vì sao sau khi kiểm tra if (user.name != null) mà truy cập user.name.length vẫn bị lỗi compile? Xử lý thế nào?

    Xem đáp án mẫu
    Type promotion chỉ áp dụng khi compiler chắc chắn giá trị không đổi giữa lúc kiểm tra và lúc dùng: biến local, và từ Dart 3.2 có thêm field vừa private vừa final. Field public hoặc không final có thể bị subclass override bằng getter hoặc bị code khác gán lại, nên không được promote. Cách xử lý chuẩn là copy ra biến local (hoặc dùng pattern if (user.name case final name?)) thay vì rải ! khắp nơi.
    class User {
  String? name;
}

void printLength(User user) {
  final name = user.name; // copy ra biến local
  if (name != null) {
    print(name.length); // name đã được promote thành String
  }
}

  2. Với Map<String, int> stock, vì sao stock['pear'] có kiểu int? chứ không phải int? Còn gọi list.first trên list rỗng thì sao?

    Xem đáp án mẫu
    Toán tử [] của Map trả về V? vì key có thể không tồn tại, nên null safety buộc bạn xử lý trường hợp thiếu: stock['pear'] ?? 0, kiểm tra null, hoặc dùng ! khi chắc chắn key có. Ngược lại list.first, list.single, list[i] có kiểu non-nullable nhưng ném lỗi runtime (StateError: No element, RangeError) khi list rỗng hoặc sai index. Từ Dart 3 có sẵn firstOrNull, lastOrNull, elementAtOrNull để nhận về null thay vì exception.
    final Map<String, int> stock = {'apple': 3};
final int pears = stock['pear'] ?? 0; // [] trả về int?

final List<int> empty = [];
print(empty.firstOrNull); // null
print(empty.first); // StateError: Bad state: No element

  3. Khi nào nên viết getter/setter trong Dart thay vì để field public? Viết getter/setter chỉ để bọc một field private có cần không?

    Xem đáp án mẫu
    Trong Dart, field public đã tự có getter/setter ngầm định, nên viết cặp getter/setter chỉ để đọc/ghi thẳng một field private là thừa (lint unnecessary_getters_setters sẽ nhắc). Getter/setter có ích khi giá trị được tính toán (int get total), khi cần kiểm tra dữ liệu trước khi gán, hoặc khi muốn bên ngoài chỉ đọc còn bên trong mới sửa được (int get count => _count;). Vì cú pháp gọi giống hệt field, sau này đổi field thành getter không làm hỏng code đang dùng nó.
    class Cart {
  final List<int> _prices = [];
  int _discount = 0;

  int get total => _prices.fold(0, (sum, p) => sum + p) - _discount;

  int get discount => _discount;
  set discount(int value) {
    if (value < 0) throw ArgumentError.value(value, 'discount');
    _discount = value;
  }
}

  4. Khi khai báo mixin, từ khoá on dùng để làm gì? Cho ví dụ trong Flutter.

    Xem đáp án mẫu
    on giới hạn mixin chỉ được dùng cho class là subtype của một kiểu nhất định; đổi lại, bên trong mixin được gọi các member của kiểu đó như setState, mounted, super.dispose(). Ví dụ quen thuộc là SingleTickerProviderStateMixin được khai báo on State<T> nên chỉ dùng được trong State. Bạn có thể tự viết mixin như LoadingMixin bên dưới rồi dùng class _LoginPageState extends State<LoginPage> with LoadingMixin để tái sử dụng logic loading cho nhiều màn hình. Từ Dart 3, chỉ những gì khai báo bằng mixin (hoặc mixin class) mới dùng được sau with.
    mixin LoadingMixin<T extends StatefulWidget> on State<T> {
  bool isLoading = false;

  Future<void> runWithLoading(Future<void> Function() task) async {
    setState(() => isLoading = true);
    try {
      await task();
    } finally {
      if (mounted) setState(() => isLoading = false);
    }
  }
}

  5. factory constructor khác constructor thường (generative) ở điểm nào? Cho ví dụ dùng thực tế.

    Xem đáp án mẫu
    Generative constructor luôn tạo một instance mới của chính class đó; factory thì không bắt buộc: nó có thể trả về instance đã cache (singleton), instance của một subclass, hoặc chạy logic trước rồi gọi constructor khác. Vì chưa có object nào được tạo sẵn nên trong factory không dùng được this và initializer list. Ví dụ thực tế hay gặp nhất là factory User.fromJson(...); còn named constructor như User.guest() chỉ là cách đặt tên nhiều constructor vì Dart không có overloading.
    class User {
  final String name;
  User(this.name);

  // named constructor
  User.guest() : name = 'Khách';

  // factory: có logic xử lý trước khi tạo object
  factory User.fromJson(Map<String, dynamic> json) {
    return User(json['name'] as String);
  }
}

  6. Vì sao khi override operator == thì bắt buộc phải override cả hashCode?

    Xem đáp án mẫu
    Quy ước của Dart: hai object bằng nhau theo == phải có cùng hashCode. Set, Map (key) tìm phần tử bằng hashCode trước rồi mới so ==, nên nếu chỉ override == thì set.contains(Point(1, 2)) có thể trả về false dù trong set có object bằng nó. Dùng Object.hash(...) để tính hash từ đúng các field tham gia so sánh, hoặc dùng package equatable/freezed; record của Dart 3 thì đã so sánh theo giá trị sẵn.
    class Point {
  final int x, y;
  const Point(this.x, this.y);

  @override
  bool operator ==(Object other) =>
      other is Point && other.x == x && other.y == y;

  @override
  int get hashCode => Object.hash(x, y);
}

  7. flutter pub get và flutter pub upgrade khác nhau thế nào? Vì sao nên commit pubspec.lock của app?

    Xem đáp án mẫu
    pub get tôn trọng pubspec.lock: package nào đã có trong lock thì giữ đúng phiên bản đó, chỉ resolve phần mới thêm hoặc vừa đổi constraint. pub upgrade bỏ qua lock, chọn bản mới nhất thoả constraint trong pubspec.yaml rồi ghi lại lock. Commit pubspec.lock giúp cả team và CI build ra cùng một bộ dependency, tránh kiểu "máy tôi chạy được"; muốn biết có bản mới hơn (kể cả major) thì dùng flutter pub outdated.

  8. late keyword dùng để làm gì? Rủi ro khi dùng late là gì?

    Xem đáp án mẫu
    Cho phép khai báo biến non-nullable nhưng khởi tạo trễ (lazy hoặc gán sau). Rủi ro: LateInitializationError nếu code truy cập biến trước khi nó được gán giá trị.

  9. Sound null safety trong Dart nghĩa là gì?

    Xem đáp án mẫu
    Compiler đảm bảo 100% một biến non-nullable (String) không bao giờ null tại runtime, khác với kiểu chỉ gợi ý như TypeScript. Biến nullable phải khai báo rõ bằng String?.

  10. Extension method trong Dart là gì? Cho một ví dụ thực tế.

    Xem đáp án mẫu
    Cho phép thêm method vào một class có sẵn (kể cả class từ package ngoài) mà không cần kế thừa. Ví dụ: thêm context.push() cho BuildContext để rút gọn cú pháp điều hướng.

  11. late final khác gì so với chỉ final?

    Xem đáp án mẫu
    final phải gán ngay khi khai báo hoặc trong constructor; late final cho phép trì hoãn gán giá trị, miễn là gán đúng một lần trước khi dùng.

Async & Isolate

Mọi rank →

  1. Khi xử lý lỗi trong Dart, on, catch (e, st), rethrow và finally khác nhau thế nào?

    Xem đáp án mẫu
    on FormatException bắt theo kiểu lỗi (viết on X catch (e) nếu cần object lỗi), nên đặt các nhánh cụ thể trước nhánh catch chung. catch (e, st) lấy thêm stack trace để log hoặc gửi lên hệ thống crash report; rethrow ném lại lỗi đang bắt và giữ nguyên stack trace gốc, còn throw e tạo stack trace mới tại chỗ ném lại. finally luôn chạy dù thành công hay lỗi, hợp để tắt loading. Với code async, tất cả chỉ có tác dụng khi lời gọi trong try được await.
    Future<User> loadUser() async {
  try {
    return await api.fetchUser();
  } on TimeoutException {
    throw AppException('Mạng chậm, thử lại sau');
  } catch (e, st) {
    logger.error('loadUser failed', e, st);
    rethrow;
  } finally {
    _loading = false;
  }
}

  2. Khi tự listen một Stream trong State, vì sao phải giữ lại StreamSubscription và cancel() nó?

    Xem đáp án mẫu
    Subscription vẫn sống sau khi widget bị gỡ khỏi cây; nếu không cancel, callback tiếp tục chạy, gọi setState() trên State đã dispose (gây lỗi) và giữ tham chiếu khiến State không được giải phóng (memory leak). Cách chuẩn là lưu subscription khi listen trong initState và gọi cancel() trong dispose() trước super.dispose(). Nếu chỉ cần hiển thị dữ liệu từ stream thì dùng StreamBuilder, nó tự quản lý subscription.
    late final StreamSubscription<int> _sub;
@override
void initState() {
  super.initState();
  _sub = ticker.stream.listen((v) => setState(() => _value = v));
}

@override
void dispose() {
  _sub.cancel();
  super.dispose();
}

  3. Trong FutureBuilder, bạn xử lý các trạng thái loading, lỗi và có dữ liệu thế nào cho đúng?

    Xem đáp án mẫu
    Dựa vào AsyncSnapshot: connectionState cho biết đang chờ (waiting) hay đã xong (done), hasError/error cho lỗi, hasData/data cho kết quả. Nên kiểm tra lỗi trước, vì nếu chỉ viết if (!snapshot.hasData) return loading thì khi API lỗi màn hình sẽ quay loading mãi. Lưu ý hasData chỉ là data != null, nên Future trả về null một cách hợp lệ cũng bị coi là chưa có dữ liệu.
    FutureBuilder<User>(
  future: _userFuture, // tạo một lần trong initState
  builder: (context, snapshot) {
    if (snapshot.connectionState != ConnectionState.done) {
      return const CircularProgressIndicator();
    }
    if (snapshot.hasError) return Text('Lỗi: ${snapshot.error}');
    if (!snapshot.hasData) return const Text('Không có dữ liệu');
    return Text(snapshot.data!.name);
  },
)

  4. Làm sao đặt timeout cho một request và xử lý khi quá thời gian?

    Xem đáp án mẫu
    Dùng future.timeout(Duration(...)): nếu Future chưa xong trong khoảng đó, nó hoàn thành với TimeoutException (từ dart:async), hoặc trả giá trị dự phòng nếu truyền onTimeout. Cần biết timeout chỉ ngừng chờ chứ không huỷ thao tác gốc, request vẫn có thể tiếp tục chạy ở nền. Với dio có thể cấu hình sẵn connectTimeout/receiveTimeout trong BaseOptions thay vì bọc từng lời gọi.
    try {
  final res = await http
      .get(Uri.parse(url))
      .timeout(const Duration(seconds: 10));
  handle(res);
} on TimeoutException {
  showError('Mạng chậm, vui lòng thử lại');
}

  5. Future và Stream khác nhau cơ bản ở điểm nào?

    Xem đáp án mẫu
    Future trả về đúng một giá trị (hoặc lỗi) trong tương lai; Stream trả về nhiều giá trị liên tiếp theo thời gian.

  6. Điều gì xảy ra nếu bạn không await một Future bên trong hàm async?

    Xem đáp án mẫu
    Hàm tiếp tục chạy ngay, không đợi Future hoàn thành, dễ gây race condition vì code phía sau chạy trước khi Future thực sự resolve.

  7. Future.wait dùng khi nào? Nếu một Future trong danh sách lỗi thì sao?

    Xem đáp án mẫu
    Dùng khi cần chạy song song nhiều Future và đợi tất cả hoàn tất. Mặc định (eagerError: false) nó vẫn đợi mọi Future xong rồi mới complete với lỗi đầu tiên, các lỗi sau bị bỏ qua; truyền eagerError: true để reject ngay khi có lỗi đầu tiên.

  8. Khi nào nên dùng compute()?

    Xem đáp án mẫu
    Khi cần xử lý tác vụ nặng CPU-bound (parse JSON lớn, xử lý ảnh) mà không muốn block UI thread — compute() chạy việc đó trên một isolate riêng rồi trả kết quả về.

Widget & Lifecycle

Mọi rank →

  1. Tạo AnimationController trong một StatefulWidget cần những gì? Vì sao cần vsync và phải dispose?

    Xem đáp án mẫu
    State cần with SingleTickerProviderStateMixin (hoặc TickerProviderStateMixin nếu có nhiều controller) để truyền vsync: this; controller được tạo trong initState và giải phóng trong dispose() trước super.dispose(). vsync gắn controller với một Ticker bị tạm dừng khi widget không hiển thị (ví dụ màn hình đang bị route khác che), tránh tốn CPU và pin cho animation không ai thấy. Quên dispose khi ticker còn chạy sẽ gặp lỗi ... was disposed with an active Ticker và rò rỉ tài nguyên.
    // trong State<Pulse> with SingleTickerProviderStateMixin
late final AnimationController _controller;
@override
void initState() {
  super.initState();
  _controller = AnimationController(vsync: this, duration: const Duration(seconds: 1));
}
@override
void dispose() {
  _controller.dispose();
  super.dispose();
}

  2. Validate form bằng Form, TextFormField và GlobalKey<FormState> hoạt động thế nào?

    Xem đáp án mẫu
    Bọc các TextFormField trong một Form có key là GlobalKey<FormState> được tạo một lần trong State; mỗi field có validator trả về chuỗi lỗi nếu sai và null nếu hợp lệ. Khi bấm submit, gọi _formKey.currentState!.validate(): nó chạy mọi validator, hiện lỗi dưới từng field và trả về true nếu tất cả hợp lệ; sau đó có thể gọi save() để kích hoạt các onSaved. Muốn báo lỗi ngay khi người dùng tương tác thì đặt autovalidateMode: AutovalidateMode.onUserInteraction.
    final _formKey = GlobalKey<FormState>();

Form(
  key: _formKey,
  child: TextFormField(
    validator: (v) => (v == null || v.isEmpty) ? 'Bắt buộc' : null,
  ),
)

// trong onPressed của nút Gửi:
if (_formKey.currentState!.validate()) submit();

  3. Vì sao gọi Scaffold.of(context) bằng chính context của hàm build tạo ra Scaffold lại báo lỗi không tìm thấy Scaffold?

    Xem đáp án mẫu
    Các hàm dạng X.of(context) tìm ngược lên các widget tổ tiên của context. context trong build thuộc về widget đang tạo ra Scaffold, tức là nằm phía trên Scaffold, nên tìm lên sẽ không thấy. Cách sửa: bọc phần cần dùng trong Builder để có context nằm dưới Scaffold, hoặc tách thành widget con riêng. Riêng hiển thị SnackBar thì dùng ScaffoldMessenger.of(context), vì MaterialApp đã tạo sẵn một ScaffoldMessenger ở phía trên.
    @override
Widget build(BuildContext context) {
  return Scaffold(
    drawer: const Drawer(),
    body: Builder(
      builder: (innerContext) => TextButton(
        onPressed: () => Scaffold.of(innerContext).openDrawer(),
        child: const Text('Mở menu'),
      ),
    ),
  );
}

  4. Tách một phần UI thành class widget riêng hay viết hàm _buildHeader() trả về Widget: hai cách khác nhau thế nào?

    Xem đáp án mẫu
    Hàm helper chỉ là cắt code cho dễ đọc: nó chạy lại mỗi khi widget cha build, dùng chung context của cha và không thể là const. Class widget riêng có Element và BuildContext của riêng nó, có thể khai báo const để Flutter bỏ qua việc rebuild khi cha rebuild, và nếu là StatefulWidget thì setState chỉ rebuild riêng phần đó. Vì vậy phần UI lớn, cần tái sử dụng hoặc có state riêng thì nên tách thành widget; helper method chỉ hợp cho đoạn nhỏ, đơn giản.
    // Helper method: luôn build lại cùng widget cha
Widget _buildHeader() => Text('Xin chào $name');

// Widget riêng: có thể const, có context riêng
class Header extends StatelessWidget {
  const Header({super.key});

  @override
  Widget build(BuildContext context) =>
      Text('Xin chào', style: Theme.of(context).textTheme.titleLarge);
}

  5. StatelessWidget vẫn có thể rebuild không? Khi nào?

    Xem đáp án mẫu
    Có. Rebuild khi parent rebuild và tạo widget mới, hoặc khi một InheritedWidget mà nó phụ thuộc thay đổi giá trị.

  6. Thứ tự các lifecycle method khi StatefulWidget được tạo lần đầu?

    Xem đáp án mẫu
    createState() → initState() → didChangeDependencies() → build().

  7. Quên gọi super.dispose() gây hậu quả gì?

    Xem đáp án mẫu
    Có thể gây memory leak hoặc lỗi, vì framework cần super.dispose() để dọn dẹp internal state của đối tượng State.

  8. Key dùng để giải quyết vấn đề gì?

    Xem đáp án mẫu
    Giúp Flutter phân biệt các widget cùng type ở cùng cấp khi thứ tự thay đổi (ví dụ list bị reorder), tránh việc Flutter match nhầm state giữa các widget.

Layout & Rendering

Mọi rank →

  1. MediaQuery.sizeOf(context) và LayoutBuilder khác nhau thế nào khi làm giao diện responsive?

    Xem đáp án mẫu
    MediaQuery.sizeOf trả về kích thước của cả cửa sổ ứng dụng, hợp với quyết định ở cấp màn hình như hiện NavigationRail hay NavigationBar. LayoutBuilder đưa ra constraints mà widget cha thực sự cấp cho widget đó, nên hợp với component tái sử dụng (một card đặt trong cột hẹp hay full màn hình đều tự đổi bố cục). Nên dùng MediaQuery.sizeOf(context) thay vì MediaQuery.of(context).size vì nó chỉ rebuild khi kích thước đổi, không rebuild khi các giá trị khác như viewInsets lúc bật bàn phím thay đổi.
    LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth >= 600) {
      return const TwoColumnLayout();
    }
    return const SingleColumnLayout();
  },
)

  2. GridView.count, GridView.extent và GridView.builder khác nhau thế nào? childAspectRatio dùng để làm gì?

    Xem đáp án mẫu
    GridView.count cố định số cột, GridView.extent cố định độ rộng tối đa của mỗi ô (số cột tự tăng theo bề rộng); cả hai nhận sẵn list children nên hợp với số item ít. GridView.builder nhận gridDelegate cùng itemBuilder và chỉ build các ô sắp hiển thị, nên dùng cho danh sách dài hoặc dữ liệu từ API. Kích thước ô do delegate quyết định: với grid cuộn dọc, childAspectRatio (mặc định 1.0) là tỉ lệ rộng/cao của ô, nội dung cao hơn sẽ bị overflow; khi đó chỉnh lại tỉ lệ hoặc dùng mainAxisExtent để cố định chiều cao ô.
    GridView.builder(
  gridDelegate: const SliverGridDelegateWithFixedCrossAxisCount(
    crossAxisCount: 2,
    childAspectRatio: 3 / 4, // rộng : cao
    mainAxisSpacing: 8,
    crossAxisSpacing: 8,
  ),
  itemCount: products.length,
  itemBuilder: (context, i) => ProductCard(product: products[i]),
)

  1. ChangeNotifierProvider(create: ...) và ChangeNotifierProvider.value(...) khác nhau thế nào? Dùng sai gây hậu quả gì?

    Xem đáp án mẫu
    create để Provider tự tạo object một lần và tự gọi dispose() khi provider bị gỡ khỏi cây, dùng khi khởi tạo một notifier mới. .value chỉ đưa một object đã tồn tại xuống cây và không dispose nó, hợp khi truyền một item có sẵn trong list hoặc chuyển notifier sang route mới. Viết .value(value: CartModel()) trong build sẽ tạo instance mới mỗi lần rebuild, làm mất state và không ai dispose; ngược lại dùng create cho object đang do nơi khác quản lý thì nó bị dispose sớm.
    // Provider tự tạo và tự dispose
ChangeNotifierProvider(
  create: (_) => CartModel(),
  child: const CartPage(),
)

// Đưa object có sẵn xuống, Provider KHÔNG dispose
ChangeNotifierProvider.value(
  value: products[index],
  child: const ProductTile(),
)

  2. Làm sao quyết định một state nên để cục bộ bằng setState hay đưa lên Provider?

    Xem đáp án mẫu
    Tài liệu Flutter chia thành ephemeral state (chỉ một widget cần, như tab đang chọn, card đang mở rộng, tiến trình animation) và app state (nhiều màn hình cần hoặc cần giữ lâu, như user đăng nhập, giỏ hàng). Ephemeral state cứ để trong StatefulWidget với setState cho gọn; app state nên đưa lên Provider/ChangeNotifier để chia sẻ mà không phải truyền qua nhiều tầng constructor. Dấu hiệu cần nâng lên là bạn bắt đầu truyền dữ liệu và callback qua nhiều tầng widget chỉ để hai nơi đồng bộ với nhau.

  3. Trong một ChangeNotifier, vì sao nên expose danh sách qua getter trả về UnmodifiableListView thay vì để public List?

    Xem đáp án mẫu
    Nếu để public List, widget có thể gọi model.items.add(...) trực tiếp: dữ liệu đổi nhưng không ai gọi notifyListeners(), UI không cập nhật và lỗi rất khó tìm. Giữ list private (_items) và expose qua UnmodifiableListView (từ dart:collection) buộc mọi thay đổi đi qua method của model, nơi luôn gọi notifyListeners(). Cách này cũng gom logic nghiệp vụ như kiểm tra trùng hay tính tổng về một chỗ.
    class CartModel extends ChangeNotifier {
  final List<Item> _items = [];

  UnmodifiableListView<Item> get items => UnmodifiableListView(_items);

  void add(Item item) {
    _items.add(item);
    notifyListeners();
  }
}

  4. Gọi setState() ngay bên trong build() gây vấn đề gì?

    Xem đáp án mẫu
    Gây vòng lặp rebuild vô hạn (build → setState → schedule rebuild → build lại) và Flutter sẽ throw assertion error ở debug mode.

  5. Vì sao setState chỉ rebuild widget đó và con của nó chứ không toàn bộ app?

    Xem đáp án mẫu
    Vì setState chỉ đánh dấu Element của State đó là dirty, Flutter chỉ rebuild subtree bắt đầu từ Element đó xuống.

  6. Consumer và context.watch() khác nhau ở phạm vi rebuild?

    Xem đáp án mẫu
    Consumer giới hạn phạm vi rebuild chỉ trong builder của nó; context.watch() gọi trong build() khiến toàn bộ widget đó rebuild khi giá trị đổi.

  7. Vì sao không nên gọi context.watch() bên trong callback như onPressed?

    Xem đáp án mẫu
    Vì watch đăng ký subscription trong quá trình build; dùng trong callback dễ gây lỗi hoặc không có tác dụng, nên dùng context.read() trong callback thay thế.

  2. Với go_router, context.go() và context.push() khác nhau thế nào?

  3. Làm sao chặn thao tác back khi form chưa lưu và hỏi xác nhận người dùng?

Việc phải quyết định trước bằng canPop (thay vì callback trả về bool như WillPopScope) là để hỗ trợ predictive back của Android.
    PopScope(
  canPop: !_hasUnsavedChanges,
  onPopInvokedWithResult: (didPop, result) async {
    if (didPop) return;
    final leave = await showDialog<bool>(
      context: context,
      builder: (_) => const ConfirmLeaveDialog(),
    );
    if (leave == true && context.mounted) Navigator.pop(context);
  },
  child: const EditForm(),

  1. Khi nào nên dùng json_serializable thay vì tự viết fromJson/toJson? Cần thiết lập những gì?

    Xem đáp án mẫu
    Tự viết ổn với vài model nhỏ, nhưng khi model nhiều và lồng nhau thì rất dễ gõ sai key hoặc cast sai kiểu; json_serializable sinh code từ annotation nên an toàn và đồng bộ hơn. Thiết lập: thêm json_annotation vào dependencies, json_serializable và build_runner vào dev_dependencies; đánh dấu class bằng @JsonSerializable(), khai báo part 'user.g.dart'; và hai hàm trỏ tới _$UserFromJson/_$UserToJson, rồi chạy dart run build_runner build. Dùng @JsonKey(name: 'full_name') khi tên key trong JSON khác tên field Dart.
    part 'user.g.dart';

@JsonSerializable()
class User {
  final int id;
  @JsonKey(name: 'full_name')
  final String fullName;
  User({required this.id, required this.fullName});
  factory User.fromJson(Map<String, dynamic> json) => _$UserFromJson(json);
  Map<String, dynamic> toJson() => _$UserToJson(this);
}

  2. Dùng package http, khi server trả 404 hoặc 500 thì http.get có ném exception không? Nên xử lý thế nào?

    Xem đáp án mẫu
    Không. http chỉ ném lỗi khi có sự cố ở tầng kết nối (mất mạng, không phân giải được tên miền…), còn mọi HTTP status đều trả về Response bình thường, nên phải tự kiểm tra response.statusCode trước khi jsonDecode body. Thường gom việc này vào một lớp API client: 2xx thì parse, còn lại ném một exception tự định nghĩa (ví dụ ApiException) chứa status và message để UI hiển thị phù hợp. Ngược lại, dio mặc định coi status ngoài 2xx là lỗi và ném DioException, có thể đổi qua validateStatus.
    final res = await http.get(Uri.parse('$baseUrl/users/1'));
if (res.statusCode == 200) {
  return User.fromJson(jsonDecode(res.body) as Map<String, dynamic>);
}
throw ApiException(res.statusCode, res.body);

  3. API trả về một mảng JSON. Parse thành List<User> thế nào cho đúng kiểu, và lỗi kiểu nào hay gặp?

    Xem đáp án mẫu
    jsonDecode trả về dynamic, thực chất là List<dynamic> chứa các Map<String, dynamic>; cần cast về List, map từng phần tử qua User.fromJson rồi gọi toList(). Lỗi hay gặp là gán thẳng List<User> users = jsonDecode(body) hay List<String> tags = json['tags'], gây lỗi runtime type 'List<dynamic>' is not a subtype of type ...; với list kiểu cơ bản dùng List<String>.from(...) hoặc .cast<String>(). Quên toList() thì nhận về Iterable lazy, mỗi lần duyệt lại sẽ parse lại từ đầu.
    Future<List<User>> fetchUsers() async {
  final res = await http.get(Uri.parse('$baseUrl/users'));
  final list = jsonDecode(res.body) as List<dynamic>;
  return list
      .map((e) => User.fromJson(e as Map<String, dynamic>))
      .toList();
}

  4. Khi nào dùng shared_preferences trong Flutter? Cách đọc, ghi thế nào, và những giới hạn cần nhớ (bất đồng bộ, kiểu dữ liệu, không dùng cho dữ liệu nhạy cảm hay dữ liệu lớn)?

    Xem đáp án mẫu
    shared_preferences lưu các cặp key–value nhỏ và bền sau khi tắt app (UserDefaults trên iOS, SharedPreferences trên Android), hợp với cài đặt đơn giản như theme, ngôn ngữ, cờ đã xem onboarding. Lấy instance bằng await SharedPreferences.getInstance() (bất đồng bộ, nên khởi tạo một lần ở main() hoặc qua DI rồi tái sử dụng), sau đó dùng getBool, getString, getInt, getDouble, getStringList (trả null nếu chưa có nên kèm ?? giáTrịMặcĐịnh) và các hàm setX (trả Future<bool>, cần await nếu muốn chắc đã ghi xong). Chỉ hỗ trợ kiểu nguyên thuỷ và List<String>; object phức tạp phải tự jsonEncode, và bạn chịu trách nhiệm migrate khi đổi cấu trúc. Giới hạn: không mã hoá nên không lưu token hay mật khẩu (dùng flutter_secure_storage), không dành cho dữ liệu lớn hay cần truy vấn (dùng SQLite, Drift hoặc Isar), và ghi từ nhiều isolate cần cẩn thận vì mỗi isolate có bản cache riêng (dùng reload(), hoặc API SharedPreferencesAsync mới hơn của package). Khi test, dùng SharedPreferences.setMockInitialValues({...}) để đặt dữ liệu giả.
    class SettingsRepository {
  SettingsRepository(this._prefs);
  final SharedPreferences _prefs; // lấy instance một lần rồi truyền vào

  bool get seenOnboarding => _prefs.getBool('seen_onboarding') ?? false;
  Future<void> markOnboardingSeen() => _prefs.setBool('seen_onboarding', true);

  ThemeMode get themeMode =>
      ThemeMode.values.byName(_prefs.getString('theme_mode') ?? 'system');
  Future<void> setThemeMode(ThemeMode mode) => _prefs.setString('theme_mode', mode.name);
}

  final prefs = await SharedPreferences.getInstance();
  runApp(MyApp(settings: SettingsRepository(prefs)));
}
