  1. Công ty có app Android (Kotlin) và iOS (Swift), logic nghiệp vụ hai bên hay lệch nhau (tính giá, validate, mô hình dữ liệu). CTO hỏi có nên dùng Kotlin Multiplatform (KMP). Bạn đánh giá và triển khai thử thế nào?

    Xem đáp án mẫu
    KMP chia sẻ code Kotlin giữa các nền tảng nhưng vẫn giữ UI native (hoặc dùng Compose Multiplatform nếu muốn chia sẻ cả UI), nên là cách giảm trùng logic mà không bỏ native. Tôi bắt đầu từ vấn đề cần giải: logic lệch hay tốc độ ra tính năng; rồi xét kỹ năng của team (dev iOS có chịu đọc Kotlin không, ai review code chung) và hệ sinh thái thư viện (Ktor, kotlinx.serialization, kotlinx-datetime, SQLDelight hoặc Room bản KMP, Koin). Chia sẻ dần từ dưới lên: module shared chứa domain, repository và network; UI vẫn là Compose/SwiftUI; phần phụ thuộc nền tảng (keychain, file, analytics) khai báo bằng interface do mỗi bên cài đặt hoặc expect/actual. Phía iOS nhận XCFramework qua SPM hoặc CocoaPods. Điểm đau cần biết: Kotlin được bridge qua Objective-C nên generic, sealed class và suspend/Flow mất ngữ nghĩa ở Swift (cần SKIE hoặc lớp bọc), build phải qua cả Gradle lẫn Xcode nên chậm hơn, debug xuyên ngôn ngữ khó hơn, và phụ thuộc vào công cụ của JetBrains. Triển khai thử: chọn một module ít UI nhưng logic phức tạp (tính giá, validate), đặt tiêu chí đo được (thời gian làm tính năng, số bug lệch hai nền tảng, kích thước binary, phản hồi của dev iOS) và tiêu chí dừng. Không migrate code cũ hàng loạt: giữ nguyên, chỉ viết tính năng mới trên shared.

  2. Màn hình feed vẫn giật dù đã tối ưu layout; Memory Profiler cho thấy hàng chục nghìn object ngắn hạn mỗi giây sinh ra trong onBindViewHolder và hàm onDraw tuỳ biến, trong khi code Kotlin nhìn rất gọn. Những allocation ẩn nào trong Kotlin hay gặp, và bạn kiểm tra thế nào?

    Xem đáp án mẫu
    Cú pháp gọn của Kotlin che nhiều allocation. (1) Lambda bắt biến (capture) tạo một object mới mỗi lần biểu thức được đánh giá nếu hàm nhận lambda không inline; lambda không bắt gì thì chỉ tạo một lần. Hàm inline như map, filter, forEach không tạo object cho lambda nhưng map/filter vẫn tạo list trung gian. (2) Boxing: Int?, List<Int>, Map<String, Long> và mọi tham số kiểu generic đều dùng Integer/Long, ngoài vùng cache -128..127 là object mới; hot path nên dùng IntArray, LongArray, SparseArray. (3) vararg tạo mảng mới mỗi lần gọi, spread *array còn copy mảng. (4) for (i in 0 until n) hoặc list.indices được biên dịch thành vòng lặp thường, nhưng for (x in list) tạo Iterator. (5) Sequence tạo thêm object cho từng bước, đáng dùng cho dữ liệu lớn hoặc khi có first/take dừng sớm, còn list nhỏ thì thường chậm hơn. (6) String template, Pair/Triple, copy() của data class, Regex(...) trong vòng lặp. (7) @JvmInline value class không cấp phát khi dùng như kiểu non-null cụ thể, nhưng bị box khi là nullable, nằm trong generic (List<UserId>) hoặc dùng như kiểu interface. Kiểm tra: Tools > Kotlin > Show Kotlin Bytecode rồi Decompile để tìm new, Integer.valueOf, iterator(); dùng allocation tracking để biết object nào sinh ra nhiều nhất. Chỉ tối ưu hot path (onDraw, onBindViewHolder, measure/layout, code chạy mỗi frame) và đo lại sau khi sửa, đừng làm xấu code ở chỗ không nóng.

  1. Giải thích cách ART thực thi code của app hiện nay (interpreter, JIT, AOT). Vì sao vài lần mở đầu sau khi cài hoặc cập nhật thường chậm hơn, và Baseline Profile giải quyết việc đó ra sao?

    Xem đáp án mẫu
    Dalvik chủ yếu thông dịch bytecode, từ Android 2.2 có thêm JIT. ART ở Android 5–6 AOT-compile toàn bộ app bằng dex2oat lúc cài, nên cài lâu và tốn dung lượng. Từ Android 7, ART dùng mô hình lai: mới cài thì code chạy bằng interpreter + JIT, JIT ghi các method nóng vào profile, rồi khi máy rảnh và đang sạc, hệ thống AOT-compile những method đó (profile-guided compilation). Vì vậy những lần mở đầu sau khi cài hoặc update chưa có code AOT nên chậm hơn và dễ jank. Baseline Profile là danh sách class/method quan trọng ship sẵn trong APK/AAB; khi cài qua Play, ART dùng nó để AOT-compile các đường code đó ngay, không phải đợi JIT tích luỹ profile. Cloud Profile của Play có tác dụng tương tự nhưng chỉ có sau khi bản phát hành đã có đủ người dùng, còn Baseline Profile phủ ngay từ ngày đầu.

  2. Đoạn double-checked locking sau có lỗi gì theo Java Memory Model? Sửa thế nào, và trong Kotlin bạn viết ra sao?

    Xem đáp án mẫu
    Lần đọc instance đầu tiên nằm ngoài synchronized, nên giữa thread khởi tạo và thread đọc không có quan hệ happens-before. Compiler và CPU được phép sắp xếp lại lệnh: việc gán reference vào instance có thể được thread khác nhìn thấy trước các lệnh ghi field trong constructor, nên thread đó thấy instance != null nhưng đọc phải object khởi tạo dở (với các field không final). Sửa bằng cách khai báo private static volatile Config instance;: lần ghi volatile happens-before mọi lần đọc volatile sau đó, nên mọi ghi trong constructor đều được nhìn thấy đầy đủ. Cách khác là holder idiom, dựa vào việc khởi tạo class của JVM vốn đã thread-safe. Trong Kotlin không cần tự viết: object hoặc by lazy (mặc định LazyThreadSafetyMode.SYNCHRONIZED) đã xử lý đúng.
    public class Config {
    private static Config instance; // thiếu volatile

    public static Config get() {
        if (instance == null) {                 // đọc không có lock
            synchronized (Config.class) {
                if (instance == null) {
                    instance = new Config();
                }
            }
        }
        return instance;
    }
}

  3. Main thread của Android vận hành thế nào với Looper, MessageQueue và Handler? Vì sao postDelayed với anonymous class hoặc lambda dễ gây leak Activity?

    Xem đáp án mẫu
    Mỗi thread có tối đa một Looper; Looper.loop() lặp liên tục lấy Message từ MessageQueue (sắp theo thời điểm when) rồi giao cho Handler của message đó xử lý. ActivityThread chuẩn bị sẵn Looper cho main thread, và callback lifecycle, sự kiện input hay frame của Choreographer đều là message trên cùng queue này, nên một message chạy lâu sẽ chặn tất cả: nhẹ thì jank, nặng thì ANR. Khi queue rỗng, thread ngủ ở tầng native (epoll) nên không tốn CPU. Về leak: message giữ target (Handler) và callback (Runnable); anonymous class hay lambda dùng member của Activity sẽ giữ tham chiếu tới Activity, nên chuỗi queue → message → Runnable → Activity tồn tại tới khi message chạy. Cách sửa: removeCallbacksAndMessages(null) khi màn hình dừng, hoặc thay bằng coroutine trong lifecycleScope với delay. Lưu ý constructor Handler() không tham số đã deprecated, phải truyền Looper rõ ràng.
    public class PromoActivity extends AppCompatActivity {
    private final Handler handler = new Handler(Looper.getMainLooper());
    @Override
    protected void onStart() {
        super.onStart();
        // Lambda gọi showPromo() nên giữ tham chiếu tới Activity
        handler.postDelayed(() -> showPromo(), 10 * 60 * 1000L);
    }

    @Override
    protected void onStop() {
        handler.removeCallbacksAndMessages(null); // gỡ mọi message đang chờ
        super.onStop();
    }
}

  4. GC của ART đã chạy concurrent, vậy vì sao vẫn nên tránh tạo object trong onDraw(), onBindViewHolder hay vòng lặp animation? Bạn phát hiện allocation churn bằng cách nào?

    Xem đáp án mẫu
    GC concurrent (concurrent copying, có từ Android 8) giảm mạnh thời gian dừng app nhưng không miễn phí: cấp phát dày khiến GC chạy thường xuyên, tốn CPU và băng thông bộ nhớ, tranh tài nguyên với main thread và RenderThread, và vẫn có những pause ngắn. Trên máy yếu, chừng đó đủ làm lỡ deadline frame (khoảng 16ms ở 60Hz, 8ms ở 120Hz). onDraw có thể chạy mỗi frame, nên tạo Paint, Path, Rect mới mỗi lần nghĩa là hàng nghìn object mỗi giây. Cách làm đúng: khởi tạo trước thành field rồi tái sử dụng, tránh autoboxing, iterator và nối chuỗi trong code nóng. Để phát hiện: Memory Profiler của Android Studio (ghi lại allocation, xem biểu đồ răng cưa và call stack), Perfetto để thấy GC trùng với frame chậm, và lint DrawAllocation cảnh báo sẵn khi cấp phát trong onDraw.
    class ChartView(context: Context) : View(context) {
  var points: List<PointF> = emptyList()
  private val paint = Paint(Paint.ANTI_ALIAS_FLAG) // tạo một lần, dùng lại mỗi frame
  private val path = Path()

  override fun onDraw(canvas: Canvas) {
    super.onDraw(canvas)
    path.reset() // thay vì Path() mới mỗi frame
    for (i in points.indices) {
      val p = points[i]
      if (i == 0) path.moveTo(p.x, p.y) else path.lineTo(p.x, p.y)
    }
    canvas.drawPath(path, paint)
  }
}

  1. Repository giữ cache mutableMapOf<String, User>() và nhiều coroutine cùng đọc ghi: thỉnh thoảng có ConcurrentModificationException hoặc mất cập nhật. Vì sao dùng coroutines không tự làm code thread-safe, và bạn bảo vệ state dùng chung thế nào (Mutex, limitedParallelism(1), atomics)? Bẫy của Mutex là gì?

    Xem đáp án mẫu
    Coroutine có thể chạy song song trên nhiều thread của Dispatchers.Default/IO, và ngay cả trên một dispatcher nhiều thread, sau mỗi điểm suspend nó có thể resume ở thread khác; nên chuỗi đọc rồi sửa rồi ghi không có đồng bộ vẫn bị race. Lựa chọn: một là Mutex với withLock { }, bảo vệ một critical section có thể chứa lời gọi suspend. Hai là thread confinement: mọi truy cập state đi qua một dispatcher đơn luồng (Dispatchers.IO.limitedParallelism(1)), giữ được thứ tự và hợp khi nhiều state liên quan, nhưng phải kỷ luật là không ai truy cập ngoài dispatcher đó. Ba là với state nhỏ thì MutableStateFlow.update { } (CAS và tự chạy lại lambda khi xung đột nên lambda phải thuần) hoặc atomics. Bốn là thiết kế để không chia sẻ: snapshot bất biến và một writer duy nhất (kiểu actor bằng Channel). Bẫy của Mutex: không reentrant, gọi withLock lồng nhau trong cùng coroutine là deadlock; giữ lock qua lời gọi mạng dài chặn mọi coroutine khác; và không dùng synchronized thay cho nó vì khối synchronized không cho phép suspend bên trong. Kiểm tra cũng cần chú ý check-then-act trên ConcurrentHashMap không atomic (dùng computeIfAbsent/compute), và nếu cần tránh gọi mạng trùng thì lưu Deferred đang chạy vào map thay vì giữ lock.
    class UserCache(private val api: UserApi) {
  private val mutex = Mutex()
  private val cache = mutableMapOf<String, User>() // chỉ truy cập trong withLock

  suspend fun get(id: String): User {
    mutex.withLock { cache[id] }?.let { return it } // khoá ngắn: chỉ đọc map
    val user = api.fetch(id) // gọi mạng ngoài khoá, không chặn các coroutine khác
    mutex.withLock { cache[id] = user }
    return user
  }
}

  2. Một dev viết flow { withContext(Dispatchers.IO) { emit(readConfig()) } } và app crash với IllegalStateException: Flow invariant is violated. Ngoài ra .catch { } đặt ở cuối pipeline không bắt được lỗi ném trong collect. Giải thích hai bất biến của Flow (context preservation, exception transparency) và cách viết đúng?

    Xem đáp án mẫu
    Flow có hai bất biến. Context preservation: phần thu thập luôn chạy trong context của collector, nên không được emit từ một context khác (như withContext bên trong flow { }), nếu không sẽ ném IllegalStateException. Muốn upstream chạy ở dispatcher khác thì dùng flowOn(Dispatchers.IO): nó chỉ ảnh hưởng các operator và block phía trên nó, tạo thêm một coroutine và channel (buffer) giữa upstream và downstream, còn collector vẫn ở context ban đầu; nếu cần phát từ nhiều coroutine hoặc callback thì dùng channelFlow/callbackFlow. Exception transparency: flow không được che lỗi của downstream. Operator catch chỉ bắt exception xảy ra ở upstream của nó; lỗi ném trong collect { } hoặc ở onEach đặt sau catch không bị bắt, muốn bắt thì đặt onEach trước catch hoặc bọc try/catch quanh collect. Vì vậy cũng đừng tự try/catch bọc lời gọi emit() trong flow { }, nó sẽ nuốt luôn lỗi của downstream. Với retry, retry/retryWhen chỉ chạy lại upstream; hãy lọc đúng loại lỗi (không retry 4xx hay CancellationException) và đặt delay backoff trong retryWhen. Nhớ rằng flow là cold: mỗi collector chạy lại block, và nên kiểm thử bằng Turbine.
    // Sai: emit từ context khác -> IllegalStateException (Flow invariant is violated)
fun readConfig(): Flow<Config> = flow {
  withContext(Dispatchers.IO) { emit(parse(file.readText())) }
}

// Đúng: flowOn chỉ đổi context của phần upstream
fun readConfig(): Flow<Config> = flow { emit(parse(file.readText())) }.flowOn(Dispatchers.IO)

    Xem đáp án mẫu
    GlobalScope là API 'delicate': coroutine không có parent nên không bao giờ bị huỷ và không có structured concurrency, mặc định chạy trên Dispatchers.Default, lỗi chưa bắt đi thẳng thành crash, và test không điều khiển được dispatcher nên không biết khi nào việc chạy xong. Thay bằng một applicationScope được inject (singleton qua Hilt, có qualifier @ApplicationScope): CoroutineScope(SupervisorJob() + dispatcher + handler). SupervisorJob để một việc nền lỗi không kéo chết các việc khác, CoroutineExceptionHandler để ghi log, dispatcher inject từ ngoài. Chọn công cụ theo hậu quả khi process bị kill: việc cần sống lâu hơn một màn hình nhưng mất đi cũng chấp nhận được (lưu nháp, ghi log, làm mới cache) thì dùng applicationScope; việc phải chạy xong bằng được dù process chết hay máy khởi động lại, cần retry và ràng buộc mạng/pin (upload, đồng bộ) thì dùng WorkManager; việc người dùng đang chờ lâu thì foreground service. Cho hàm suspend của repository tự gọi appScope.launch { ... }.join() (hoặc async + await): người gọi chờ được kết quả, còn nếu họ bị huỷ thì việc vẫn chạy tiếp. Để test, repository nhận CoroutineScope và CoroutineDispatcher qua constructor (đừng hardcode Dispatchers.IO trong withContext); trong runTest truyền this hoặc backgroundScope làm scope, StandardTestDispatcher(testScheduler) làm dispatcher, rồi dùng advanceUntilIdle(). Cẩn thận lambda trong applicationScope giữ tham chiếu Activity là leak vĩnh viễn.

    @Composable
fun TagFlow(modifier: Modifier = Modifier, spacing: Dp = 8.dp, content: @Composable () -> Unit) {
  Layout(content = content, modifier = modifier) { measurables, constraints ->
    val gap = spacing.roundToPx()
    // Mỗi con chỉ được đo một lần
    val placeables = measurables.map { it.measure(constraints.copy(minWidth = 0, minHeight = 0)) }

    val positions = ArrayList<IntOffset>(placeables.size)
    var x = 0
    var y = 0
    var rowHeight = 0
    for (p in placeables) {
      if (x > 0 && x + p.width > constraints.maxWidth) { // hết chỗ: xuống hàng
        x = 0
        y += rowHeight + gap
        rowHeight = 0
      }
      positions += IntOffset(x, y)
      x += p.width + gap
      rowHeight = maxOf(rowHeight, p.height)
    }
    layout(constraints.maxWidth, y + rowHeight) {
      placeables.forEachIndexed { i, p -> p.placeRelative(positions[i]) }
    }
  }
}

}

suspend fun <T> safeCall(block: suspend () -> T): Outcome<T> = try {
  Outcome.Success(block())
} catch (e: CancellationException) {
  throw e
} catch (e: IOException) {
  Outcome.Failure(AppError.NoConnection)
} catch (e: HttpException) {
  Outcome.Failure(
    when (e.code()) {
      401 -> AppError.Unauthorized
      422 -> AppError.Validation(parseFieldErrors(e))
      else -> AppError.Server(e.code())

  1. Bạn lưu access token và refresh token trên Android thế nào cho an toàn? EncryptedSharedPreferences còn là lựa chọn tốt không?

    Xem đáp án mẫu
    androidx.security:security-crypto (gồm EncryptedSharedPreferences, MasterKey) đã deprecated, nên với code mới tôi tự mã hoá: tạo AES key trong Android Keystore (key không export được, có thể nằm trong TEE/StrongBox), mã hoá token bằng AES-GCM rồi lưu IV cùng ciphertext vào DataStore hoặc file trong internal storage. Keystore không ngăn kẻ đã root máy gọi key thông qua chính process của app, nhưng ngăn việc copy key ra khỏi thiết bị. Access token ngắn hạn có thể chỉ giữ trong memory, refresh token mới cần lưu bền và nên được backend rotate. Không log token, loại file chứa token khỏi backup (dataExtractionRules, với Android 11 trở xuống là fullBackupContent), vì key Keystore không đi theo bản backup nên dữ liệu restore sang máy mới không giải mã được. Cuối cùng phải xử lý KeyPermanentlyInvalidatedException (key yêu cầu xác thực người dùng bị vô hiệu khi user tắt khoá màn hình hoặc thêm vân tay) bằng cách xoá key và cho đăng nhập lại.
    fun encrypt(plain: ByteArray): Pair<ByteArray, ByteArray> {
  val ks = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
  val key = ks.getKey(ALIAS, null) as? SecretKey ?: KeyGenerator
    .getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    .apply {
      init(KeyGenParameterSpec.Builder(ALIAS, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .build())
    }.generateKey()
  val cipher = Cipher.getInstance("AES/GCM/NoPadding")
  cipher.init(Cipher.ENCRYPT_MODE, key) // Keystore tự sinh IV ngẫu nhiên
  return cipher.iv to cipher.doFinal(plain) // lưu cả IV và ciphertext
}

    Thứ nhất là bề mặt API: nhỏ, ổn định và chủ động ẩn đi. Bật Kotlin explicit API mode để mọi khai báo public phải ghi rõ, dùng internal cho phần còn lại, và thêm binary-compatibility-validator (apiCheck) vào CI để mọi thay đổi API public hiện ra trong diff và bị review. Theo semver: thêm tuỳ chọn là bản minor, đổi hoặc xoá là major sau một thời gian @Deprecated. Kotlin có vài bẫy tương thích nhị phân: thêm tham số (kể cả có giá trị mặc định) vào hàm public là tương thích nguồn nhưng làm vỡ binary, nên cần giữ overload cũ hoặc dùng @JvmOverloads từ đầu; data class public dễ vỡ vì copy và componentN đổi theo constructor. Thứ hai là dependency: không lộ thư viện nặng hay dễ xung đột (OkHttp, Gson, Coroutines) ra API public, dùng implementation và chỉ dùng api khi kiểu đó thật sự nằm trong chữ ký public; ít dependency và minSdk thấp. Thứ ba là cách tích hợp: khởi tạo tường minh qua Sdk.init(context, config) hoặc App Startup thay vì giấu trong ContentProvider làm chậm startup của host app; SDK tự quản lý thread, không chặn main thread, không làm crash app host (bắt lỗi nội bộ) và bật tắt được log. Thứ tư là đóng gói: AAR kèm consumer ProGuard rules để host bật R8 không phải tự viết keep rule, và manifest không tự thêm permission thừa. Cuối cùng là tài liệu, app mẫu, changelog, và ma trận test chạy với nhiều phiên bản AGP, Kotlin, OkHttp.

kotlin {
  explicitApi() // mọi khai báo public phải ghi rõ visibility và kiểu trả về
}

android {
  defaultConfig {
    consumerProguardFiles("consumer-rules.pro") // app host bật R8 không phải tự viết keep rule
  }
}

dependencies {
  implementation(libs.okhttp) // không lộ OkHttp ra API public của SDK
}

  1. Hai senior trong team tranh luận gay gắt trên PR về việc chuyển từ MVVM sang MVI, PR bị treo một tuần. Với vai trò tech lead, bạn xử lý thế nào?

    Xem đáp án mẫu
    Trước hết tôi tách tranh luận kiến trúc ra khỏi PR: PR được đánh giá theo chuẩn hiện hành của team, đúng chuẩn và không có lỗi thì merge, không để một quyết định lớn chặn việc nhỏ. Sau đó mời hai người viết đề xuất ngắn dạng ADR: vấn đề cụ thể đang gặp (bug state, khó test, khó debug), phương án, trade-off, chi phí chuyển đổi, và bàn bằng ví dụ trong chính codebase thay vì sở thích cá nhân. Nếu chưa ngã ngũ thì làm thử có time-box trên một feature và đánh giá theo tiêu chí đã thống nhất từ trước. Người ra quyết định cuối phải rõ ràng; khi đã quyết, cả team 'disagree and commit' và ADR được lưu lại. Song song, tôi nói chuyện riêng với từng người để giữ quan hệ, và chốt quy tắc review: góp ý vào code chứ không vào người, phân biệt rõ comment blocking với nit.

  2. Bạn muốn đề xuất migrate dần app từ XML View sang Jetpack Compose nhưng PM lo ảnh hưởng roadmap. Bạn thuyết phục và lên kế hoạch thế nào?

Đề xuất là migrate tăng dần chứ không viết lại toàn bộ: màn hình mới viết bằng Compose, màn hình cũ chỉ chuyển khi đằng nào cũng phải sửa lớn, hai bên chung sống qua ComposeView và AndroidView.   3. Đang ở giữa dự án 3 tháng (làm lại luồng thanh toán) thì bạn nhận ra tiến độ chậm khoảng 30% so với kế hoạch, trong khi ngày ra mắt gắn với chiến dịch marketing đã công bố. Bạn xử lý thế nào, đặc biệt là cách báo cho các bên liên quan?

    Xem đáp án mẫu
    Việc đầu tiên là báo sớm thay vì cố bù trong im lặng, nhưng đi kèm số liệu và phương án chứ không chỉ báo tin xấu. Tôi dành vài giờ tìm nguyên nhân thật: ước lượng sai do thiếu thông tin, requirement thay đổi, backend trễ, hay nợ kỹ thuật ở phần cũ, vì mỗi loại có cách xử lý khác nhau. Sau đó dựng lại kế hoạch theo phần việc còn lại, có khoảng ước lượng (tốt nhất, khả dĩ, xấu nhất) thay vì một con số, rồi đưa cho PM các lựa chọn kèm đánh đổi rõ ràng: cắt phạm vi (bản đầu chỉ có luồng cốt lõi, các phương thức thanh toán phụ ra sau), dời ngày, thêm người (nhớ định luật Brooks: thêm người giữa chừng thường làm chậm hơn trong ngắn hạn), hoặc giảm chất lượng (tôi không khuyến nghị với thanh toán). Đề xuất dựa trên tiêu chí đo được như rủi ro tài chính và mức cam kết của chiến dịch. Song song giảm rủi ro kỹ thuật: đặt bản ra mắt sau feature flag và staged rollout để tách ngày marketing khỏi ngày bật cho toàn bộ user, làm phần rủi ro nhất trước (tích hợp cổng thanh toán, sau đó mới tới UI), và cập nhật tiến độ ngắn mỗi tuần. Sau dự án, họp rút kinh nghiệm: vì sao ước lượng lệch, lần sau thêm buffer và chia mốc nhỏ sớm hơn.

  4. Bản phát hành 5.12 vừa rollout 20% thì cảnh báo Crashlytics báo crash-free users giảm từ 99,7% xuống 97%, review 1 sao đang tăng và kênh support bắt đầu nhắn. Bạn là tech lead đang on-call. Bạn điều phối xử lý sự cố này thế nào, từ phút đầu tiên đến sau khi xong?

    Xem đáp án mẫu
    Ưu tiên giảm thiệt hại trước, tìm nguyên nhân gốc sau. Khoảng 15 phút đầu: xác nhận cảnh báo là thật (Crashlytics, Play vitals), khoanh vùng theo phiên bản, OS, dòng máy, màn hình và tỷ lệ người dùng bị ảnh hưởng; đánh giá mức độ (mất dữ liệu hay chặn thanh toán khác hẳn lỗi nhỏ), tuyên bố sự cố và giao vai trò rõ ràng (người điều phối, người điều tra, người liên lạc) để không ai làm trùng việc. Chặn thiệt hại ngay: tạm dừng staged rollout trên Play Console; nếu lỗi nằm sau feature flag thì tắt từ xa; nếu cần thì chuẩn bị hotfix với versionCode cao hơn vì Play không cho quay về bản cũ, và cân nhắc in-app update để đẩy người đã nhận bản lỗi lên bản sửa. Liên lạc: một kênh duy nhất, cập nhật theo nhịp cố định (ví dụ 30 phút một lần) nêu rõ đã biết gì, chưa biết gì và lần cập nhật tiếp theo, kèm cách xử lý tạm cho support; stakeholder cần biết tác động và thời gian, không cần chi tiết kỹ thuật. Sửa: thay đổi nhỏ nhất có thể, không nhét thêm việc khác vào hotfix, review nhanh nhưng vẫn test trên nhóm máy bị ảnh hưởng, rollout lại theo 1% → 5% → 20% → 100% và chỉ nới khi chỉ số ổn. Vài ngày sau: viết post-mortem không đổ lỗi (blameless) gồm timeline, nguyên nhân gốc, vì sao không bắt được sớm hơn (thiếu test, rollout quá nhanh, không có flag, không có máy đó trong QA) và các hành động phòng ngừa có người chịu trách nhiệm cùng hạn chót: thêm test hồi quy, đặt cổng rollout theo crash-free, rút ngắn thời gian phát hiện (MTTD) và khắc phục (MTTR). Người viết đoạn code lỗi được bảo vệ: lỗi là của quy trình đã để nó lọt qua.
