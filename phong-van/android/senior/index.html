Java & JVM

Mọi rank →

  1. Giải thích cách ART thực thi code của app hiện nay (interpreter, JIT, AOT). Vì sao vài lần mở đầu sau khi cài hoặc cập nhật thường chậm hơn, và Baseline Profile giải quyết việc đó ra sao?

    Xem đáp án mẫu
    Dalvik chủ yếu thông dịch bytecode, từ Android 2.2 có thêm JIT. ART ở Android 5–6 AOT-compile toàn bộ app bằng dex2oat lúc cài, nên cài lâu và tốn dung lượng. Từ Android 7, ART dùng mô hình lai: mới cài thì code chạy bằng interpreter + JIT, JIT ghi các method nóng vào profile, rồi khi máy rảnh và đang sạc, hệ thống AOT-compile những method đó (profile-guided compilation). Vì vậy những lần mở đầu sau khi cài hoặc update chưa có code AOT nên chậm hơn và dễ jank. Baseline Profile là danh sách class/method quan trọng ship sẵn trong APK/AAB; khi cài qua Play, ART dùng nó để AOT-compile các đường code đó ngay, không phải đợi JIT tích luỹ profile. Cloud Profile của Play có tác dụng tương tự nhưng chỉ có sau khi bản phát hành đã có đủ người dùng, còn Baseline Profile phủ ngay từ ngày đầu.

  2. Đoạn double-checked locking sau có lỗi gì theo Java Memory Model? Sửa thế nào, và trong Kotlin bạn viết ra sao?

    Xem đáp án mẫu
    Lần đọc instance đầu tiên nằm ngoài synchronized, nên giữa thread khởi tạo và thread đọc không có quan hệ happens-before. Compiler và CPU được phép sắp xếp lại lệnh: việc gán reference vào instance có thể được thread khác nhìn thấy trước các lệnh ghi field trong constructor, nên thread đó thấy instance != null nhưng đọc phải object khởi tạo dở (với các field không final). Sửa bằng cách khai báo private static volatile Config instance;: lần ghi volatile happens-before mọi lần đọc volatile sau đó, nên mọi ghi trong constructor đều được nhìn thấy đầy đủ. Cách khác là holder idiom, dựa vào việc khởi tạo class của JVM vốn đã thread-safe. Trong Kotlin không cần tự viết: object hoặc by lazy (mặc định LazyThreadSafetyMode.SYNCHRONIZED) đã xử lý đúng.
    public class Config {
    private static Config instance; // thiếu volatile

    public static Config get() {
        if (instance == null) {                 // đọc không có lock
            synchronized (Config.class) {
                if (instance == null) {
                    instance = new Config();
                }
            }
        }
        return instance;
    }
}

  3. Main thread của Android vận hành thế nào với Looper, MessageQueue và Handler? Vì sao postDelayed với anonymous class hoặc lambda dễ gây leak Activity?

    Xem đáp án mẫu
    Mỗi thread có tối đa một Looper; Looper.loop() lặp liên tục lấy Message từ MessageQueue (sắp theo thời điểm when) rồi giao cho Handler của message đó xử lý. ActivityThread chuẩn bị sẵn Looper cho main thread, và callback lifecycle, sự kiện input hay frame của Choreographer đều là message trên cùng queue này, nên một message chạy lâu sẽ chặn tất cả: nhẹ thì jank, nặng thì ANR. Khi queue rỗng, thread ngủ ở tầng native (epoll) nên không tốn CPU. Về leak: message giữ target (Handler) và callback (Runnable); anonymous class hay lambda dùng member của Activity sẽ giữ tham chiếu tới Activity, nên chuỗi queue → message → Runnable → Activity tồn tại tới khi message chạy. Cách sửa: removeCallbacksAndMessages(null) khi màn hình dừng, hoặc thay bằng coroutine trong lifecycleScope với delay. Lưu ý constructor Handler() không tham số đã deprecated, phải truyền Looper rõ ràng.
    public class PromoActivity extends AppCompatActivity {
    private final Handler handler = new Handler(Looper.getMainLooper());
    @Override
    protected void onStart() {
        super.onStart();
        // Lambda gọi showPromo() nên giữ tham chiếu tới Activity
        handler.postDelayed(() -> showPromo(), 10 * 60 * 1000L);
    }

    @Override
    protected void onStop() {
        handler.removeCallbacksAndMessages(null); // gỡ mọi message đang chờ
        super.onStop();
    }
}

  4. GC của ART đã chạy concurrent, vậy vì sao vẫn nên tránh tạo object trong onDraw(), onBindViewHolder hay vòng lặp animation? Bạn phát hiện allocation churn bằng cách nào?

    Xem đáp án mẫu
    GC concurrent (concurrent copying, có từ Android 8) giảm mạnh thời gian dừng app nhưng không miễn phí: cấp phát dày khiến GC chạy thường xuyên, tốn CPU và băng thông bộ nhớ, tranh tài nguyên với main thread và RenderThread, và vẫn có những pause ngắn. Trên máy yếu, chừng đó đủ làm lỡ deadline frame (khoảng 16ms ở 60Hz, 8ms ở 120Hz). onDraw có thể chạy mỗi frame, nên tạo Paint, Path, Rect mới mỗi lần nghĩa là hàng nghìn object mỗi giây. Cách làm đúng: khởi tạo trước thành field rồi tái sử dụng, tránh autoboxing, iterator và nối chuỗi trong code nóng. Để phát hiện: Memory Profiler của Android Studio (ghi lại allocation, xem biểu đồ răng cưa và call stack), Perfetto để thấy GC trùng với frame chậm, và lint DrawAllocation cảnh báo sẵn khi cấp phát trong onDraw.
    class ChartView(context: Context) : View(context) {
  var points: List<PointF> = emptyList()
  private val paint = Paint(Paint.ANTI_ALIAS_FLAG) // tạo một lần, dùng lại mỗi frame
  private val path = Path()

  override fun onDraw(canvas: Canvas) {
    super.onDraw(canvas)
    path.reset() // thay vì Path() mới mỗi frame
    for (i in points.indices) {
      val p = points[i]
      if (i == 0) path.moveTo(p.x, p.y) else path.lineTo(p.x, p.y)
    }
    canvas.drawPath(path, paint)
  }
}

  1. Làm sao tái hiện và xử lý process death một cách có hệ thống trong app lớn? Sau khi process bị kill, state nào mất và state nào được khôi phục?

    Xem đáp án mẫu
    Khi app ở background, hệ thống có thể kill process để lấy bộ nhớ. Lúc user quay lại, Android tạo process mới, khôi phục back stack Activity/Fragment (kể cả back stack của Navigation) cùng các Bundle đã lưu, nhưng mọi thứ chỉ nằm trong memory đều mất: singleton, cache, biến static, instance ViewModel cũ. Tái hiện: đưa app xuống background rồi chạy adb shell am kill <package>; khác với tuỳ chọn 'Don't keep activities' chỉ destroy Activity còn process vẫn sống. Xử lý: state UI tối thiểu (id, query, tab đang chọn, input của form) lưu bằng SavedStateHandle/rememberSaveable; dữ liệu lớn để trong DB rồi load lại theo id; không giả định singleton đã được màn hình trước khởi tạo, vì màn hình sâu có thể là màn hình đầu tiên chạy trong process mới. Đừng nhét list lớn vào Bundle vì giới hạn Binder transaction (khoảng 1MB) dễ gây TransactionTooLargeException.
    @HiltViewModel
class CheckoutViewModel @Inject constructor(
  private val savedState: SavedStateHandle,
  orderRepo: OrderRepository,
) : ViewModel() {
  // Chỉ lưu id và input nhỏ; dữ liệu lớn load lại từ DB theo id
  private val orderId: String = checkNotNull(savedState["orderId"])
  val note = savedState.getStateFlow("note", "")
  val order = orderRepo.observeOrder(orderId)
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)

  fun onNoteChange(value: String) { savedState["note"] = value }
}

  1. Bạn xây design system bằng Compose cho 5 team cùng dùng thế nào để UI nhất quán mà không làm chậm tốc độ phát triển?

    Xem đáp án mẫu
    Tôi đặt design system trong module :core:designsystem gồm hai lớp. Lớp token: màu, typography, spacing, shape được cung cấp qua CompositionLocal trong một AppTheme (bọc hoặc thay MaterialTheme), dùng staticCompositionLocalOf cho giá trị hiếm khi đổi vì đọc rẻ, đổi thì recompose cả subtree. Lớp component: AppButton, AppTextField… với API hẹp, nhận tham số ngữ nghĩa như variant = Primary thay vì màu tuỳ ý, để thiết kế có thể thay đổi tập trung. Mỗi component có @Preview và screenshot test cho light/dark, font scale lớn, RTL để chặn regression. Về quy trình: designer và dev dùng chung tên token, có owner và cách đóng góp component mới, lint cấm hard-code màu hoặc dùng thẳng MaterialTheme.colorScheme trong feature module. Màn hình View cũ thì ánh xạ cùng bộ token sang theme XML trong thời gian chuyển đổi.
    @Immutable
data class AppColors(val primary: Color, val surface: Color, val danger: Color)
val LocalAppColors = staticCompositionLocalOf<AppColors> { error("Chưa bọc trong AppTheme") }

@Composable
fun AppTheme(dark: Boolean = isSystemInDarkTheme(), content: @Composable () -> Unit) {
  val colors = if (dark) DarkColors else LightColors
  CompositionLocalProvider(LocalAppColors provides colors, content = content)
}

// Feature module đọc token qua AppTheme.colors.primary
object AppTheme {
  val colors: AppColors
    @Composable get() = LocalAppColors.current
}

Kiến trúc & DI

Mọi rank →

  1. App có khoảng 20 feature module. Bạn đặt quy tắc phụ thuộc giữa các module thế nào? Feature A cần mở màn hình của feature B thì làm sao để A không phụ thuộc B?

    Xem đáp án mẫu
    Quy tắc tôi đặt: :app phụ thuộc mọi feature; feature chỉ phụ thuộc các module :core:* (designsystem, data, domain, network…), tuyệt đối không phụ thuộc feature khác; :core không biết gì về feature. Nhờ vậy các feature build song song, sửa feature A không làm recompile B, và không bao giờ có vòng phụ thuộc. Để điều hướng chéo, feature A chỉ expose callback như onOpenProfile, còn :app — nơi duy nhất biết mọi feature — nối callback đó tới route của B. Nếu cần chia sẻ contract (route, interface service), tách feature thành :feature:b:api nhẹ và :feature:b:impl; A chỉ được phụ thuộc b:api, còn implementation được nối qua DI ở :app. Quy tắc này phải được kiểm tra tự động trong CI (plugin kiểm tra module graph hoặc custom Gradle task), không chỉ dựa vào review.
    // :feature:feed — không biết gì về feature profile
fun NavGraphBuilder.feedScreen(onOpenProfile: (userId: String) -> Unit) {
  composable<FeedRoute> { FeedScreen(onUserClick = onOpenProfile) }
}

// :app — nơi duy nhất ghép các feature với nhau
NavHost(navController, startDestination = FeedRoute) {
  feedScreen(onOpenProfile = { id -> navController.navigate(ProfileRoute(id)) })
  profileScreen(onBack = { navController.popBackStack() })
}

  2. Team chuyển sang trunk-based development và muốn mọi tính năng lớn đều nằm sau feature flag. Bạn thiết kế hệ thống flag phía Android thế nào để không biến thành nợ kỹ thuật?

    Xem đáp án mẫu
    Tôi định nghĩa flag tập trung và có kiểu (enum hoặc sealed class gồm key và giá trị mặc định), ẩn provider (Firebase Remote Config, LaunchDarkly hay backend riêng) sau interface FeatureFlags để test dùng fake và đổi vendor không ảnh hưởng feature. Giá trị fetch bất đồng bộ, cache local, chỉ áp dụng ở thời điểm an toàn như lần mở app hoặc mở luồng kế tiếp; khi offline luôn có default. Phân loại rõ release toggle (ngắn hạn, phải xoá), experiment và kill switch (dài hạn). Kiểm tra flag ở biên, như entry điều hướng hoặc chỗ DI chọn implementation, thay vì rải if khắp nơi. Chống nợ: mỗi flag có owner, hạn xoá và ticket dọn sau khi rollout 100%, CI cảnh báo flag quá hạn, kèm màn hình debug cho QA override. Lưu ý code sau flag vẫn nằm trong APK, nên quyền truy cập tính năng nhạy cảm phải do backend kiểm soát.

Gradle & Build

Mọi rank →

  1. Trong dự án multi-module, api và implementation khác nhau thế nào? Vì sao lạm dụng api vừa làm build chậm vừa làm kiến trúc lỏng lẻo?

    Xem đáp án mẫu
    implementation chỉ đưa dependency vào compile classpath của chính module đó; module phụ thuộc vào nó không thấy được (dù lúc runtime vẫn được đóng gói). api thì lộ dependency ra compile classpath của mọi module phía trên. Về build: khi ABI của một dependency khai báo api thay đổi, mọi module tiêu thụ phải recompile; với implementation, Gradle chỉ recompile module trực tiếp, các module phía trên được bỏ qua nếu ABI của module ở giữa không đổi (compile avoidance). Về kiến trúc: api cho phép feature module dùng thẳng class của Retrofit hay Room đi qua :core, làm rò rỉ chi tiết implementation. Quy tắc: chỉ dùng api khi kiểu của dependency xuất hiện trong public API của module (tham số, kiểu trả về, superclass). Dependency Analysis Gradle Plugin giúp phát hiện khai báo thừa hoặc sai.
    // :core:network/build.gradle.kts
dependencies {
  // Public API của module trả về OkHttpClient nên module dùng nó cần thấy kiểu này
  api(libs.okhttp)
  // Chỉ dùng bên trong, không lộ ra ngoài
  implementation(libs.kotlinx.serialization.json)
}

  2. CI build mất 15 phút, build incremental trên máy dev cũng chậm. Với codebase khoảng 50 module, bạn tối ưu Gradle theo hướng nào?

    Xem đáp án mẫu
    Đo trước khi sửa: Build Scan (--scan) hoặc Build Analyzer cho biết thời gian nằm ở phase configuration hay execution, task nào không cacheable, annotation processor nào chậm. Các đòn bẩy chính: bật configuration cache để bỏ qua cả phase configuration khi build script và input không đổi; bật build cache, CI đẩy lên remote cache còn máy dev kéo về; chuyển kapt sang KSP vì kapt phải sinh Java stub cho code Kotlin; bỏ logic nặng ở top-level build script (đọc file, gọi git) khỏi phase configuration. Gom cấu hình chung vào convention plugin trong build-logic thay vì subprojects {}/allprojects {} vốn tạo coupling giữa các project, quản lý version bằng version catalog. Về cấu trúc: module nhỏ, đồ thị phụ thuộc nông, dùng implementation để thay đổi ở một module không lan rộng, nhờ vậy Gradle chạy song song tốt hơn. Trên CI thì chỉ build và test các module bị ảnh hưởng bởi thay đổi.

  3. Bản release parse JSON ra object toàn field null rồi crash, trong khi bản debug chạy bình thường. Bạn nghi R8 — điều tra và xử lý thế nào?

    Xem đáp án mẫu
    R8 vừa shrink (xoá code không reachable), vừa obfuscate (đổi tên), vừa optimize, và nó chỉ nhìn thấy những gì được tham chiếu tĩnh. Thư viện dựa vào reflection như Gson đọc field theo tên, nên khi field bị đổi tên thì JSON không map được; R8 còn có thể thấy field không bao giờ được gán trong code và coi nó luôn mang giá trị mặc định. Điều tra: tái hiện bằng bản build có isMinifyEnabled = true, retrace stack trace bằng mapping.txt, xem usage.txt để biết R8 đã xoá gì. Xử lý: thêm keep rule hẹp nhất có thể cho model hoặc dùng @Keep; tốt hơn là chuyển sang thư viện sinh code như kotlinx.serialization hay Moshi codegen để không phụ thuộc reflection. Tránh keep cả package hay -dontobfuscate; và nhớ R8 full mode (mặc định từ AGP 8.0) tối ưu mạnh hơn, nên rule từng đủ với ProGuard có thể không còn đủ.

  1. App có cold start khoảng 2,5 giây trên máy tầm trung, trong Application.onCreate đang khởi tạo cả chục SDK. Bạn đo và tối ưu thế nào?

    Xem đáp án mẫu
    Trước hết phải đo đúng: dùng Macrobenchmark với StartupTimingMetric trên máy thật, bản release (R8 bật, không debuggable), và gọi reportFullyDrawn() để có cả TTFD chứ không chỉ TTID; mở Perfetto/System Trace để xem main thread bận gì trong bindApplication và activityStart. Tối ưu theo thứ tự: SDK nào chưa cần cho frame đầu thì init lazy hoặc dời ra sau first frame; gom các ContentProvider tự khởi tạo của thư viện bằng App Startup (có thể tắt auto-init rồi gọi khi cần); đưa I/O ra khỏi main thread và tránh khởi tạo eager các object nặng trong DI graph. Sau đó thêm Baseline Profile để ART AOT-compile sẵn đường code startup ngay khi cài, cùng Startup Profile để R8 xếp các class startup vào DEX chính. Cuối cùng đưa benchmark vào CI để bắt regression thay vì đo một lần rồi thôi.

  2. QA báo màn hình feed giật khi cuộn nhanh trên máy tầm thấp, còn trên máy dev thì mượt. Bạn đo và khoanh vùng jank thế nào?

    Xem đáp án mẫu
    Tôi tái hiện trên đúng loại máy yếu với bản release, vì bản debug chậm hơn nhiều (đặc biệt với Compose) nên số đo không có ý nghĩa. Để định lượng, viết Macrobenchmark với FrameTimingMetric cho kịch bản cuộn, còn ở production thì gắn JankStats kèm state (tên màn hình, loại item) để biết jank xảy ra ở đâu trên máy người dùng thật. Để tìm nguyên nhân, chụp Perfetto/System Trace: xem frame nào vượt deadline, main thread hay RenderThread bận, các slice như RV OnBindView, inflate, GC hay lock contention; thêm custom section bằng trace("…") { } của androidx.tracing quanh đoạn code nghi ngờ. Thủ phạm hay gặp: bind nặng (format ngày, parse HTML), layout lồng sâu, decode ảnh trên main thread, cấp phát nhiều gây GC. Sửa xong phải đo lại bằng cùng benchmark để chứng minh cải thiện.

  3. LeakCanary báo MapActivity bị leak, retaining path đi qua một listener đăng ký vào singleton LocationRepository. Bạn phân tích và sửa thế nào? Còn những nguồn leak Context phổ biến nào khác?

    Xem đáp án mẫu
    Activity đã onDestroy nhưng vẫn reachable từ GC root: singleton sống suốt process giữ listener, mà lambda đó capture this của Activity, kéo theo cả view hierarchy và bitmap không được thu hồi. Cách sửa là unregister đối xứng với register theo lifecycle (onStart/onStop hoặc DefaultLifecycleObserver), và singleton chỉ được giữ applicationContext. Các nguồn leak hay gặp khác: Handler.postDelayed với Runnable giữ Activity, coroutine hay thread tự tạo chạy lâu thay vì dùng lifecycleScope, Fragment giữ binding sau onDestroyView, ViewModel giữ View hoặc Activity Context, callback của SDK bên thứ ba không được gỡ. LeakCanary chỉ nên thêm bằng debugImplementation; nó theo dõi các object đã destroy, object nào sau 5 giây và một lần GC vẫn còn thì bị coi là retained; khi số object retained đạt ngưỡng, nó dump heap và chỉ ra chuỗi tham chiếu mạnh ngắn nhất tới GC root.
    class MapActivity : AppCompatActivity() {
  // Lambda gọi updateMarker() nên capture MapActivity
  private val listener: (Location) -> Unit = { updateMarker(it) }

  override fun onStart() {
    super.onStart()
    LocationRepository.addListener(listener) // singleton sống cả process
  }

  override fun onStop() {
    LocationRepository.removeListener(listener) // thiếu dòng này là leak
    super.onStop()
  }
}

Mọi rank →

  1. Bạn lưu access token và refresh token trên Android thế nào cho an toàn? EncryptedSharedPreferences còn là lựa chọn tốt không?

    Xem đáp án mẫu
    androidx.security:security-crypto (gồm EncryptedSharedPreferences, MasterKey) đã deprecated, nên với code mới tôi tự mã hoá: tạo AES key trong Android Keystore (key không export được, có thể nằm trong TEE/StrongBox), mã hoá token bằng AES-GCM rồi lưu IV cùng ciphertext vào DataStore hoặc file trong internal storage. Keystore không ngăn kẻ đã root máy gọi key thông qua chính process của app, nhưng ngăn việc copy key ra khỏi thiết bị. Access token ngắn hạn có thể chỉ giữ trong memory, refresh token mới cần lưu bền và nên được backend rotate. Không log token, loại file chứa token khỏi backup (dataExtractionRules, với Android 11 trở xuống là fullBackupContent), vì key Keystore không đi theo bản backup nên dữ liệu restore sang máy mới không giải mã được. Cuối cùng phải xử lý KeyPermanentlyInvalidatedException (key yêu cầu xác thực người dùng bị vô hiệu khi user tắt khoá màn hình hoặc thêm vân tay) bằng cách xoá key và cho đăng nhập lại.
    fun encrypt(plain: ByteArray): Pair<ByteArray, ByteArray> {
  val ks = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
  val key = ks.getKey(ALIAS, null) as? SecretKey ?: KeyGenerator
    .getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    .apply {
      init(KeyGenParameterSpec.Builder(ALIAS, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .build())
    }.generateKey()
  val cipher = Cipher.getInstance("AES/GCM/NoPadding")
  cipher.init(Cipher.ENCRYPT_MODE, key) // Keystore tự sinh IV ngẫu nhiên
  return cipher.iv to cipher.doFinal(plain) // lưu cả IV và ciphertext
}

  2. Bạn triển khai certificate pinning cho app ngân hàng thế nào? Rủi ro lớn nhất của pinning là gì?

    Xem đáp án mẫu
    Tôi pin public key (hash SPKI) thay vì cả certificate, để server renew certificate với cùng key không làm hỏng app, và luôn có ít nhất một backup pin cho key dự phòng chưa dùng. Có hai cách: Network Security Config với <pin-set> (khai báo qua android:networkSecurityConfig trong Manifest, có expiration, áp dụng ở tầng TrustManager của nền tảng), hoặc CertificatePinner của OkHttp nếu cần logic động. Rủi ro lớn nhất là tự khoá app: nếu server đổi key mà bản app đang chạy không có pin tương ứng, mọi request đều fail và chỉ sửa được bằng cách cập nhật app, còn user không cập nhật thì app chết hẳn. Vì vậy cần quy trình rotate key phối hợp với backend, đặt expiration và theo dõi lỗi pinning. Cũng phải hiểu đúng phạm vi: pinning chống MITM trên đường truyền (kể cả khi có CA lạ được cài thêm), nhưng không chống được người kiểm soát thiết bị dùng root và Frida để bypass.

  3. Backend muốn chặn request đến từ app bị sửa đổi, emulator hoặc bot. Bạn tích hợp Play Integrity API thế nào cho đúng?

    Xem đáp án mẫu
    SafetyNet Attestation đã bị thay bằng Play Integrity API. Luồng đúng: app xin integrity token (standard request: gọi prepareIntegrityToken trước để warm up, khi cần thì request kèm requestHash băm từ nội dung hành động; classic request thì dùng nonce do server sinh), rồi gửi token lên backend. Backend gọi server của Google để giải mã rồi mới đọc verdict: appIntegrity (đúng package, chứng chỉ ký, được Play nhận diện), deviceIntegrity (ví dụ MEETS_DEVICE_INTEGRITY) và accountDetails (licensing). Backend phải đối chiếu requestHash/nonce và thời điểm để chống replay; tuyệt đối không ra quyết định trên client vì client có thể bị hook. Chính sách nên theo mức rủi ro: chặn cứng ở hành động nhạy cảm như thanh toán, còn lại có thể chỉ ghi nhận hoặc yêu cầu xác thực thêm, vì có user hợp lệ dùng ROM tuỳ biến. API có quota nên không gọi cho mọi request, và Integrity chỉ là một lớp, cần kết hợp rate limiting và kiểm tra phía server.

  2. Nếu phải tự thiết kế một thư viện tải ảnh kiểu Coil/Glide, bạn sẽ có những thành phần nào và xử lý bộ nhớ, hiệu năng ra sao?

    Xem đáp án mẫu
    Pipeline gồm: request (url, kích thước đích, transformation) → memory cache (LruCache bitmap với key gồm url + size + transformation, giới hạn theo một phần heap) → disk cache (DiskLruCache) → network (OkHttp) → decode → transform → hiển thị. Quan trọng nhất là decode có downsample theo kích thước view (inSampleSize hoặc ImageDecoder.setTargetSize), vì một ảnh 4000×3000 ở ARGB_8888 đã chiếm khoảng 48MB; cân nhắc RGB_565 hoặc hardware bitmap khi phù hợp. Về concurrency: decode trên dispatcher giới hạn song song, gộp các request trùng key đang chạy, huỷ request khi view bị recycle hoặc lifecycle bị destroy, và gắn request với view để không hiển thị nhầm ảnh khi view được tái sử dụng. Thư viện lắng nghe onTrimMemory để thu nhỏ cache khi hệ thống thiếu bộ nhớ. API nên có builder bất biến, extension kiểu ImageView.load(url), placeholder/error và prefetch cho list.

  3. Thiết kế sync engine cho app ghi chú offline-first: user sửa trên nhiều thiết bị, kể cả khi offline. Bạn đồng bộ và xử lý xung đột thế nào?

    Xem đáp án mẫu
    Mỗi bản ghi có id do client sinh (UUID), version do server cấp, cờ dirty và xoá mềm (tombstone) để đồng bộ được cả thao tác xoá. Mọi thay đổi ghi vào DB local trước (UI chỉ đọc từ DB), đồng thời thêm vào outbox; một unique work của WorkManager với constraint mạng đẩy outbox lên (push), rồi kéo thay đổi về (pull) theo cursor thay vì tải lại toàn bộ. Xung đột được phát hiện khi server so baseVersion client gửi lên với version hiện tại; khi lệch phải chọn chiến lược: last-write-wins (đơn giản nhưng có thể mất dữ liệu), merge theo từng field, hoặc giữ cả hai bản cho user chọn; văn bản cộng tác thời gian thực mới cần đến CRDT/OT. Đừng lấy giờ máy client làm căn cứ vì có thể lệch. Mọi thao tác phải idempotent để retry an toàn. Sync được kích hoạt khi mở app, khi nhận push báo có thay đổi, và periodic work làm lưới an toàn.
