  1. Vì sao reified chỉ dùng được trong hàm inline? Khi nào cần đánh dấu lambda là crossinline hoặc noinline?

    Xem đáp án mẫu
    Generic trên JVM bị type erasure nên trong hàm thường không biết T là gì lúc runtime: không viết được is T hay T::class. Hàm inline được chép thân vào chỗ gọi, nên compiler thay T bằng kiểu cụ thể tại từng call site; đó là lý do reified chỉ đi cùng inline, ví dụ quen thuộc là by viewModels<T>(). Lambda truyền vào hàm inline cũng được inline nên cho phép non-local return. Nếu hàm inline gọi lambda trong một ngữ cảnh khác như Runnable, object hay lambda khác thì phải đánh dấu crossinline để cấm non-local return; noinline dùng khi cần giữ lambda như một object để lưu lại hoặc truyền cho hàm không inline. Lạm dụng inline cho hàm lớn làm phình bytecode, nên chỉ dùng khi có tham số lambda hoặc cần reified.
    inline fun <reified T> Gson.fromJson(json: String): T =
  fromJson(json, object : TypeToken<T>() {}.type)

inline fun View.postSafely(crossinline action: () -> Unit) {
  post { action() } // lambda chạy trong Runnable khác nên cần crossinline
}

  2. Vì sao truyền List<Cat> vào hàm nhận List<Animal> thì được, còn MutableList<Cat> vào MutableList<Animal> lại lỗi compile? out và in giải quyết việc này thế nào?

    Xem đáp án mẫu
    List<out E> của Kotlin là covariant: nó chỉ trả E ra chứ không nhận E vào, nên coi List<Cat> là List<Animal> là an toàn. MutableList<E> là invariant vì vừa đọc vừa ghi: nếu cho phép, hàm nhận MutableList<Animal> có thể add(Dog()) vào list mèo và phá vỡ type safety. Ở chỗ dùng có thể khai báo use-site variance: MutableList<out Animal> khi chỉ đọc (producer), MutableList<in Cat> khi chỉ ghi vào (consumer), tương ứng quy tắc PECS ? extends/? super của Java. Khi tự viết class, khai báo interface Source<out T> ở declaration site, và compiler sẽ kiểm tra T không xuất hiện ở vị trí tham số đầu vào.

  1. Một class Java đếm số request đang chạy bằng private volatile int active; và active++ được gọi từ nhiều thread. Code này có đúng không? Phân biệt volatile, synchronized và AtomicInteger.

    Xem đáp án mẫu
    Không đúng. volatile chỉ đảm bảo visibility (thread khác luôn thấy giá trị mới nhất) và chống reorder quanh biến đó, nhưng active++ gồm ba bước đọc, cộng, ghi; hai thread có thể cùng đọc một giá trị và mất một lần tăng. synchronized đảm bảo cả mutual exclusion lẫn visibility cho cả khối code, dùng khi phải bảo vệ nhiều biến hoặc thao tác ghép kiểu check-then-act. AtomicInteger.incrementAndGet() dùng CAS nên atomic mà không cần khoá, phù hợp nhất cho một bộ đếm đơn lẻ. volatile một mình chỉ đủ khi một thread ghi và các thread khác chỉ đọc, như cờ dừng volatile boolean running.
    class RequestTracker {
  private final AtomicInteger active = new AtomicInteger();
  private int total; // được bảo vệ bởi khoá của this

  void start() {
    active.incrementAndGet(); // atomic, không cần khoá
    synchronized (this) {
      total++;
    }
  }

  int active() { return active.get(); }
}

  2. Module Java cũ dùng ExecutorService để tải ảnh nền. Những lỗi hay gặp khi dùng ExecutorService trên Android là gì, và khi chuyển sang Kotlin bạn nối nó với coroutines thế nào?

    Xem đáp án mẫu
    Lỗi hay gặp: tạo pool mới cho mỗi request hoặc không bao giờ shutdown(), làm rò rỉ thread; dùng Executors.newCachedThreadPool() không giới hạn số thread khi tải hàng trăm ảnh cùng lúc; gọi future.get() trên main thread làm chặn UI và dễ gây ANR. Task cũng không biết vòng đời màn hình nên vẫn chạy và giữ tham chiếu tới Activity sau khi nó bị huỷ, còn future.cancel(true) chỉ interrupt thread, task không kiểm tra interrupt thì vẫn chạy tiếp. Khi chuyển sang Kotlin, có thể giữ pool hiện có và biến nó thành dispatcher bằng executor.asCoroutineDispatcher(), gọi qua withContext từ viewModelScope để có structured concurrency và cancellation theo vòng đời; hoặc dùng luôn Dispatchers.IO/Dispatchers.Default.

  3. App thỉnh thoảng bị ANR. Trace cho thấy main thread chờ khoá của CartManager, còn thread sync chờ khoá của UserManager. Với code Java dưới đây, vì sao app treo và bạn phòng tránh thế nào?

    Xem đáp án mẫu
    Đây là deadlock do hai thread xin hai khoá theo thứ tự ngược nhau: thread sync vào checkout() giữ khoá CartManager rồi xin khoá UserManager, đúng lúc main thread vào logout() giữ khoá UserManager rồi xin khoá CartManager. Không bên nào nhả khoá nên main thread treo vĩnh viễn và app bị ANR; trong ANR trace, thread kẹt ở trạng thái Blocked kèm dòng waiting to lock <...> held by thread N, lần theo là thấy vòng chờ. Cách phòng chính: không gọi sang method của object khác (nhất là callback, listener) khi đang giữ khoá, chỉ khoá đúng đoạn đọc ghi state của mình rồi gọi ra ngoài sau khi đã nhả. Nếu buộc phải giữ nhiều khoá thì luôn xin theo một thứ tự cố định trong cả codebase, hoặc dùng ReentrantLock.tryLock có timeout. Với code Kotlin mới, giao state cho một thread hoặc dispatcher đơn luồng thường đơn giản hơn tự quản lý nhiều khoá.
    class CartManager {

}

class UserManager {

  1. Màn Home tải song song banner và danh sách gợi ý bằng hai async trong coroutineScope. Chỉ cần API gợi ý lỗi là cả màn hình báo lỗi, banner cũng mất. Vì sao, và sửa thế nào để khối nào lỗi thì chỉ khối đó lỗi?

    Xem đáp án mẫu
    Đây là structured concurrency: trong coroutineScope, một coroutine con thất bại sẽ huỷ cả scope, kéo theo huỷ mọi coroutine anh em, rồi exception được ném ra khỏi coroutineScope. Muốn các khối độc lập thì dùng supervisorScope: con lỗi không huỷ anh em và không huỷ scope. Với async, exception được giữ trong Deferred và chỉ ném ra khi gọi await(), nên bọc từng await() trong try/catch để biến lỗi thành trạng thái riêng của khối đó, nhớ ném lại CancellationException. supervisorScope vẫn chờ mọi con hoàn thành và vẫn bị huỷ khi scope cha bị huỷ, nên không phá vỡ tính structured.
    suspend fun loadHome(): HomeUi = supervisorScope {
  val banner = async { api.banners() }
  val suggestions = async { api.suggestions() }
  // khối nào lỗi thì null, khối còn lại vẫn hiển thị
  HomeUi(banner.awaitOrNull(), suggestions.awaitOrNull())
}

suspend fun <T> Deferred<T>.awaitOrNull(): T? = try {
  await()
} catch (e: CancellationException) {
  throw e // không nuốt cancellation
} catch (e: Exception) {
  null
}

  2. Bạn gọi job.cancel() nhưng coroutine vẫn tiếp tục chạy: log vẫn in, file vẫn được ghi. Những nguyên nhân thường gặp là gì và xử lý thế nào?

    Xem đáp án mẫu
    Cancellation trong coroutines là cooperative: cancel() chỉ chuyển Job sang trạng thái cancelling, code chỉ dừng khi chạm tới điểm kiểm tra như các hàm suspend của kotlinx.coroutines (delay, withContext, yield…) hoặc khi tự kiểm tra isActive/ensureActive(). Nguyên nhân hay gặp: vòng lặp tính toán nặng không có suspension point; gọi API blocking như Thread.sleep hay IO đồng bộ (dùng runInterruptible nếu cần ngắt được); và nuốt CancellationException bằng catch (e: Exception) hoặc runCatching khiến vòng lặp chạy tiếp. Cách đúng: gọi ensureActive() trong vòng lặp, luôn ném lại CancellationException, và nếu cần gọi hàm suspend để dọn dẹp trong finally thì bọc bằng withContext(NonCancellable).
    suspend fun compressAll(files: List<File>) = withContext(Dispatchers.Default) {
  for (file in files) {
    ensureActive() // ném CancellationException nếu đã bị cancel
    compress(file) // hàm CPU-bound, không suspend
  }
}

try {

  3. ViewModel cần báo cho UI các sự kiện một lần như hiện Snackbar hay điều hướng sau khi lưu thành công. Dùng StateFlow, SharedFlow hay Channel? Mỗi cách có bẫy gì?

    Xem đáp án mẫu

MutableSharedFlow() mặc định replay = 0: nếu lúc emit không có collector (UI đang ở background) thì sự kiện mất luôn. Channel(Channel.BUFFERED) kết hợp receiveAsFlow() giữ sự kiện trong buffer tới khi có người nhận và mỗi sự kiện chỉ giao cho một collector, nên hợp với sự kiện một lần hơn; vẫn còn khe hẹp mất sự kiện nếu collector bị huỷ đúng lúc nhận, thường giảm bằng cách collect trên Dispatchers.Main.immediate. Hướng dẫn kiến trúc của Google còn gợi ý cách khác: mô hình hoá sự kiện thành state (vd. userMessage trong UiState) và để UI báo lại đã xử lý xong để xoá đi.

  4. Vì sao nhiều codebase viết stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), UiState.Loading)? Con số 5000 có ý nghĩa gì, và so với Eagerly/Lazily thì sao?

    Xem đáp án mẫu
    stateIn biến một Flow cold (vd. query Room) thành StateFlow hot dùng chung cho mọi collector, kèm giá trị khởi tạo để UI luôn có gì đó để vẽ. WhileSubscribed(5_000) chỉ chạy upstream khi có ít nhất một collector; khi collector cuối cùng rời đi, nó chờ thêm 5 giây rồi mới dừng upstream. Khi xoay màn hình, UI cũ ngừng collect và UI mới collect lại chỉ sau vài trăm ms nên upstream không bị khởi động lại; còn khi app nằm background lâu, upstream dừng hẳn để không giữ query, listener hay kết nối vô ích. Eagerly chạy ngay và chỉ dừng khi scope bị huỷ; Lazily bắt đầu ở collector đầu tiên rồi cũng chạy mãi, nên dễ tốn tài nguyên khi UI không hiển thị.

  5. Bạn cần bọc một API dạng listener (vd. ConnectivityManager.NetworkCallback) thành Flow. Viết bằng callbackFlow thế nào và cần lưu ý gì?

    Xem đáp án mẫu
    callbackFlow tạo một Flow cold có channel bên trong: mỗi collector đăng ký listener riêng, callback đẩy giá trị bằng trySend (không suspend, gọi được từ thread bất kỳ), và cuối block bắt buộc gọi awaitClose { ... } để giữ flow sống và huỷ đăng ký listener khi collector bị cancel. Thiếu awaitClose thì flow ném IllegalStateException ngay khi block chạy xong. Nếu callback báo lỗi, gọi close(exception) để kết thúc flow với lỗi. Khi listener bắn nhanh hơn tốc độ xử lý thì cấu hình buffer()/conflate(); nếu nhiều màn hình cùng cần dữ liệu thì shareIn/stateIn để không đăng ký listener nhiều lần.
    fun ConnectivityManager.observeOnline(): Flow<Boolean> = callbackFlow {
  val callback = object : ConnectivityManager.NetworkCallback() {
    override fun onAvailable(network: Network) { trySend(true) }
    override fun onLost(network: Network) { trySend(false) }
  }
  registerDefaultNetworkCallback(callback)
  awaitClose { unregisterNetworkCallback(callback) } // chạy khi collector dừng
}.distinctUntilChanged()

  6. Màn Home cần ghép dữ liệu từ ba nguồn Flow độc lập (user, orders từ Room, settings từ DataStore) thành một UiState. Bạn dùng combine, zip hay merge, và những chi tiết nào (giá trị đầu tiên, lỗi, giá trị trùng) hay gây lỗi?

    Xem đáp án mẫu
    combine(a, b, c) { ... } phát một giá trị mỗi khi bất kỳ flow nào phát giá trị mới, kết hợp với giá trị mới nhất của các flow còn lại; đây là lựa chọn đúng khi ghép state từ nhiều nguồn thành một UiState. Chi tiết quan trọng: combine chỉ phát lần đầu khi tất cả các flow đã phát ít nhất một giá trị, nên nếu một nguồn (như settings) chưa bao giờ phát thì màn hình mãi ở trạng thái ban đầu; nguồn có thể chưa có dữ liệu cần onStart { emit(default) }. zip ghép theo cặp một-một (phần tử thứ n của flow này với phần tử thứ n của flow kia) và kết thúc khi một flow kết thúc, hợp cho hai chuỗi có tương ứng thứ tự, hiếm khi đúng cho state UI. merge gộp nhiều flow cùng kiểu thành một dòng xen kẽ theo thời gian, hợp cho sự kiện từ nhiều nguồn (analytics, thông báo). Cần ghép nhiều hơn 5 flow thì dùng combine(listOf(...)). Lỗi: một flow ném exception thì cả combine kết thúc với lỗi, nên catch ngay trên nhánh đó nếu muốn nguồn ấy lỗi mà màn hình vẫn dùng được. Dùng distinctUntilChanged ở nguồn đổi nhiều, và đưa phép biến đổi nặng ra flowOn(Dispatchers.Default) thay vì làm trong lambda của combine trên main. Kết thúc bằng stateIn(viewModelScope, WhileSubscribed(5_000), Loading).
    class HomeViewModel(
  userRepo: UserRepository,
  orderRepo: OrderRepository,
  settings: SettingsRepository,
) : ViewModel() {

  val state: StateFlow<HomeUiState> = combine(
    userRepo.observeUser(),
    orderRepo.observeOrders().catch { emit(emptyList()) }, // nguồn này lỗi thì dùng danh sách rỗng, màn hình vẫn dùng được
    settings.observeCurrency().onStart { emit(Currency.VND) }, // có giá trị mặc định: combine không bị kẹt chờ
  ) { user, orders, currency ->
    HomeUiState.Ready(
      greeting = user.name,
      orders = orders.map { it.toUi(currency) },
    )
  }
    .flowOn(Dispatchers.Default) // phép map nặng không chạy trên main
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), HomeUiState.Loading)
}

  7. Ô tìm kiếm gọi API mỗi lần gõ, kết quả của từ khoá cũ đôi khi về sau và đè lên kết quả mới, đồng thời app gửi quá nhiều request. Bạn dựng pipeline Flow thế nào với debounce, distinctUntilChanged, flatMapLatest, và nó khác flatMapConcat/flatMapMerge ra sao?

    Xem đáp án mẫu
    Giữ query trong một MutableStateFlow rồi biến đổi: debounce(300) chờ user ngừng gõ rồi mới phát, map { it.trim() }, distinctUntilChanged() bỏ lần phát trùng, sau đó flatMapLatest { q -> repo.search(q) }. Mỗi query mới sẽ huỷ flow bên trong của query trước, nên kết quả cũ không bao giờ đè lên kết quả mới. Hai biến thể còn lại không có tính chất này: flatMapMerge chạy các flow song song và phát theo thứ tự hoàn thành, flatMapConcat chạy lần lượt nên phải chờ hết từ khoá cũ mới tới từ khoá mới. Query rỗng nên xử lý riêng (trả trạng thái nhàn rỗi hoặc gợi ý) thay vì gọi API. Bắt lỗi bên trong flatMapLatest (catch ngay trên flow con) để một lần lỗi không làm hỏng cả pipeline, vì lỗi thoát ra ngoài sẽ kết thúc flow và ô tìm kiếm ngừng hoạt động. Kết thúc bằng stateIn(viewModelScope, WhileSubscribed(5_000), initial) để UI collect. Khi test debounce, dùng thời gian ảo của runTest (advanceTimeBy) chứ không delay thật.
    @OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
class SearchViewModel(private val repo: SearchRepository) : ViewModel() {
  private val query = MutableStateFlow("")

  val results: StateFlow<SearchUiState> = query
    .debounce(300) // chờ user ngừng gõ
    .map { it.trim() }
    .distinctUntilChanged()
    .flatMapLatest { q -> // query mới huỷ request của query cũ
      if (q.isEmpty()) {
        flowOf(SearchUiState.Idle)
      } else {
        flow { emit(SearchUiState.Success(repo.search(q))) }
          .onStart { emit(SearchUiState.Loading) }
          .catch { emit(SearchUiState.Error(it.message)) } // lỗi chỉ nằm trong nhánh này
      }
    }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), SearchUiState.Idle)

  fun onQueryChange(text: String) { query.value = text }
}

  1. Collect StateFlow từ ViewModel bằng lifecycleScope.launch { flow.collect { ... } } trong Activity có vấn đề gì? repeatOnLifecycle và collectAsStateWithLifecycle giải quyết ra sao?

    Xem đáp án mẫu
    Coroutine của lifecycleScope chỉ bị huỷ ở onDestroy, nên khi app vào background collector vẫn chạy: UI cập nhật vô ích, và vì vẫn còn subscriber nên upstream dùng WhileSubscribed (GPS, socket, query DB) không bao giờ dừng. Các API cũ như launchWhenStarted chỉ tạm treo coroutine chứ không huỷ, nên upstream vẫn bị giữ, và đã bị deprecated. repeatOnLifecycle(Lifecycle.State.STARTED) chạy block khi lifecycle đạt STARTED, huỷ block khi xuống dưới STARTED (onStop) và chạy lại mỗi lần quay về foreground. Trong Compose, collectAsStateWithLifecycle() làm đúng việc này, khác với collectAsState() vốn collect suốt thời gian composable còn trong composition, kể cả khi app ở background.

  2. Hai Fragment trong cùng một flow cần chia sẻ danh sách sản phẩm đã chọn, và một ViewModel cần productId lúc khởi tạo mà bạn không biết truyền thế nào. ViewModel có những phạm vi nào (Activity, Fragment, nav graph), và truyền tham số bằng SavedStateHandle hay Factory?

  override fun authenticate(route: Route?, response: Response): Request? {
    if (response.priorResponse != null) return null // đã retry mà vẫn 401
    val newToken = synchronized(this) {
      val sent = response.request.header("Authorization")?.removePrefix("Bearer ")
      if (store.accessToken != sent) store.accessToken // thread khác đã refresh
      else authApi.refreshBlocking(store.refreshToken)?.also { store.accessToken = it }
    } ?: return null // refresh thất bại: đăng xuất
    return response.request.newBuilder().header("Authorization", "Bearer $newToken").build()
  }
}

  @Before
  fun setUp() {
    server.start()

      .addConverterFactory(Json.asConverterFactory("application/json".toMediaType()))
      .build()
      .create(UserApi::class.java)
  }

  @After

  @Test
  fun parsesUserAndSendsCorrectRequest() = runTest {

    val user = api.getUser("1")

    assertEquals("/users/1", server.takeRequest().path) // kiểm tra request thật sự đã gửi
  }

  @Test

    assertFailsWith<HttpException> { api.getUser("1") }
  }
}

    Xem đáp án mẫu
    Component có exported="true" cho phép app khác khởi chạy nó (và component có intent-filter thì trước Android 12 mặc định là exported); từ Android 12 phải khai báo tường minh. Component không cần mở cho bên ngoài thì đặt exported="false"; component phải công khai thì coi mọi extra là input không đáng tin, validate kỹ và kiểm tra quyền của người gọi. Lỗi intent redirection: lấy một Intent từ extra do app khác gửi rồi startActivity nó có thể bị lợi dụng để mở component không export của chính app. PendingIntent mutable có thể bị bên nhận sửa nội dung; từ Android 12 bắt buộc khai báo FLAG_IMMUTABLE (chỉ dùng FLAG_MUTABLE khi thật cần như inline reply) và nên dùng explicit intent. WebView: chỉ tải nội dung tin cậy qua HTTPS, tắt allowFileAccess và allowContentAccess nếu không cần, tránh addJavascriptInterface với nội dung bên ngoài vì JS trong trang gọi được vào method của app (chỉ method có @JavascriptInterface bị lộ nhưng vẫn là bề mặt tấn công), kiểm tra URL trong shouldOverrideUrlLoading. Dữ liệu nhạy cảm: không để token dạng rõ trong SharedPreferences hay DataStore mà mã hoá bằng khoá trong Keystore, không log, loại khỏi backup (android:allowBackup="false" hoặc dataExtractionRules), và cấm cleartext traffic (usesCleartextTraffic="false" hoặc network security config). Cuối cùng chạy lint bảo mật, và pentest hay quét bằng công cụ như MobSF trước khi phát hành.
