  1. val và var khác nhau thế nào? Khai báo val list = mutableListOf(1, 2) rồi gọi list.add(3) có được không?

    Xem đáp án mẫu
    var là biến gán lại được, còn val là tham chiếu chỉ gán một lần (read-only), tương tự final trong Java. val chỉ khoá tham chiếu chứ không khoá object nó trỏ tới: list.add(3) vẫn chạy vì MutableList cho sửa nội dung, chỉ có gán list = ... sang list khác mới lỗi compile. Muốn nội dung cũng không sửa được thì dùng kiểu read-only List (tạo bằng listOf). Riêng const val là hằng compile-time, chỉ nhận kiểu nguyên thuỷ hoặc String và chỉ khai báo ở top-level, trong object hoặc companion object. Thói quen tốt là mặc định dùng val, chỉ chuyển sang var khi thật sự cần gán lại.
    const val MAX_RETRY = 3 // hằng compile-time, khai báo ở top-level

fun main() {
  val list = mutableListOf(1, 2)
  list.add(3)               // OK: sửa nội dung object
  // list = mutableListOf() // lỗi compile: val không gán lại được

  var count = 0
  count += 1                // OK
  println("$list $count")   // [1, 2, 3] 1
}

  2. Kotlin chống NullPointerException bằng cách nào? Giải thích ?., ?: và !! qua ví dụ.

    Xem đáp án mẫu
    Kotlin tách kiểu non-null (String) và nullable (String?); compiler không cho gọi thẳng method trên kiểu nullable, nên phần lớn lỗi null bị chặn ngay lúc compile thay vì crash lúc chạy. ?. (safe call) chỉ gọi khi giá trị khác null, ngược lại cả biểu thức trả về null. ?: (Elvis) đưa ra giá trị thay thế khi vế trái là null, hay dùng kèm return để thoát sớm khỏi hàm. !! ép về non-null và ném NullPointerException nếu giá trị đang là null, nên chỉ dùng khi thật sự chắc chắn; thấy !! rải rác khắp code thường là dấu hiệu xử lý null chưa tốt.
    fun greet(name: String?) {
  val length = name?.length ?: 0   // null thì lấy 0
  println("Độ dài: $length")

  val upper = name?.uppercase()     // kiểu String?
  println(upper)                    // có thể in ra null

  println(name!!.length)            // name null -> NullPointerException
}

  3. data class trong Kotlin tự sinh ra những gì? Khi nào nên dùng nó?

    Xem đáp án mẫu
    Dựa trên các property khai báo trong primary constructor, data class tự sinh equals()/hashCode() so sánh theo giá trị, toString() dễ đọc, copy() để tạo bản sao đổi vài field, và các hàm componentN() cho destructuring. Nhờ vậy hai object cùng dữ liệu được coi là bằng nhau, rất hợp cho model nhận từ API, item trong danh sách hay UI state. Lưu ý: property khai báo trong thân class không tham gia equals/toString/copy; primary constructor phải có ít nhất một tham số và mọi tham số đều là val/var; copy() chỉ là shallow copy. Nên dùng val để object bất biến, cần đổi thì gọi copy().
    data class User(val id: Int, val name: String)

fun main() {
  val a = User(1, "An")
  val b = User(1, "An")
  println(a == b)             // true: so sánh theo giá trị
  println(a)                  // User(id=1, name=An)

  val c = a.copy(name = "Bình")
  val (id, name) = c          // destructuring
  println("$id $name")        // 1 Bình
}

  4. when trong Kotlin khác switch của Java ở những điểm nào?

    Xem đáp án mẫu
    when không cần break và không có fall-through: nhánh đầu tiên khớp sẽ chạy rồi thoát. Điều kiện linh hoạt hơn nhiều: gộp nhiều giá trị bằng dấu phẩy, kiểm tra khoảng với in 5..7, kiểm tra kiểu với is (kèm smart cast), hoặc viết when không có đối số để thay chuỗi if-else if dài. when còn là expression nên trả về được giá trị; khi dùng như expression thì phải phủ hết mọi trường hợp, thường bằng nhánh else (với enum hay sealed class đã liệt kê đủ thì không cần else).
    fun grade(score: Int): String = when (score) {
  10 -> "Xuất sắc"
  8, 9 -> "Giỏi"
  in 5..7 -> "Khá"
  else -> "Cần cố gắng"
}

fun describe(x: Any): String = when (x) {
  is String -> "Chuỗi dài ${x.length}" // smart cast sang String
  is Int -> "Số $x"
  else -> "Kiểu khác"
}

  5. List và MutableList trong Kotlin khác nhau thế nào? Các hàm như filter, map có sửa list gốc không?

    Xem đáp án mẫu
    Kotlin tách interface read-only (List, Set, Map) và mutable (MutableList, MutableSet, MutableMap): listOf() trả về List không có add/remove, còn mutableListOf() cho phép sửa. Read-only nghĩa là không sửa được qua tham chiếu đó, chưa chắc object bên dưới bất biến; thói quen tốt là giữ MutableList private trong class và chỉ expose List ra ngoài. filter, map, sortedBy không đụng vào list gốc mà trả về list mới, nên nối chuỗi gọi rất gọn. Bẫy hay gặp: sort() mới là hàm sắp xếp tại chỗ trên MutableList, còn sorted() trả về list mới và gọi xong không gán lại thì coi như không làm gì.
    data class Product(val name: String, val price: Int)

val products = listOf(
  Product("Áo", 200), Product("Mũ", 50), Product("Giày", 500)
)

val names = products
  .filter { it.price >= 100 }      // bỏ sản phẩm dưới 100
  .sortedByDescending { it.price }
  .map { it.name }

println(names) // [Giày, Áo]

  6. Extension function là gì? Nó có thực sự thêm method vào class gốc không?

    Xem đáp án mẫu
    Extension function cho phép viết thêm hàm cho một class có sẵn (kể cả String hay class của thư viện) mà không cần kế thừa hay sửa source, rồi gọi như method bình thường: "0912345678".isValidPhone(). Thực chất compiler biến nó thành hàm static nhận object làm tham số đầu tiên, nên class gốc không hề thay đổi. Vì vậy extension không truy cập được member private, được chọn theo kiểu khai báo lúc compile chứ không đa hình, và nếu trùng signature với member function thì member luôn thắng. Hợp nhất cho các tiện ích nhỏ như kiểm tra dữ liệu, format chuỗi, ẩn/hiện View; tránh nhồi logic nghiệp vụ vào extension.
    fun String.isValidPhone(): Boolean =
  length == 10 && startsWith("0") && all { it.isDigit() }

fun String.toSlug(): String = trim().lowercase().replace(" ", "-")

fun main() {
  println("0912345678".isValidPhone()) // true
  println(" Hello World ".toSlug())     // hello-world
}

Java & JVM

Mọi rank →

  1. Abstract class và interface trong Java khác nhau thế nào? Khi nào chọn cái nào?

    Xem đáp án mẫu
    Abstract class có thể có state (field instance), constructor, cả method đã cài đặt lẫn method abstract, nhưng một class chỉ extends được một class. Interface mô tả một hợp đồng hành vi; một class implements được nhiều interface, và từ Java 8 interface có thêm default method và static method, nhưng vẫn không có field instance (field nào cũng là hằng public static final) và không có constructor. Chọn abstract class khi các lớp con thực sự là cùng một loại và cần chia sẻ code, state (ví dụ một BaseActivity). Chọn interface khi nhiều class không liên quan cần cùng một khả năng, như Comparable hay các listener kiểu OnClickListener.

  2. Overload và override khác nhau thế nào? Cái nào được quyết định lúc compile, cái nào lúc runtime?

    Xem đáp án mẫu
    Overload là nhiều method cùng tên trong một class nhưng khác danh sách tham số (số lượng hoặc kiểu); compiler chọn method nào ngay lúc compile dựa trên kiểu khai báo của đối số. Chỉ khác kiểu trả về thì không phải overload hợp lệ. Override là lớp con định nghĩa lại method của lớp cha với cùng signature; method nào chạy được quyết định lúc runtime theo kiểu thực của object (dynamic dispatch). Khi override nên luôn gắn @Override để compiler bắt lỗi gõ sai tên hay tham số; không được thu hẹp access modifier, và method static, private, final thì không override được.
    class Animal {
  void speak() { System.out.println("..."); }
}

class Dog extends Animal {
  @Override
  void speak() { System.out.println("Gâu"); } // override

  void speak(int times) {                     // overload
    for (int i = 0; i < times; i++) speak();
  }
}

Animal a = new Dog();
a.speak(); // in "Gâu": quyết định lúc runtime

  3. Vì sao override equals() trong Java thì phải override cả hashCode()? Quên thì chuyện gì xảy ra?

    Xem đáp án mẫu
    Hợp đồng của Object quy định: hai object equals nhau thì bắt buộc có cùng hashCode. HashMap và HashSet dùng hashCode để chọn bucket trước rồi mới so equals; nếu chỉ override equals, hai object bằng nhau vẫn mang hashCode mặc định (thường khác nhau) nên rơi vào bucket khác. Hậu quả là set.contains(...) trả về false, HashSet chứa phần tử trùng, map.get(...) không tìm thấy dù key "bằng" nhau. Chiều ngược lại không bắt buộc: trùng hashCode chưa chắc equals. Nên tính hash từ đúng các field dùng trong equals (ví dụ Objects.hash(...)); trong Kotlin, data class đã tự sinh cả hai.
    class Point {
  final int x, y;
  Point(int x, int y) { this.x = x; this.y = y; }

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point)) return false;
    Point p = (Point) o;
    return x == p.x && y == p.y;
  }

  @Override
  public int hashCode() { return Objects.hash(x, y); }
}

  4. Vì sao String trong Java là immutable? Nối chuỗi nhiều lần trong vòng lặp nên dùng gì?

    Xem đáp án mẫu
    Mọi thao tác như concat, replace, toUpperCase đều trả về một String mới, object cũ giữ nguyên. Thiết kế này giúp String dùng chung an toàn giữa nhiều thread, làm key của HashMap ổn định (hash không đổi nên cache lại được), cho phép JVM dùng chung các literal trong String pool, và an toàn khi truyền làm đường dẫn file hay URL. Mặt trái là nối bằng + trong vòng lặp tạo ra nhiều object trung gian; khi đó dùng StringBuilder (nhanh, không thread-safe) thay vì StringBuffer (có synchronized). Bẫy hay gặp: gọi s.toUpperCase(); mà không gán lại thì s không đổi.
    String s = "hello";
s.toUpperCase();          // không gán lại -> s vẫn là "hello"
s = s.toUpperCase();      // s trỏ tới object mới "HELLO"

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 3; i++) {
  sb.append(i).append(',');
}
System.out.println(sb);   // 0,1,2,

  5. Checked exception và unchecked exception khác nhau thế nào? Gọi một hàm Java ném IOException từ Kotlin thì cần lưu ý gì?

    Xem đáp án mẫu
    Checked exception là lớp con của Exception nhưng không thuộc nhánh RuntimeException (ví dụ IOException); compiler Java bắt buộc phải try/catch hoặc khai báo throws. Unchecked exception là RuntimeException và các lớp con (NullPointerException, IllegalArgumentException, IndexOutOfBoundsException), thường do lỗi lập trình nên không bắt buộc xử lý; Error như OutOfMemoryError cũng không bị kiểm tra. Kotlin không có checked exception, nên khi gọi API Java ném IOException compiler không nhắc gì, bạn phải tự nhớ bắt lỗi nếu không muốn app crash. Ngược lại, hàm Kotlin muốn code Java bắt buộc xử lý exception thì gắn @Throws(IOException::class).

Activity, Fragment & Lifecycle

Mọi rank →

  1. Kể tên 4 thành phần chính (app component) của một ứng dụng Android và vai trò của từng thành phần.

    Xem đáp án mẫu
    Activity là một màn hình có giao diện, nơi người dùng tương tác trực tiếp. Service chạy tác vụ không cần giao diện, như phát nhạc hay đồng bộ dữ liệu. BroadcastReceiver nhận sự kiện do hệ thống hoặc app khác phát ra, ví dụ máy khởi động xong (BOOT_COMPLETED), pin yếu hay bật chế độ máy bay. ContentProvider chia sẻ dữ liệu có cấu trúc giữa các app qua URI content://, ví dụ danh bạ hay thư viện ảnh. Cả bốn đều là điểm mà hệ thống có thể khởi động app của bạn, và đều khai báo trong AndroidManifest.xml (riêng BroadcastReceiver còn đăng ký động bằng code được).

  2. File AndroidManifest.xml dùng để làm gì? Muốn một Activity hiện icon ở launcher thì khai báo thế nào?

    Xem đáp án mẫu
    Manifest là bản mô tả app cho hệ thống: các component (Activity, Service, BroadcastReceiver, ContentProvider), quyền cần dùng (uses-permission), icon, theme và các intent-filter. Component không khai báo thì hệ thống không biết tới; ví dụ quên khai báo Activity mà gọi startActivity sẽ crash với ActivityNotFoundException. Activity mở đầu tiên từ launcher cần intent-filter gồm action MAIN và category LAUNCHER. Với app target Android 12 (API 31) trở lên, component nào có intent-filter phải khai báo rõ android:exported; thiếu thuộc tính này thì Android Studio báo lỗi khi build và app không cài được lên máy Android 12 trở lên.
    <manifest xmlns:android="http://schemas.android.com/apk/res/android">
  <uses-permission android:name="android.permission.INTERNET" />

  <application android:label="@string/app_name">
    <activity
      android:name=".MainActivity"
      android:exported="true">
      <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
      </intent-filter>
    </activity>
  </application>
</manifest>

  3. Kể các callback chính trong vòng đời Activity. Từ màn A mở màn B (B che kín A) rồi bấm Back thì thứ tự gọi thế nào?

    Xem đáp án mẫu
    Các callback chính: onCreate (khởi tạo, gọi setContentView), onStart (bắt đầu hiển thị), onResume (ở foreground, nhận tương tác), onPause (mất focus), onStop (không còn hiển thị), onDestroy (bị huỷ); ngoài ra onRestart chạy trước onStart khi quay lại từ trạng thái stopped. Mở B: A.onPause → B.onCreate → B.onStart → B.onResume → A.onStop. A chỉ stop sau khi B đã hiện lên, vì vậy onPause phải thật nhanh, không làm việc nặng. Bấm Back: B.onPause → A.onRestart → A.onStart → A.onResume → B.onStop → B.onDestroy. Nếu B trong suốt hoặc dạng dialog, không che kín A, thì A chỉ dừng ở onPause.

  4. Explicit intent và implicit intent khác nhau thế nào? Khi dùng implicit intent cần cẩn thận điều gì?

    Xem đáp án mẫu
    Explicit intent chỉ rõ component đích bằng class, dùng để mở màn hình hay service trong chính app: Intent(this, DetailActivity::class.java). Implicit intent chỉ mô tả hành động (ACTION_VIEW, ACTION_SEND, ACTION_DIAL) kèm data, hệ thống tìm các app có intent-filter phù hợp để xử lý, có nhiều app thì hiện hộp chọn. Nếu không có app nào nhận, startActivity ném ActivityNotFoundException, nên phải bắt exception này. Khi target Android 11 trở lên, kiểm tra trước bằng resolveActivity còn cần khai báo <queries> trong manifest, vì vậy bắt exception là cách đơn giản hơn. Riêng Service thì luôn dùng explicit intent.
    // Explicit: mở màn hình trong app
startActivity(Intent(this, DetailActivity::class.java))

// Implicit: nhờ app khác mở link
val intent = Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"))
try {
  startActivity(intent)
} catch (e: ActivityNotFoundException) {
  Toast.makeText(this, "Không có app mở được link", Toast.LENGTH_SHORT).show()
}

  5. Fragment là gì, vì sao dùng Fragment thay vì tạo nhiều Activity? Truyền dữ liệu vào Fragment thế nào cho đúng?

    Xem đáp án mẫu
    Fragment là một phần giao diện có vòng đời riêng nhưng luôn phải nằm trong một Activity (hoặc Fragment khác) và được quản lý bởi FragmentManager. Dùng Fragment giúp tái sử dụng UI, chia màn hình lớn thành nhiều phần (tablet hiện list và chi tiết cạnh nhau), làm tab hay bottom navigation trong một Activity. Dữ liệu nên truyền qua arguments (một Bundle) chứ không qua constructor có tham số: khi xoay màn hình hoặc process bị huỷ, hệ thống mặc định tạo lại Fragment bằng constructor rỗng và chỉ khôi phục arguments. Truyền qua constructor thì dữ liệu sẽ mất, thậm chí crash nếu class không có constructor rỗng.
    class DetailFragment : Fragment(R.layout.fragment_detail) {
  companion object {
    fun newInstance(productId: Int) = DetailFragment().apply {
      arguments = bundleOf("product_id" to productId)
    }
  }

  override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)
    val id = requireArguments().getInt("product_id")
    // hiển thị chi tiết sản phẩm theo id
  }
}

Jetpack Compose & View

Mọi rank →

  1. dp, sp và px khác nhau thế nào? Vì sao cỡ chữ nên dùng sp?

    Xem đáp án mẫu
    px là pixel vật lý, nên cùng một giá trị trông to nhỏ khác nhau trên các máy có mật độ điểm ảnh khác nhau. dp (density-independent pixel) được quy đổi theo mật độ màn hình: 1dp bằng 1px ở mdpi (160dpi) và bằng 3px ở xxhdpi (480dpi), nên kích thước hiển thị gần như nhau trên mọi máy; dùng cho kích thước, margin, padding. sp giống dp nhưng còn co giãn theo cỡ chữ người dùng chọn trong cài đặt, nên dùng cho text để tôn trọng accessibility. Bẫy hay gặp: đặt chiều cao cố định bằng dp cho View chứa text, người dùng tăng cỡ chữ thì text bị cắt; nên để wrap_content hoặc dùng minHeight.

  2. Khi nào dùng LinearLayout, khi nào dùng ConstraintLayout? layout_weight hoạt động thế nào?

    Xem đáp án mẫu
    LinearLayout xếp các view con thành một hàng (horizontal) hoặc một cột (vertical), rất dễ dùng cho bố cục đơn giản. Khi giao diện phức tạp, lồng nhiều LinearLayout làm cây view sâu và tốn thời gian measure/layout, nhất là layout_weight lồng nhau khiến view con bị đo nhiều lần. ConstraintLayout định vị từng view bằng ràng buộc với parent hoặc view khác, nhờ đó dựng màn hình phức tạp mà cây view vẫn phẳng. layout_weight chia phần không gian còn trống theo tỉ lệ; muốn chia đúng tỉ lệ thì đặt kích thước theo chiều đó là 0dp, ví dụ hai nút weight 1 và 2 sẽ chiếm 1/3 và 2/3 chiều ngang.

  3. RecyclerView gồm những thành phần nào? Vì sao nó hiệu quả hơn việc tạo sẵn view cho từng item trong một ScrollView?

    Xem đáp án mẫu
    RecyclerView cần LayoutManager (xếp item dạng list dọc/ngang hay lưới), Adapter (biết có bao nhiêu item và bind dữ liệu vào view) và ViewHolder (giữ sẵn tham chiếu tới các view con của một item). Thay vì tạo view cho mọi item, nó chỉ tạo đủ view để lấp màn hình cộng vài view dự phòng; khi cuộn, view ra khỏi màn hình được tái sử dụng cho item mới và chỉ cần gọi lại onBindViewHolder để đổ dữ liệu. Nhờ vậy list hàng nghìn phần tử vẫn mượt và tốn ít bộ nhớ. Bẫy hay gặp: vì view bị tái sử dụng, trong onBindViewHolder phải set lại mọi trạng thái ở cả nhánh if lẫn else, nếu không item mới sẽ mang trạng thái của item cũ.
    class UserAdapter(private val users: List<User>) :
  RecyclerView.Adapter<UserAdapter.VH>() {
  class VH(view: View) : RecyclerView.ViewHolder(view) {
    val name: TextView = view.findViewById(R.id.tvName)
  }
  override fun onCreateViewHolder(parent: ViewGroup, viewType: Int) = VH(
    LayoutInflater.from(parent.context).inflate(R.layout.item_user, parent, false)
  )
  override fun onBindViewHolder(holder: VH, position: Int) {
    holder.name.text = users[position].name
  }
  override fun getItemCount() = users.size
}

  4. Trong Jetpack Compose, hàm @Composable là gì? Column, Row, Box khác nhau thế nào và vì sao thứ tự gọi Modifier lại quan trọng?

    Xem đáp án mẫu
    @Composable đánh dấu một hàm mô tả UI: thay vì tạo rồi sửa từng View, bạn gọi hàm với dữ liệu hiện tại và Compose tự vẽ lại (recompose) khi dữ liệu đổi. Column xếp các con theo chiều dọc, Row theo chiều ngang, còn Box xếp chồng các con lên nhau, hay dùng cho badge hoặc chữ đè lên ảnh. Modifier là một chuỗi áp dụng lần lượt theo thứ tự viết: padding(16.dp).background(Color.Red) thì nền đỏ nằm bên trong phần padding, còn background(Color.Red).padding(16.dp) thì nền phủ cả vùng padding. Tương tự, đặt clickable trước hay sau padding quyết định vùng bấm có gồm phần padding hay không.

  5. Bấm nút nhưng số đếm trên màn hình Compose không tăng. Đoạn code sau sai ở đâu và sửa thế nào?

    Xem đáp án mẫu
    count là biến local thường: tăng nó không báo cho Compose biết cần vẽ lại, và kể cả khi hàm được gọi lại thì count lại khởi tạo về 0. Cần hai thứ: mutableStateOf để Compose theo dõi giá trị và lên lịch recomposition khi giá trị đổi, và remember để giữ state qua các lần recompose. Sửa thành var count by remember { mutableStateOf(0) } (cần import getValue/setValue của androidx.compose.runtime). Lưu ý remember chỉ sống khi composable còn trong cây; xoay màn hình làm Activity bị tạo lại thì giá trị vẫn mất, muốn giữ thì dùng rememberSaveable hoặc đưa state lên ViewModel.
    @Composable
fun Counter() {
  var count = 0
  Button(onClick = { count++ }) {
    Text("Đã bấm $count lần")
  }
}

  1. Truyền dữ liệu từ màn danh sách sang màn chi tiết bằng Intent thế nào? Muốn truyền cả một object thì làm sao?

    Xem đáp án mẫu
    Ở màn gửi dùng putExtra với cặp key–value kiểu cơ bản (Int, String, Boolean…), ở màn nhận đọc lại bằng intent.getIntExtra, getStringExtra…; key nên là hằng số dùng chung để tránh gõ sai. Với object, cho class implement Parcelable (trong Kotlin dùng plugin kotlin-parcelize với @Parcelize cho gọn) rồi đọc bằng IntentCompat.getParcelableExtra, vì bản getParcelableExtra(key) cũ đã deprecated từ Android 13. Serializable cũng dùng được nhưng chậm hơn do dựa vào reflection. Chỉ nên truyền dữ liệu nhỏ như id: Intent đi qua Binder có giới hạn kích thước, nhét list lớn hay bitmap dễ gặp TransactionTooLargeException; màn chi tiết nên nhận id rồi tự tải dữ liệu.

  1. SharedPreferences dùng để lưu gì? commit() và apply() khác nhau thế nào?

    Xem đáp án mẫu
    SharedPreferences lưu các cặp key–value nhỏ kiểu cơ bản (Boolean, Int, String, Set<String>…) vào một file XML trong thư mục riêng của app, hợp cho cài đặt như theme, ngôn ngữ, đã xem onboarding chưa. commit() ghi xuống đĩa đồng bộ và trả về Boolean báo thành công, gọi trên main thread có thể làm giật UI; apply() cập nhật bộ nhớ ngay rồi ghi đĩa bất đồng bộ, không trả kết quả, thường là lựa chọn mặc định. Không dùng nó cho dữ liệu lớn hay có cấu trúc (dùng Room) và không lưu token, mật khẩu dạng plain text. Với code mới, Jetpack DataStore là lựa chọn được khuyến nghị thay thế vì API bất đồng bộ và an toàn hơn.

Background & Service

Mọi rank →

  1. Service có tự chạy trên background thread không? Viết code tải file ngay trong onStartCommand có vấn đề gì?

    Xem đáp án mẫu
    Không. Service chỉ là component không có giao diện, mặc định chạy trên main thread của process giống như Activity. Tải file hay gọi mạng trực tiếp trong onStartCommand sẽ chặn main thread, làm đơ UI và có thể gây ANR, nên phải tự đưa việc nặng sang thread khác (coroutine, executor). Ngoài ra từ Android 8.0, hệ thống giới hạn background service khi app không ở foreground: việc người dùng đang thấy như phát nhạc dùng foreground service kèm notification, còn việc có thể hoãn nhưng phải chắc chắn chạy (đồng bộ, upload log) thì dùng WorkManager. IntentService từng tự chạy trên worker thread nhưng đã deprecated.

Gradle & Build

Mọi rank →

  1. APK và AAB khác nhau thế nào? Vì sao Google Play yêu cầu AAB?

    Xem đáp án mẫu
    APK là file cài đặt mà thiết bị chạy được trực tiếp. AAB (Android App Bundle) là định dạng để publish lên Google Play chứ không cài thẳng lên máy; Play dùng nó sinh ra các APK tối ưu riêng cho từng thiết bị (tách theo ABI của CPU, mật độ màn hình, ngôn ngữ), nên người dùng tải về ít dung lượng hơn. Từ tháng 8/2021, app mới đăng lên Google Play bắt buộc dùng AAB. Vì Play tự build APK từ AAB nên cần Play App Signing: Google giữ app signing key, còn bạn ký bản upload bằng upload key. Muốn cài thử AAB lên máy thì dùng bundletool để sinh APK; còn gửi bản test trực tiếp cho tester thì thường build APK.
