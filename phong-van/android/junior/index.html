  1. Trong code review, bạn thấy đồng nghiệp dùng lẫn lộn let, apply, also, run. Bạn giải thích cách chọn scope function thế nào?

    Xem đáp án mẫu
    Chọn theo hai câu hỏi: trong block tham chiếu object bằng this hay it, và block trả về gì. apply (this, trả về chính object) hợp để cấu hình object vừa tạo; also (it, trả về chính object) cho việc phụ như log, validate mà không làm đứt chuỗi gọi; let (it, trả về kết quả lambda) hay đi cùng ?. để xử lý giá trị nullable hoặc biến đổi giá trị; run (this, trả về kết quả lambda) khi vừa truy cập member vừa tính ra một giá trị, còn with(obj) { } giống run nhưng không phải extension. Bẫy hay gặp là lồng nhiều scope function khiến this/it bị che và rất khó đọc; quá hai tầng thì nên tách ra biến có tên rõ ràng.
    val intent = Intent(context, DetailActivity::class.java).apply {
    putExtra("product_id", productId) // this = Intent, trả về Intent
}

val nameLength = user?.name?.let { it.trim().length } ?: 0 // trả về Int

val saved = repository.save(order).also { log("Đã lưu ${it.id}") }

  2. lateinit var và val ... by lazy khác nhau thế nào? Khi nào app crash với UninitializedPropertyAccessException?

    Xem đáp án mẫu
    lateinit dành cho var kiểu non-null và không phải primitive, được gán từ bên ngoài sau khi tạo object, ví dụ binding gán trong onCreate hay field được inject. Đọc nó trước khi gán sẽ ném UninitializedPropertyAccessException, hay gặp khi callback hoặc observer chạy sớm hơn chỗ khởi tạo; có thể kiểm tra bằng ::binding.isInitialized. by lazy dành cho val: lambda khởi tạo chạy ở lần đọc đầu tiên rồi cache kết quả, mặc định thread-safe (LazyThreadSafetyMode.SYNCHRONIZED). Bẫy với lazy là cache thứ gắn với lifecycle: trong Fragment, lazy tham chiếu tới view sẽ giữ view cũ sau khi Fragment tạo lại view lúc quay về từ back stack.

  3. Màn thanh toán hỗ trợ tiền mặt, thẻ (kèm 4 số cuối) và ví điện tử (kèm tên ví). Vì sao enum class không đủ để mô tả, và bạn dùng sealed class/sealed interface thế nào?

    Xem đáp án mẫu
    Mỗi hằng của enum class là một instance duy nhất được tạo sẵn, mọi hằng có cùng tập property với giá trị cố định, nên không gắn được dữ liệu riêng cho từng lần dùng: không thể có Card mang số 1234 cho đơn này và 5678 cho đơn khác. sealed cũng giới hạn tập kiểu con ngay lúc compile (chỉ khai báo được trong cùng module và cùng package), nhưng mỗi kiểu con là class bình thường: có thể là data class mang field riêng và tạo bao nhiêu instance cũng được; kiểu không cần dữ liệu thì dùng data object. Vì compiler biết đủ các kiểu con, when trên kiểu sealed phủ hết các nhánh mà không cần else; thêm phương thức thanh toán mới thì mọi chỗ chưa xử lý báo lỗi compile, miễn là không viết nhánh else. enum vẫn hợp với tập giá trị cố định không mang dữ liệu riêng, như SortOrder.ASC/DESC.
    sealed interface PaymentMethod {
    data object Cash : PaymentMethod
    data class Card(val last4: String) : PaymentMethod
    data class EWallet(val provider: String) : PaymentMethod
}

fun label(method: PaymentMethod): String = when (method) {
    PaymentMethod.Cash -> "Tiền mặt"
    is PaymentMethod.Card -> "Thẻ **** ${method.last4}"
    is PaymentMethod.EWallet -> "Ví ${method.provider}"
}

  4. Gọi một method Java trả về String từ Kotlin, code compile bình thường nhưng crash NullPointerException lúc chạy. Vì sao Kotlin không chặn được lúc compile?

    Xem đáp án mẫu
    Kiểu trả về từ Java không có thông tin nullability nên Kotlin coi là platform type, IDE hiển thị là String!: compiler cho phép dùng như String hay String? và không bắt kiểm tra null. Nếu gán vào biến khai báo String, Kotlin chèn kiểm tra và ném NullPointerException ngay tại dòng gán khi Java trả về null; nếu dùng thẳng (gọi .length) thì NPE xảy ra ở lời gọi đó. Cách an toàn là khai báo rõ String? khi không chắc chắn, và phía Java nên gắn @Nullable/@NonNull (của androidx.annotation) để Kotlin nhận đúng kiểu. Phần lớn API của Android SDK và AndroidX đã có sẵn các annotation này.
    // Java: public String getNickname() { return nickname; } // có thể trả về null

val nick: String = javaUser.nickname   // crash ngay tại đây nếu null
val safe: String? = javaUser.nickname  // phải tự xử lý null
val display = safe ?: "Khách"

  5. Chuỗi list.filter { }.map { }.first() trên danh sách vài chục nghìn phần tử chạy chậm và tốn bộ nhớ. Sequence khác List ở điểm nào, và khi nào nên gọi asSequence()?

    Xem đáp án mẫu
    Các hàm trên List/Iterable là eager: mỗi bước (filter, map) duyệt hết cả danh sách và tạo một list trung gian rồi mới sang bước sau. Sequence là lazy: các bước trung gian chỉ được ghi lại, tới thao tác kết thúc (first, toList, count) mới chạy, và từng phần tử đi qua cả chuỗi bước rồi mới tới phần tử kế tiếp. Nhờ vậy không có list trung gian và có thể dừng sớm với first, take, find. Nên dùng khi danh sách lớn, nhiều bước biến đổi hoặc chỉ cần vài phần tử đầu; với list nhỏ hoặc chỉ một bước thì List thường nhanh hơn, không cần asSequence(). Bẫy: Sequence không có size hay truy cập theo index, mỗi lần gọi thao tác kết thúc thường chạy lại cả chuỗi nên cần toList() nếu dùng kết quả nhiều lần, và lambda có side effect (log, đổi biến bên ngoài) chạy theo thứ tự khác hẳn bản List.
    val result = listOf(1, 2, 3, 4)
    .asSequence()
    .filter { println("filter $it"); it % 2 == 0 }
    .map { println("map $it"); it * 10 }
    .first()
// In ra: filter 1, filter 2, map 2; result = 20, hai phần tử 3 và 4 không bao giờ được duyệt
// Với List: in filter 1-4 trước, rồi mới map 2 và map 4

  1. HashMap trong Java tìm phần tử thế nào? Vì sao dùng object có thể thay đổi (mutable) làm key là nguy hiểm?

    Xem đáp án mẫu
    HashMap lưu entry trong một mảng bucket: khi put/get, nó gọi hashCode() của key để chọn bucket, rồi dùng equals() để so với các key trong bucket đó. Nhiều key rơi vào cùng bucket (collision) được nối thành danh sách, và từ Java 8 bucket quá dài được chuyển thành cây để tránh tìm kiếm tuyến tính. Nếu sửa field tham gia tính hashCode sau khi đã put, lần get sau tính ra hash khác nên tìm sai chỗ và trả về null, dù entry vẫn nằm trong map. Vì vậy key nên là kiểu immutable (String, Integer, data class chỉ có val), và nhớ HashMap không thread-safe.
    Map<Point, String> map = new HashMap<>();
Point p = new Point(1, 2); // equals/hashCode tính từ x, y
map.put(p, "A");

p.x = 5; // sửa field tham gia hashCode sau khi put
System.out.println(map.get(p));         // null: tìm sai bucket
System.out.println(map.containsValue("A")); // true: entry vẫn còn đó

  2. Trong Java, vì sao s1 == s2 lúc đúng lúc sai với hai String cùng nội dung? Sang Kotlin thì == có bị như vậy không?

    Xem đáp án mẫu
    Trong Java, == với object so sánh tham chiếu, còn equals() mới so nội dung. String literal được intern vào String pool nên hai literal giống nhau trỏ cùng một object và == tình cờ ra true; còn String tạo lúc runtime (new String(...), nối chuỗi với biến, đọc từ API hay EditText) là object mới nên == ra false. Vì vậy luôn so String bằng equals(), hoặc viết "admin".equals(role) để không NPE khi role là null. Trong Kotlin, == gọi equals() và xử lý sẵn null, còn so tham chiếu phải dùng ===, nên bẫy này chủ yếu gặp khi đọc hoặc sửa code Java cũ.
    String a = "android";
String b = "android";
String c = new String("android");

System.out.println(a == b);      // true: cùng object trong String pool
System.out.println(a == c);      // false: c là object mới
System.out.println(a.equals(c)); // true: so nội dung

  3. Vì sao trong Java, biến local dùng bên trong lambda hoặc anonymous class phải là final hoặc effectively final? Kotlin xử lý khác thế nào?

    Xem đáp án mẫu
    Lambda hay anonymous class có thể chạy sau khi method đã return (callback click, callback mạng), lúc đó biến local trên stack không còn nữa. Java giải quyết bằng cách copy giá trị biến vào lambda; để bản copy và biến gốc không bao giờ lệch nhau, Java chỉ cho capture biến không bị gán lại sau khi khởi tạo (effectively final). Muốn thay đổi giá trị thì dùng field của class hoặc bọc trong object như AtomicInteger. Kotlin cho phép lambda sửa var local bằng cách tự bọc biến vào một object Ref ở bytecode; tiện, nhưng nên nhớ nếu lambda chạy ở thread khác thì biến đó bị đọc ghi từ nhiều thread.
    int count = 0;
button.setOnClickListener(v -> {
    count++; // lỗi compile: count không effectively final
});

AtomicInteger clicks = new AtomicInteger();
button.setOnClickListener(v -> clicks.incrementAndGet()); // hợp lệ

  4. Generics trong Java bị type erasure nghĩa là gì? Nó gây ra lỗi gì khi parse JSON thành List<User> bằng Gson?

    Xem đáp án mẫu
    Thông tin kiểu generic chỉ được compiler dùng để kiểm tra lúc compile rồi bị xoá khỏi bytecode: lúc runtime List<User> và List<String> đều chỉ là List. Vì thế không thể viết new T(), obj instanceof List<String> hay lấy T.class. Với Gson, gọi gson.fromJson(json, List.class) thì Gson không biết phần tử là User nên tạo list chứa LinkedTreeMap; code vẫn compile (chỉ có warning unchecked) và chỉ crash ClassCastException khi lấy phần tử ra dùng như User. Cách đúng là truyền new TypeToken<List<User>>() {}.getType(), vì kiểu generic của lớp con ẩn danh được giữ lại trong metadata của class. Kotlin có inline + reified để giữ kiểu trong hàm inline, nhưng bản chất JVM vẫn là erasure.

  1. Màn hình chi tiết cần gọi hai API độc lập (thông tin sản phẩm và đánh giá). Bạn dùng launch hay async để gọi song song? Hai builder này khác nhau thế nào?

    Xem đáp án mẫu
    launch trả về Job, dùng cho việc không cần kết quả trả về; async trả về Deferred<T> và lấy kết quả bằng await(). Để chạy song song, tạo cả hai async trước rồi mới await; viết async { ... }.await() liền nhau thì thực chất vẫn tuần tự. Bọc trong coroutineScope để nếu một request lỗi thì request còn lại bị huỷ theo và exception được ném ra đúng chỗ gọi, bắt bằng try/catch bên ngoài. Lưu ý async không có nghĩa là "chạy ở background": nó vẫn chạy trên dispatcher của scope, việc chuyển thread là trách nhiệm của withContext hoặc của hàm suspend main-safe như hàm suspend của Retrofit.
    fun loadDetail(id: String) = viewModelScope.launch {
    try {
        val (product, reviews) = coroutineScope {
            val p = async { repo.getProduct(id) }
            val r = async { repo.getReviews(id) }
            p.await() to r.await() // hai request chạy song song
        }
        _state.value = DetailState.Success(product, reviews)
    } catch (e: IOException) {
        _state.value = DetailState.Error("Mất kết nối, thử lại sau")
    }
}

  2. Hàm suspend có tự chạy ở background thread không? Nên đặt withContext(Dispatchers.IO) ở tầng nào?

    Xem đáp án mẫu
    Không. suspend chỉ có nghĩa là hàm có thể tạm dừng mà không chặn thread; code bên trong vẫn chạy trên dispatcher của coroutine gọi nó, nên một hàm suspend đọc file kiểu blocking được gọi từ viewModelScope (mặc định Dispatchers.Main.immediate) vẫn chặn main thread. Google khuyến nghị hàm suspend phải main-safe: lớp nào làm việc blocking thì tự chuyển thread bằng withContext, thường ở repository hoặc data source, để ViewModel gọi thoải mái từ main. Dispatchers.IO dành cho việc chờ I/O (file, database, SDK blocking), Dispatchers.Default cho tính toán nặng như sort list lớn hay xử lý ảnh. Hàm suspend của Retrofit và DAO suspend của Room đã main-safe sẵn, không cần bọc thêm.

  3. viewModelScope, lifecycleScope và GlobalScope khác nhau thế nào? Vì sao không nên dùng GlobalScope để gọi API của một màn hình?

    Xem đáp án mẫu
    viewModelScope bị huỷ khi ViewModel bị clear, tức khi màn hình thực sự đóng chứ không phải khi xoay máy, nên hợp để gọi API và giữ kết quả cho UI. lifecycleScope gắn với Activity/Fragment (với view của Fragment thì dùng viewLifecycleOwner.lifecycleScope) và bị huỷ khi lifecycle DESTROYED, nên request bắt đầu ở đây bị huỷ rồi phải gọi lại mỗi lần xoay máy; nó hợp với việc thuần UI như collect state. GlobalScope không gắn với vòng đời nào: coroutine chạy tiếp sau khi màn hình đóng, lambda giữ tham chiếu tới ViewModel/View gây rò rỉ bộ nhớ, và có thể cập nhật UI đã bị huỷ. Việc thực sự phải chạy tiếp khi người dùng rời màn hình (upload, đồng bộ) nên giao cho WorkManager hoặc một scope ở tầng application được quản lý rõ ràng.

  4. Dự án đang chuyển từ LiveData sang StateFlow. Hai cái khác nhau ở những điểm nào cần lưu ý?

    Xem đáp án mẫu
    Cả hai đều giữ giá trị hiện tại và phát cho observer mới, nhưng StateFlow bắt buộc có giá trị khởi tạo, bỏ qua giá trị mới nếu equals giá trị cũ, và là API Kotlin thuần nên dùng được ở tầng domain/data và test không cần Android. LiveData tự nhận biết lifecycle: chỉ gửi giá trị khi observer ở trạng thái STARTED/RESUMED và tự gỡ khi DESTROYED. StateFlow không có cơ chế đó, nên collect thẳng trong lifecycleScope.launch sẽ tiếp tục chạy khi app ở background; cần bọc trong repeatOnLifecycle(Lifecycle.State.STARTED) (View) hoặc dùng collectAsStateWithLifecycle() (Compose). Ngoài ra LiveData.setValue phải gọi trên main thread, còn MutableStateFlow.value gán được từ thread bất kỳ.
    // ViewModel
private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
val uiState: StateFlow<UiState> = _uiState.asStateFlow()

// Fragment
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { render(it) }
    }
}

  5. Màn danh sách đơn hàng dùng suspend fun getOrders(): List<Order>, nên sau khi thêm đơn ở màn khác, quay lại phải gọi tải lại thủ công. Flow giải quyết việc này thế nào, cold flow là gì, và nó khác hàm suspend trả List ở đâu?

    Xem đáp án mẫu
    Hàm suspend trả List chỉ cho đúng một kết quả rồi kết thúc: dữ liệu đổi sau đó thì phải gọi lại. Flow<T> là luồng nhiều giá trị theo thời gian. Flow là cold: code trong flow { } không chạy cho tới khi có collect, và mỗi collector chạy lại từ đầu (khác StateFlow là hot, luôn giữ giá trị hiện tại dù không ai nghe). collect là hàm suspend nên phải gọi trong coroutine; các operator trung gian như map, filter, onEach chỉ dựng pipeline, đến khi có terminal operator (collect, first, toList) mới chạy. Với Room, DAO khai báo fun observeOrders(): Flow<List<Order>> (không cần suspend): Room chạy query ngoài main thread và phát lại danh sách mới mỗi khi bảng liên quan thay đổi, nên UI tự cập nhật mà không phải tải lại. Bẫy: collect trên Flow của Room không bao giờ kết thúc, nên code viết sau nó trong cùng coroutine không bao giờ chạy, muốn thu thập nhiều flow phải launch riêng từng cái; và Room phát lại khi bảng đổi dù kết quả query vẫn như cũ, thêm distinctUntilChanged() nếu UI không cần vẽ lại.
    @Dao
interface OrderDao {
    @Query("SELECT * FROM orders ORDER BY created_at DESC")
    fun observeOrders(): Flow<List<Order>> // không cần suspend, Room tự phát lại khi bảng đổi
}

class OrderViewModel(dao: OrderDao) : ViewModel() {
    val pendingOrders: StateFlow<List<Order>> = dao.observeOrders()
        .map { orders -> orders.filter { it.status == Status.PENDING } } // chưa chạy gì cho tới khi có collector
        .distinctUntilChanged()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())
}

  6. Một dev bọc try { viewModelScope.launch { api.load() } } catch (e: Exception) { ... } nhưng khi API lỗi app vẫn crash. Vì sao try/catch bên ngoài launch không bắt được lỗi, nên đặt nó ở đâu, và launch, async, CoroutineExceptionHandler xử lý exception khác nhau thế nào?

    Xem đáp án mẫu
    launch chỉ khởi động coroutine rồi trả về Job ngay, nên khi khối try kết thúc thì coroutine còn chưa chạy tới api.load(); lỗi ném sau đó nằm ngoài try. Exception trong launch không được ném lại cho nơi gọi mà lan lên Job cha, rồi tới CoroutineExceptionHandler hoặc handler mặc định của thread, nên app crash. Cách đúng là đặt try/catch bên trong coroutine, quanh lời gọi suspend, và bắt đúng loại lỗi (IOException, HttpException); nếu bắt Exception rộng thì phải ném lại CancellationException, không thì tín hiệu huỷ bị nuốt. async khác launch: lỗi được giữ trong Deferred và ném ra ở await(). Nhưng async là con của scope nên lỗi vẫn huỷ scope cha ngay, chỉ bọc await() bằng try/catch thì chưa đủ; hãy bọc cả coroutineScope { } chứa async, vì coroutineScope ném lại lỗi cho nơi gọi. } catch (e: IOException) { /* không bao giờ chạy */ }

    try {
        _state.value = UiState.Success(api.load())
    } catch (e: IOException) {

}

            val o = async { api.getOrders() }
            u.await() to o.await()
        }

  2. App tải ảnh bìa 4000×3000 từ server bằng BitmapFactory.decodeStream rồi gán vào ImageView nhỏ. Trên máy cấu hình thấp, cuộn danh sách vài chục ảnh thì crash OutOfMemoryError. Vì sao một file JPEG vài trăm KB lại ngốn nhiều RAM đến vậy, và bạn khắc phục thế nào?

    Xem đáp án mẫu
    JPEG/PNG là dạng nén; để hiển thị phải giải mã thành bitmap không nén trong RAM, tốn khoảng width × height × 4 byte (ARGB_8888): ảnh 4000×3000 chiếm 4000 × 3000 × 4 ≈ 48MB dù ImageView chỉ rộng vài trăm px, và vài chục ảnh như vậy vượt xa heap của app. Cách xử lý là downsample: chỉ giải mã ở kích thước cần hiển thị. Với BitmapFactory, đọc kích thước bằng inJustDecodeBounds = true (chưa cấp bộ nhớ cho pixel), tính inSampleSize (luỹ thừa của 2) rồi mới giải mã thật. Thực tế dùng Coil (AsyncImage trong Compose) hoặc Glide: chúng đo kích thước view để downsample, giải mã ngoài main thread, huỷ request khi view bị tái sử dụng, có memory cache (LRU) và disk cache, nên cuộn mượt mà không OOM. Bẫy: ImageView dùng wrap_content hoặc composable không có kích thước rõ ràng khiến loader không biết kích thước đích và có thể giải mã ở kích thước rất lớn (đặt kích thước cụ thể, hoặc override(w, h) của Glide, size(w, h) của Coil); giữ Bitmap trong biến static hay ViewModel gây leak. Phía server nên trả thumbnail đúng cỡ (CDN resize) để tiết kiệm cả mạng.
    fun decodeSampled(file: File, reqWidth: Int, reqHeight: Int): Bitmap {
    // Bước 1: chỉ đọc kích thước, chưa cấp bộ nhớ cho pixel
    val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeFile(file.path, bounds)

    var sample = 1
    while (bounds.outWidth / (sample * 2) >= reqWidth && bounds.outHeight / (sample * 2) >= reqHeight) {
        sample *= 2
    }

    // Bước 2: giải mã thật ở kích thước đã thu nhỏ
    val options = BitmapFactory.Options().apply { inSampleSize = sample }
    return BitmapFactory.decodeFile(file.path, options) ?: error("Không giải mã được ảnh")
}

(2) Giảm thiệt hại trước khi tìm nguyên nhân: nếu tính năng nằm sau feature flag hoặc Remote Config thì tắt đi; nếu đang phát hành theo staged rollout thì tạm dừng (halt rollout) trên Play Console để không lan thêm. Android không thu hồi được bản đã cài, nên "rollback" thực chất là phát hành hotfix với versionCode cao hơn. (3) Tìm nguyên nhân: đọc stack trace (cần đã upload mapping R8 mới thấy tên thật), xem custom key và breadcrumb, đối chiếu với các commit của bản này, rồi tái hiện đúng trên bản release, đúng máy và đúng OS. (4) Sửa nhỏ nhất có thể, thêm test cho đúng ca này, nhờ review nhanh, đưa hotfix lên theo rollout từng phần và theo dõi crash-free. (5) Sau cùng cập nhật cho mọi người và viết postmortem không đổ lỗi: nguyên nhân gốc, vì sao test và review bỏ sót, việc cần làm (rollout 1–5% trước, feature flag, thêm test). Điều nên tránh là im lặng, đoán mò hay đổ lỗi cho cá nhân.
