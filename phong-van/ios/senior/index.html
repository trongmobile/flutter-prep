  1. Team phát hành SDK nội bộ dưới dạng XCFramework cho các app khác build bằng phiên bản Xcode khác nhau. Sau khi nâng Xcode, app tích hợp báo module được biên dịch bằng phiên bản Swift khác, và việc thêm một case vào enum public của SDK làm vỡ các app tích hợp. Bạn xử lý thế nào?

    Xem đáp án mẫu
    Mặc định module Swift không ổn định giữa các phiên bản compiler: file .swiftmodule mô tả API phụ thuộc vào compiler đã build ra nó nên bản compiler khác không import được. Khi phân phối binary phải bật library evolution (BUILD_LIBRARY_FOR_DISTRIBUTION = YES, tức -enable-library-evolution): compiler sinh thêm .swiftinterface, một dạng text ổn định được build lại phía người dùng, nên binary dùng được với compiler mới hơn. Đổi lại compiler phải chừa chỗ cho việc API tiến hoá, nên một số truy cập đi gián tiếp và chậm hơn một chút. Nó cũng quyết định quy tắc nâng cấp API tương thích: enum public không @frozen được coi là 'có thể thêm case', người dùng bắt buộc viết @unknown default khi switch nên thêm case không làm vỡ nguồn; @frozen là lời hứa layout không đổi (nhanh hơn nhưng sau này không thêm case hay field được). @inlinable và @usableFromInline đưa thân hàm vào interface để người dùng inline, nhưng sau đó implementation bị đóng đinh vì đã nằm trong binary của client, nên chỉ dùng cho hot path. open cho phép subclass và override ở ngoài module nên khoá hợp đồng chặt hơn nhiều so với public; mặc định chọn public và final. Ngoài việc nhớ cờ, cần chạy swift-api-digester trên CI để phát hiện thay đổi API làm vỡ tương thích, đóng gói XCFramework đủ slice thiết bị và simulator, kèm dSYM và Privacy Manifest nếu SDK dùng API thuộc diện phải khai báo.

  1. Mỗi lần mở rồi đóng màn hình chi tiết, memory tăng thêm vài MB nhưng Memory Graph Debugger không báo leak nào. Bạn truy nguyên nhân thế nào?

    Xem đáp án mẫu
    Memory Graph chỉ đánh dấu leak (biểu tượng tím) cho object không còn đường tham chiếu nào từ root, điển hình là một retain cycle bị bỏ rơi. Object vẫn bị giữ bởi singleton, cache, observer dạng block của NotificationCenter, closure lưu trong service hay Timer thì vẫn reachable nên không bị báo, đó là abandoned memory. Cách tìm là dùng Allocations với Mark Generation: đánh dấu, mở rồi đóng màn hình vài lần, đánh dấu tiếp, rồi xem object nào sống sót qua các generation. Sau đó mở Memory Graph tại object đó để thấy chuỗi tham chiếu từ root, và bật Malloc Stack Logging trong scheme để biết nó được cấp phát ở đâu. Một kiểm tra rẻ mà hiệu quả là log trong deinit của view controller và ViewModel để phát hiện sớm.

  2. Store kiểu Redux giữ AppState là struct chứa mảng vài nghìn tin nhắn. Time Profiler cho thấy mỗi lần nhận tin mới, reducer lại copy toàn bộ mảng dù Array có copy-on-write. Vì sao, và sửa thế nào?

    Xem đáp án mẫu
    Copy-on-write chỉ tránh được copy khi buffer được tham chiếu duy nhất đúng lúc ghi. Reducer kiểu var next = state rồi next.messages.append(m) khiến buffer đang được cả state cũ trong store lẫn next cùng giữ khi append, nên lần nào cũng copy cả mảng: chi phí O(n) cho mỗi tin, kèm áp lực memory. Cách sửa là cho reducer nhận inout AppState và sửa tại chỗ, để buffer chỉ có một chủ và append không phải copy; các thư viện như TCA cũng thiết kế reducer nhận inout State. Ngoài ra tránh để nơi khác giữ bản sao state trong lúc ghi (middleware, lịch sử undo, snapshot gửi cho UI), vì mỗi bản sao còn sống lại buộc lần ghi kế tiếp phải copy. Sửa xong đo lại bằng Time Profiler để chắc phần copy đã biến mất.
    struct AppState { var messages: [Message] = [] }

// Chậm: lúc append, buffer bị cả state lẫn next cùng giữ -> copy cả mảng
func reduce(_ state: AppState, _ message: Message) -> AppState {
  var next = state
  next.messages.append(message)
  return next
}

// Nhanh: sửa tại chỗ, buffer chỉ có một chủ nên append không phải copy
func reduce(_ state: inout AppState, _ message: Message) {
  state.messages.append(message)
}

  3. App bị hệ thống kill khi quay lại từ background hoặc khi đang dùng camera và ảnh; log chỉ ghi jetsam hay EXC_RESOURCE, không có exception, và Memory Graph không thấy leak. Giải thích cách iOS quản lý memory và cách bạn điều tra?

    Xem đáp án mẫu
    iOS không swap ra đĩa; khi thiếu memory, jetsam kill process (app nền trước, còn app foreground chỉ bị kill khi vượt giới hạn riêng của nó) mà không đi qua exception hay crash handler thông thường nên Crashlytics hay không thấy. Con số cần quan tâm là memory footprint gồm dirty memory và compressed memory, chứ không phải kích thước file; clean memory (file mmap có thể nạp lại) không nặng, còn bitmap đã decode, buffer và cache đều là dirty. Giới hạn phụ thuộc thiết bị (máy ít RAM thì thấp hơn) và hệ thống không bảo đảm báo trước: didReceiveMemoryWarning có thể không tới kịp. Điều tra: xem Memory gauge của Xcode và Instruments (Allocations, VM Tracker) trên máy thật để biết phần dirty nằm ở đâu, rồi kiểm tra các nguồn quen thuộc: ảnh full-resolution, pixel buffer hay AVCaptureSession bị giữ lại, NSCache không giới hạn cost, nhiều bản sao của dữ liệu lớn (Data → String → model). Giảm footprint bằng downsample ảnh, đọc file theo kiểu mmap (Data(contentsOf:options: .mappedIfSafe)) hoặc stream thay vì nạp cả file, và nhả cache khi vào background (app nền chiếm nhiều memory là ứng viên bị kill đầu tiên). Dùng os_proc_available_memory() để biết còn bao nhiêu byte trước khi làm việc nặng như xử lý ảnh hay chạy model ML. Dữ liệu ở production lấy từ MetricKit: MXMemoryMetric cho peak memory và MXAppExitMetric đếm số lần app thoát vì vượt giới hạn memory hay bị kill do áp lực memory ở nền, cộng với mục Memory của Organizer. Tính năng thật sự cần nhiều memory có thể xin entitlement com.apple.developer.kernel.increased-memory-limit trên thiết bị hỗ trợ.

  os_proc_available_memory() > estimatedBytes * 2 // chừa dư địa an toàn

  1. Bạn cần một ImageCache dùng chung cho cả app: đọc rất nhiều từ cellForRowAt trên main thread, thỉnh thoảng ghi từ background. Bạn bảo vệ state của nó bằng actor, @MainActor hay lock? Đánh đổi là gì?

    Xem đáp án mẫu
    Actor an toàn nhất vì compiler kiểm tra isolation giúp, nhưng mọi truy cập từ bên ngoài phải await: cellForRowAt vốn đồng bộ không đọc ngay được mà phải tạo Task, ảnh hiện trễ một nhịp, và mọi lời gọi xếp hàng tuần tự qua actor. @MainActor cho đọc đồng bộ ngay trên main, hợp khi truy cập chủ yếu từ UI và thao tác rất nhẹ, nhưng việc ghi từ background phải nhảy về main. Class final bọc state bằng lock (NSLock, OSAllocatedUnfairLock) và đánh dấu @unchecked Sendable thì đọc đồng bộ được từ mọi thread với chi phí rất thấp; đổi lại an toàn dựa vào kỷ luật của người viết: critical section ngắn, không bao giờ giữ lock qua await. Với cache nóng như ảnh tôi thường chọn lock, đóng gói trong một type nhỏ; state nghiệp vụ có nhiều bước async thì để actor.

  2. Code cũ dùng DispatchSemaphore trên main thread để chờ kết quả từ một queue .utility, và Xcode báo cảnh báo priority inversion. Vấn đề là gì và sửa thế nào?

    Xem đáp án mẫu
    Priority inversion xảy ra khi thread ưu tiên cao (main, QoS user-interactive) phải chờ một việc đang chạy ở QoS thấp; việc đó lại bị các tác vụ ưu tiên hơn chen ngang, nên main bị treo lâu hơn cần thiết. Với lock có owner như os_unfair_lock hay khi gọi DispatchQueue.sync, hệ thống biết ai đang giữ để tạm nâng priority cho bên đó; còn DispatchSemaphore và DispatchGroup.wait() không biết ai sẽ signal nên không làm được. Cách sửa tốt nhất là không block main: chuyển sang callback hoặc async/await, vì khi await một Task thì priority của task được escalate theo bên đang chờ. Nếu bắt buộc phải đồng bộ, dùng lock có owner và giữ critical section thật ngắn.
    // Code cũ: main thread chờ semaphore, hệ thống không biết nâng priority cho ai
func loadConfigSync() -> Config {
  let semaphore = DispatchSemaphore(value: 0)
  var result: Config?
  DispatchQueue.global(qos: .utility).async {
    result = ConfigLoader.load()
    semaphore.signal()
  }
  semaphore.wait() // main bị block: hang + priority inversion
  return result!
}

  3. Bạn được giao đưa một codebase UIKit lớn lên Swift 6 language mode. Lập kế hoạch thế nào để không 'đóng băng' cả team hàng tháng?

    Xem đáp án mẫu
    Tôi migrate theo từng module chứ không bật một lần cho cả app. Bước một: giữ Swift 5 mode nhưng bật strict concurrency checking mức complete để có danh sách cảnh báo, bắt đầu từ các module lá ít phụ thuộc như model, networking, rồi mới tới feature và app target. Bước hai: làm rõ isolation, như view controller và ViewModel là @MainActor, value type đi qua ranh giới concurrency thì Sendable, state dùng chung chuyển vào actor; thư viện bên thứ ba chưa cập nhật thì @preconcurrency import để tạm hạ cảnh báo. @unchecked Sendable và nonisolated(unsafe) chỉ dùng khi thật sự có lock bảo vệ, kèm comment giải thích. Module nào sạch cảnh báo thì bật Swift 6 mode cho riêng module đó và để CI chặn cảnh báo mới. Các bản Swift gần đây còn cho đặt default isolation là MainActor cho cả module, rất hợp với module UI vì giảm hẳn số annotation phải viết.

  4. Một service cũ dùng DispatchSemaphore.wait() bên trong hàm async để chờ callback, và app thỉnh thoảng treo hoàn toàn dù CPU rất rảnh. Thread pool của Swift Concurrency hoạt động thế nào, vì sao chặn thread trong code async nguy hiểm, và Task { } khác Task.detached ra sao?

    Xem đáp án mẫu
    Swift Concurrency chạy task trên cooperative thread pool có số thread xấp xỉ số core CPU, thay vì mỗi tác vụ một thread như GCD. Giả định nền tảng là task không chặn thread: khi await, task suspend và thread được trả lại cho task khác. Nếu trong hàm async bạn gọi API chặn như DispatchSemaphore.wait(), DispatchQueue.sync chờ kết quả từ task khác hay Thread.sleep, bạn chiếm mất một thread của pool; vài task như vậy đủ chiếm hết pool, và task cần chạy để signal semaphore không còn thread nào để chạy, thế là deadlock (treo mà CPU rảnh). Cách sửa là withCheckedContinuation để chờ callback mà không chặn thread, hoặc đưa việc blocking bắt buộc (I/O đồng bộ của thư viện C) sang một queue GCD riêng rồi await qua continuation. Để phát hiện, chạy với biến môi trường LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 (thu pool còn một thread) để lộ các chỗ chặn. Về Task { } và Task.detached: Task { } là task không có cấu trúc nhưng thừa hưởng context nơi tạo (actor isolation, priority, task-local), nên Task { } trong hàm @MainActor mà làm việc CPU nặng vẫn chiếm main thread; Task.detached không thừa hưởng gì, chạy ngoài actor, nhưng cũng không bị huỷ theo task cha nên phải tự quản lý. Swift 6.2 thêm @concurrent để đánh dấu hàm async luôn chạy ngoài actor của caller, giúp rõ ràng hơn việc nặng chạy ở đâu.
    // Sai: chiếm một thread của cooperative pool, vài task như vậy là pool cạn thread và treo
func loadConfig() async -> Config {
  let semaphore = DispatchSemaphore(value: 0)
  var result: Config!
  legacy.load { config in
    result = config
    semaphore.signal()
  }
  semaphore.wait() // chặn thread
  return result
}

// Đúng: suspend, thread được trả lại cho pool
func loadConfig() async -> Config {
  await withCheckedContinuation { continuation in
    legacy.load { continuation.resume(returning: $0) }
  }
}

@MainActor
func onTap() {
  Task { heavyCompute() }          // thừa hưởng MainActor: vẫn chiếm main thread
  Task.detached { heavyCompute() } // không thừa hưởng actor: chạy ngoài main, tự quản lý việc huỷ

  5. Bạn cần dùng CLLocationManager (callback qua delegate) trong code async/await, dưới dạng for await location in tracker.updates(). Bạn bọc bằng AsyncStream thế nào, và cần để ý gì về huỷ, buffer và vòng đời?

    Xem đáp án mẫu
    AsyncStream chuyển nguồn sự kiện kiểu delegate thành một chuỗi bất đồng bộ: tạo bằng AsyncStream.makeStream(of:bufferingPolicy:) để lấy cả stream lẫn continuation, gọi continuation.yield(value) từ callback (an toàn từ thread bất kỳ) và continuation.finish() khi nguồn kết thúc. Điểm quan trọng nhất là dọn dẹp: gán continuation.onTermination để dừng startUpdatingLocation() khi consumer thoát vòng lặp, Task bị huỷ hay stream kết thúc; thiếu bước này GPS chạy mãi và tốn pin. Về buffer, mặc định là .unbounded; với dữ liệu kiểu 'giá trị mới nhất' như vị trí nên dùng .bufferingNewest(1) để consumer chậm không làm bộ nhớ phình ra, còn sự kiện không được bỏ sót (log, tin nhắn) thì giữ .unbounded hoặc giới hạn có chủ đích. AsyncStream là unicast: nhiều consumer sẽ tranh nhau từng phần tử chứ không mỗi nơi nhận một bản, nên muốn chia sẻ cho nhiều nơi cần tạo stream riêng cho từng người đăng ký hoặc dùng Combine/AsyncChannel của swift-async-algorithms. Nguồn có thể lỗi thì dùng AsyncThrowingStream. Vòng for await nên chạy trong Task gắn với vòng đời UI (.task { } của SwiftUI tự huỷ khi view biến mất) để không tạo task mồ côi. Cuối cùng, tránh retain cycle giữa delegate, continuation và closure onTermination.
    final class LocationTracker: NSObject, CLLocationManagerDelegate {
  private let manager = CLLocationManager()
  private var continuation: AsyncStream<CLLocation>.Continuation?

  func updates() -> AsyncStream<CLLocation> {
    let (stream, continuation) = AsyncStream.makeStream(
      of: CLLocation.self,
      bufferingPolicy: .bufferingNewest(1) // chỉ cần vị trí mới nhất
    )
    self.continuation = continuation
    manager.delegate = self
    manager.startUpdatingLocation()
    continuation.onTermination = { [weak self] _ in
      self?.manager.stopUpdatingLocation() // consumer thoát hoặc bị huỷ thì tắt GPS
    }
    return stream
  }

  func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
    locations.forEach { continuation?.yield($0) }
  }
}

// SwiftUI: .task tự huỷ khi view biến mất, kéo theo onTermination
.task {
  for await location in tracker.updates() { model.update(location) }
}

  1. Màn chat đã dùng UICollectionViewDiffableDataSource, nhưng khi một tin nhắn được sửa thì cell nhấp nháy và mất vị trí cuộn, và thỉnh thoảng crash vì identifier trùng. Identifier của snapshot nên là gì, và reloadItems khác reconfigureItems thế nào?

    Xem đáp án mẫu
    Diffable data source so sánh các snapshot bằng identifier (Hashable): identifier mới là item được thêm, identifier biến mất là item bị xoá, identifier còn nguyên là cùng một item (có thể đã di chuyển). Vì vậy identifier phải định danh thực thể (id ổn định), không phải toàn bộ nội dung. Nếu dùng nguyên struct Message làm identifier thì khi tin được sửa, nội dung đổi nên hash đổi và snapshot hiểu đó là một item bị xoá cộng một item mới (cell nhấp nháy, mất vị trí cuộn); và các identifier phải duy nhất trong cùng một snapshot, trùng là crash. Hãy dùng Message.ID làm identifier và lấy dữ liệu hiện tại từ một nguồn riêng trong cell registration. Khi nội dung đổi nhưng id giữ nguyên thì phải báo cho data source biết, vì snapshot thấy identifier không đổi nên mặc định không cập nhật cell: reloadItems dựng lại cell (dequeue một cell mới), còn reconfigureItems (iOS 15 trở lên) cập nhật chính cell đang hiển thị, rẻ hơn và giữ nguyên trạng thái tạm thời của cell. apply có thể gọi từ background queue miễn là luôn dùng nhất quán một queue; dùng animatingDifferences: false cho lần tải đầu hoặc khi dữ liệu thay đổi quá lớn. Với dữ liệu đổi dồn dập, gom thay đổi (debounce hoặc áp dụng theo lô) thay vì apply cho từng sự kiện.

  var spacing: CGFloat = 8

  func sizeThatFits(proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) -> CGSize {
    arrange(in: proposal.width ?? .infinity, subviews: subviews).size
  }

  func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) {
    let result = arrange(in: bounds.width, subviews: subviews)
    for (subview, origin) in zip(subviews, result.origins) {
      subview.place(at: CGPoint(x: bounds.minX + origin.x, y: bounds.minY + origin.y), proposal: .unspecified)
    }
  }

  // Tính vị trí các chip; có thể lưu vào cache để tránh tính hai lần
  private func arrange(in width: CGFloat, subviews: Subviews) -> (size: CGSize, origins: [CGPoint]) {
    var origins: [CGPoint] = []
    var x: CGFloat = 0
    var y: CGFloat = 0
    var rowHeight: CGFloat = 0
    var maxX: CGFloat = 0
    for subview in subviews {
      let size = subview.sizeThatFits(.unspecified) // kích thước tự nhiên của chip
      if x > 0 && x + size.width > width { // hết chỗ: xuống hàng
        x = 0
        y += rowHeight + spacing
        rowHeight = 0
      }
      origins.append(CGPoint(x: x, y: y))
      x += size.width + spacing
      maxX = max(maxX, x - spacing)
      rowHeight = max(rowHeight, size.height)
    }
    return (CGSize(width: maxX, height: y + rowHeight), origins)
  }
}

    struct RetryPolicy {
  var maxAttempts = 3
  var baseDelay: Duration = .milliseconds(500)

  func shouldRetry(status: Int, method: String) -> Bool {
    let idempotent = ["GET", "PUT", "DELETE"].contains(method)
    return idempotent && (status == 429 || (500...599).contains(status))
  }

  func delay(attempt: Int, retryAfter: Duration?) -> Duration {
    if let retryAfter { return retryAfter } // server bảo chờ bao lâu thì chờ đúng vậy
    let exponential = baseDelay * (1 << (attempt - 1))
    return exponential * Double.random(in: 0.5...1.5) // jitter: tránh mọi client retry cùng lúc
  }
}

func send<T: Decodable>(_ endpoint: Endpoint<T>) async throws -> T {
  var attempt = 1
  while true {
    // Task bị huỷ thì data(for:) và Task.sleep đều throw, vòng lặp tự thoát
    let (data, response) = try await session.data(for: endpoint.urlRequest())
    guard let http = response as? HTTPURLResponse else { throw APIError.invalidResponse }
    if (200..<300).contains(http.statusCode) { return try decoder.decode(T.self, from: data) }

    guard attempt < policy.maxAttempts, policy.shouldRetry(status: http.statusCode, method: endpoint.method) else {
      throw APIError.http(status: http.statusCode, body: data)
    }
    let retryAfter = http.value(forHTTPHeaderField: "Retry-After").flatMap(Double.init).map { Duration.seconds($0) }
    try await Task.sleep(for: policy.delay(attempt: attempt, retryAfter: retryAfter))
    attempt += 1
  }
}

}

    Upload chạy trong process của app sẽ bị suspend vài giây sau khi app vào nền, nên cần URLSession cấu hình background (URLSessionConfiguration.background(withIdentifier:)): hệ thống (daemon nsurlsessiond) thực hiện transfer ngoài process, kể cả khi app bị suspend hay hệ thống terminate. Ràng buộc: chỉ dùng uploadTask(with:fromFile:) (không upload từ Data hay stream), nên phải ghi file multipart hoặc binary ra thư mục tạm trước; và phải dùng delegate chứ không dùng completion handler. Khi transfer xong lúc app không chạy, hệ thống relaunch app ở nền và gọi application(_:handleEventsForBackgroundURLSession:completionHandler:); phải tạo lại session với cùng identifier để nhận event delegate, và gọi completion handler trong urlSessionDidFinishEvents(forBackgroundURLSession:). Cần lưu trạng thái bền (DB local: id job, đường dẫn file, trạng thái) để ánh xạ kết quả khi app được relaunch và hiển thị tiến độ. File lớn nên chia chunk hoặc dùng giao thức resumable (tus, S3 multipart) để lỗi mạng chỉ phải gửi lại phần dở, kèm idempotency key. Đặt isDiscretionary hợp lý: việc không gấp để hệ thống chọn lúc có Wi-Fi hoặc đang sạc, còn việc user đang chờ thì không bật discretionary. Giới hạn cần nói thẳng với PM: user force-quit thì hệ thống huỷ transfer nền, và app không chạy code trong lúc upload nên không thể xử lý từng chunk; phải mã hoá hay nén xong trước khi đẩy task vào session.
    final class UploadManager: NSObject, URLSessionTaskDelegate {
  static let shared = UploadManager()
  var backgroundCompletion: (() -> Void)? // AppDelegate gán khi được relaunch

  private var session: URLSession!

  private override init() {
    super.init()
    let config = URLSessionConfiguration.background(withIdentifier: "vn.shop.upload")
    config.sessionSendsLaunchEvents = true
    config.isDiscretionary = false // user đang chờ kết quả nên không để hệ thống trì hoãn
    // Tạo lại session với cùng identifier để nhận lại các event của lần chạy trước
    session = URLSession(configuration: config, delegate: self, delegateQueue: nil)
  }

  func enqueue(file: URL, to url: URL, jobID: String) {
    var request = URLRequest(url: url)
    request.httpMethod = "PUT"
    let task = session.uploadTask(with: request, fromFile: file) // bắt buộc upload từ file
    task.taskDescription = jobID // ánh xạ lại với DB khi app được relaunch
    task.resume()
  }

  func urlSession(_ session: URLSession, task: URLSessionTask, didCompleteWithError error: Error?) {
    // Cập nhật trạng thái job trong DB: đã gửi hoặc cần retry
  }

  func urlSessionDidFinishEvents(forBackgroundURLSession session: URLSession) {
    DispatchQueue.main.async {
      self.backgroundCompletion?() // báo hệ thống đã xử lý xong để app được suspend lại
      self.backgroundCompletion = nil
    }
  }
}

// AppDelegate
func application(_ application: UIApplication,
                 handleEventsForBackgroundURLSession identifier: String,
                 completionHandler: @escaping () -> Void) {
  UploadManager.shared.backgroundCompletion = completionHandler // truy cập .shared cũng tạo lại session
}

  2. Một bạn junior liên tục để lọt retain cycle và force unwrap, PR nào cũng phải sửa nhiều vòng. Với vai trò senior, bạn làm gì?

    Xem đáp án mẫu
    Tôi coi đây là vấn đề của cả quy trình chứ không chỉ của một người. Về con người: ngồi pair một buổi để cùng tìm một retain cycle bằng Memory Graph, giải thích vì sao chứ không chỉ để lại comment 'thêm weak self', và khuyến khích mở draft PR sớm để góp ý từ lúc thiết kế. Về công cụ: bật các rule SwiftLint như force_unwrapping, weak_delegate, và thêm helper trong test kiểm tra view controller được giải phóng sau khi đóng, để máy bắt lỗi thay cho người review.   3. Hai ngày trước ngày ra mắt gắn với chiến dịch marketing, bản build bị App Review từ chối với lý do Guideline 5.1.1 (quyền riêng tư và thu thập dữ liệu). Bạn xử lý thế nào, cả về kỹ thuật lẫn giao tiếp?

Nếu cho rằng Apple hiểu sai thì trả lời trong Resolution Center bằng bằng chứng, hoặc kháng nghị lên App Review Board; cách này chậm hơn nên không thể dựa vào nó khi có deadline. Về giao tiếp, tôi báo ngay cho PM và marketing với thời gian dự kiến và các kịch bản (kịp, trễ một hai ngày), đồng thời đề xuất tách ngày chiến dịch khỏi ngày build lên store: chọn 'Manually release this version' để tự quyết lúc phát hành sau khi đã được duyệt, và đặt tính năng mới sau feature flag hoặc remote config để backend bật đúng ngày. Về phòng ngừa lâu dài: nộp duyệt sớm hơn mốc quan trọng ít nhất một tuần, có checklist trước khi nộp (quyền, Privacy Manifest, tài khoản demo, xoá tài khoản), chạy TestFlight external sớm, và ghi lại các lý do từ chối cũ vào tài liệu chung của team.
