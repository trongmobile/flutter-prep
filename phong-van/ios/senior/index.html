Memory & ARC

Mọi rank →

  1. Mỗi lần mở rồi đóng màn hình chi tiết, memory tăng thêm vài MB nhưng Memory Graph Debugger không báo leak nào. Bạn truy nguyên nhân thế nào?

    Xem đáp án mẫu
    Memory Graph chỉ đánh dấu leak (biểu tượng tím) cho object không còn đường tham chiếu nào từ root, điển hình là một retain cycle bị bỏ rơi. Object vẫn bị giữ bởi singleton, cache, observer dạng block của NotificationCenter, closure lưu trong service hay Timer thì vẫn reachable nên không bị báo, đó là abandoned memory. Cách tìm là dùng Allocations với Mark Generation: đánh dấu, mở rồi đóng màn hình vài lần, đánh dấu tiếp, rồi xem object nào sống sót qua các generation. Sau đó mở Memory Graph tại object đó để thấy chuỗi tham chiếu từ root, và bật Malloc Stack Logging trong scheme để biết nó được cấp phát ở đâu. Một kiểm tra rẻ mà hiệu quả là log trong deinit của view controller và ViewModel để phát hiện sớm.

  2. Store kiểu Redux giữ AppState là struct chứa mảng vài nghìn tin nhắn. Time Profiler cho thấy mỗi lần nhận tin mới, reducer lại copy toàn bộ mảng dù Array có copy-on-write. Vì sao, và sửa thế nào?

    Xem đáp án mẫu
    Copy-on-write chỉ tránh được copy khi buffer được tham chiếu duy nhất đúng lúc ghi. Reducer kiểu var next = state rồi next.messages.append(m) khiến buffer đang được cả state cũ trong store lẫn next cùng giữ khi append, nên lần nào cũng copy cả mảng: chi phí O(n) cho mỗi tin, kèm áp lực memory. Cách sửa là cho reducer nhận inout AppState và sửa tại chỗ, để buffer chỉ có một chủ và append không phải copy; các thư viện như TCA cũng thiết kế reducer nhận inout State. Ngoài ra tránh để nơi khác giữ bản sao state trong lúc ghi (middleware, lịch sử undo, snapshot gửi cho UI), vì mỗi bản sao còn sống lại buộc lần ghi kế tiếp phải copy. Sửa xong đo lại bằng Time Profiler để chắc phần copy đã biến mất.
    struct AppState { var messages: [Message] = [] }

// Chậm: lúc append, buffer bị cả state lẫn next cùng giữ -> copy cả mảng
func reduce(_ state: AppState, _ message: Message) -> AppState {
  var next = state
  next.messages.append(message)
  return next
}

// Nhanh: sửa tại chỗ, buffer chỉ có một chủ nên append không phải copy
func reduce(_ state: inout AppState, _ message: Message) {
  state.messages.append(message)
}

Concurrency

Mọi rank →

  1. Bạn cần một ImageCache dùng chung cho cả app: đọc rất nhiều từ cellForRowAt trên main thread, thỉnh thoảng ghi từ background. Bạn bảo vệ state của nó bằng actor, @MainActor hay lock? Đánh đổi là gì?

    Xem đáp án mẫu
    Actor an toàn nhất vì compiler kiểm tra isolation giúp, nhưng mọi truy cập từ bên ngoài phải await: cellForRowAt vốn đồng bộ không đọc ngay được mà phải tạo Task, ảnh hiện trễ một nhịp, và mọi lời gọi xếp hàng tuần tự qua actor. @MainActor cho đọc đồng bộ ngay trên main, hợp khi truy cập chủ yếu từ UI và thao tác rất nhẹ, nhưng việc ghi từ background phải nhảy về main. Class final bọc state bằng lock (NSLock, OSAllocatedUnfairLock) và đánh dấu @unchecked Sendable thì đọc đồng bộ được từ mọi thread với chi phí rất thấp; đổi lại an toàn dựa vào kỷ luật của người viết: critical section ngắn, không bao giờ giữ lock qua await. Với cache nóng như ảnh tôi thường chọn lock, đóng gói trong một type nhỏ; state nghiệp vụ có nhiều bước async thì để actor.

  2. Code cũ dùng DispatchSemaphore trên main thread để chờ kết quả từ một queue .utility, và Xcode báo cảnh báo priority inversion. Vấn đề là gì và sửa thế nào?

    Xem đáp án mẫu
    Priority inversion xảy ra khi thread ưu tiên cao (main, QoS user-interactive) phải chờ một việc đang chạy ở QoS thấp; việc đó lại bị các tác vụ ưu tiên hơn chen ngang, nên main bị treo lâu hơn cần thiết. Với lock có owner như os_unfair_lock hay khi gọi DispatchQueue.sync, hệ thống biết ai đang giữ để tạm nâng priority cho bên đó; còn DispatchSemaphore và DispatchGroup.wait() không biết ai sẽ signal nên không làm được. Cách sửa tốt nhất là không block main: chuyển sang callback hoặc async/await, vì khi await một Task thì priority của task được escalate theo bên đang chờ. Nếu bắt buộc phải đồng bộ, dùng lock có owner và giữ critical section thật ngắn.
    // Code cũ: main thread chờ semaphore, hệ thống không biết nâng priority cho ai
func loadConfigSync() -> Config {
  let semaphore = DispatchSemaphore(value: 0)
  var result: Config?
  DispatchQueue.global(qos: .utility).async {
    result = ConfigLoader.load()
    semaphore.signal()
  }
  semaphore.wait() // main bị block: hang + priority inversion
  return result!
}

  3. Bạn được giao đưa một codebase UIKit lớn lên Swift 6 language mode. Lập kế hoạch thế nào để không 'đóng băng' cả team hàng tháng?

    Xem đáp án mẫu
    Tôi migrate theo từng module chứ không bật một lần cho cả app. Bước một: giữ Swift 5 mode nhưng bật strict concurrency checking mức complete để có danh sách cảnh báo, bắt đầu từ các module lá ít phụ thuộc như model, networking, rồi mới tới feature và app target. Bước hai: làm rõ isolation, như view controller và ViewModel là @MainActor, value type đi qua ranh giới concurrency thì Sendable, state dùng chung chuyển vào actor; thư viện bên thứ ba chưa cập nhật thì @preconcurrency import để tạm hạ cảnh báo. @unchecked Sendable và nonisolated(unsafe) chỉ dùng khi thật sự có lock bảo vệ, kèm comment giải thích. Module nào sạch cảnh báo thì bật Swift 6 mode cho riêng module đó và để CI chặn cảnh báo mới. Các bản Swift gần đây còn cho đặt default isolation là MainActor cho cả module, rất hợp với module UI vì giảm hẳn số annotation phải viết.

  1. Màn hình SwiftUI có danh sách vài nghìn dòng bị khựng mỗi khi một bộ đếm nhỏ ở header thay đổi. Bạn điều tra và tối ưu thế nào?

    Xem đáp án mẫu
    Trước hết xác định body nào chạy lại và vì sao: tạm thêm let _ = Self._printChanges() vào body, hoặc dùng template SwiftUI trong Instruments để đếm số lần view cập nhật. Nguyên nhân hay gặp là cả màn hình quan sát một ObservableObject lớn: bất kỳ @Published nào đổi cũng khiến mọi view dùng object đó tính lại body. Cách sửa: chuyển sang @Observable để view chỉ phụ thuộc property nó thực sự đọc, tách phần hay đổi thành view con riêng, dùng List/LazyVStack với id ổn định, và đưa việc nặng như sort, filter, format ra khỏi body. Tránh AnyView tràn lan vì nó che kiểu tĩnh khiến SwiftUI khó diff, và tránh id sinh mới mỗi lần render vì nó phá identity, buộc SwiftUI dựng lại view thay vì cập nhật.
    struct FeedScreen: View {

    }
  }
}

Kiến trúc & DI

Mọi rank →

  1. App có hơn 30 dev cùng làm trên một target khổng lồ, build sạch mất hơn 10 phút và conflict liên tục. Bạn lập lộ trình tách module thế nào để không phải dừng làm tính năng, và đo hiệu quả ra sao?

    Xem đáp án mẫu
    Tôi bắt đầu bằng số liệu: thời gian clean build, incremental build sau khi sửa một file hay đụng tới (Build Timeline của Xcode, log build trên CI) và số conflict theo thư mục, để có baseline và biết chỗ nào đau nhất. Sau đó tách dần từ dưới lên thay vì big bang: trước là phần lá ít phụ thuộc như Networking, DesignSystem, Analytics, rồi mới tới từng feature; mỗi bước là một PR nhỏ merge được ngay, app vẫn chạy bình thường suốt quá trình. Quy tắc phụ thuộc (feature không import feature, chỉ đi qua module interface) được ghi thành tài liệu và kiểm tra tự động trên CI để graph không mục dần. Mỗi module có owner qua CODEOWNERS và demo app riêng để dev làm UI mà không cần build cả app. Sau mỗi giai đoạn so lại với baseline; build time không giảm thì xem lại ranh giới module thay vì tiếp tục chia nhỏ.

  2. Khi tách app thành nhiều module, bạn chọn link static hay dynamic? Đánh đổi là gì?

    Xem đáp án mẫu
    Static library/framework được copy vào binary lúc link: launch nhanh vì dyld không phải load thêm image và linker còn loại bỏ được code chết, đổi lại mỗi thay đổi đều phải link lại một binary lớn. Dynamic framework được load lúc chạy: build incremental nhanh hơn và có thể dùng chung giữa app với extension để giảm dung lượng, nhưng mỗi framework làm tăng thời gian launch trước main. Bẫy hay gặp là một module static bị link vào cả app lẫn một dynamic framework, tạo ra hai bản copy, singleton thành hai instance và runtime cảnh báo class bị trùng. Với SPM, product để .automatic thì Xcode tự quyết và thường link static; từ Xcode 15 có mergeable libraries cho phép Debug dùng dynamic còn Release gộp vào binary như static.

  3. Thiết kế feature flag cho app iOS thế nào để vừa tắt được tính năng lỗi trong vài phút, vừa không biến thành nợ kỹ thuật?

    Xem đáp án mẫu
    Mỗi flag có giá trị mặc định an toàn compile sẵn trong app; giá trị remote được fetch, cache lại và chốt tại một điểm ổn định như đầu session để UI không đổi giữa chừng. Code đọc flag qua một protocol được inject chứ không gọi thẳng SDK remote config, để unit test và preview đặt được giá trị cụ thể. Tôi tách kill switch (sống lâu, dùng để tắt nhanh khi có sự cố) khỏi release flag (phải xoá ngay sau khi rollout 100%); mỗi flag có owner và hạn xoá, CI cảnh báo flag quá hạn. Cũng cần nhớ App Review không chấp nhận tính năng ẩn chưa qua duyệt, nên flag dùng để rollout dần chứ không để lén bật tính năng mới sau khi app đã được duyệt.
    enum Flag: String { case newCheckout, qrPayment }

protocol FeatureFlags {
  func isEnabled(_ flag: Flag) -> Bool
}

struct RemoteFeatureFlags: FeatureFlags {
  static let defaults: [Flag: Bool] = [.newCheckout: false, .qrPayment: false]
  let snapshot: [String: Bool] // giá trị remote đã cache, chốt lúc bắt đầu session

  func isEnabled(_ flag: Flag) -> Bool {
    snapshot[flag.rawValue] ?? Self.defaults[flag] ?? false
  }
}

Networking & Storage

Mọi rank →

  1. App bán hàng cho phép nhân viên tạo đơn khi mất mạng và tự đồng bộ khi có mạng lại. Bạn thiết kế phần sync thế nào để không mất đơn và không tạo đơn trùng?

    Xem đáp án mẫu
    Database local (Core Data, SwiftData hoặc SQLite qua GRDB) là nguồn dữ liệu cho UI; mỗi thao tác ghi vừa cập nhật bản local vừa thêm một bản ghi vào outbox trong cùng transaction, nên app có bị kill giữa chừng cũng không mất. Mỗi mutation mang một idempotency key do client sinh một lần (UUID), server dùng key đó để bỏ qua request lặp lại, nhờ vậy retry sau timeout không tạo đơn trùng. Bộ sync xử lý outbox theo thứ tự, retry với exponential backoff, được kích hoạt khi app vào foreground, khi NWPathMonitor báo có mạng, và qua BGAppRefreshTask như một tối ưu chứ không phải điều kiện bắt buộc. Chiều kéo về dùng delta sync theo cursor hoặc version; xung đột phải có chính sách rõ ràng (server thắng, so version, hoặc để user chọn) thay vì để mặc định ngầm.

Mọi rank →

  1. App chính, widget và Notification Service Extension cần dùng chung trạng thái đăng nhập và database. Bạn tổ chức thế nào, cần lưu ý gì?

    Xem đáp án mẫu
    Extension là process riêng với sandbox riêng, nên các target phải bật cùng một App Group: file và database đặt trong container của group, cấu hình nhỏ dùng UserDefaults(suiteName:), còn token để trong Keychain với access group dùng chung. Hai process có thể ghi cùng lúc nên cần cơ chế phối hợp: SQLite chạy WAL, Core Data bật persistent history tracking để app thấy thay đổi do extension ghi, và báo widget vẽ lại bằng WidgetCenter. Extension có giới hạn memory chặt hơn app nhiều, nên đừng khởi tạo cả dependency graph của app bên trong. Bẫy nặng nhất là crash 0xdead10cc: process bị suspend khi đang giữ file lock hoặc transaction SQLite trong shared container sẽ bị hệ thống kill, vì vậy phải ghi xong trước khi vào background hoặc bọc thao tác ghi bằng background task.

  2. App cần tự làm mới dữ liệu ở background vài giờ một lần và dọn database vào ban đêm. Bạn dùng BGTaskScheduler thế nào cho đúng?

    Xem đáp án mẫu
    Việc làm mới nhẹ dùng BGAppRefreshTaskRequest, việc nặng như dọn database dùng BGProcessingTaskRequest (có thể yêu cầu cắm sạc, có mạng). Identifier phải khai báo trong BGTaskSchedulerPermittedIdentifiers của Info.plist, bật Background Modes tương ứng, và đăng ký handler trước khi app launch xong, nếu không sẽ crash. earliestBeginDate chỉ là mốc sớm nhất; hệ thống tự chọn thời điểm dựa trên pin, mạng và thói quen dùng app. User tắt Background App Refresh thì refresh task không chạy, còn app đã bị user force-quit thì thường không được chạy task nền cho tới khi user mở lại. Trong handler phải đặt expirationHandler để huỷ việc đang làm, luôn gọi setTaskCompleted(success:) và lên lịch lần kế tiếp. Khi debug có thể ép hệ thống chạy task bằng lệnh LLDB _simulateLaunchForTaskWithIdentifier.
    // Trong application(_:didFinishLaunchingWithOptions:)
BGTaskScheduler.shared.register(forTaskWithIdentifier: "vn.shop.refresh", using: nil) { task in
  self.handleRefresh(task as! BGAppRefreshTask)
}

func handleRefresh(_ task: BGAppRefreshTask) {
  scheduleNextRefresh() // luôn lên lịch cho lần kế tiếp
  let work = Task {
    let ok = await syncEngine.pullChanges()
    task.setTaskCompleted(success: ok && !Task.isCancelled)
  }
  task.expirationHandler = { work.cancel() } // hết giờ thì huỷ việc đang làm
}

  3. App chat mã hoá đầu cuối cần hiện push có preview nội dung và ảnh. Bạn dùng silent push hay Notification Service Extension? Vì sao?

    Xem đáp án mẫu
    Tôi chọn Notification Service Extension. Silent push (content-available: 1) chỉ là gợi ý để đánh thức app, bị hệ thống throttle và không được giao cho app mà user đã force-quit, nên không dùng được cho thông báo bắt buộc phải tới tay người dùng. Với NSE, server gửi push hiển thị có mutable-content: 1; extension nhận trong didReceive(_:withContentHandler:), giải mã bằng khoá đọc từ Keychain dùng chung, tải ảnh rồi gắn UNNotificationAttachment trước khi gọi contentHandler. Extension chỉ có khoảng 30 giây và ít memory; nếu lỗi hoặc hết giờ, hệ thống hiện nguyên alert gốc. Vì vậy alert gốc chỉ nên là câu chung chung như 'Bạn có tin nhắn mới', còn ciphertext đặt trong một field riêng của payload.

Performance

Mọi rank →

  1. User báo feed cuộn giật trên iPhone đời cũ, còn máy của dev thì mượt. Bạn dùng Instruments để tìm nguyên nhân thế nào?

    Xem đáp án mẫu
    Đầu tiên là profile bản Release trên đúng loại máy yếu: build Debug thiếu tối ưu của compiler, còn Simulator chạy bằng CPU/GPU của Mac nên số đo không phản ánh thực tế. Dùng template Animation Hitches để biết frame nào bị trễ, rồi Time Profiler để xem main thread đang làm gì lúc đó; bật Invert Call Tree và Hide System Libraries để hàm của app tốn CPU nhất nổi lên đầu. Thủ phạm hay gặp là decode ảnh, parse JSON, tạo DateFormatter hay tính chiều cao text ngay trong cellForRowAt, hoặc Auto Layout lồng nhau quá sâu. Nếu main thread nhàn mà vẫn hitch thì nghi phía render: offscreen rendering, blending, ảnh lớn hơn kích thước hiển thị. Sửa xong phải đo lại đúng kịch bản cũ để chứng minh có cải thiện.

  2. App mất gần 3 giây cho cold launch và PM muốn giảm một nửa. Bạn phân tích và tối ưu thế nào?

    Xem đáp án mẫu
    Tôi tách launch làm hai đoạn. Trước main: dyld load và link các dynamic framework, chạy static initializer và +load của Objective-C; càng nhiều dynamic framework thì đoạn này càng dài, nên gộp hoặc chuyển sang link static và loại bỏ +load. Từ main tới frame đầu tiên: mọi việc trong didFinishLaunching, khởi tạo SDK, mở database, dựng root view controller; chỉ giữ thứ cần cho frame đầu, còn lại lazy hoặc dời ra sau khi UI hiện. Đo bằng template App Launch của Instruments trên máy thật ở trạng thái cold launch (ví dụ sau khi khởi động lại máy), và theo dõi số liệu thật của user qua Xcode Organizer hoặc MetricKit. Bẫy hay gặp là SDK analytics, quảng cáo khởi tạo đồng bộ và singleton nặng bị chạm tới quá sớm.

  3. Màn hình gallery hiển thị lưới thumbnail từ ảnh chụp camera và app bị kill vì hết memory. Vì sao, và xử lý thế nào?

    Xem đáp án mẫu
    Dung lượng file JPEG không quyết định memory: khi hiển thị, ảnh được decode thành bitmap khoảng width × height × 4 byte, nên ảnh 12MP (4032×3024) chiếm gần 50MB dù chỉ hiện trong ô 100×100 point. Vài chục ảnh như vậy đủ khiến app bị hệ thống kill vì vượt giới hạn memory. Cách đúng là downsample bằng ImageIO: tạo thumbnail có kích thước pixel tối đa bằng kích thước ô nhân scale màn hình, không bao giờ decode ảnh gốc, và làm việc này trên background queue. Kết quả nên cache bằng NSCache với cost là số byte đã decode. Với trường hợp đơn giản, từ iOS 15 có sẵn preparingThumbnail(of:) của UIImage.
    func downsample(at url: URL, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
  // Không cache ảnh gốc khi tạo image source
  let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
  guard let source = CGImageSourceCreateWithURL(url as CFURL, sourceOptions) else { return nil }
  let maxPixel = max(pointSize.width, pointSize.height) * scale
  let options = [
    kCGImageSourceCreateThumbnailFromImageAlways: true,
    kCGImageSourceShouldCacheImmediately: true, // decode ngay tại đây, trên background
    kCGImageSourceCreateThumbnailWithTransform: true,
    kCGImageSourceThumbnailMaxPixelSize: maxPixel
  ] as CFDictionary
  guard let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, options) else { return nil }
  return UIImage(cgImage: cgImage)
}

    Xem đáp án mẫu

  3. Crash report của bản production chỉ toàn địa chỉ hex, không có tên hàm. Quy trình symbolicate đúng là gì, và vì sao hay bị thiếu dSYM?

    Xem đáp án mẫu
    Binary release đã bị strip symbol, nên cần file dSYM sinh ra từ đúng lần build đó; crash report và dSYM được khớp với nhau qua UUID của binary chứ không qua version hay build number. Build release phải đặt DEBUG_INFORMATION_FORMAT = dwarf-with-dsym, giữ lại archive, và upload dSYM của app cùng các framework lên Crashlytics/Sentry ngay trong pipeline. Thiếu dSYM thường do build lại cùng version trên máy khác nên UUID khác, framework bên thứ ba không kèm dSYM, hoặc bản build trên CI quên bước upload. Kiểm tra UUID bằng dwarfdump --uuid, symbolicate tay bằng atos hoặc để Xcode Organizer làm. Bitcode đã bị deprecated từ Xcode 14, nên dSYM giờ do bạn tạo ra lúc archive, không còn phải tải về từ App Store Connect như trước.

  1. App ngân hàng cần lưu refresh token và một khoá để ký giao dịch, yêu cầu Face ID mỗi lần ký. Bạn lưu trữ trên iOS thế nào?

    Xem đáp án mẫu
    Refresh token để trong Keychain, không bao giờ trong UserDefaults hay file plist, với accessibility vừa đủ: cần đọc lúc máy khoá (refresh ở background) thì AfterFirstUnlockThisDeviceOnly, không cần thì WhenUnlockedThisDeviceOnly; hậu tố ThisDeviceOnly ngăn item theo bản backup sang máy khác. Khoá ký nên sinh trong Secure Enclave: private key không bao giờ rời chip, app chỉ gửi dữ liệu vào để ký, và gắn SecAccessControl với .biometryCurrentSet để mỗi lần ký phải qua Face ID; khi user thay đổi dữ liệu sinh trắc, khoá mất hiệu lực và phải đăng ký lại. Server giữ public key để verify chữ ký. Lưu ý item Keychain có thể còn lại sau khi gỡ app, nên lần chạy đầu sau khi cài lại cần dọn dữ liệu cũ.
    let access = SecAccessControlCreateWithFlags(
  nil,
  kSecAttrAccessibleWhenUnlockedThisDeviceOnly,

  2. Team bảo mật yêu cầu certificate pinning cho API thanh toán. Bạn triển khai thế nào để app không 'chết' hàng loạt khi server đổi chứng chỉ?

    Xem đáp án mẫu
    Tôi pin public key (hash SPKI) thay vì cả certificate, vì certificate được gia hạn định kỳ còn cặp khoá có thể giữ nguyên; và luôn có ít nhất một pin dự phòng cho khoá sẽ xoay sang, để app đang chạy ngoài thị trường không mất kết nối. Quy trình quan trọng không kém code: lịch xoay khoá thống nhất với backend, log lỗi pinning để phát hiện sớm, và có sẵn cơ chế buộc cập nhật. System Design

Mọi rank →

  1. Thiết kế phía client cho app chat 1-1 và nhóm: kết nối realtime, lưu trữ, trạng thái tin nhắn và push. Bạn trình bày thế nào?

    Xem đáp án mẫu
    Kết nối realtime qua WebSocket (URLSessionWebSocketTask hoặc thư viện), có heartbeat, reconnect với exponential backoff, và sau khi nối lại thì kéo phần còn thiếu theo sequence cuối cùng đã nhận. Database local là nguồn dữ liệu cho UI, phân trang ngược khi user cuộn lên. Gửi tin theo kiểu optimistic: tạo bản ghi local với clientId và trạng thái sending, hiện ngay; server xác nhận thì cập nhật serverId, sequence và chuyển sang sent; mất mạng thì nằm trong outbox chờ retry, server dựa vào clientId để chống trùng. Thứ tự tin dựa vào sequence do server cấp, không dựa vào đồng hồ thiết bị. Khi app không chạy thì nhận qua APNs, dùng Notification Service Extension để giải mã và hiện preview; trạng thái đã nhận, đã đọc là các event riêng, nên gộp theo batch để giảm tải.
    enum DeliveryState: String, Codable {
  case sending, sent, delivered, read, failed
}

struct Message: Codable, Identifiable {
  let clientId: UUID      // client sinh, dùng để chống trùng khi retry
  var serverId: String?   // nil khi server chưa xác nhận
  var sequence: Int64?    // thứ tự do server cấp, dùng để sắp xếp
  let conversationId: String
  var body: String
  var state: DeliveryState
  var id: UUID { clientId }
}

  2. Nếu phải tự viết thư viện tải và cache ảnh thay cho Kingfisher hay SDWebImage, bạn thiết kế những thành phần nào?

    Xem đáp án mẫu
    Tôi chia thành bốn phần. Memory cache dùng NSCache lưu ảnh đã decode và downsample, cost là số byte của bitmap để giới hạn theo dung lượng thật, và tự bị xả khi hệ thống thiếu memory. Disk cache lưu dữ liệu gốc với key là hash của URL, có giới hạn tổng dung lượng, dọn theo LRU và tôn trọng thời hạn cache. Tầng tải gộp request trùng: nhiều nơi cùng xin một URL thì chỉ có một request mạng; request bị huỷ khi không còn ai cần (cell đã bị reuse), và có prefetch qua UITableViewDataSourcePrefetching. Decode và downsample luôn chạy ngoài main thread; khi gán ảnh vào cell phải kiểm tra cell vẫn đang hiển thị đúng URL đó để không hiện nhầm ảnh.

    Xem đáp án mẫu
    Tôi coi đây là vấn đề của cả quy trình chứ không chỉ của một người. Về công cụ: bật các rule SwiftLint như force_unwrapping, weak_delegate, và thêm helper trong test kiểm tra view controller được giải phóng sau khi đóng, để máy bắt lỗi thay cho người review.
