  1. Trong code review bạn thấy func makeRepository() -> any UserRepository ở chỗ này và func render(_ shape: some Shape) ở chỗ khác. some và any khác nhau thế nào, khi nào chọn cái nào?

    Xem đáp án mẫu
    some P là opaque type: luôn là một kiểu cụ thể duy nhất mà compiler biết lúc compile, chỉ bị che với người gọi; vì vậy hàm -> some View phải trả về cùng một kiểu ở mọi nhánh, và compiler tối ưu được bằng static dispatch, specialization. Ở vị trí tham số, some P là cách viết gọn của generic <T: P>. any P là existential: một cái hộp chứa được bất kỳ kiểu nào conform P, kiểu thật có thể khác nhau lúc runtime; đổi lại tốn chi phí box (có thể cấp phát heap nếu giá trị lớn), dynamic dispatch, và các API dính tới associatedtype/Self bị hạn chế. Thực tế nên mặc định dùng some/generic, chỉ dùng any khi cần tập hợp dị chủng như [any Shape], hoặc khi kiểu cụ thể chỉ được chọn lúc runtime như factory trả về mock hay bản thật.

  2. Array, Dictionary của Swift là value type nhưng gán qua lại rất rẻ nhờ copy-on-write. Nếu bạn tự viết một struct bọc storage là class (vd. một buffer lớn), làm sao để nó cũng có copy-on-write?

    Xem đáp án mẫu
    Copy-on-write nghĩa là khi gán sang biến khác, hai bản chỉ chia sẻ chung một buffer; việc copy thật chỉ xảy ra khi một bản muốn ghi trong lúc buffer đang được chia sẻ. Struct tự viết chứa class thì mặc định không có COW: copy struct chỉ copy tham chiếu, sửa qua bản này thì bản kia cũng đổi theo, phá vỡ value semantics. Cách làm: trước mọi thao tác ghi, gọi isKnownUniquelyReferenced(&storage); nếu storage đang được chia sẻ thì clone ra bản mới rồi mới ghi. Lưu ý COW không tự có cho mọi struct, chỉ có ở các collection chuẩn và những kiểu tự cài đặt như trên; struct thường nhiều field thì về nguyên tắc vẫn được copy toàn bộ khi gán.
    final class Storage {
  var values: [Int]
  init(_ values: [Int]) { self.values = values }
}

struct Buffer {
  private var storage = Storage([])

  mutating func append(_ x: Int) {
    if !isKnownUniquelyReferenced(&storage) {
      storage = Storage(storage.values) // đang bị chia sẻ: clone trước khi ghi
    }
    storage.values.append(x)
  }
}

  3. Bạn muốn các property như volume, progress luôn bị giới hạn trong một khoảng giá trị mà không phải lặp code ở từng setter. Viết property wrapper thế nào, và projectedValue (truy cập qua $) dùng để làm gì?

    Xem đáp án mẫu
    Property wrapper là type đánh dấu @propertyWrapper có wrappedValue; khi viết @Clamped(0...1) var volume = 0.5, compiler sinh ra backing storage _volume kiểu Clamped<Double> và chuyển mọi lần đọc/ghi volume sang _volume.wrappedValue, nên logic giới hạn nằm ở một chỗ. projectedValue là giá trị phụ truy cập qua $volume, dùng để lộ thêm thông tin hoặc API, giống @State có $ trả về Binding, @Published có $ trả về publisher. Hạn chế cần biết: không khai báo được property wrapper trong protocol requirement, và vì logic chạy trong getter/setter ở mỗi lần truy cập nên đừng đặt việc nặng vào đó.
    @propertyWrapper
struct Clamped<Value: Comparable> {
  private var value: Value
  let range: ClosedRange<Value>
  init(wrappedValue: Value, _ range: ClosedRange<Value>) {
    self.range = range
    self.value = min(max(wrappedValue, range.lowerBound), range.upperBound)
  }
  var wrappedValue: Value {
    get { value }
    set { value = min(max(newValue, range.lowerBound), range.upperBound) }
  }
  var projectedValue: ClosedRange<Value> { range } // đọc qua $volume
}
// Dùng: @Clamped(0...1) var volume = 0.5  -> gán volume = 2 sẽ thành 1

  4. Codebase trộn nhiều kiểu xử lý lỗi: try? nuốt lỗi khắp nơi, hàm trả Optional để báo thất bại, completion (Result<T, Error>) -> Void, và fatalError ở chỗ không chắc. Bạn chuẩn hoá xử lý lỗi trong Swift thế nào: throws, Result, typed throws, LocalizedError, và khi nào dùng try?, try!?

    Xem đáp án mẫu
    throws là cách mặc định cho hàm có thể thất bại: lỗi là giá trị conform Error (thường là enum có associated value), caller buộc phải xử lý bằng do/catch, try? hoặc truyền tiếp (rethrows cho hàm nhận closure có thể throw); với async/await, lỗi đi qua await rất tự nhiên nên async throws thay phần lớn completion handler. Result<Success, Failure> hợp khi cần lưu hay truyền kết quả như một giá trị (callback cũ, lưu trong state), chuyển qua lại bằng Result { try ... } và .get(). Từ Swift 6 có typed throws (throws(ParseError)) cho phép khai báo kiểu lỗi cụ thể để caller catch đầy đủ mà không cần ép kiểu; nên dùng ở tầng nội bộ có tập lỗi đóng, còn API công khai hay tầng có nhiều nguồn lỗi thường vẫn dùng throws thường để dễ tiến hoá. try? biến lỗi thành nil nên mất thông tin: chỉ dùng khi thất bại thật sự không quan trọng (cache, dọn dẹp), không dùng để nuốt lỗi của việc người dùng đang chờ. try! và fatalError dành cho lỗi lập trình (invariant bị vi phạm), không dùng cho lỗi môi trường như mạng, file, dữ liệu server. Thiết kế lỗi: mỗi tầng có kiểu lỗi riêng với ý nghĩa nghiệp vụ và map lỗi tầng dưới lên (URLError thành PaymentError.network); conform LocalizedError để có errorDescription thân thiện cho UI thay vì lộ thông điệp kỹ thuật. Luôn xử lý CancellationError riêng vì huỷ không phải lỗi cần báo user, và tránh catch rỗng, ít nhất phải log lại.
    enum PaymentError: LocalizedError {

  5. App hiển thị giờ đặt hàng lệch 7 tiếng ở một số máy, DateFormatter tạo trong cellForRow làm cuộn chậm, và giá tiền hiện 1,000.00 thay vì 1.000 ₫ trên máy đặt ngôn ngữ khác. Bạn xử lý Date, DateFormatter, Locale và TimeZone đúng thế nào?

    Xem đáp án mẫu
    Date là một thời điểm tuyệt đối (số giây từ một mốc tham chiếu) và không có múi giờ; múi giờ và định dạng chỉ xuất hiện khi chuyển Date thành chuỗi hoặc tính theo lịch. Lệch 7 tiếng thường do parse chuỗi UTC (ISO 8601 có Z) rồi hiển thị bằng formatter sai timeZone, hoặc ngược lại coi giờ local là UTC. Server nên gửi ISO 8601 có offset hoặc epoch; client parse bằng ISO8601DateFormatter rồi hiển thị theo TimeZone.current của user, hoặc theo múi giờ nghiệp vụ như Asia/Ho_Chi_Minh nếu giờ đặt hàng phải cố định theo cửa hàng. Định dạng chuỗi cố định cho giao tiếp máy (yyyy-MM-dd) phải đặt locale = Locale(identifier: "en_US_POSIX"), nếu không lịch hoặc kiểu giờ 12/24 của máy user có thể làm hỏng kết quả. Hiển thị cho người dùng thì dùng style theo locale (dateStyle/timeStyle, setLocalizedDateFormatFromTemplate) thay vì tự ghép chuỗi; từ iOS 15 có FormatStyle (date.formatted(date: .abbreviated, time: .shortened), price.formatted(.currency(code: "VND"))) gọn và tự theo locale. DateFormatter và NumberFormatter tạo tốn kém nên tạo một lần rồi tái sử dụng (static), không tạo trong cellForRow; dùng chung giữa các thread được miễn là không đổi cấu hình sau khi đã chia sẻ. Tính toán ngày dùng Calendar (date(byAdding:), startOfDay(for:)), không cộng 86400 giây vì một ngày có thể dài 23 hoặc 25 giờ khi đổi giờ mùa hè; tiền tệ dùng Decimal thay vì Double.

  6. Một protocol có extension cung cấp implementation mặc định. Struct conform ghi đè method đó, nhưng khi gọi qua biến kiểu protocol thì lại chạy bản mặc định trong extension chứ không phải bản của struct. Vì sao, và static dispatch khác dynamic dispatch thế nào trong Swift?

    Xem đáp án mẫu
    Method được khai báo trong protocol (requirement) được gọi qua protocol witness table, tức dynamic dispatch: bản của kiểu cụ thể được chọn lúc chạy. Method chỉ có trong extension mà không nằm trong protocol thì không có trong witness table; Swift dispatch tĩnh theo kiểu khai báo của biểu thức lúc compile. Vì thế biến kiểu any Greeter gọi bản trong extension, còn biến kiểu Person mới gọi bản của struct, đúng hiện tượng bạn gặp. Cách sửa: khai báo method đó trong protocol như một requirement (extension chỉ cung cấp bản mặc định), khi đó override của kiểu cụ thể được dùng ở mọi nơi. Nếu cố ý muốn một tiện ích không bị override thì để trong extension là hợp lý. Với class: method final và private dispatch tĩnh, method thường dùng vtable (dynamic), @objc dynamic đi qua Objective-C runtime (cần cho KVO hay swizzling), còn struct và enum dispatch tĩnh vì không kế thừa. Hiểu điều này giải thích vì sao final và struct nhanh hơn, và vì sao generic <T: Greeter> hay some Greeter luôn gọi đúng method của kiểu cụ thể (kiểu đã biết khi specialize) còn any Greeter đi qua witness table. Hệ quả thực tế khi test: mock chỉ thay thế được những method nằm trong requirement của protocol, nên logic mặc định nằm trong extension ngoài requirement sẽ không mock được.
    protocol Greeter {
  func hello() -> String // requirement: dynamic dispatch qua witness table
}

extension Greeter {
  func hello() -> String { "Xin chào (mặc định)" }
  func goodbye() -> String { "Tạm biệt (mặc định)" } // KHÔNG nằm trong protocol: dispatch tĩnh
}

struct Person: Greeter {
  func hello() -> String { "Chào bạn" }
  func goodbye() -> String { "Hẹn gặp lại" }
}

let p = Person()
let g: any Greeter = p
print(g.hello())   // "Chào bạn": requirement, chọn theo kiểu thật lúc chạy
print(g.goodbye()) // "Tạm biệt (mặc định)": theo kiểu khai báo, bỏ qua bản của Person
print(p.goodbye()) // "Hẹn gặp lại": biến có kiểu Person

  1. ViewModel lắng nghe một AsyncStream bằng Task { for await event in stream { ... } }. Màn hình đã đóng nhưng deinit của ViewModel không bao giờ chạy. Vì sao, và thêm [weak self] có đủ không?

    Xem đáp án mẫu
    Closure của Task giữ self mạnh suốt thời gian task chạy, mà vòng for await trên một stream không kết thúc thì task chạy mãi, nên ViewModel không bao giờ được giải phóng. Chỉ thêm [weak self] là chưa đủ nếu ngay đầu task viết guard let self rồi mới vào vòng lặp, vì khi đó self lại bị giữ mạnh trong suốt vòng lặp. Cách đúng là giữ handle của task và cancel() khi màn hình biến mất (từ onDisappear hoặc coordinator), hoặc chỉ unwrap self bên trong từng vòng lặp. Trong SwiftUI, modifier .task tự cancel khi view biến mất nên là cách gọn nhất. Lưu ý không thể dựa vào deinit để cancel task, vì deinit chính là thứ đang không chạy.
    @MainActor
final class ChatViewModel {
  private var listenTask: Task<Void, Never>?

  func start(stream: AsyncStream<Message>) {
    listenTask = Task { [weak self] in
      for await message in stream {
        guard let self else { return } // chỉ giữ self mạnh trong từng vòng
        self.handle(message)
      }
    }
  }

  func stop() { listenTask?.cancel() }
}

  1. Màn Home cần gọi 3 API độc lập (profile, banner, khuyến mãi), còn màn danh sách phải tải thumbnail cho N sản phẩm. Bạn dùng async let hay TaskGroup cho từng trường hợp? Nếu một request throw thì các request còn lại ra sao?

    Xem đáp án mẫu
    async let hợp với số task cố định, biết trước lúc viết code, mỗi task có thể trả về kiểu khác nhau; withThrowingTaskGroup dành cho số task động như N thumbnail, kết quả cùng kiểu và được nhận về theo thứ tự hoàn thành. Cả hai đều là structured concurrency: child task không sống lâu hơn scope tạo ra nó, task cha bị cancel thì child cũng bị cancel. Khi lỗi thoát khỏi scope, các child còn đang chạy bị cancel và được chờ kết thúc rồi hàm mới throw ra ngoài. Bẫy hay gặp: với async let, lỗi chỉ lộ ra khi await tới đúng biến đó nên thứ tự await quyết định phát hiện lỗi sớm hay muộn; còn viết let a = try await f() liên tiếp thì các request chạy tuần tự chứ không song song.
    func loadHome() async throws -> HomeData {
  async let profile = api.fetchProfile()
  async let banners = api.fetchBanners()
  async let deals = api.fetchDeals()
  // Ba request chạy song song, chờ đủ cả ba
  return try await HomeData(profile: profile, banners: banners, deals: deals)
}
func loadThumbnails(ids: [String]) async throws -> [String: Data] {
  try await withThrowingTaskGroup(of: (String, Data).self) { group in
    for id in ids { group.addTask { try await (id, api.thumbnail(id)) } }
    var result: [String: Data] = [:]
    for try await (id, data) in group { result[id] = data }
    return result
  }
}

  2. Bạn đưa logic refresh token vào một actor để tránh race condition, nhưng log vẫn cho thấy API refresh bị gọi 2–3 lần khi nhiều request cùng gặp 401. Vì sao actor không chặn được, và sửa thế nào?

    Xem đáp án mẫu
    Actor chỉ đảm bảo tại một thời điểm có tối đa một đoạn code chạy trên nó, nhưng actor là reentrant: tại mỗi await, actor được phép xử lý lời gọi khác. Request thứ nhất thấy token hết hạn và await refresh; trong lúc chờ, request thứ hai vào actor, cũng thấy token hết hạn và gọi refresh lần nữa. Cách sửa phổ biến là lưu Task refresh đang chạy vào một property, các lời gọi đến sau chỉ await chính task đó. Nguyên tắc chung khi viết actor: sau mỗi await đừng giả định state còn như cũ, hãy kiểm tra lại, và gom phần đọc rồi sửa state vào đoạn đồng bộ không có await.
    actor TokenProvider {
  private var token: Token?
  private var refreshTask: Task<Token, Error>?

  func validToken() async throws -> Token {
    if let token, !token.isExpired { return token }
    if let refreshTask { return try await refreshTask.value } // đã có người refresh
    let task = Task { try await authAPI.refresh() }
    refreshTask = task
    defer { refreshTask = nil }
    let newToken = try await task.value
    token = newToken
    return newToken
  }
}

  3. ViewModel gán @Published từ completion handler của URLSession và Xcode báo tím "Publishing changes from background threads is not allowed". Với Swift Concurrency, bạn sửa thế nào cho triệt để thay vì rải DispatchQueue.main.async khắp nơi?

    Xem đáp án mẫu
    Đánh dấu cả ViewModel là @MainActor: mọi property và method của nó được cô lập trên main actor, compiler buộc code từ ngữ cảnh khác phải await khi truy cập, nên không còn chuyện quên chuyển về main thread. Đồng thời đổi sang API async như URLSession.data(for:): khi await, hàm chỉ suspend chứ không block main thread, request được xử lý ở nơi khác và khi xong thì quay lại main actor để gán state. Còn DispatchQueue.main.async phải nhớ đặt ở từng chỗ và compiler không kiểm tra giúp. Bẫy cần biết: @MainActor không làm việc nặng nhẹ đi, nếu parse JSON lớn hay xử lý ảnh đồng bộ ngay trong method của ViewModel thì main thread vẫn bị chiếm, phần đó nên tách sang type hoặc actor khác.

  4. Ô search gọi API mỗi khi user gõ, và kết quả của từ khoá cũ đôi khi về sau, đè lên kết quả mới. Bạn huỷ request cũ thế nào? Gọi task.cancel() thì code trong task có dừng ngay không?

    case .restricted: onChange?(.restricted)
    case .denied: onChange?(.denied) // chỉ đưa user tới Settings được

  3. Test cho tầng networking đang gọi server thật nên chậm và flaky; bạn muốn test cả URLSession thật (header, decode, retry) mà không chạm mạng. URLProtocol stub hoạt động thế nào, và nó khác mock bằng protocol ra sao?

    Xem đáp án mẫu
    Mock bằng protocol (một APIClient giả) hợp để test ViewModel vì thay luôn cả client. Nhưng muốn test chính client (build request có đúng header và body không, xử lý 401, retry, decode lỗi) thì phải chạy code URLSession thật. URLProtocol là điểm chặn của URL loading system: tạo subclass StubURLProtocol rồi đăng ký vào URLSessionConfiguration.protocolClasses của một session dùng riêng trong test (dùng .ephemeral để không dính cache hay cookie); khi session xử lý request, nó hỏi canInit(with:) rồi gọi startLoading() để ta trả HTTPURLResponse và Data giả qua client?.urlProtocol(...). Nhờ vậy test kiểm tra được cả request đã gửi (xác nhận URL, method, header ngay trong handler) và giả lập được các tình huống khó: 503 rồi 200 để test retry, timeout, URLError(.notConnectedToInternet), body hỏng. Tránh URLProtocol.registerClass toàn cục vì làm các test lẫn vào nhau; hãy truyền session đã cấu hình vào client qua initializer. Test cần chạy nhanh và xác định: không sleep, và backoff nhận một Clock hoặc closure sleep để test điều khiển thời gian. Handler thường là biến tĩnh nên các test dùng chung stub không được chạy song song (Swift Testing mặc định chạy song song, cần trait .serialized). Khi kiểm tra body của request upload trong URLProtocol, đọc httpBodyStream chứ không phải httpBody. Thêm vài test tích hợp thật với server staging ở pipeline riêng, không nằm trong test chạy mỗi PR.
    final class StubURLProtocol: URLProtocol {
  nonisolated(unsafe) static var handler: ((URLRequest) throws -> (HTTPURLResponse, Data))?

  override class func canInit(with request: URLRequest) -> Bool { true }
  override class func canonicalRequest(for request: URLRequest) -> URLRequest { request }

  override func startLoading() {
    guard let handler = Self.handler else { return }
    do {
      let (response, data) = try handler(request)
      client?.urlProtocol(self, didReceive: response, cacheStoragePolicy: .notAllowed)
      client?.urlProtocol(self, didLoad: data)
      client?.urlProtocolDidFinishLoading(self)
    } catch {
      client?.urlProtocol(self, didFailWithError: error)
    }
  }

  override func stopLoading() {}
}

func makeSession() -> URLSession {
  let config = URLSessionConfiguration.ephemeral
  config.protocolClasses = [StubURLProtocol.self] // chỉ session này bị chặn, không đụng URLSession.shared
  return URLSession(configuration: config)
}

  1. Bạn thêm đăng nhập bằng Face ID/Touch ID: gọi LAContext.evaluatePolicy, thành công thì cho vào luôn. Reviewer phản đối cách làm này. Dùng LocalAuthentication đúng cách thế nào, các lỗi cần xử lý là gì, và vì sao nên gắn với Keychain?

    Xem đáp án mẫu
    Kết quả evaluatePolicy chỉ là một Bool trả về trong process của app, nên nếu quyết định mở khoá chỉ dựa vào nó thì kẻ tấn công có thể hook để luôn trả true. Cách bền hơn là gắn bí mật với sinh trắc: lưu refresh token hay khoá vào Keychain với SecAccessControl yêu cầu .biometryCurrentSet hoặc .userPresence; khi đọc item, hệ thống hiện hộp thoại Face ID và chỉ trả dữ liệu nếu xác thực thành công, nên không thể bỏ qua ở tầng app. Về LAContext: gọi canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics, error:) để biết máy có hỗ trợ và đã đăng ký sinh trắc chưa (biometryType cho biết .faceID hay .touchID để chọn icon và chữ), rồi evaluatePolicy(_:localizedReason:) (có bản async); dùng .deviceOwnerAuthentication nếu cho phép fallback sang mật mã máy. Chuỗi NSFaceIDUsageDescription bắt buộc trong Info.plist, thiếu sẽ crash trên máy có Face ID. Xử lý LAError: .userCancel (không phải lỗi, quay về màn đăng nhập thường), .userFallback (user chọn nhập mật khẩu), .biometryLockout (sai nhiều lần, cần mật mã), .biometryNotEnrolled và .biometryNotAvailable (ẩn tính năng hoặc hướng dẫn bật), .authenticationFailed. Khi user thêm hay đổi dữ liệu sinh trắc, item gắn .biometryCurrentSet mất hiệu lực, app phải cho đăng nhập lại bằng mật khẩu và đăng ký lại. Luôn có đường đăng nhập thay thế, hỏi bật sinh trắc sau khi đăng nhập thành công (opt-in) và xoá item khi user đăng xuất.

  kSecClass as String: kSecClassGenericPassword,
  kSecAttrService as String: "vn.shop.auth",
  kSecAttrAccount as String: "refreshToken",
]

// Lưu refresh token: chỉ đọc được sau khi qua Face ID/Touch ID
func saveToken(_ token: Data) throws {
  let access = SecAccessControlCreateWithFlags(
    nil, kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly, .biometryCurrentSet, nil
  )!
  SecItemDelete(base as CFDictionary) // xoá bản cũ nếu có
  var query = base
  query[kSecAttrAccessControl as String] = access
  query[kSecValueData as String] = token
  guard SecItemAdd(query as CFDictionary, nil) == errSecSuccess else { throw AuthError.keychain }
}

func loadToken() throws -> Data {
  let context = LAContext()
  context.localizedReason = "Đăng nhập vào tài khoản"
  var query = base
  query[kSecReturnData as String] = true
  query[kSecUseAuthenticationContext as String] = context // đọc item sẽ hiện hộp thoại Face ID của hệ thống
  var item: CFTypeRef?
  let status = SecItemCopyMatching(query as CFDictionary, &item)
  guard status == errSecSuccess, let data = item as? Data else {
    throw status == errSecUserCanceled ? AuthError.cancelled : AuthError.keychain
  }
  return data
}
