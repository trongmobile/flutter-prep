  1. Trong code review bạn thấy func makeRepository() -> any UserRepository ở chỗ này và func render(_ shape: some Shape) ở chỗ khác. some và any khác nhau thế nào, khi nào chọn cái nào?

    Xem đáp án mẫu
    some P là opaque type: luôn là một kiểu cụ thể duy nhất mà compiler biết lúc compile, chỉ bị che với người gọi; vì vậy hàm -> some View phải trả về cùng một kiểu ở mọi nhánh, và compiler tối ưu được bằng static dispatch, specialization. Ở vị trí tham số, some P là cách viết gọn của generic <T: P>. any P là existential: một cái hộp chứa được bất kỳ kiểu nào conform P, kiểu thật có thể khác nhau lúc runtime; đổi lại tốn chi phí box (có thể cấp phát heap nếu giá trị lớn), dynamic dispatch, và các API dính tới associatedtype/Self bị hạn chế. Thực tế nên mặc định dùng some/generic, chỉ dùng any khi cần tập hợp dị chủng như [any Shape], hoặc khi kiểu cụ thể chỉ được chọn lúc runtime như factory trả về mock hay bản thật.

  2. Array, Dictionary của Swift là value type nhưng gán qua lại rất rẻ nhờ copy-on-write. Nếu bạn tự viết một struct bọc storage là class (vd. một buffer lớn), làm sao để nó cũng có copy-on-write?

    Xem đáp án mẫu
    Copy-on-write nghĩa là khi gán sang biến khác, hai bản chỉ chia sẻ chung một buffer; việc copy thật chỉ xảy ra khi một bản muốn ghi trong lúc buffer đang được chia sẻ. Struct tự viết chứa class thì mặc định không có COW: copy struct chỉ copy tham chiếu, sửa qua bản này thì bản kia cũng đổi theo, phá vỡ value semantics. Cách làm: trước mọi thao tác ghi, gọi isKnownUniquelyReferenced(&storage); nếu storage đang được chia sẻ thì clone ra bản mới rồi mới ghi. Lưu ý COW không tự có cho mọi struct, chỉ có ở các collection chuẩn và những kiểu tự cài đặt như trên; struct thường nhiều field thì về nguyên tắc vẫn được copy toàn bộ khi gán.
    final class Storage {
  var values: [Int]
  init(_ values: [Int]) { self.values = values }
}

struct Buffer {
  private var storage = Storage([])

  mutating func append(_ x: Int) {
    if !isKnownUniquelyReferenced(&storage) {
      storage = Storage(storage.values) // đang bị chia sẻ: clone trước khi ghi
    }
    storage.values.append(x)
  }
}

  3. Bạn muốn các property như volume, progress luôn bị giới hạn trong một khoảng giá trị mà không phải lặp code ở từng setter. Viết property wrapper thế nào, và projectedValue (truy cập qua $) dùng để làm gì?

    Xem đáp án mẫu
    Property wrapper là type đánh dấu @propertyWrapper có wrappedValue; khi viết @Clamped(0...1) var volume = 0.5, compiler sinh ra backing storage _volume kiểu Clamped<Double> và chuyển mọi lần đọc/ghi volume sang _volume.wrappedValue, nên logic giới hạn nằm ở một chỗ. projectedValue là giá trị phụ truy cập qua $volume, dùng để lộ thêm thông tin hoặc API, giống @State có $ trả về Binding, @Published có $ trả về publisher. Hạn chế cần biết: không khai báo được property wrapper trong protocol requirement, và vì logic chạy trong getter/setter ở mỗi lần truy cập nên đừng đặt việc nặng vào đó.
    @propertyWrapper
struct Clamped<Value: Comparable> {
  private var value: Value
  let range: ClosedRange<Value>
  init(wrappedValue: Value, _ range: ClosedRange<Value>) {
    self.range = range
    self.value = min(max(wrappedValue, range.lowerBound), range.upperBound)
  }
  var wrappedValue: Value {
    get { value }
    set { value = min(max(newValue, range.lowerBound), range.upperBound) }
  }
  var projectedValue: ClosedRange<Value> { range } // đọc qua $volume
}
// Dùng: @Clamped(0...1) var volume = 0.5  -> gán volume = 2 sẽ thành 1

  1. ViewModel lắng nghe một AsyncStream bằng Task { for await event in stream { ... } }. Màn hình đã đóng nhưng deinit của ViewModel không bao giờ chạy. Vì sao, và thêm [weak self] có đủ không?

    Xem đáp án mẫu
    Closure của Task giữ self mạnh suốt thời gian task chạy, mà vòng for await trên một stream không kết thúc thì task chạy mãi, nên ViewModel không bao giờ được giải phóng. Chỉ thêm [weak self] là chưa đủ nếu ngay đầu task viết guard let self rồi mới vào vòng lặp, vì khi đó self lại bị giữ mạnh trong suốt vòng lặp. Cách đúng là giữ handle của task và cancel() khi màn hình biến mất (từ onDisappear hoặc coordinator), hoặc chỉ unwrap self bên trong từng vòng lặp. Trong SwiftUI, modifier .task tự cancel khi view biến mất nên là cách gọn nhất. Lưu ý không thể dựa vào deinit để cancel task, vì deinit chính là thứ đang không chạy.
    @MainActor
final class ChatViewModel {
  private var listenTask: Task<Void, Never>?

  func start(stream: AsyncStream<Message>) {
    listenTask = Task { [weak self] in
      for await message in stream {
        guard let self else { return } // chỉ giữ self mạnh trong từng vòng
        self.handle(message)
      }
    }
  }

  func stop() { listenTask?.cancel() }
}

  1. Màn Home cần gọi 3 API độc lập (profile, banner, khuyến mãi), còn màn danh sách phải tải thumbnail cho N sản phẩm. Bạn dùng async let hay TaskGroup cho từng trường hợp? Nếu một request throw thì các request còn lại ra sao?

    Xem đáp án mẫu
    async let hợp với số task cố định, biết trước lúc viết code, mỗi task có thể trả về kiểu khác nhau; withThrowingTaskGroup dành cho số task động như N thumbnail, kết quả cùng kiểu và được nhận về theo thứ tự hoàn thành. Cả hai đều là structured concurrency: child task không sống lâu hơn scope tạo ra nó, task cha bị cancel thì child cũng bị cancel. Khi lỗi thoát khỏi scope, các child còn đang chạy bị cancel và được chờ kết thúc rồi hàm mới throw ra ngoài. Bẫy hay gặp: với async let, lỗi chỉ lộ ra khi await tới đúng biến đó nên thứ tự await quyết định phát hiện lỗi sớm hay muộn; còn viết let a = try await f() liên tiếp thì các request chạy tuần tự chứ không song song.
    func loadHome() async throws -> HomeData {
  async let profile = api.fetchProfile()
  async let banners = api.fetchBanners()
  async let deals = api.fetchDeals()
  // Ba request chạy song song, chờ đủ cả ba
  return try await HomeData(profile: profile, banners: banners, deals: deals)
}
func loadThumbnails(ids: [String]) async throws -> [String: Data] {
  try await withThrowingTaskGroup(of: (String, Data).self) { group in
    for id in ids { group.addTask { try await (id, api.thumbnail(id)) } }
    var result: [String: Data] = [:]
    for try await (id, data) in group { result[id] = data }
    return result
  }
}

  2. Bạn đưa logic refresh token vào một actor để tránh race condition, nhưng log vẫn cho thấy API refresh bị gọi 2–3 lần khi nhiều request cùng gặp 401. Vì sao actor không chặn được, và sửa thế nào?

    Xem đáp án mẫu
    Actor chỉ đảm bảo tại một thời điểm có tối đa một đoạn code chạy trên nó, nhưng actor là reentrant: tại mỗi await, actor được phép xử lý lời gọi khác. Request thứ nhất thấy token hết hạn và await refresh; trong lúc chờ, request thứ hai vào actor, cũng thấy token hết hạn và gọi refresh lần nữa. Cách sửa phổ biến là lưu Task refresh đang chạy vào một property, các lời gọi đến sau chỉ await chính task đó. Nguyên tắc chung khi viết actor: sau mỗi await đừng giả định state còn như cũ, hãy kiểm tra lại, và gom phần đọc rồi sửa state vào đoạn đồng bộ không có await.
    actor TokenProvider {
  private var token: Token?
  private var refreshTask: Task<Token, Error>?

  func validToken() async throws -> Token {
    if let token, !token.isExpired { return token }
    if let refreshTask { return try await refreshTask.value } // đã có người refresh
    let task = Task { try await authAPI.refresh() }
    refreshTask = task
    defer { refreshTask = nil }
    let newToken = try await task.value
    token = newToken
    return newToken
  }
}

  3. ViewModel gán @Published từ completion handler của URLSession và Xcode báo tím "Publishing changes from background threads is not allowed". Với Swift Concurrency, bạn sửa thế nào cho triệt để thay vì rải DispatchQueue.main.async khắp nơi?

    Xem đáp án mẫu
    Đánh dấu cả ViewModel là @MainActor: mọi property và method của nó được cô lập trên main actor, compiler buộc code từ ngữ cảnh khác phải await khi truy cập, nên không còn chuyện quên chuyển về main thread. Đồng thời đổi sang API async như URLSession.data(for:): khi await, hàm chỉ suspend chứ không block main thread, request được xử lý ở nơi khác và khi xong thì quay lại main actor để gán state. Còn DispatchQueue.main.async phải nhớ đặt ở từng chỗ và compiler không kiểm tra giúp. Bẫy cần biết: @MainActor không làm việc nặng nhẹ đi, nếu parse JSON lớn hay xử lý ảnh đồng bộ ngay trong method của ViewModel thì main thread vẫn bị chiếm, phần đó nên tách sang type hoặc actor khác.

  4. Ô search gọi API mỗi khi user gõ, và kết quả của từ khoá cũ đôi khi về sau, đè lên kết quả mới. Bạn huỷ request cũ thế nào? Gọi task.cancel() thì code trong task có dừng ngay không?

    Xem đáp án mẫu
    Cancellation trong Swift Concurrency là cooperative: cancel() chỉ đánh dấu task đã bị huỷ, code bên trong phải tự kiểm tra bằng Task.isCancelled, try Task.checkCancellation(), hoặc gọi các API có hỗ trợ huỷ như Task.sleep và các hàm async của URLSession (chúng throw khi task bị cancel). Cách làm: giữ tham chiếu Task hiện tại, cancel nó trước khi tạo task mới, dùng Task.sleep để debounce. Quan trọng là kiểm tra lại Task.isCancelled sau khi await xong và trước khi gán kết quả, nếu không response của từ khoá cũ vẫn có thể ghi đè. Trong SwiftUI có thể dùng .task(id: query), SwiftUI tự cancel task cũ mỗi khi query đổi.
    // Trong ViewModel @MainActor
private var searchTask: Task<Void, Never>?

func queryChanged(_ text: String) {
  searchTask?.cancel()
  searchTask = Task {
    try? await Task.sleep(for: .milliseconds(300)) // debounce
    guard !Task.isCancelled else { return }
    let result = try? await api.search(text)
    guard !Task.isCancelled, let result else { return } // bỏ kết quả cũ
    items = result
  }
}

  5. Team còn dùng một SDK cũ chỉ có API dạng callback. Bạn bọc nó thành hàm async thế nào, và bẫy nào có thể khiến app crash hoặc treo?

    Xem đáp án mẫu
    Dùng withCheckedThrowingContinuation: bên trong gọi API cũ, khi callback trả về thì resume(returning:) hoặc resume(throwing:) (có sẵn Result thì dùng resume(with:)). Luật bắt buộc là resume đúng một lần trên mọi nhánh: resume hai lần sẽ crash, quên resume thì task treo mãi và bản checked chỉ log cảnh báo continuation bị leak. withUnsafeContinuation bỏ các kiểm tra này để nhanh hơn một chút, chỉ nên dùng khi đã chắc chắn code đúng. Nếu callback được gọi nhiều lần (delegate vị trí, tiến trình download) thì continuation không phù hợp, hãy dùng AsyncStream với continuation.yield và onTermination để dọn dẹp.
    func loadProfile(id: String) async throws -> Profile {
  try await withCheckedThrowingContinuation { continuation in
    legacySDK.fetchProfile(id: id) { profile, error in
      if let profile {
        continuation.resume(returning: profile)
      } else {
        // Nhánh nào cũng phải resume đúng một lần
        continuation.resume(throwing: error ?? SDKError.unknown)
      }
    }
  }
}

  6. Bật Swift 6 language mode, project báo hàng loạt lỗi liên quan tới Sendable khi truyền dữ liệu giữa các actor và task. Sendable nghĩa là gì, và bạn xử lý các lỗi này theo hướng nào?

    Xem đáp án mẫu
    Sendable đánh dấu kiểu có thể chuyển qua ranh giới concurrency (giữa các actor, vào task khác) mà không gây data race. Struct/enum không public có mọi thành phần Sendable thì được suy ra tự động, actor luôn Sendable, còn class chỉ hợp lệ khi là final và chỉ chứa let có kiểu Sendable, hoặc được cô lập vào global actor như @MainActor. Hướng xử lý: ưu tiên model là struct bất biến, đưa state mutable dùng chung vào actor, đánh dấu @MainActor cho type thuộc UI. @unchecked Sendable chỉ dùng khi tự bảo vệ bằng lock và chấp nhận tự chịu trách nhiệm; @preconcurrency import giúp tạm giảm lỗi từ module bên thứ ba chưa cập nhật. Nên migrate từng module: bật strict concurrency mức complete ở Swift 5 mode để thấy warning trước, sửa xong mới chuyển sang Swift 6 mode.

  7. Codebase đang dùng Combine cho màn search (debounce, removeDuplicates, flatMap). Team muốn chuyển sang async/await. Combine và AsyncSequence khác nhau ở điểm nào, phần nào nên giữ Combine?

    Xem đáp án mẫu
    Combine là push-based: publisher đẩy giá trị cho subscriber, có sẵn nhiều operator theo thời gian như debounce, throttle, combineLatest, subscription sống theo AnyCancellable. AsyncSequence là pull-based: consumer dùng for await lấy từng giá trị, tự gắn với cancellation của task và với actor, code đọc tuần tự dễ hiểu; nhưng thư viện chuẩn chưa có operator theo thời gian, cần thêm package swift-async-algorithms. Có thể chuyển dần vì publisher nào cũng có .values để dùng như AsyncSequence. Pipeline phản ứng nhiều nguồn đang chạy ổn thì cứ giữ Combine, còn gọi API một lần thì async/await gọn hơn. Riêng màn search, flatMap không huỷ request của từ khoá cũ nên kết quả cũ có thể về sau và đè kết quả mới; dùng map + switchToLatest để chỉ giữ request mới nhất.
    init(api: SearchAPI) {
  $query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .removeDuplicates()
    .map { text in api.search(text) } // AnyPublisher<[Item], Never>
    .switchToLatest()                  // bỏ kết quả của từ khoá cũ
    .receive(on: DispatchQueue.main)
    .assign(to: &$items)               // không giữ self, tự huỷ theo object
}

  1. Bạn đổi constant của một constraint rồi gọi UIView.animate, nhưng view nhảy ngay sang vị trí mới mà không có animation. Giải thích layout cycle và cách sửa; setNeedsLayout khác layoutIfNeeded thế nào?

    Xem đáp án mẫu
    Đổi constraint không cập nhật frame ngay: UIKit chỉ đánh dấu view cần layout lại, tới lần cập nhật kế tiếp của run loop mới chạy layoutSubviews từ trên xuống. setNeedsLayout() chỉ đánh dấu rồi trả về ngay, layout xảy ra sau; layoutIfNeeded() ép layout chạy đồng bộ ngay lập tức nếu đang có đánh dấu. Vì vậy muốn animate thì đổi constant trước, rồi trong block animation gọi layoutIfNeeded() trên view cha chung (thường là view của VC) để frame mới được tính bên trong animation. Nên gọi layoutIfNeeded() một lần trước khi đổi constraint để hoàn tất thay đổi đang chờ, tránh chúng bị cuốn vào animation. Cùng lý do đó, frame đọc trong viewDidLoad thường chưa đúng, hãy dùng viewDidLayoutSubviews.
    view.layoutIfNeeded() // hoàn tất layout đang chờ
bottomConstraint.constant = keyboardHeight
UIView.animate(withDuration: 0.25) {
  self.view.layoutIfNeeded() // frame mới được tính trong block animation
}

  2. Nút "đóng" được đặt lệch một nửa ra ngoài bounds của view cha (cha đã tắt clipsToBounds), phần lòi ra ngoài bấm không ăn. Vì sao, và hit-testing với responder chain hoạt động thế nào?

    Xem đáp án mẫu
    Khi chạm, UIKit gọi hitTest(_:with:) từ window đi xuống: mỗi view kiểm tra point(inside:with:), nếu điểm nằm ngoài bounds của mình thì bỏ qua toàn bộ cây con, nên phần subview lòi ra ngoài cha không bao giờ nhận touch dù vẫn được vẽ. View cũng bị bỏ qua khi isHidden, alpha dưới 0.01 hoặc isUserInteractionEnabled = false. Cách sửa là override point(inside:with:) của view cha để tính thêm vùng của nút, hoặc đơn giản hơn là đổi layout cho nút nằm gọn trong cha. Sau khi tìm được view nhận touch, event được xử lý theo responder chain: view, các superview, view controller, window rồi UIApplication, cho tới khi có responder xử lý; action gửi tới target nil cũng được tìm dọc chuỗi này.

  1. Form nhập liệu bị mất hết text đã gõ mỗi khi bật/tắt trạng thái loading, dù text nằm trong @State của view con. Nguyên nhân liên quan tới identity của view là gì, và sửa thế nào?

    Xem đáp án mẫu
    SwiftUI gắn @State với identity của view chứ không gắn với struct view. Identity gồm structural identity (vị trí trong cây, mỗi nhánh if/else là một vị trí khác nhau) và explicit identity (id trong ForEach, modifier .id(...)). Nếu viết if isLoading { FormView().disabled(true) } else { FormView() } thì khi đổi nhánh, SwiftUI coi đó là hai view khác nhau, huỷ view cũ cùng state của nó rồi tạo view mới. Cách sửa là giữ một view duy nhất và thay đổi bằng modifier (.disabled(isLoading), .opacity, .overlay) thay vì rẽ nhánh. Ngược lại, khi muốn chủ động reset state (đổi user, đổi sản phẩm), gắn .id(product.id) để SwiftUI tạo view mới; đừng dùng .id(UUID()) vì view sẽ bị tạo lại ở mỗi lần render.
    // Sai: hai nhánh là hai identity khác nhau, state của FormView bị reset
if isLoading {
  FormView().disabled(true)
} else {
  FormView()
}

// Đúng: một identity, chỉ đổi modifier
FormView()
  .disabled(isLoading)
  .overlay { if isLoading { ProgressView() } }

  2. Team chuyển ViewModel từ ObservableObject + @Published sang macro @Observable. Cơ chế cập nhật view khác gì, và @StateObject, @ObservedObject, @EnvironmentObject được thay bằng gì?

    Xem đáp án mẫu

Mọi rank →

  1. ViewController của bạn tự push màn tiếp theo và biết quá nhiều về flow (login xong đi đâu, mở từ notification thì vào màn nào). Coordinator giải quyết việc này thế nào, và có bẫy gì về bộ nhớ?

    Xem đáp án mẫu
    Coordinator tách trách nhiệm điều hướng ra khỏi ViewController: VC chỉ báo sự kiện (user đã login, đã chọn sản phẩm) qua delegate hoặc closure, còn coordinator quyết định tạo màn nào, inject dependency gì và push hay present. Nhờ vậy VC tái sử dụng được ở nhiều flow, deep link chỉ cần gọi vào coordinator, và logic flow test được mà không cần dựng UI. Bẫy bộ nhớ: coordinator không ai giữ sẽ bị giải phóng ngay sau start(), nên coordinator cha phải giữ con trong mảng childCoordinators và xoá khi flow kết thúc; ngược lại VC chỉ nên giữ coordinator bằng weak để không tạo retain cycle. Chỗ hay sót là khi user bấm nút Back hệ thống hoặc vuốt để quay lại, cần bắt qua UINavigationControllerDelegate để dọn child coordinator.

  2. Mọi service trong app đều được truy cập qua singleton kiểu APIClient.shared, giờ viết unit test cho ViewModel thì không mock được. Bạn refactor theo hướng dependency injection thế nào?

    Xem đáp án mẫu
    Định nghĩa protocol mô tả đúng những gì ViewModel cần (vd. ProductFetching có fetchProducts()), cho APIClient conform, rồi truyền vào ViewModel qua initializer. Khi test chỉ cần truyền một stub hoặc fake conform protocol, không đụng tới mạng. Để refactor dần mà không phải sửa mọi chỗ gọi cùng lúc, có thể tạm để default value service: any ProductFetching = APIClient.shared trong init. Việc lắp ráp dependency nên dồn về một chỗ (composition root như App, SceneDelegate hoặc coordinator) thay vì mỗi class tự lấy singleton. Service locator hay DI container (như Swinject) tiện cho app lớn nhưng che giấu dependency, lỗi thiếu đăng ký chỉ lộ ra lúc runtime; còn constructor injection thì compiler kiểm tra giúp.

    Xem đáp án mẫu

Để feature gọi nhau, tách phần interface (protocol như ProductDetailBuilding hoặc enum route) ra một module nhẹ dùng chung, implementation nằm trong feature, rồi app target inject implementation lúc khởi tạo. Nhờ vậy dependency graph một chiều, không vòng, sửa một feature chỉ build lại module đó và những module phụ thuộc nó, mỗi feature có thể có demo app và test riêng.   1. Bạn import vài nghìn record từ API vào Core Data và UI bị giật. Chuyển sang background context thế nào cho đúng, và làm sao để viewContext thấy dữ liệu mới?

    Xem đáp án mẫu
    Dùng newBackgroundContext() hoặc performBackgroundTask và làm mọi thao tác bên trong perform, vì mỗi NSManagedObjectContext gắn với queue riêng và không thread-safe; viewContext chỉ dùng trên main thread cho UI. Đặt viewContext.automaticallyMergesChangesFromParent = true để sau khi background context save(), thay đổi được merge sang context của UI. Với lượng rất lớn, NSBatchInsertRequest nhanh hơn nhiều vì ghi thẳng xuống store, nhưng nó bỏ qua context nên phải tự merge (qua persistent history tracking hoặc mergeChanges(fromRemoteContextSave:into:)). Không truyền NSManagedObject giữa các context, hãy truyền objectID. Đặt mergePolicy phù hợp để tránh lỗi conflict khi hai context cùng sửa một record.
    container.viewContext.automaticallyMergesChangesFromParent = true

func importProducts(_ dtos: [ProductDTO]) async throws {
  let context = container.newBackgroundContext()
  context.mergePolicy = NSMergePolicy.mergeByPropertyObjectTrump
  try await context.perform {
    for dto in dtos {
      let product = Product(context: context)
      product.id = dto.id
      product.name = dto.name
    }
    try context.save() // viewContext tự merge thay đổi
  }
}

  2. Dự án mới target iOS 17 trở lên, team phân vân giữa SwiftData và Core Data. Bạn cân nhắc những gì trước khi chọn?

    Xem đáp án mẫu
    SwiftData xây trên nền Core Data nhưng API thuần Swift: model khai báo bằng macro @Model, quản lý qua ModelContainer/ModelContext, SwiftUI đọc dữ liệu bằng @Query tự cập nhật, ít boilerplate hơn hẳn. Đổi lại nó còn mới: một số thứ của Core Data như NSFetchedResultsController cho UIKit, batch insert/update hay tuỳ biến sâu chưa có tương đương đầy đủ, và hành vi có thay đổi giữa các bản iOS nên cần test kỹ trên từng phiên bản hỗ trợ. Về concurrency, ModelContext và object @Model không Sendable; việc nặng ở background dùng actor @ModelActor với context riêng, giữa các context chỉ truyền PersistentIdentifier. App SwiftUI là chính, schema vừa phải thì SwiftData hợp lý; app UIKit lớn, cần kiểm soát hiệu năng chặt hoặc đã đầu tư Core Data thì nên giữ Core Data, và hai bên có thể dùng chung một store để chuyển dần.

  3. Bạn cần cache ảnh avatar trong app. NSCache, Dictionary và URLCache khác nhau thế nào, và bạn kết hợp chúng ra sao?

    Xem đáp án mẫu
    NSCache là cache trong RAM, thread-safe, tự giải phóng phần tử khi hệ thống thiếu bộ nhớ, đặt được countLimit/totalCostLimit (chỉ là giới hạn mềm) và key phải là object như NSString/NSURL. Dictionary thì không tự dọn khi thiếu bộ nhớ và không an toàn khi đọc ghi từ nhiều thread. URLCache cache response HTTP trên RAM và disk theo header của server (Cache-Control, ETag…), nên chỉ hiệu quả khi server trả header phù hợp và response không quá lớn so với dung lượng cache. Kiến trúc hay dùng là hai tầng: NSCache giữ UIImage đã decode để hiển thị tức thì, tầng disk (URLCache hoặc tự ghi file vào thư mục Caches) giữ dữ liệu qua các lần mở app. Ngoài ra nên gộp các request trùng URL đang chạy để không tải một ảnh nhiều lần.

    Xem đáp án mẫu

  2. Swift Testing (@Test, #expect) khác XCTest ở những điểm nào? Dự án đang có vài trăm test XCTest thì có nên chuyển hết không?

    Xem đáp án mẫu
    Swift Testing dùng macro thay cho quy ước đặt tên: hàm gắn @Test là một test, không cần kế thừa XCTestCase, suite có thể là struct và mỗi test chạy trên một instance mới. #expect(a == b) thay cho cả họ XCTAssert... và khi fail hiển thị rõ giá trị từng vế; #require thì dừng test ngay khi điều kiện sai, hay dùng để unwrap optional. Có sẵn test tham số hoá @Test(arguments:), trait như .tags, .disabled, và mặc định chạy song song nên test dùng chung state toàn cục dễ flaky. Hai framework chạy chung được trong cùng target, nên không cần chuyển hết: viết test mới bằng Swift Testing, chuyển dần khi động vào test cũ. UI test và performance test (XCUIApplication, measure) hiện vẫn viết bằng XCTest.

struct PriceFormatterTests {

    #expect(PriceFormatter.vnd(amount) == expected)
  }

  @Test func parseValidPrice() throws {
    let value = try #require(PriceFormatter.parse("1.000 ₫")) // nil thì dừng test
    #expect(value == 1000)
  }
}
