  1. Vì sao compiler bắt thêm @escaping khi bạn lưu closure tham số vào property hoặc gọi nó trong completion của request mạng? Closure non-escaping có lợi gì?

    Xem đáp án mẫu
    Mặc định closure tham số là non-escaping: compiler đảm bảo nó chỉ được gọi trong lúc hàm đang chạy và không bị giữ lại sau khi hàm return. Khi closure được lưu vào property, đưa vào DispatchQueue.main.async hay completion của URLSession, nó sống lâu hơn hàm nên phải đánh dấu @escaping. Closure escaping có thể giữ self lâu hơn dự kiến và gây retain cycle, vì vậy trong class Swift bắt viết rõ self. để bạn ý thức được mình đang capture gì. Closure non-escaping như tham số của map, filter, sorted(by:) an toàn hơn: không cần [weak self] và compiler tối ưu được tốt hơn.
    final class ProfileService {
  var onUpdate: ((User) -> Void)?

  // Lưu closure lại để gọi sau -> bắt buộc @escaping
  func observe(_ handler: @escaping (User) -> Void) {
    onUpdate = handler
  }

  // Chỉ dùng trong lúc hàm chạy -> non-escaping là đủ
  func active(_ users: [User], where rule: (User) -> Bool) -> [User] {
    users.filter(rule)
  }
}

    Xem đáp án mẫu
    Khai báo protocol Reusable có static var reuseIdentifier, rồi dùng protocol extension cung cấp sẵn giá trị mặc định là tên class; cell chỉ cần conform là có identifier, không phải gõ chuỗi tay ở cả chỗ register lẫn chỗ dequeue. Đây là ví dụ điển hình của protocol extension (default implementation) kết hợp generic constraint để bỏ code lặp mà vẫn giữ type-safe.

    guard let cell = dequeueReusableCell(withIdentifier: T.reuseIdentifier, for: indexPath) as? T else {
      fatalError("\(T.reuseIdentifier) đang register sai class")
    }
    return cell
  }

  4. Mảng players chứa struct Player; bạn viết for var p in players { p.score += 1 } nhưng điểm trong mảng không đổi, trong khi đổi Player thành class thì lại đổi. Giải thích và sửa cho trường hợp struct thế nào?

    Xem đáp án mẫu
    Struct là value type: khi vòng lặp lấy từng phần tử ra, p là một bản sao độc lập, nên p.score += 1 chỉ sửa bản sao rồi bị bỏ đi và mảng gốc không đổi. Nếu viết for p in players thì p là hằng, compiler báo lỗi vì không gán được vào property. Với class, phần tử của mảng là tham chiếu tới object, p trỏ cùng object nên sửa là thấy ngay ở mọi nơi đang giữ nó, kể cả mảng khác bạn vừa gán let backup = players, vì chép mảng lúc này chỉ chép các tham chiếu. Với struct, hãy sửa qua index như players[i].score += 1, hoặc dựng mảng mới bằng map. Chọn struct khi mỗi nơi cần bản dữ liệu riêng, chọn class khi cần một object chung được nhiều nơi thay đổi.
    struct Player {
  var name: String
  var score = 0
}

var players = [Player(name: "An"), Player(name: "Bình")]

for var p in players {
  p.score += 1              // chỉ sửa bản sao
  print(p.score)            // 1
}
print(players.map(\.score)) // [0, 0]

for i in players.indices { players[i].score += 1 }
print(players.map(\.score)) // [1, 1]

  5. Model có enum OrderStatus: String, Codable với ba case pending, shipping, done. Backend thêm trạng thái "refunded" và bản app cũ không hiển thị được cả danh sách đơn hàng. Vì sao, và bạn làm enum chịu được giá trị lạ thế nào?

    Xem đáp án mẫu
    Với enum có raw value, Codable tự sinh chỉ chấp nhận đúng các case đã khai báo; gặp chuỗi lạ nó ném DecodingError.dataCorrupted, và vì lỗi nằm trong một phần tử nên cả mảng đơn hàng decode thất bại. Cách sửa là thêm case unknown rồi tự viết init(from:): đọc chuỗi bằng singleValueContainer và dùng OrderStatus(rawValue: raw) ?? .unknown, để giá trị lạ rơi vào unknown thay vì làm hỏng cả response. Ở UI, switch cho unknown một hiển thị trung tính chứ không fatalError. Cùng tư tưởng đó với enum của Apple: thêm @unknown default vào switch để khi SDK mới bổ sung case, compiler cảnh báo chỗ chưa xử lý, còn app cũ chạy trên iOS mới vẫn có nhánh dự phòng.
    enum OrderStatus: String, Codable {
  case pending, shipping, done
  case unknown

  init(from decoder: Decoder) throws {
    let raw = try decoder.singleValueContainer().decode(String.self)
    self = OrderStatus(rawValue: raw) ?? .unknown // "refunded" -> .unknown
  }
}

  6. Bạn dùng struct Product làm phần tử của Set và làm key của Dictionary, compiler báo Type 'Product' does not conform to protocol 'Hashable'. Khi nào compiler tự sinh Equatable/Hashable, khi nào phải tự viết, và Comparable, Identifiable liên quan thế nào?

    Xem đáp án mẫu
    Với struct và enum, chỉ cần khai báo : Hashable (trong định nghĩa kiểu hoặc extension cùng file) là compiler tự sinh == và hash(into:), miễn mọi stored property hay associated value đều đã Hashable; lỗi trên nghĩa là chưa khai báo, hoặc có một property không conform (như [String: Any]). Class thì không được sinh tự động. Phải tự viết khi 'cùng một đối tượng' chỉ xét theo một phần dữ liệu, ví dụ id: để compiler sinh theo mọi field thì cùng sản phẩm mà đổi giá đã thành hai phần tử khác nhau trong Set. Luật cần nhớ: hai giá trị == thì phải có cùng hash, nên đã so theo id thì chỉ băm id, vi phạm sẽ làm Set/Dictionary tìm sai. Hashable cũng là điều kiện của item trong UICollectionViewDiffableDataSource: băm theo mọi field thì sửa một field là item bị coi như item mới (xoá rồi chèn, mất animation và vị trí cuộn), nên dùng id làm item identifier và reconfigureItems khi nội dung đổi. Identifiable chỉ cần id: Hashable cho ForEach/List, không kéo theo Equatable. Comparable chỉ cần tự viết <, các toán tử còn lại có sẵn; enum không có raw value được sinh < theo thứ tự khai báo case.
    struct Product: Hashable, Identifiable {
  let id: Int
  var name: String
  var price: Int

  // So sánh và băm theo id: đổi giá vẫn là cùng một sản phẩm
  static func == (lhs: Product, rhs: Product) -> Bool { lhs.id == rhs.id }
  func hash(into hasher: inout Hasher) { hasher.combine(id) }
}

enum Priority: Comparable { case low, medium, high } // compiler sinh `<` theo thứ tự case

var cart: Set<Product> = [Product(id: 1, name: "Áo", price: 200)]
cart.insert(Product(id: 1, name: "Áo", price: 250))  // bị bỏ qua vì đã có id 1
print(cart.count, Priority.low < .high)              // 1 true

  7. Review code thấy orders.map { $0.items }.reduce([], +), names.map { Int($0) } rồi tự lọc nil, và một chuỗi filter/map/sorted chạy ngay trong body cho cả nghìn phần tử. map, compactMap, flatMap, filter, reduce, sorted khác nhau thế nào, và lazy có tác dụng gì?

    Xem đáp án mẫu
    map biến đổi từng phần tử và giữ nguyên số lượng; filter giữ phần tử thoả điều kiện; compactMap biến đổi rồi bỏ kết quả nil, thay cho map + lọc + force unwrap; flatMap biến mỗi phần tử thành một sequence rồi làm phẳng ([[Item]] thành [Item]), gọn hơn map { $0.items }.reduce([], +) và tránh copy mảng ở từng vòng. Bẫy lịch sử: trước Swift 4.1, flatMap với closure trả Optional cũng bỏ nil, giờ phải dùng compactMap; flatMap trên Optional vẫn còn, dùng để tránh Optional<Optional>. reduce(_:_:) gom về một giá trị; khi gom vào Array hay Dictionary nên dùng reduce(into:) để sửa tại chỗ, thay vì tạo bản copy mới mỗi vòng (O(n²)). sorted(by:) trả mảng mới, còn sort(by:) sắp xếp tại chỗ trên var. lazy trì hoãn tính toán: array.lazy.map { }.filter { }.first xử lý từng phần tử theo nhu cầu, không sinh mảng trung gian và dừng ngay khi có kết quả; đổi lại closure chạy lại mỗi lần duyệt, nên chỉ dùng khi chuỗi dài hoặc chỉ cần vài phần tử. Lọc/sắp xếp nặng thì tính một lần ở ViewModel, đừng để trong body hay cellForRowAt vì chúng chạy lại liên tục.
    struct Order { let items: [String] }
let orders = [Order(items: ["Áo", "Mũ"]), Order(items: ["Giày", "Áo"])]

let all = orders.flatMap(\.items)                     // ["Áo", "Mũ", "Giày", "Áo"]
let numbers = ["1", "x", "3"].compactMap { Int($0) }  // [1, 3], bỏ "x"

// reduce(into:) sửa dictionary tại chỗ, không copy mỗi vòng
let count = all.reduce(into: [String: Int]()) { $0[$1, default: 0] += 1 }
print(count["Áo"] ?? 0)                               // 2

// lazy: dừng ngay khi tìm thấy, không tạo mảng một triệu phần tử
let firstBig = (1...1_000_000).lazy.map { $0 * $0 }.first { $0 > 1_000 } // 1024

  1. Bạn pop màn hình chi tiết ra nhưng deinit của DetailViewController không bao giờ chạy. Trong code có đoạn gán callback cho ViewModel như dưới. Nguyên nhân và cách sửa?

    Xem đáp án mẫu
    VC giữ strong viewModel, viewModel giữ strong closure onUpdate, còn closure lại capture strong self là chính VC, tạo thành retain cycle nên reference count không bao giờ về 0 và cả VC lẫn ViewModel bị leak. Sửa bằng capture list [weak self] rồi guard let self else { return } trong closure; khi VC bị pop, không còn ai giữ VC nên nó được giải phóng và chu trình bị phá. Cách kiểm tra nhanh là đặt print hoặc breakpoint trong deinit, hoặc mở Memory Graph trong Xcode để xem object nào còn sống sau khi rời màn hình.
    final class DetailViewController: UIViewController {
  let viewModel = DetailViewModel()

  override func viewDidLoad() {
    super.viewDidLoad()
    // Gây leak: viewModel.onUpdate = { state in self.render(state) }
    viewModel.onUpdate = { [weak self] state in
      guard let self else { return }
      self.render(state)
    }
  }

  deinit { print("DetailViewController deinit") }

  2. Vì sao property delegate thường được khai báo weak? Viết weak var delegate: PickerDelegate? mà compiler báo lỗi thì sửa thế nào?

    Xem đáp án mẫu
    Quan hệ hay gặp là VC (owner) giữ strong một view hay object con, còn object con gọi ngược lại VC qua delegate; nếu delegate cũng strong thì hai bên giữ nhau và không bao giờ được giải phóng. Vì vậy delegate để weak, và nó phải là optional vì ARC tự gán nil khi object bị huỷ. weak chỉ áp dụng cho reference type, nên protocol phải được giới hạn cho class bằng protocol PickerDelegate: AnyObject; nếu không, compiler báo lỗi vì struct hay enum cũng có thể conform. UIKit cũng làm như vậy: delegate và dataSource của UITableView đều là weak.

  3. weak và unowned khác nhau thế nào? Có phải closure nào dùng self cũng phải viết [weak self] không?

    Xem đáp án mẫu
    Cả hai đều không làm tăng strong reference count. weak luôn là optional và tự thành nil khi object bị giải phóng nên an toàn; unowned giả định object vẫn còn sống, truy cập sau khi object đã bị huỷ sẽ crash, nên chỉ dùng khi chắc chắn object được tham chiếu sống ít nhất lâu bằng bên giữ nó. Không phải closure nào cũng cần [weak self]: closure non-escaping như của map, hay closure chạy một lần rồi được giải phóng như UIView.animate, DispatchQueue.main.async chỉ giữ self tạm thời, không tạo chu trình. Cần weak khi self trực tiếp hoặc gián tiếp đang giữ closure đó, hoặc khi không muốn kéo dài vòng đời màn hình chỉ để chờ một request mạng chậm.

  4. Màn hình nhập OTP đếm ngược bằng Timer.scheduledTimer(timeInterval: 1, target: self, selector: #selector(tick), userInfo: nil, repeats: true). Thoát màn hình rồi mà tick vẫn chạy và deinit không bao giờ được gọi. Vì sao, và sửa thế nào?

    Xem đáp án mẫu
    Timer kiểu target-selector giữ strong reference tới target cho tới khi bị invalidate(), còn run loop thì giữ timer đang chạy. VC vì thế được timer giữ sống mãi: tick chạy tiếp, deinit không chạy, nên đặt invalidate() trong deinit là vô ích. Ngay cả gán timer = nil cũng không dừng được timer vì run loop vẫn giữ nó. Cách đúng là chủ động invalidate() khi rời màn hình, ví dụ trong viewWillDisappear. Nên dùng API block scheduledTimer(withTimeInterval:repeats:block:) kèm [weak self] để timer không giữ VC, và tự invalidate() khi self đã nil. Timer lặp quên invalidate là nguồn leak rất hay gặp ở countdown, polling hay banner tự chuyển.
    final class OTPViewController: UIViewController {
  private var timer: Timer?
  private var remaining = 60

  override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)
    timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] timer in
      guard let self else { timer.invalidate(); return }
      self.remaining -= 1
      if self.remaining <= 0 { timer.invalidate() }
    }
  }

  override func viewWillDisappear(_ animated: Bool) {
    super.viewWillDisappear(animated)
    timer?.invalidate()   // chỉ gán timer = nil thì timer vẫn chạy
    timer = nil
  }
}

  1. Gọi API bằng URLSession rồi gán dữ liệu và tableView.reloadData() ngay trong completion; đôi khi UI không cập nhật, Xcode hiện cảnh báo tím của Main Thread Checker. Vì sao và sửa thế nào?

    Xem đáp án mẫu
    Completion của URLSession.dataTask chạy trên một background queue của session, không phải main thread. UIKit không thread-safe, mọi thao tác với view phải chạy trên main thread; cập nhật từ thread khác có thể không hiển thị, hiển thị trễ hoặc crash ngẫu nhiên. Cách sửa là decode ở background rồi dùng DispatchQueue.main.async để gán dữ liệu và reload; mảng làm data source cũng nên chỉ được sửa trên main để table view không đọc trúng lúc đang ghi. Main Thread Checker được bật mặc định khi chạy debug, đừng bỏ qua những cảnh báo tím này.
    URLSession.shared.dataTask(with: url) { [weak self] data, _, error in
  // Đang ở background thread
  guard let data, error == nil,
        let items = try? JSONDecoder().decode([Product].self, from: data) else { return }
  DispatchQueue.main.async {
    self?.items = items          // data source cũng sửa trên main

}.resume()

  2. Phân biệt serial queue với concurrent queue, sync với async trong GCD. Cần một logger được gọi từ nhiều thread trong app thì bạn thiết kế thế nào?

    Xem đáp án mẫu
    Serial hay concurrent là tính chất của queue: serial chạy từng task một theo thứ tự FIFO, concurrent cho phép nhiều task chạy song song dù vẫn bắt đầu theo thứ tự đưa vào. sync hay async là cách gọi: sync chặn thread hiện tại tới khi task chạy xong, async đưa task vào queue rồi đi tiếp ngay. DispatchQueue.main là serial, DispatchQueue.global() là concurrent. Với logger, dùng một serial queue riêng: ghi bằng async để nơi gọi (kể cả main thread) không bị chặn, đọc bằng sync khi cần lấy kết quả; mọi truy cập đi qua cùng một queue nên không có data race và log giữ đúng thứ tự.
    final class Logger {
  private let queue = DispatchQueue(label: "com.app.logger") // serial mặc định
  private var lines: [String] = []

  func log(_ message: String) {
    queue.async { self.lines.append(message) } // không chặn nơi gọi
  }

  func allLines() -> [String] {
    queue.sync { lines } // đọc cũng đi qua queue
  }
}

  3. Một bạn viết DispatchQueue.main.sync { ... } trong viewDidLoad để "chắc chắn chạy trên main" và app crash ngay khi mở màn hình. Giải thích vì sao.

    Xem đáp án mẫu
    viewDidLoad vốn đã chạy trên main thread. sync chặn thread hiện tại cho tới khi block chạy xong, nhưng block lại được xếp vào main queue, mà main queue là serial và chỉ chạy được block mới khi main thread rảnh: hai bên chờ nhau mãi, tức deadlock. Với trường hợp gọi sync lên đúng serial queue mà thread hiện tại đang chạy như thế này, libdispatch phát hiện được và chủ động dừng app (crash EXC_BREAKPOINT) thay vì để treo; còn deadlock giữa nhiều thread chờ chéo nhau thì app thường chỉ đứng hình. Đang ở background mà cần cập nhật UI thì dùng DispatchQueue.main.async; nếu đã ở main thread thì cứ gọi thẳng.

func handle<T: Decodable>(_ data: Data?, _ response: URLResponse?, _ error: Error?) -> Result<T, APIError> {
  if let error { return .failure(.transport(error)) }
  guard let http = response as? HTTPURLResponse, let data else { return .failure(.server(-1)) }
  switch http.statusCode {
  case 200..<300:
    do { return .success(try JSONDecoder().decode(T.self, from: data)) }
    catch { return .failure(.decoding(error)) }
  case 401: return .failure(.unauthorized)
  default: return .failure(.server(http.statusCode))
  }
}

  private let url = URL.cachesDirectory.appending(path: "feed.json")

  func load() -> [Post]? {
    guard let data = try? Data(contentsOf: url) else { return nil }
    return try? JSONDecoder().decode([Post].self, from: data)
  }

  func save(_ posts: [Post]) {
    guard let data = try? JSONEncoder().encode(posts) else { return }
    try? data.write(to: url, options: .atomic)
  }
}
