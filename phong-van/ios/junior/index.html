  1. Vì sao compiler bắt thêm @escaping khi bạn lưu closure tham số vào property hoặc gọi nó trong completion của request mạng? Closure non-escaping có lợi gì?

    Xem đáp án mẫu
    Mặc định closure tham số là non-escaping: compiler đảm bảo nó chỉ được gọi trong lúc hàm đang chạy và không bị giữ lại sau khi hàm return. Khi closure được lưu vào property, đưa vào DispatchQueue.main.async hay completion của URLSession, nó sống lâu hơn hàm nên phải đánh dấu @escaping. Closure escaping có thể giữ self lâu hơn dự kiến và gây retain cycle, vì vậy trong class Swift bắt viết rõ self. để bạn ý thức được mình đang capture gì. Closure non-escaping như tham số của map, filter, sorted(by:) an toàn hơn: không cần [weak self] và compiler tối ưu được tốt hơn.
    final class ProfileService {
  var onUpdate: ((User) -> Void)?

  // Lưu closure lại để gọi sau -> bắt buộc @escaping
  func observe(_ handler: @escaping (User) -> Void) {
    onUpdate = handler
  }

  // Chỉ dùng trong lúc hàm chạy -> non-escaping là đủ
  func active(_ users: [User], where rule: (User) -> Bool) -> [User] {
    users.filter(rule)
  }
}

  2. Capture list [x] trong closure khác gì so với dùng biến x trực tiếp? Ngoài [weak self], bạn còn dùng capture list vào việc gì?

    Xem đáp án mẫu
    Không có capture list, closure capture chính biến, nên nó đọc giá trị tại thời điểm closure chạy và thấy mọi thay đổi sau đó. Với [x], giá trị của x được copy ngay lúc tạo closure và cố định từ đó. Điều này hữu ích khi muốn chụp lại trạng thái hiện tại, ví dụ giữ requestId để bỏ qua response của request cũ, hoặc chỉ capture một dependency như [service] thay vì cả self. Lưu ý với reference type, [obj] vẫn là strong reference, chỉ là tham chiếu được cố định; muốn không giữ object thì phải dùng [weak obj].
    var page = 1
let printNow = { print("page =", page) }
let printSnapshot = { [page] in print("page =", page) }

page = 2
printNow()      // page = 2
printSnapshot() // page = 1

  3. Dự án có hàng chục loại cell, chỗ nào cũng viết dequeueReusableCell(withIdentifier: "ProductCell", for: indexPath) as! ProductCell và thỉnh thoảng crash vì gõ sai identifier. Bạn dùng protocol extension và generics để gọn lại thế nào?

    Xem đáp án mẫu
    Khai báo protocol Reusable có static var reuseIdentifier, rồi dùng protocol extension cung cấp sẵn giá trị mặc định là tên class; cell chỉ cần conform là có identifier, không phải gõ chuỗi tay ở cả chỗ register lẫn chỗ dequeue. Tiếp theo viết một hàm generic trong extension của UITableView với ràng buộc T: UITableViewCell & Reusable: kiểu T được suy ra từ chỗ gọi, nên phép ép kiểu chỉ nằm ở một nơi và báo lỗi rõ ràng nếu identifier bị register với class khác. Đây là ví dụ điển hình của protocol extension (default implementation) kết hợp generic constraint để bỏ code lặp mà vẫn giữ type-safe.
    protocol Reusable {
  static var reuseIdentifier: String { get }
}
extension Reusable {
  static var reuseIdentifier: String { String(describing: self) }
}
extension UITableView {
  func dequeue<T: UITableViewCell & Reusable>(for indexPath: IndexPath) -> T {
    guard let cell = dequeueReusableCell(withIdentifier: T.reuseIdentifier, for: indexPath) as? T else {
      fatalError("\(T.reuseIdentifier) đang register sai class")
    }
    return cell
  }
}

Memory & ARC

Mọi rank →

  1. Bạn pop màn hình chi tiết ra nhưng deinit của DetailViewController không bao giờ chạy. Trong code có đoạn gán callback cho ViewModel như dưới. Nguyên nhân và cách sửa?

    Xem đáp án mẫu
    VC giữ strong viewModel, viewModel giữ strong closure onUpdate, còn closure lại capture strong self là chính VC, tạo thành retain cycle nên reference count không bao giờ về 0 và cả VC lẫn ViewModel bị leak. Sửa bằng capture list [weak self] rồi guard let self else { return } trong closure; khi VC bị pop, không còn ai giữ VC nên nó được giải phóng và chu trình bị phá. Cách kiểm tra nhanh là đặt print hoặc breakpoint trong deinit, hoặc mở Memory Graph trong Xcode để xem object nào còn sống sau khi rời màn hình.
    final class DetailViewController: UIViewController {
  let viewModel = DetailViewModel()

  override func viewDidLoad() {
    super.viewDidLoad()
    // Gây leak: viewModel.onUpdate = { state in self.render(state) }
    viewModel.onUpdate = { [weak self] state in
      guard let self else { return }
      self.render(state)
    }
  }

  deinit { print("DetailViewController deinit") }
}

  2. Vì sao property delegate thường được khai báo weak? Viết weak var delegate: PickerDelegate? mà compiler báo lỗi thì sửa thế nào?

    Xem đáp án mẫu
    Quan hệ hay gặp là VC (owner) giữ strong một view hay object con, còn object con gọi ngược lại VC qua delegate; nếu delegate cũng strong thì hai bên giữ nhau và không bao giờ được giải phóng. Vì vậy delegate để weak, và nó phải là optional vì ARC tự gán nil khi object bị huỷ. weak chỉ áp dụng cho reference type, nên protocol phải được giới hạn cho class bằng protocol PickerDelegate: AnyObject; nếu không, compiler báo lỗi vì struct hay enum cũng có thể conform. UIKit cũng làm như vậy: delegate và dataSource của UITableView đều là weak.

  3. weak và unowned khác nhau thế nào? Có phải closure nào dùng self cũng phải viết [weak self] không?

    Xem đáp án mẫu
    Cả hai đều không làm tăng strong reference count. weak luôn là optional và tự thành nil khi object bị giải phóng nên an toàn; unowned giả định object vẫn còn sống, truy cập sau khi object đã bị huỷ sẽ crash, nên chỉ dùng khi chắc chắn object được tham chiếu sống ít nhất lâu bằng bên giữ nó. Không phải closure nào cũng cần [weak self]: closure non-escaping như của map, hay closure chạy một lần rồi được giải phóng như UIView.animate, DispatchQueue.main.async chỉ giữ self tạm thời, không tạo chu trình. Cần weak khi self trực tiếp hoặc gián tiếp đang giữ closure đó, hoặc khi không muốn kéo dài vòng đời màn hình chỉ để chờ một request mạng chậm.

Concurrency

Mọi rank →

  1. Gọi API bằng URLSession rồi gán dữ liệu và tableView.reloadData() ngay trong completion; đôi khi UI không cập nhật, Xcode hiện cảnh báo tím của Main Thread Checker. Vì sao và sửa thế nào?

    Xem đáp án mẫu
    Completion của URLSession.dataTask chạy trên một background queue của session, không phải main thread. UIKit không thread-safe, mọi thao tác với view phải chạy trên main thread; cập nhật từ thread khác có thể không hiển thị, hiển thị trễ hoặc crash ngẫu nhiên. Cách sửa là decode ở background rồi dùng DispatchQueue.main.async để gán dữ liệu và reload; mảng làm data source cũng nên chỉ được sửa trên main để table view không đọc trúng lúc đang ghi. Main Thread Checker được bật mặc định khi chạy debug, đừng bỏ qua những cảnh báo tím này.
    URLSession.shared.dataTask(with: url) { [weak self] data, _, error in
  // Đang ở background thread
  guard let data, error == nil,
        let items = try? JSONDecoder().decode([Product].self, from: data) else { return }
  DispatchQueue.main.async {
    self?.items = items          // data source cũng sửa trên main
    self?.tableView.reloadData()
  }
}.resume()

  2. Phân biệt serial queue với concurrent queue, sync với async trong GCD. Cần một logger được gọi từ nhiều thread trong app thì bạn thiết kế thế nào?

    Xem đáp án mẫu
    Serial hay concurrent là tính chất của queue: serial chạy từng task một theo thứ tự FIFO, concurrent cho phép nhiều task chạy song song dù vẫn bắt đầu theo thứ tự đưa vào. sync hay async là cách gọi: sync chặn thread hiện tại tới khi task chạy xong, async đưa task vào queue rồi đi tiếp ngay. DispatchQueue.main là serial, DispatchQueue.global() là concurrent. Với logger, dùng một serial queue riêng: ghi bằng async để nơi gọi (kể cả main thread) không bị chặn, đọc bằng sync khi cần lấy kết quả; mọi truy cập đi qua cùng một queue nên không có data race và log giữ đúng thứ tự.
    final class Logger {
  private let queue = DispatchQueue(label: "com.app.logger") // serial mặc định
  private var lines: [String] = []

  func log(_ message: String) {
    queue.async { self.lines.append(message) } // không chặn nơi gọi
  }

  func allLines() -> [String] {
    queue.sync { lines } // đọc cũng đi qua queue
  }
}

  3. Một bạn viết DispatchQueue.main.sync { ... } trong viewDidLoad để "chắc chắn chạy trên main" và app crash ngay khi mở màn hình. Giải thích vì sao.

    Xem đáp án mẫu
    viewDidLoad vốn đã chạy trên main thread. sync chặn thread hiện tại cho tới khi block chạy xong, nhưng block lại được xếp vào main queue, mà main queue là serial và chỉ chạy được block mới khi main thread rảnh: hai bên chờ nhau mãi, tức deadlock. Với trường hợp gọi sync lên đúng serial queue mà thread hiện tại đang chạy như thế này, libdispatch phát hiện được và chủ động dừng app (crash EXC_BREAKPOINT) thay vì để treo; còn deadlock giữa nhiều thread chờ chéo nhau thì app thường chỉ đứng hình. Đang ở background mà cần cập nhật UI thì dùng DispatchQueue.main.async; nếu đã ở main thread thì cứ gọi thẳng.

  4. Màn hình Home cần gọi song song 3 API (banner, danh mục, sản phẩm) và chỉ tắt loading khi cả 3 xong. Bạn làm bằng GCD thế nào, cần tránh lỗi gì?

    Xem đáp án mẫu
    Dùng DispatchGroup: gọi enter() trước mỗi request, leave() khi request kết thúc, rồi notify(queue: .main) để tắt loading khi bộ đếm về 0. Lỗi hay gặp nhất là quên leave() ở nhánh lỗi khiến notify không bao giờ chạy và loading quay mãi; đặt defer { group.leave() } ở đầu completion để chắc chắn luôn gọi. Ngược lại, gọi leave() nhiều hơn enter() sẽ crash. Không dùng group.wait() trên main thread vì nó chặn UI, và đừng để nhiều completion cùng ghi vào một mảng chung từ các thread khác nhau.
    let group = DispatchGroup()
var banners: [Banner] = []
var products: [Product] = []
group.enter()
api.fetchBanners { result in
  defer { group.leave() } // luôn leave, kể cả khi lỗi
  if case .success(let items) = result { banners = items }
}
group.enter()
api.fetchProducts { result in
  defer { group.leave() }
  if case .success(let items) = result { products = items }
}
group.notify(queue: .main) { self.render(banners, products) }

UIKit & Lifecycle

Mọi rank →

  1. Màn đăng ký có form dài đặt trong UIScrollView; khi bàn phím hiện lên thì che mất các ô nhập phía dưới và người dùng không cuộn tới được. Bạn xử lý thế nào?

    Xem đáp án mẫu
    Với một UIScrollView đặt trong view controller thường, UIKit không tự điều chỉnh inset theo bàn phím, nên phải thu vùng hiển thị của scroll view lại đúng bằng phần bị bàn phím che. Cách truyền thống là lắng nghe UIResponder.keyboardWillShowNotification và keyboardWillHideNotification, đọc frame bàn phím từ keyboardFrameEndUserInfoKey, đổi sang hệ toạ độ của view rồi đặt scrollView.contentInset.bottom (và verticalScrollIndicatorInsets) theo phần bị che, khi bàn phím ẩn thì trả về 0. Từ iOS 15 gọn hơn: neo đáy scroll view vào view.keyboardLayoutGuide.topAnchor, Auto Layout tự co giãn theo chiều cao bàn phím. Nếu ô đang nhập vẫn bị che thì gọi scrollRectToVisible để cuộn tới nó. SwiftUI thì mặc định tự tránh bàn phím, khác với UIKit.
    // iOS 15+: đáy scroll view bám theo mép trên của bàn phím
NSLayoutConstraint.activate([
  scrollView.topAnchor.constraint(equalTo: view.safeAreaLayoutGuide.topAnchor),
  scrollView.leadingAnchor.constraint(equalTo: view.leadingAnchor),
  scrollView.trailingAnchor.constraint(equalTo: view.trailingAnchor),
  scrollView.bottomAnchor.constraint(equalTo: view.keyboardLayoutGuide.topAnchor)
])
// Khi bàn phím ẩn, keyboardLayoutGuide nằm ở đáy safe area

  2. Cell có label mô tả nhiều dòng nhưng chiều cao cell vẫn cố định, chữ bị cắt. Cần làm gì để self-sizing cell hoạt động?

    Xem đáp án mẫu
    Đặt tableView.rowHeight = UITableView.automaticDimension cùng một estimatedRowHeight hợp lý, và label phải có numberOfLines = 0. Quan trọng nhất là constraint bên trong contentView phải tạo thành một chuỗi liên tục từ top tới bottom để Auto Layout tính ra được chiều cao; thiếu constraint bottom, hoặc add subview vào chính cell thay vì contentView, là lý do phổ biến khiến cell không giãn. Ngoài ra kiểm tra xem có ai implement tableView(_:heightForRowAt:) trả về số cố định không, vì nó ghi đè cơ chế tự tính chiều cao.

  3. App thỉnh thoảng crash với lỗi Invalid update: invalid number of rows in section 0 khi thêm, xoá item rồi gọi insertRows/deleteRows. Diffable data source giúp gì, dùng thế nào?

    Xem đáp án mẫu
    Lỗi xảy ra khi số row mà data source báo sau cập nhật không khớp với số row trước đó cộng trừ các thay đổi bạn khai báo, thường do quên cập nhật mảng hoặc cập nhật sai thứ tự. UITableViewDiffableDataSource thay cách làm thủ công đó: bạn dựng một NSDiffableDataSourceSnapshot mô tả toàn bộ section và item hiện tại rồi apply, nó tự tính khác biệt và chạy animation, nên không còn chuyện lệch số lượng. Item identifier phải Hashable và duy nhất trong snapshot; nên dùng id ổn định của model, vì nếu dùng cả struct làm identifier thì mỗi lần sửa nội dung sẽ bị coi là xoá rồi chèn item mới.

SwiftUI

Mọi rank →

  1. Màn hình SwiftUI khai báo @ObservedObject var viewModel = ProfileViewModel(), thỉnh thoảng dữ liệu đang nhập bị reset và API bị gọi lại khi view cha cập nhật. Vì sao? Khi nào dùng @StateObject?

    Xem đáp án mẫu
    Struct view trong SwiftUI được tạo lại mỗi khi view cha tính lại body. Với @ObservedObject, mỗi lần như vậy biểu thức ProfileViewModel() chạy lại và tạo object mới, nên state cũ mất, và nếu ViewModel gọi API trong init thì request bị bắn lại. Với @StateObject, SwiftUI chỉ tạo object một lần cho mỗi identity của view và giữ nó suốt vòng đời view, bất kể struct được tạo lại bao nhiêu lần. Quy tắc: view nào tạo ra và sở hữu object thì dùng @StateObject; view chỉ nhận object từ bên ngoài truyền vào thì dùng @ObservedObject.
    final class ProfileViewModel: ObservableObject {
  @Published var name = ""
}

struct ProfileScreen: View {
  @StateObject private var viewModel = ProfileViewModel() // view này sở hữu
  var body: some View { ProfileForm(viewModel: viewModel) }
}

struct ProfileForm: View {
  @ObservedObject var viewModel: ProfileViewModel // chỉ nhận từ ngoài
  var body: some View { TextField("Tên", text: $viewModel.name) }
}

  2. Bạn tách một nút bật/tắt yêu thích ra view con, nhưng bấm ở view con thì view cha không hề biết. Dùng @Binding giải quyết thế nào, và vì sao không dùng @State ở view con?

    Xem đáp án mẫu
    @State tạo ra một nguồn dữ liệu riêng do chính view con sở hữu; nếu view cha truyền giá trị vào @State thì đó chỉ là giá trị khởi tạo, sau đó hai bên tách rời nhau. @Binding không sở hữu dữ liệu mà là tham chiếu hai chiều tới một nguồn nằm ở nơi khác: view cha giữ @State và truyền $isFavorite xuống, view con đọc và ghi qua binding, thay đổi đi thẳng về state của cha và cả hai cùng cập nhật. Đây là nguyên tắc single source of truth: mỗi dữ liệu chỉ có một chủ sở hữu, các view khác nhận binding. Trong Preview có thể dùng .constant(true) để tạo một binding cố định.

  3. Danh sách todo dùng ForEach(todos.indices, id: \.self) hoặc ForEach(names, id: \.self). Khi xoá hoặc chèn phần tử thì animation sai, trạng thái của row này nhảy sang row khác. Vì sao?

    Xem đáp án mẫu
    SwiftUI dùng id để biết row nào là row nào giữa các lần cập nhật. Dùng index làm id thì khi xoá phần tử đầu, mọi row phía sau đổi id, SwiftUI hiểu là nội dung các row bị thay đổi chứ không phải một row bị xoá, nên animation sai và @State bên trong row (đang mở rộng, đang nhập dở) bị gắn nhầm sang dữ liệu khác. Dùng \.self với dữ liệu có thể trùng nhau (hai todo cùng tên) thì id không còn duy nhất và hành vi không xác định. Cách đúng là cho model conform Identifiable với id ổn định: id từ server, hoặc UUID tạo một lần khi tạo object, tuyệt đối không tạo mới trong body.
    struct Todo: Identifiable {
  let id: UUID   // tạo một lần khi tạo Todo, không đổi
  var title: String
}

// Sai: id theo vị trí, thay đổi khi xoá/chèn
ForEach(todos.indices, id: \.self) { i in TodoRow(todo: todos[i]) }

// Đúng: id gắn với dữ liệu
ForEach(todos) { todo in TodoRow(todo: todo) }

  1. Màn danh sách dùng segue showDetail để mở màn chi tiết, màn này được nhúng trong một UINavigationController trên storyboard. Trong prepare(for:sender:) bạn viết segue.destination as! ProductDetailViewController và app crash. Vì sao, và truyền dữ liệu qua segue thế nào cho đúng?

    Xem đáp án mẫu
    segue.destination là view controller mà segue trỏ tới trên storyboard, ở đây chính là UINavigationController chứ không phải màn chi tiết bên trong, nên as! ép kiểu thất bại và crash. Cần ép segue.destination sang UINavigationController rồi lấy topViewController của nó mới ra ProductDetailViewController. Nên kiểm tra segue.identifier để phân biệt các segue và dùng as? thay cho as!. Dữ liệu chỉ gán vào property thường như var product: Product?, vì lúc này view của màn đích chưa load nên outlet vẫn là nil; màn đích tự đổ dữ liệu lên UI trong viewDidLoad. Từ iOS 13 có thể dùng @IBSegueAction để tự khởi tạo VC đích và truyền dependency qua init.
    // Gọi bằng performSegue(withIdentifier: "showDetail", sender: product)
override func prepare(for segue: UIStoryboardSegue, sender: Any?) {
  guard segue.identifier == "showDetail",
        let nav = segue.destination as? UINavigationController,
        let detail = nav.topViewController as? ProductDetailViewController,
        let product = sender as? Product else { return }
  detail.product = product   // property thường, không đụng tới outlet
}

  2. Khi chuyển từ NavigationView sang NavigationStack, cách điều hướng bằng NavigationLink(value:) kết hợp .navigationDestination(for:) có lợi gì so với NavigationLink(destination:) kiểu cũ?

    Xem đáp án mẫu
    Từ iOS 16, Apple đưa ra NavigationStack (và NavigationSplitView cho giao diện nhiều cột) để thay thế NavigationView, API cũ được đánh dấu deprecated. Với NavigationLink(destination:), view đích được khởi tạo ngay khi link được tạo, nên một list dài có thể khởi tạo cả trăm view đích (kèm ViewModel trong init) dù người dùng chưa bấm. Kiểu mới tách dữ liệu khỏi đích đến: link chỉ mang một giá trị Hashable, còn .navigationDestination(for: Product.self) khai báo một lần cách dựng màn hình cho kiểu đó, và view đích chỉ được tạo khi thực sự push. Lưu ý đặt .navigationDestination bên trong NavigationStack nhưng bên ngoài container lazy như List, LazyVStack, nếu không link có thể không hoạt động.

  1. API trả JSON dạng snake_case, có field lúc có lúc không, có field đôi khi là null. Bạn thiết kế model Codable thế nào để decode không vỡ?

    Xem đáp án mẫu
    Về tên key, có thể đặt decoder.keyDecodingStrategy = .convertFromSnakeCase cho cả decoder, hoặc khai báo enum CodingKeys: String, CodingKey khi tên lệch nhiều hay muốn kiểm soát từng field. Không nên trộn hai cách: strategy chuyển key của JSON sang camelCase trước rồi mới so với CodingKeys, nên raw value "user_id" sẽ không khớp. Field có thể thiếu hoặc null thì khai báo optional, vì decoder tổng hợp sẵn dùng decodeIfPresent cho optional nên cả hai trường hợp đều thành nil; còn để non-optional thì cả object, và cả mảng chứa nó, decode thất bại. Đừng dùng try? nuốt lỗi: bắt DecodingError và log ra để biết chính xác key nào sai.

  2. Backend trả price lúc là số 120000, lúc là chuỗi "120000", còn field tags có khi không có. Bạn viết init(from:) tuỳ biến thế nào?

    Xem đáp án mẫu
    Khi kiểu dữ liệu không ổn định thì tự viết init(from decoder:): lấy container theo CodingKeys, thử decode kiểu này, không được thì thử kiểu kia, cuối cùng ném DecodingError có mô tả rõ ràng thay vì gán bừa một giá trị. Field có thể thiếu mà muốn có giá trị mặc định thì dùng decodeIfPresent(...) ?? []. Nhớ rằng viết init(from:) ngay trong thân struct sẽ làm mất memberwise initializer tự sinh; muốn giữ lại để tiện tạo dữ liệu test thì đặt nó trong extension. Về lâu dài vẫn nên thống nhất kiểu dữ liệu với backend.
    struct Product: Decodable {
  let price: Int
  let tags: [String]
  enum CodingKeys: String, CodingKey { case price, tags }
  init(from decoder: Decoder) throws {
    let c = try decoder.container(keyedBy: CodingKeys.self)
    let number = try? c.decode(Int.self, forKey: .price)
    let text = try? c.decode(String.self, forKey: .price)
    guard let value = number ?? text.flatMap({ Int($0) }) else {
      throw DecodingError.dataCorruptedError(forKey: .price, in: c, debugDescription: "price sai kiểu")
    }
    price = value
    tags = try c.decodeIfPresent([String].self, forKey: .tags) ?? [] // thiếu key -> []
  }
}

  3. Server trả HTTP 401 hoặc 500 nhưng trong completion của dataTask thì error vẫn là nil, app đem body lỗi đi decode rồi báo lỗi parse khó hiểu. Vì sao, và xử lý thế nào cho đúng?

    Xem đáp án mẫu
    error của URLSession chỉ khác nil khi lỗi ở tầng transport: mất mạng, timeout, không phân giải được host, lỗi SSL, request bị cancel. Server trả 4xx hay 5xx vẫn là một response HTTP hợp lệ, nên error là nil và data chứa body lỗi. Vì vậy phải ép response sang HTTPURLResponse và kiểm tra statusCode trước khi decode: 2xx mới decode model, 401 map thành lỗi hết phiên để đưa người dùng về đăng nhập, các mã khác thành lỗi server có thông báo phù hợp. Nên gom logic này vào một API client dùng chung trả về Result<T, APIError> để mọi màn hình xử lý giống nhau.
    enum APIError: Error { case transport(Error), unauthorized, server(Int), decoding(Error) }

func handle<T: Decodable>(_ data: Data?, _ response: URLResponse?, _ error: Error?) -> Result<T, APIError> {
  if let error { return .failure(.transport(error)) }
  guard let http = response as? HTTPURLResponse, let data else { return .failure(.server(-1)) }
  switch http.statusCode {
  case 200..<300:
    do { return .success(try JSONDecoder().decode(T.self, from: data)) }
    catch { return .failure(.decoding(error)) }
  case 401: return .failure(.unauthorized)
  default: return .failure(.server(http.statusCode))
  }
}

App lifecycle & Platform

Mọi rank →

  1. Người dùng đang điền một form dài thì chuyển sang app khác, một lúc sau quay lại thấy app khởi động lại từ đầu và mất hết dữ liệu. Vì sao, và nên lưu nháp vào lúc nào?

    Xem đáp án mẫu
    Khi vào background, app chỉ được chạy thêm một khoảng ngắn rồi chuyển sang suspended: vẫn nằm trong bộ nhớ nhưng không chạy code. Khi cần bộ nhớ cho app khác, hệ thống có thể kill app đang suspended mà không gọi applicationWillTerminate, nên lần mở sau là khởi động lại từ đầu. Vì vậy phải lưu trạng thái quan trọng ngay khi app rời foreground, trong sceneWillResignActive hoặc sceneDidEnterBackground (SwiftUI thì theo dõi scenePhase), hoặc tốt hơn là lưu nháp ngay trong lúc người dùng nhập. Muốn khôi phục cả màn hình đang mở thì dùng state restoration như @SceneStorage trong SwiftUI hoặc NSUserActivity.

  2. Mô tả luồng push notification từ lúc app xin quyền tới khi máy nhận được thông báo. Device token cần được xử lý thế nào?

    Xem đáp án mẫu
    App gọi UNUserNotificationCenter.current().requestAuthorization để xin quyền hiển thị thông báo, và UIApplication.shared.registerForRemoteNotifications() để đăng ký với APNs. Hệ thống trả device token qua application(_:didRegisterForRemoteNotificationsWithDeviceToken:); app chuyển Data sang chuỗi hex rồi gửi lên backend, gắn với user đang đăng nhập. Khi cần gửi, backend gọi APNs (xác thực bằng key .p8 hoặc certificate) kèm token và payload, APNs đẩy xuống thiết bị. Token có thể thay đổi, và token của môi trường sandbox (bản debug) khác production, nên mỗi lần app khởi động hãy đăng ký lại và gửi token mới nhận được lên server thay vì cache cứng một giá trị.

  1. Bạn chuyển access token từ UserDefaults sang Keychain. Ngoài chuyện an toàn hơn, khi làm việc với Keychain có những bẫy nào cần biết?

    Xem đáp án mẫu
