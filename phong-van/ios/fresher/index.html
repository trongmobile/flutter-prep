  1. Optional trong Swift là gì? Có những cách nào để lấy giá trị ra khỏi một Optional, và vì sao nên hạn chế force unwrap !?

    Xem đáp án mẫu
    Optional (T?) nghĩa là biến có thể chứa giá trị kiểu T hoặc nil; bản chất nó là enum với hai case .some và .none. Biến non-optional không bao giờ nhận nil, nên compiler buộc bạn xử lý trường hợp thiếu dữ liệu ngay khi viết code. Cách lấy giá trị an toàn: if let/guard let, toán tử ?? để có giá trị mặc định, optional chaining user?.address?.city (gặp nil thì cả biểu thức thành nil). Force unwrap ! crash ngay lập tức nếu giá trị là nil, nên chỉ dùng khi chắc chắn tuyệt đối.
    var nickname: String? = nil

let display = nickname ?? "Khách"   // "Khách"
let length = nickname?.count          // Int?, đang là nil

if let name = nickname {
    print("Xin chào \(name)")         // chỉ chạy khi khác nil
}

// print(nickname!.count)             // crash vì nickname là nil

  2. if let và guard let khác nhau thế nào? Khi nào bạn chọn guard let?

    Xem đáp án mẫu
    Cả hai đều unwrap Optional, khác nhau ở phạm vi của biến. Với if let, biến đã unwrap chỉ dùng được bên trong khối {} của if. Với guard let, biến dùng được ở toàn bộ phần còn lại của hàm, đổi lại nhánh else bắt buộc thoát khỏi scope bằng return, throw, break, continue hoặc fatalError(), thiếu là lỗi compile. Vì vậy guard let hợp để kiểm tra điều kiện ở đầu hàm theo kiểu early exit, tránh if lồng nhiều tầng. Từ Swift 5.7 có thể viết gọn if let name { thay cho if let name = name {.

  3. Struct và class trong Swift khác nhau thế nào? Vì sao khai báo let với một instance struct thì không sửa được property, còn với class thì vẫn sửa được?

    Xem đáp án mẫu
    Struct là value type: gán sang biến khác hay truyền vào hàm sẽ tạo bản sao độc lập. Class là reference type: nhiều biến cùng trỏ tới một object, sửa ở chỗ này thì chỗ khác cũng thấy; class còn có kế thừa, deinit và được quản lý bằng ARC. Với struct, let đóng băng cả giá trị nên không sửa được property nào; với class, let chỉ cố định tham chiếu, property var bên trong object vẫn sửa được. Swift khuyến khích dùng struct làm mặc định cho model, chỉ dùng class khi cần chia sẻ trạng thái, kế thừa hoặc làm việc với API như UIViewController.
    struct PointS { var x = 0 }
class PointC { var x = 0 }

var a = PointS()
var b = a        // tạo bản sao
b.x = 10
print(a.x)       // 0

let c = PointC()
let d = c        // cùng một object
d.x = 10
print(c.x)       // 10

let s = PointS()
// s.x = 5       // lỗi compile: s là let

  4. Enum có associated value là gì? Cho ví dụ dùng switch để hiển thị trạng thái tải dữ liệu của một màn hình.

    Xem đáp án mẫu
    Mỗi case của enum có thể mang kèm dữ liệu riêng với kiểu khác nhau, ví dụ .loaded([String]) mang danh sách còn .failed(message:) mang thông báo lỗi. switch trên enum bắt buộc phủ hết các case, thiếu là lỗi compile, nên khi thêm case mới compiler chỉ ra mọi chỗ cần sửa; vì lý do đó nên tránh default khi switch trên enum của chính mình. Dùng case .failed(let message) để lấy dữ liệu đi kèm. Khác với raw value (enum Direction: String) cố định cho từng case, associated value được truyền vào lúc tạo giá trị.
    enum LoadState {
    case loading
    case loaded([String])
    case failed(message: String)
}
func render(_ state: LoadState) {
    switch state {
    case .loading:
        print("Đang tải...")
    case .loaded(let items):
        print("Có \(items.count) mục")
    case .failed(let message):
        print("Lỗi: \(message)")
    }
}

  5. Closure trong Swift là gì? Giải thích cú pháp trailing closure và $0 qua ví dụ filter, map, reduce.

    Xem đáp án mẫu
    Closure là khối code có thể gán vào biến, truyền làm tham số hoặc trả về từ hàm; nó còn capture được biến ở phạm vi bao quanh để dùng về sau. Khi closure là tham số cuối, có thể viết nó ra ngoài dấu ngoặc tròn (trailing closure). Nếu kiểu đã suy ra được thì bỏ kiểu tham số, bỏ return với closure chỉ có một biểu thức, và dùng tên viết tắt $0, $1. Nên viết tắt vừa phải: closure dài nhiều dòng thì đặt tên tham số rõ ràng cho dễ đọc.
    let prices = [120, 45, 300, 80]

// Viết đầy đủ
let cheap = prices.filter({ (price: Int) -> Bool in
    return price < 100
})

// Trailing closure + tên viết tắt
let doubled = prices.map { $0 * 2 }
let total = prices.reduce(0) { $0 + $1 }

print(cheap)   // [45, 80]
print(total)   // 545

  6. Protocol và extension trong Swift dùng để làm gì? Extension có thêm được stored property không?

    Xem đáp án mẫu
    Protocol định nghĩa một hợp đồng gồm các method/property mà kiểu tuân theo (struct, class, enum) phải cài đặt, giúp code làm việc được với bất kỳ kiểu nào thoả protocol; UITableViewDataSource là ví dụ quen thuộc. Extension thêm method, computed property, initializer hoặc conformance protocol cho kiểu có sẵn, kể cả kiểu bạn không có source như String, Int. Extension không thêm được stored property cho instance và không override được method đã có. Cách dùng phổ biến là tách mỗi protocol conformance ra một extension riêng cho gọn, như extension ProfileViewController: UITableViewDataSource.
    protocol Describable {
    var summary: String { get }
}

struct Product: Describable {
    let name: String
    let price: Int
    var summary: String { "\(name) - \(price)đ" }
}

extension Int {
    var isEven: Bool { self % 2 == 0 } // computed property: OK
    // var cache = 0                   // lỗi: không thêm được stored property
}

  7. Swift xử lý lỗi bằng throws, do/catch, try? và try! như thế nào? Khi nào dùng try??

    Xem đáp án mẫu
    Hàm có thể ném lỗi được đánh dấu throws, lỗi là giá trị của kiểu conform protocol Error (thường là enum). Khi gọi phải viết try và đặt trong do/catch để xử lý, hoặc để lỗi lan tiếp ra ngoài nếu hàm hiện tại cũng throws. try? đổi kết quả thành Optional, có lỗi thì nhận nil, hợp khi không cần biết lý do lỗi; try! crash nếu có lỗi nên rất hạn chế dùng. Bẫy hay gặp là lạm dụng try? khiến lỗi bị nuốt mất, lúc debug không biết vì sao dữ liệu rỗng.
    enum LoginError: Error { case emptyPassword, wrongPassword }
func login(password: String) throws -> String {
    if password.isEmpty { throw LoginError.emptyPassword }
    if password != "123456" { throw LoginError.wrongPassword }
    return "token-abc"
}

do {
    let token = try login(password: "")
    print(token)
} catch LoginError.emptyPassword {
    print("Vui lòng nhập mật khẩu")
} catch {
    print("Lỗi khác: \(error)")
}

  8. Array, Dictionary và Set trong Swift khác nhau thế nào? Vì sao dictionary[key] trả về Optional?

    Xem đáp án mẫu
    Array là danh sách có thứ tự, truy cập theo index, cho phép phần tử trùng. Index ngoài phạm vi là crash lúc chạy nên cần kiểm tra trước, hoặc dùng first/last vốn trả về Optional. Dictionary lưu các cặp key–value với key phải Hashable và duy nhất, thứ tự duyệt không được đảm bảo. dict[key] trả về Value? vì key có thể chưa tồn tại; dùng if let, ?? hoặc dict[key, default: 0] để lấy giá trị an toàn. Set chứa các phần tử Hashable duy nhất và không có thứ tự, kiểm tra contains rất nhanh và có sẵn phép toán tập hợp như union, intersection, subtracting, nên hợp để loại trùng hoặc kiểm tra tồn tại. Cả ba đều là struct (value type), nên gán sang biến khác là tạo bản sao độc lập và khai báo bằng let thì không sửa được nội dung.
    var names = ["An", "Bình", "An"]        // Array: có thứ tự, cho phép trùng
names.append("Chi")
print(names[0], names.first ?? "")       // An An

var scores = ["An": 8, "Bình": 6]        // Dictionary
print(scores["Chi"] as Any)              // nil (key chưa có)
scores["Chi", default: 0] += 5           // key mới bắt đầu từ giá trị mặc định 0
print(scores["Chi"] ?? 0)                // 5

let tags: Set = ["swift", "ios", "swift"]
print(tags.count)                        // 2 (đã loại trùng)
print(tags.contains("ios"))              // true

  9. Stored property, computed property, lazy và property observer (didSet) khác nhau thế nào?

    Xem đáp án mẫu
    Stored property lưu giá trị ngay trong instance (var hoặc let). Computed property không lưu gì mà tính lại mỗi lần đọc qua get (và tuỳ chọn set), hợp cho giá trị suy ra từ property khác như area hay fullName; nó luôn khai báo bằng var. lazy var chỉ tính giá trị ở lần truy cập đầu tiên rồi lưu lại, hợp cho thứ tốn kém như DateFormatter hay view phức tạp; nó chỉ dùng được với var, và trong struct thì việc truy cập lần đầu là mutating. Property observer willSet/didSet chạy ngay trước và sau mỗi lần giá trị thay đổi, hay dùng để cập nhật UI khi model đổi; chúng không chạy khi gán giá trị trong init của chính type đó. Nhớ phân biệt: computed property chạy lại code mỗi lần đọc nên đừng đặt việc nặng ở đó.
    struct Rectangle {
    var width: Double
    var height: Double
    var area: Double { width * height }   // computed: tính lại mỗi lần đọc
}

class Profile {
    var name: String = "" {
        didSet { print("Đổi tên: \(oldValue) -> \(name)") } // observer
    }
    lazy var formatter: DateFormatter = {  // chỉ tạo ở lần dùng đầu tiên
        let f = DateFormatter()
        f.dateFormat = "dd/MM/yyyy"
        return f
    }()
}

let profile = Profile()
profile.name = "An"   // in: Đổi tên:  -> An

  10. init trong Swift hoạt động thế nào? Struct và class khác nhau ra sao về khởi tạo, và convenience init dùng để làm gì?

    Xem đáp án mẫu
    Quy tắc cốt lõi: mọi stored property phải có giá trị trước khi instance được dùng (riêng var kiểu Optional tự mang giá trị nil). Struct được cấp sẵn memberwise initializer, ví dụ Point(x: 3) khi các property có giá trị mặc định; nếu tự viết init ngay trong thân struct thì mất memberwise init (viết trong extension thì vẫn giữ). Class không có memberwise init nên phải tự viết. Designated init là init chính: nó phải khởi tạo mọi property của chính class đó rồi mới gọi super.init của lớp cha, sau bước này mới được dùng self hay sửa property thừa kế. convenience init là init phụ, bắt buộc gọi một init khác của cùng class (self.init(...)), thường chỉ để cung cấp giá trị mặc định. init? là failable init, trả về nil khi dữ liệu không hợp lệ. required init buộc lớp con phải cài lại, như init?(coder:) của UIView.
    struct Point {
    var x = 0
    var y = 0
}
let p = Point(x: 3)            // memberwise init, y lấy giá trị mặc định

class Animal {
    let name: String
    init(name: String) { self.name = name }
}

class Dog: Animal {
    let breed: String
    init(name: String, breed: String) {
        self.breed = breed      // 1. khởi tạo property của chính class
        super.init(name: name)  // 2. rồi mới gọi init của lớp cha
    }
    convenience init(breed: String) {
        self.init(name: "Chưa đặt tên", breed: breed) // phải gọi init khác của cùng class
    }
}

struct Age {
    let value: Int
    init?(_ value: Int) {       // failable init
        guard value >= 0 else { return nil }
        self.value = value
    }
}

  11. Các mức access control của Swift (private, fileprivate, internal, public, open) khác nhau thế nào? Mặc định là mức nào?

    Xem đáp án mẫu
    Xếp từ hẹp đến rộng: private chỉ dùng được trong khai báo bao quanh (và các extension của nó trong cùng file); fileprivate dùng được trong cả file; internal dùng được trong cùng module (app hoặc framework) và là mức mặc định khi bạn không viết gì; public cho module khác dùng nhưng không cho kế thừa hay override bên ngoài module; open (chỉ áp dụng cho class và member của nó) cho module khác dùng cả kế thừa lẫn override. Với app chỉ có một module, thực tế bạn dùng private và mặc định internal; public/open chỉ cần khi viết framework hoặc Swift Package. Thói quen tốt là đặt private cho mọi thứ không cần lộ ra, và dùng private(set) khi muốn bên ngoài đọc được nhưng chỉ bên trong được sửa, ví dụ private(set) var items trong ViewModel để View không tự ý sửa dữ liệu.
    final class CartViewModel {
    private(set) var items: [String] = []   // ngoài đọc được, chỉ trong class mới sửa
    private var discount = 0.0              // chỉ dùng bên trong class

    func add(_ item: String) {              // internal (mặc định)
        items.append(item)
    }
}

let cart = CartViewModel()
cart.add("Áo")
print(cart.items)             // ["Áo"]
// cart.items.append("Mũ")    // lỗi compile: setter là private
// cart.discount = 0.1        // lỗi compile: discount là private

Memory & ARC

Mọi rank →

  1. ARC là gì? Khi nào một object bị giải phóng khỏi bộ nhớ?

    Xem đáp án mẫu
    ARC (Automatic Reference Counting) quản lý bộ nhớ cho instance của class: mỗi strong reference làm tăng bộ đếm tham chiếu, khi reference bị gán nil hoặc ra khỏi scope thì bộ đếm giảm, về 0 thì object được giải phóng và deinit chạy. Khác garbage collector, ARC không có tiến trình quét chạy nền; compiler chèn sẵn lệnh retain/release lúc build nên object được giải phóng ngay khi không còn ai giữ. Struct và enum là value type nên không được đếm tham chiếu theo cách này. Điểm yếu của ARC là không tự xử lý được hai object giữ strong reference lẫn nhau (retain cycle).
    class Player {
    let name: String
    init(name: String) { self.name = name }
    deinit { print("\(name) được giải phóng") }
}

var p1: Player? = Player(name: "An") // bộ đếm = 1
var p2 = p1                           // bộ đếm = 2
p1 = nil                              // bộ đếm = 1, chưa giải phóng
p2 = nil                              // bộ đếm = 0 -> deinit chạy

  2. Strong reference và weak reference khác nhau thế nào? Vì sao biến weak luôn phải có kiểu Optional?

    Xem đáp án mẫu
    Strong reference (mặc định) giữ object sống: còn ít nhất một strong reference thì object chưa bị giải phóng. Weak reference trỏ tới object nhưng không tăng bộ đếm; khi object bị giải phóng, ARC tự đặt mọi weak reference tới nó về nil. Chính vì có thể tự thành nil bất cứ lúc nào nên biến weak bắt buộc có kiểu Optional. Dùng weak để phá vòng tham chiếu trong quan hệ cha – con: cha giữ con bằng strong, con trỏ ngược về cha bằng weak, như delegate hay department trong ví dụ dưới.
    class Department {
    var manager: Employee?           // strong: phòng ban giữ nhân viên
    deinit { print("Department deinit") }
}

class Employee {
    weak var department: Department? // weak: không giữ ngược phòng ban
    deinit { print("Employee deinit") }
}

var d: Department? = Department()
let e = Employee()
d?.manager = e
e.department = d
d = nil // in "Department deinit", e.department tự thành nil

UIKit & Lifecycle

Mọi rank →

  1. Kể các method vòng đời chính của UIViewController. Gọi API lấy dữ liệu nên đặt ở viewDidLoad hay viewWillAppear?

    Xem đáp án mẫu
    Thứ tự chính: viewDidLoad (view đã được load, chỉ gọi một lần) → viewWillAppear → viewDidAppear mỗi lần màn hình hiện ra, và viewWillDisappear → viewDidDisappear khi bị che hoặc rời đi; override thì nhớ gọi super. viewDidLoad hợp để setup một lần và gọi API lần đầu. viewWillAppear chạy lại mỗi lần quay về màn hình (ví dụ pop từ màn chi tiết), hợp để làm mới dữ liệu có thể đã đổi, nhưng đặt API nặng ở đây thì mỗi lần quay lại đều gọi lại. Bẫy: từ iOS 13 modal mặc định hiện dạng sheet, khi sheet đóng thì màn hình bên dưới không được gọi lại viewWillAppear.

  2. Auto Layout hoạt động thế nào? Tạo view bằng code, thêm constraint xong nhưng console báo "Unable to simultaneously satisfy constraints", bạn kiểm tra gì?

    Xem đáp án mẫu
    Auto Layout tính frame của view từ các constraint giữa các anchor (top, leading, width, centerX…), nên mỗi view cần đủ thông tin để xác định vị trí và kích thước, không thiếu (ambiguous) và không mâu thuẫn (conflict). UILabel, UIButton có intrinsic content size nên thường chỉ cần constraint vị trí. Khi tạo view bằng code phải đặt translatesAutoresizingMaskIntoConstraints = false; nếu quên, UIKit tự sinh constraint từ autoresizing mask và chúng xung đột với constraint của bạn. Ngoài ra phải addSubview trước khi activate constraint, và neo nội dung vào safeAreaLayoutGuide để không bị notch che.
    let titleLabel = UILabel()
titleLabel.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(titleLabel)

NSLayoutConstraint.activate([
    titleLabel.topAnchor.constraint(equalTo: view.safeAreaLayoutGuide.topAnchor, constant: 16),
    titleLabel.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 16),
    titleLabel.trailingAnchor.constraint(equalTo: view.trailingAnchor, constant: -16)
])
// Không cần height: UILabel có intrinsic content size

  3. UITableViewDataSource và UITableViewDelegate khác nhau thế nào? Để hiển thị một danh sách đơn giản cần cài đặt những method nào?

    Xem đáp án mẫu
    DataSource trả lời câu hỏi "hiển thị cái gì": có bao nhiêu section/row và cell cho từng IndexPath; hai method bắt buộc là numberOfRowsInSection và cellForRowAt. Delegate lo phần giao diện và tương tác: chiều cao row, header/footer, chạm vào row (didSelectRowAt), swipe action. Trong cellForRowAt luôn lấy cell bằng dequeueReusableCell(withIdentifier:for:) để tái sử dụng, và identifier phải được đăng ký trước (bằng register hoặc trong storyboard), nếu không app crash. Quên gán tableView.dataSource = self là lý do phổ biến khiến bảng trống trơn.
    extension ContactsViewController: UITableViewDataSource {

        contacts.count
    }

    func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {

  4. @IBOutlet và @IBAction là gì? Vì sao đổi tên một biến outlet xong thì app crash với lỗi "this class is not key value coding-compliant for the key…"?

    Xem đáp án mẫu
    @IBOutlet đánh dấu property để Interface Builder nối với một view trong storyboard/xib, còn @IBAction đánh dấu method nhận sự kiện như chạm nút. Outlet thường có dạng @IBOutlet weak var titleLabel: UILabel!: implicitly unwrapped vì chỉ có giá trị sau khi view được load, và Xcode mặc định để weak vì superview đã giữ view đó. Storyboard lưu kết nối theo tên; đổi tên biến trong code mà không nối lại thì lúc load view, UIKit gán vào key không còn tồn tại và crash với lỗi trên. Cách sửa: mở Connections Inspector, xoá kết nối cũ có dấu cảnh báo rồi nối lại.

  5. Dựng UI bằng storyboard, xib hay viết code khác nhau thế nào? Dự án nhiều người cùng làm thì bạn chọn cách nào?

    Xem đáp án mẫu
    Storyboard trực quan, kéo thả nhanh, nhìn được luồng màn hình qua segue, hợp để học và làm prototype; nhưng nó là file XML lớn, nhiều người cùng sửa rất dễ conflict khi merge, và lỗi kết nối outlet chỉ lộ ra lúc runtime. Xib hợp cho từng view hoặc cell riêng lẻ, ít conflict hơn. Viết UI bằng code dễ review, dễ tái sử dụng, merge nhẹ nhàng, đổi lại dài dòng hơn và không xem trước trực quan. Dự án làm nhóm thường chọn code hoặc chia mỗi màn hình một storyboard/xib, còn màn hình mới ngày càng hay được viết bằng SwiftUI.

  6. Vì sao UITableView tái sử dụng cell (dequeueReusableCell)? Lỗi nào hay gặp nếu không cấu hình lại cell đầy đủ?

    Xem đáp án mẫu
    Table view chỉ tạo đủ số cell đang hiện trên màn hình; khi một cell cuộn ra khỏi tầm nhìn nó được đưa vào hàng đợi, rồi dequeueReusableCell(withIdentifier:for:) trao lại cho row mới, nhờ vậy danh sách hàng nghìn dòng vẫn mượt và ít tốn bộ nhớ. Hệ quả là cell nhận về vẫn còn giữ trạng thái của row trước đó. Nếu trong cellForRowAt bạn chỉ đặt giá trị ở một nhánh, ví dụ if task.isDone { textColor = .gray } mà không có nhánh ngược lại, thì khi cuộn nhiều dòng chưa xong cũng bị xám; hoặc ảnh của row cũ hiện ra trước khi ảnh mới tải xong. Cách đúng: luôn gán lại mọi thuộc tính ở cả hai nhánh, dọn dẹp trong prepareForReuse() của cell (xoá ảnh, huỷ tác vụ tải ảnh), và lưu trạng thái như đã chọn hay đã mở rộng trong model chứ không lưu trong cell. Cell phải được đăng ký bằng register(_:forCellReuseIdentifier:) hoặc là prototype cell trong storyboard, nếu không dequeue sẽ crash.
    func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {

    // vẫn giữ màu xám và dấu tick của row trước
    cell.textLabel?.textColor = task.isDone ? .gray : .label
    cell.accessoryType = task.isDone ? .checkmark : .none
    return cell
}

  7. UIStackView giúp gì so với tự viết constraint? axis, alignment, distribution và spacing hoạt động thế nào?

    Xem đáp án mẫu
    UIStackView xếp các arrangedSubviews thành một hàng hoặc một cột và tự sinh constraint giữa chúng, nên form đăng nhập hay thanh nút chỉ cần đặt constraint cho riêng stack view. axis chọn hướng xếp (.vertical hoặc .horizontal), spacing là khoảng cách giữa các view, alignment căn theo trục vuông góc (.fill, .leading, .center...), còn distribution quyết định cách chia chỗ dọc theo trục xếp: .fill (một view giãn ra để lấp đầy), .fillEqually (chia đều), .equalSpacing... Gọi isHidden = true cho một view con thì stack view tự thu gọn khoảng trống của nó, rất tiện để ẩn hiện nhãn báo lỗi mà không phải sửa constraint. Cần thêm view bằng addArrangedSubview (không phải addSubview) và đặt translatesAutoresizingMaskIntoConstraints = false cho stack khi tạo bằng code. Với .fill, nếu nhiều view có content hugging priority bằng nhau thì Auto Layout không biết view nào nên giãn; hãy đặt setContentHuggingPriority khác nhau.

let form = UIStackView(arrangedSubviews: [titleLabel, emailField, errorLabel, loginButton])

form.spacing = 12
form.alignment = .fill
form.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(form)

SwiftUI

Mọi rank →

  1. SwiftUI khác UIKit ở điểm cơ bản nào? Vì sao view trong SwiftUI là struct chứ không phải class?

    Xem đáp án mẫu
    UIKit theo kiểu imperative: bạn tạo view object rồi tự cập nhật nó khi dữ liệu đổi (label.text = ...). SwiftUI theo kiểu declarative: bạn mô tả UI như một hàm của state trong body, khi state đổi SwiftUI tự tính lại body và cập nhật phần khác biệt lên màn hình. View trong SwiftUI là struct nhẹ, chỉ là bản mô tả và được tạo lại liên tục với chi phí thấp, nên đừng lưu dữ liệu cần giữ lâu trong property thường của view. Hai bên dùng chung được: UIHostingController nhúng SwiftUI vào UIKit, còn UIViewRepresentable đưa view UIKit vào SwiftUI.

  2. @State dùng để làm gì? Vì sao trong Button không thể viết count += 1 nếu count chỉ là property thường của view?

    Xem đáp án mẫu
    View là struct và body không phải mutating, nên property thường không sửa được từ bên trong view (lỗi Cannot assign to property: 'self' is immutable). @State để SwiftUI lưu giá trị ở vùng nhớ do framework quản lý, tách khỏi struct, nên giá trị không mất khi view struct được tạo lại; mỗi lần giá trị đổi, SwiftUI chạy lại body để cập nhật UI. @State dành cho state đơn giản thuộc riêng view đó (bộ đếm, công tắc, text đang nhập) nên khai báo private; muốn view con sửa được thì truyền $count, tức một binding.
    struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack(spacing: 12) {
            Text("Đã bấm \(count) lần")
            Button("Tăng") {
                count += 1 // body được tính lại
            }
        }
    }
}

  3. VStack, HStack, ZStack khác nhau thế nào? Làm sao đẩy một nút về sát mép phải màn hình?

    Xem đáp án mẫu
    VStack xếp view con theo chiều dọc, HStack theo chiều ngang, còn ZStack xếp chồng lên nhau (view khai báo sau nằm trên), hay dùng để đặt chữ lên ảnh. Mỗi stack có alignment và spacing để căn chỉnh, và mặc định chỉ to vừa đủ nội dung. Spacer() chiếm hết khoảng trống còn lại theo trục của stack chứa nó, nên HStack { Text("Giỏ hàng"); Spacer(); Button(...) } sẽ đẩy nút về sát mép phải. Một cách khác là gắn .frame(maxWidth: .infinity, alignment: .trailing) cho nút.

  4. Vì sao trong SwiftUI thứ tự modifier lại quan trọng? .padding().background(.yellow) và .background(.yellow).padding() khác nhau thế nào?

    Xem đáp án mẫu
    Mỗi modifier không sửa view gốc mà bọc nó trong một view mới, nên modifier được áp dụng từ trong ra ngoài đúng theo thứ tự viết. .padding().background(.yellow) thêm khoảng đệm trước rồi tô nền cho cả khối, nên vùng vàng rộng hơn chữ. .background(.yellow).padding() tô nền vừa khít chữ rồi mới thêm khoảng trống trong suốt bên ngoài. Tương tự, đặt .frame trước hay sau .background cũng cho vùng nền khác nhau, nên khi UI lệch so với thiết kế hãy kiểm tra thứ tự modifier trước tiên.
    Text("Sale 50%")
    .padding()
    .background(.yellow) // nền vàng phủ cả phần padding

Text("Sale 50%")
    .background(.yellow) // nền vàng vừa khít chữ
    .padding()           // padding trong suốt bên ngoài

  5. some View trong var body: some View nghĩa là gì? Vì sao không viết thẳng View làm kiểu trả về được?

    Xem đáp án mẫu
    View là protocol có associated type (Body), nên trước đây không dùng trần làm kiểu trả về được. some View là opaque return type: hàm trả về đúng một kiểu cụ thể tuân thủ View, compiler biết kiểu thật (ví dụ ModifiedContent<Text, _PaddingLayout>) còn nơi gọi chỉ thấy "một thứ là View". Nhờ giữ nguyên thông tin kiểu mà SwiftUI so sánh và cập nhật cây view hiệu quả, khác với việc bọc tất cả vào AnyView (xoá kiểu, mất tối ưu). Hệ quả: mọi nhánh trong body phải ra cùng một kiểu cụ thể. if/else trong body trả về hai view khác kiểu vẫn hợp lệ vì body được gắn @ViewBuilder, nó gói hai nhánh vào một kiểu chung. Ở hàm thường thì không có sẵn điều này: hai câu return khác kiểu gây lỗi "Function declares an opaque return type, but the return statements in its body do not have matching underlying types", nên cần thêm @ViewBuilder hoặc bọc bằng Group.
    struct ProfileView: View {
    var isLoggedIn: Bool

    var body: some View {           // body luôn ra đúng một kiểu cụ thể
        VStack {
            if isLoggedIn {         // @ViewBuilder cho phép if/else khác kiểu
                Text("Xin chào")
            } else {
                Button("Đăng nhập") { }
            }
        }
        .padding()
    }
}

// Hàm thường: cần @ViewBuilder mới trả về được hai kiểu khác nhau
@ViewBuilder
func badge(isNew: Bool) -> some View {
    if isNew { Text("Mới") } else { Image(systemName: "checkmark") }
}

  6. Hiển thị danh sách trong SwiftUI bằng List và ForEach thế nào? Identifiable dùng để làm gì?

    Xem đáp án mẫu
    List hiển thị dữ liệu thành các hàng cuộn được (tái sử dụng hàng như UITableView); ForEach là view lặp qua một collection để sinh view, dùng được bên trong List, VStack, Section... SwiftUI cần biết định danh ổn định của từng phần tử để so sánh khi dữ liệu thay đổi, nên model tuân thủ Identifiable với property id duy nhất (như UUID hoặc id từ server), hoặc chỉ định bằng id: \.field. Không nên dùng index làm id nếu danh sách có thể thêm, xoá hay sắp xếp lại, vì SwiftUI sẽ gán nhầm state cho hàng khác. Vuốt để xoá dùng .onDelete (chỉ có trên ForEach), nút tuỳ biến dùng .swipeActions, kéo để làm mới dùng .refreshable. List đã có sẵn style và hành vi hệ thống; nếu cần giao diện tuỳ biến hoàn toàn thì dùng ScrollView kèm LazyVStack.
    struct Todo: Identifiable {
    let id = UUID()
    var title: String
}

struct TodoListView: View {
    @State private var todos = [Todo(title: "Học Swift"), Todo(title: "Làm bài tập")]

    var body: some View {
        List {
            ForEach(todos) { todo in          // dùng được vì Todo: Identifiable
                Text(todo.title)
            }
            .onDelete { offsets in            // vuốt để xoá
                todos.remove(atOffsets: offsets)
            }
        }
    }
}

  1. Trong UIKit, push một màn hình bằng UINavigationController và present modal khác nhau thế nào? Đóng mỗi loại ra sao?

    Xem đáp án mẫu
    Push (navigationController?.pushViewController(vc, animated: true)) đưa màn hình mới vào stack của navigation controller, có sẵn nút Back và cử chỉ vuốt từ mép trái để quay lại, hợp với luồng đi sâu như danh sách → chi tiết; đóng bằng popViewController(animated:). Present (present(vc, animated: true)) mở màn hình dạng modal cho tác vụ tách biệt như đăng nhập, chọn ảnh; đóng bằng dismiss(animated:). Bẫy hay gặp: màn hình hiện tại không nằm trong UINavigationController thì navigationController là nil, lời gọi push bị bỏ qua mà không báo lỗi. Từ iOS 13 modal mặc định là sheet, muốn toàn màn hình thì đặt modalPresentationStyle = .fullScreen.

  2. Muốn truyền productId sang màn hình chi tiết, rồi gửi kết quả chỉnh sửa ngược về màn hình trước, bạn làm thế nào?

    Xem đáp án mẫu
    Truyền đi: gán dữ liệu vào property (hoặc initializer) của view controller đích trước khi push/present; với segue thì gán trong prepare(for:sender:). Đừng gán thẳng vào outlet như detailVC.nameLabel.text = ... lúc này, vì view chưa load nên outlet còn nil và app crash; hãy lưu vào property rồi đổ lên UI trong viewDidLoad. Truyền ngược về: dùng delegate (protocol) hoặc closure callback do màn hình trước gán, màn hình sau gọi khi có kết quả rồi pop/dismiss. Trong closure nên dùng [weak self] khi tham chiếu màn hình trước, đây là thói quen tốt để tránh retain cycle.
    class EditNameViewController: UIViewController {
    var currentName = ""               // dữ liệu truyền vào
    var onSave: ((String) -> Void)?    // callback trả kết quả về

    func saveTapped(newName: String) {
        onSave?(newName)
        navigationController?.popViewController(animated: true)
    }
}

Mọi rank →

  1. MVC trong iOS là gì? Vì sao hay gặp "Massive View Controller" và cách giảm nhẹ ban đầu?

    Xem đáp án mẫu
    MVC chia app thành Model (dữ liệu và luật nghiệp vụ), View (giao diện như UIView, cell) và Controller (UIViewController, nối hai bên: nhận thao tác người dùng, cập nhật model, đẩy dữ liệu lên view). Đây là mẫu Apple dùng sẵn trong UIKit nên là mặc định của hầu hết project. Thực tế UIViewController thường ôm quá nhiều việc: quản lý vòng đời view, làm data source và delegate, gọi mạng, parse JSON, format dữ liệu, điều hướng. Kết quả là file hàng nghìn dòng, khó đọc và khó viết test (Massive View Controller). Cách giảm nhẹ: tách việc gọi mạng sang service hoặc repository, đưa logic format và kiểm tra dữ liệu về model hoặc struct riêng, tách data source/delegate ra object riêng, chia màn hình lớn thành view tuỳ biến hoặc child view controller. Bước tiếp theo là MVVM (ViewModel giữ state và logic trình bày, ViewController chỉ gắn lên UI) kết hợp Coordinator cho điều hướng; SwiftUI hợp tự nhiên với MVVM. Điểm cần nhấn mạnh khi phỏng vấn: vấn đề không nằm ở bản thân MVC mà ở việc phân chia trách nhiệm.
    // Model: dữ liệu + format thuộc về model, không nằm trong ViewController
struct Product {
    let name: String
    let price: Int
    var priceText: String { "\(price.formatted())đ" }
}

// Service tách riêng: ViewController không cần biết gọi mạng thế nào
protocol ProductService {
    func fetchProducts(completion: @escaping ([Product]) -> Void)
}

final class ProductViewController: UIViewController {
    private let service: ProductService
    private var products: [Product] = []
    private let tableView = UITableView()

    init(service: ProductService) {
        self.service = service
        super.init(nibName: nil, bundle: nil)
    }
    required init?(coder: NSCoder) { fatalError("init(coder:) chưa cài đặt") }

    override func viewDidLoad() {
        super.viewDidLoad()
        service.fetchProducts { [weak self] items in
            self?.products = items
            self?.tableView.reloadData()   // ViewController chỉ điều phối
        }
    }
}

  1. UserDefaults phù hợp để lưu gì? Có nên lưu access token hay mật khẩu vào đó không?

    Xem đáp án mẫu
    UserDefaults lưu cặp key–value nhỏ như cài đặt người dùng (ngôn ngữ, dark mode) hay cờ đã xem onboarding. Dữ liệu được ghi thành file plist trong thư mục của app và được nạp vào bộ nhớ khi dùng, nên không hợp với dữ liệu lớn như danh sách sản phẩm hay ảnh. Nó cũng không được bảo vệ như Keychain: ai lấy được file (qua bản backup hay máy jailbreak) là đọc được, nên token và mật khẩu phải lưu trong Keychain.   2. Muốn lưu một struct như UserSettings vào UserDefaults thì làm thế nào? Vì sao gán thẳng struct vào lại crash?

    Xem đáp án mẫu
    UserDefaults chỉ lưu được kiểu property list: String, số, Bool, Date, Data, cùng Array và Dictionary chứa các kiểu đó. Gán struct tuỳ biến vào set(_:forKey:) vẫn compile được vì tham số có kiểu Any?, nhưng lúc chạy sẽ crash với lỗi Attempt to insert non-property list object. Cách làm là cho struct conform Codable, dùng JSONEncoder chuyển thành Data rồi lưu, khi đọc thì dùng JSONDecoder chuyển ngược lại. Cách này chỉ hợp với dữ liệu nhỏ; dữ liệu lớn nên lưu file hoặc dùng database.
    struct UserSettings: Codable {
    var fontSize: Int
    var isDarkMode: Bool
}

let settings = UserSettings(fontSize: 16, isDarkMode: true)
// UserDefaults.standard.set(settings, forKey: "settings") // crash lúc runtime

if let data = try? JSONEncoder().encode(settings) {
    UserDefaults.standard.set(data, forKey: "settings")
}
if let data = UserDefaults.standard.data(forKey: "settings"),
   let saved = try? JSONDecoder().decode(UserSettings.self, from: data) {
    print(saved.fontSize) // 16
}

  3. Gọi API bằng URLSession và giải mã JSON bằng Codable thế nào? Vì sao gọi http:// lại bị chặn?

    Xem đáp án mẫu
    Ba bước: tạo URL, gọi URLSession.shared.dataTask(with:) (completion nhận Data?, URLResponse?, Error?) và nhớ gọi resume() thì request mới chạy, rồi giải mã bằng JSONDecoder vào struct tuân thủ Codable. Tên property trùng key JSON; khác tên thì khai báo CodingKeys hoặc đặt keyDecodingStrategy = .convertFromSnakeCase. Completion chạy trên thread nền nên cập nhật UI phải quay về DispatchQueue.main.async; với async/await thì viết try await URLSession.shared.data(from:). Đừng chỉ kiểm tra error: server trả 404 hay 500 vẫn cho error == nil, nên phải đọc cả HTTPURLResponse.statusCode. Gọi http:// (không phải https://) bị App Transport Security (ATS) chặn mặc định với lỗi -1022. Cách đúng là dùng HTTPS cho server; chỉ khi bất đắc dĩ mới khai báo ngoại lệ cho từng domain trong NSAppTransportSecurity ở Info.plist, còn bật NSAllowsArbitraryLoads cho toàn app thì nên tránh vì dễ bị Apple hỏi khi duyệt.
    struct Post: Codable {
    let id: Int
    let title: String
}

func loadPosts(completion: @escaping ([Post]) -> Void) {
    guard let url = URL(string: "https://jsonplaceholder.typicode.com/posts") else { return }

    URLSession.shared.dataTask(with: url) { data, response, error in
        guard error == nil,
              let http = response as? HTTPURLResponse, (200..<300).contains(http.statusCode),
              let data = data,
              let posts = try? JSONDecoder().decode([Post].self, from: data) else {
            print("Tải thất bại")
            return
        }
        DispatchQueue.main.async { completion(posts) } // về main thread trước khi cập nhật UI
    }.resume()                                          // quên resume() thì request không chạy
}

App lifecycle & Platform

Mọi rank →

  1. AppDelegate và SceneDelegate khác nhau thế nào? Vì sao từ iOS 13 lại có thêm SceneDelegate?

    Xem đáp án mẫu
    AppDelegate xử lý sự kiện ở mức cả tiến trình app: khởi động (application(_:didFinishLaunchingWithOptions:)), cấu hình thư viện bên thứ ba, đăng ký push notification. Từ iOS 13, phần giao diện được tách sang SceneDelegate vì một app (nhất là trên iPad) có thể mở nhiều cửa sổ cùng lúc, mỗi scene có UIWindow và vòng đời riêng: scene(_:willConnectTo:options:) để tạo window, sceneDidBecomeActive, sceneDidEnterBackground… Khi app dùng scene, các callback như applicationDidEnterBackground của AppDelegate không còn được gọi. App SwiftUI dùng @main struct MyApp: App thì không cần hai file này, vẫn gắn được AppDelegate qua @UIApplicationDelegateAdaptor.

  2. File Info.plist dùng để làm gì? Kể vài key quan trọng bạn hay phải sửa.

    Xem đáp án mẫu
    Info.plist chứa thông tin cấu hình mà hệ thống đọc về app, như bundle identifier, tên hiển thị dưới icon (CFBundleDisplayName), version và build number, launch screen, các hướng màn hình hỗ trợ, cấu hình scene. Các mô tả lý do xin quyền như NSCameraUsageDescription cũng khai báo ở đây; thiếu key này mà app truy cập camera thì hệ thống sẽ dừng app ngay. Ở các phiên bản Xcode gần đây, nhiều giá trị được khai báo trong tab Info/Build Settings của target và Xcode tự sinh vào Info.plist lúc build, nên project mới có thể không có file Info.plist riêng hoặc file rất ngắn.

  3. Bundle identifier là gì? Version và build number khác nhau thế nào khi đẩy bản mới lên TestFlight?

    Xem đáp án mẫu
    Bundle identifier (ví dụ com.example.shopapp) là định danh duy nhất của app trong hệ sinh thái Apple, gắn với App ID, provisioning profile, push notification và app trên App Store Connect; đổi bundle ID thì hệ thống coi là một app khác, và sau khi đã upload build thì không đổi được nữa. Version (CFBundleShortVersionString, ví dụ 1.2.0) là số phiên bản người dùng thấy trên App Store. Build number (CFBundleVersion, ví dụ 45) đánh dấu từng lần build: cùng một version có thể upload nhiều build lên TestFlight, nhưng mỗi lần phải tăng build number, trùng với build đã có sẽ bị từ chối. Trong Build Settings, hai giá trị này là MARKETING_VERSION và CURRENT_PROJECT_VERSION.

  4. Certificate, App ID và provisioning profile liên quan với nhau thế nào? Vì sao app chạy được trên simulator nhưng lên máy thật lại báo lỗi signing?

    Xem đáp án mẫu
    Simulator không yêu cầu ký app, còn thiết bị thật thì bắt buộc. Có ba thành phần: Certificate (development hoặc distribution) chứng minh bạn là nhà phát triển do Apple cấp, và cặp private key của nó nằm trong Keychain trên máy bạn, mất key thì phải tạo lại hoặc export file .p12 sang máy khác; App ID (gắn với bundle identifier) định danh app cùng các capability được bật cho nó như push notification; Provisioning profile gắn App ID, certificate và danh sách thiết bị được phép (với bản development, ad hoc) hoặc kiểu phân phối (App Store), và được đóng gói vào app khi build. Hệ thống chỉ cho chạy khi chữ ký khớp profile. Các lỗi hay gặp: No profiles for 'com.x.y' were found, bundle ID đã bị tài khoản khác đăng ký, máy chưa nằm trong profile, certificate hoặc profile hết hạn. Người mới chỉ cần bật Automatically manage signing và chọn Team trong Signing & Capabilities để Xcode tự tạo profile; Apple ID miễn phí (Personal Team) cài app lên máy thật được nhưng app chỉ chạy được 7 ngày và bị giới hạn capability.

  5. Swift Package Manager, CocoaPods và Carthage khác nhau thế nào? Dự án mới bạn chọn cái nào?

    Xem đáp án mẫu
    Swift Package Manager (SPM) được tích hợp sẵn trong Xcode: thêm thư viện qua File > Add Package Dependencies bằng URL và quy tắc phiên bản, không cần cài công cụ gì thêm, không sửa cấu trúc project, và phiên bản đã chốt được ghi trong Package.resolved để cả team dùng cùng một bản. CocoaPods là công cụ cũ viết bằng Ruby, khai báo trong Podfile, sau pod install tạo ra file .xcworkspace và thư mục Pods/; nó từng là chuẩn, nhiều thư viện cũ hay thư viện Objective-C vẫn chỉ có Pod, nhưng cài chậm và dễ xung đột phiên bản. Carthage build sẵn thư viện thành framework rồi bạn tự ghép vào project, nhẹ và không can thiệp vào project nhưng thao tác thủ công nhiều nên giờ ít người dùng. Dự án mới nên chọn SPM; chỉ dùng CocoaPods khi một thư viện bắt buộc cần. Dù dùng cách nào cũng nên commit file khoá phiên bản (Package.resolved, Podfile.lock) để build giống nhau trên mọi máy.
